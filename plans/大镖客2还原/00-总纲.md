## 🔴 2026-11-12 · 动资产会让 ModKit **每次打开都变慢** —— 正确姿势与分工

> **一句话**：让 ModKit 变慢的是**「资产缺失」**，不是「删除这个动作」。
> 只要还有东西引用着解析不到的网格，每次打开都会去反复解析。
> 要动资产，必须把**所有引用网格的东西一起挪走**；**删除由用户做，新增/导入由 AI 做。**

### 一、机制

```
Modules\RDR2Map\RuntimeDataCache\   53,738 个 .rdc / 2.47 GB
    ↑ 按资产 GUID 存 ModKit 编译好的运行时数据（几何 / 贴图）
```

打开模块时 ModKit 会：① 扫 `Assets\` 建资产表 → ② 扫 `Prefabs\*.xml` / `SceneObj\` / `SceneEditData\`，
把里面引用的资产逐个解析 → ③ **解析不到的会反复尝试** ⇒ 引用越多越慢。

### 二、实测触发过全量重扫的三种操作（都踩过）

| # | 操作 | 后果 |
|---|---|---|
| 1 | 手动往 `Assets\materials\v2` 塞 `_mtl.tpac` | 下次打开全量重扫 |
| 2 | 批量删 `Assets\meshes\**\*_geo.tpac`（2,533 个） | 下次打开全量重扫 |
| 3 | **只挪场景、没挪 prefab** | prefab 本身就是 2,402 个 mesh 的引用表 ⇒ 照样慢 |

第 3 条是 2026-11-12 当场犯的错：以为挪走 `SceneObj` 就完事，
忘了 `Prefabs\rdr2_lod_prefabs.xml` 里写着 2,402 个 `meta_mesh_component`。

### 三、正确姿势（要清就一次清干净）

动网格资产之前，把下面**四样一起**挪到 `RDR2Map\_scene_backup\`：

```
Assets\meshes\**\*_geo.tpac      ← 待删 / 待重导的资产
SceneObj\Main_map\               ← 场景
SceneEditData\Main_map\          ← 可编辑地形
Prefabs\*.xml                    ← 景深碎片 prefab（2,402 个 mesh 引用）
```

> `ModuleData\*.xml`（settlements / items / cultures …）不用挪，它们不引用 mesh。

**顺序**：备份 → 四样全挪走 → 再增删资产 → 导完 → 按 `_scene_backup` 原路放回。

**自检判据**：`Assets\meshes` 为空时，`SceneObj` / `SceneEditData` / `Prefabs` **也必须为空**。

### 四、分工铁律（2026-11-12 用户明确）

| 操作 | 谁做 | 原因 |
|---|---|---|
| **删除** tpac / 资产 / 场景 / prefab | **用户** | 删除会触发全量重扫，时机必须由用户掌握 |
| **新增 / 导入**（材质 tpac、网格、贴图） | **AI** | 走批量导入脚本，有 F12 急停保护 |

### 五、事故时间线（复盘）

```
13:1x  批量删 2,533 个 _geo.tpac + 2,533 个 AssetSources 镜像
13:16  起批量导入（5 批），用户感到 ModKit 打开变慢
13:21  导入被停止牌中止（0/506）
13:22  把 SceneObj / SceneEditData 挪进 _scene_backup（**漏了 Prefabs**）
13:2x  用户指出 Prefabs 也引用缺失网格 ⇒ 补挪
```

**教训**：清单要一次列全（「谁引用网格」），不要挪一个看一个。

## 🔴 2026-11-12 · **UV 被翻了两次**（v2 导出已翻 + flip_v.py 又翻一次）

> **一句话**：`deliverable\models` 与压缩交付 `ImportReady` **都已经是正确的 1−v**；
> 后来 `flip_v.py` 又对 ImportReady 翻了一次 ⇒ 变回原始 v ⇒ 全部 21,029 个模型的 V 反了。
> **`flip_v.py` 永久作废，任何时候都不要再跑。**

### 一、怎么发现的（三方对比，以 2026-11-09 修好且实机验证的版本为基准）

| 版本 | 相对基准 | 判定 |
|---|---|---|
| `RDR2\AssetSources\models\main_map_lod\sdn_test\new_area_slod4__split_sdn.trf` | — | **基准**（11-09 修好、实机确认） |
| `deliverable\models\new_area_slod4__split_sdn.trf` | 相同 **65.7%** ｜ 1−v **0.0%** | ✅ 正确 |
| `RDR2Map\...\ImportReady\...\new_area_slod4__split_sdn.trf` | 相同 0.1% ｜ 1−v **65.6%** | ❌ 多翻一次 |
| ImportReady vs deliverable\models | 1−v **54.0%** | 确认是「再翻一次」 |

按分类抽查 13 个目录，**全部**呈现 `1−v`（相同的仅 0.2%）⇒ 不是个别文件，是整批。

### 二、为什么会犯

```
2026-11-09 的结论：引擎按左下原点采样，.ydr 是左上原点 ⇒ TRF 里必须写 1−v
                  修法 = 在 read_mdl() 里翻一次，make_part() 不再翻
2026-11-11 v2 导出：已经按这个结论写成 1−v（deliverable\models 正确）
2026-11-11 21:06   flip_v.py 又在 ImportReady 上翻了一次 ⇒ 抵消 ⇒ 回到原始 v
```

`flip_v.py` 还有 `flipped.txt` 标记文件（21,032 条路径），**标记反而让人以为"只翻一次没问题"**，
但真正的问题是「根本不该翻」。

### 三、修法与教训

- **修法**：对 `ImportReady\meshes` 原地再翻一次（v → 1−v），抵消。
  **不能**拿 `deliverable\models` 覆盖 —— 那是**减面前的源**（33.41 GB / 25,777 个），
  ImportReady 是**减面后的成品**（19.46 GB / 21,029 个），覆盖会丢掉减面与 LOD 策略。
- **教训 1**：处理链上「已经做过某变换」要写进**数据契约**，不能只写在脚本注释里。
- **教训 2**：任何「批量改 UV / 法线 / 坐标」的脚本，跑之前先用**已实机验证的样本**做三方对比。
- **教训 3**：`deliverable\models`（源）与 `ImportReady`（成品）体积差 1.7 倍，**永远别互相覆盖**。

## 🔴 2026-11-12 · 模型命名统一改 `_far`（**引擎会剥 `_lod`，实测确认**）

> **一句话**：ModKit 导入时会把模型名末尾的 `_lod` / `_lodNN` **剥掉**再注册资产名，
> 于是 `main_map_lod` 里 872 个远景模型**互相覆盖**（135 段铁路只剩 1 段）。
> 全量改名为 `_far` / `_farNN` 解决 —— `_far` 实测不被剥。

### 一、实测证据（4 个测试文件，2026-11-12）

| TRF 文件名 | TRF 内部部件头 | **注册出的资产名** | 结论 |
|---|---|---|---|
| `zzzf_test_lod00.trf` | `zzzf_test_lod00.0` | **`zzzf_test`** | `_lodNN` 被剥 |
| `zzzf_test2_far00.trf` | `zzzf_test2_far00.0` | **`zzzf_test2_far00`** | ✅ **`_far` 不剥** |
| `zzzf_test3.trf` | `zzzf_test3_lod07.0` | **`zzzf_test3`** | 内部名带也剥 |
| `zzzf_test4_lod07.trf` | `zzzf_test4.0` | **`zzzf_test4`** | 文件名带也剥 |

**三条硬规则（别再踩）**

1. 被剥的只有 **`_lod` / `_lodNN`**（末尾）—— `_slod`、`_far`、`_lod_42`（带下划线）都**不剥**
2. 剥的时候**文件名和 TRF 内部部件头都会看**，任一含 `_lodNN` 都会被剥 ⇒ **改名必须两处同时改**
3. 别的类不受影响：`_slod` 704 个保持原样

## 🔴 坐标换算（Blender ↔ RDR2 世界 ↔ ModKit 场景）—— **唯一口径，2026-11-10 实测定标**

> 用途：你在 Blender 里量一栋楼，能在 ModKit 里用实体列表找到同一栋；反过来也一样。

**三套坐标，各管一层**

| 层 | 在哪 | 单位 | X | Y | Z | 数值范围 |
|---|---|---|---|---|---|---|
| ① **Blender / 摆位表** | `sdn.blend` 里对象的世界坐标 = `placement_sdn.jsonl` 的 `loc` | 米 | 东 | 北 | 上 | x −1712..1192 · y −973..1975 |
| ② **RDR2 世界**（解包原生） | 4 m/px 高度图 / `terrain_sdn_meta.json` 的 `rect_m` | 米 | 东 | 北 | 上 | x 512..3840 · y −3072..768 |
| ③ **ModKit 场景** | `SceneObj\rdr2_sanit_denis` | 米（1:1） | 东 | **北（Y+）** | 上 | x 0..3328 · y 0..3840 |

**公式（只差平移，XY 严格线性）**

```
① → ②    world_x = loc_x + 2176        world_y = loc_y + (-1088)
① → ③    scene_x = loc_x + 1664        scene_y = loc_y + 1984
③ → ①    loc_x   = scene_x - 1664      loc_y   = scene_y - 1984
```

**常数怎么来的（不是拍的）**

| 常数 | 算式 | 含义 |
|---|---|---|
| 2176 | `rect_x0 + 宽/2` = 512 + 1664 | 场景矩形 X 中心 |
| **1984** | **blend 高/2 = 3968 / 2** | blend 的 Y 半宽（blend 竖直范围 **3968 m**，比地形多 128 m） |
| −1088 | `rect_y0 + 1984` = −3072 + 1984 | blend 原点在世界坐标里的 y |
| 1664 | 宽/2 = 3328/2 | ①→③ 的 X 平移 |

- **为什么 blend 是 3968 而地形是 3840**：地形生成时按 `13×15@256` 的正方形节点约束，**北边裁掉了 128 m**（`terrain_sdn_meta.json` 里写着）；blend 仍保留 3968 的原始竖直范围 ⇒ 两者中心差 **64 m**，于是场景里 `scene_y = loc_y + 1984`。
- 实测复核：用 156 个**贴地件**（road / rail_decal / track_decal / stone / rock）的 `loc.z` 与地形高度对齐反解，**中位残差 0.51 m**；若假设"原点=矩形中心"则是 2.33 m，明显更差。
- 交叉验证：锚点 `new_gar_05_house_a10`（旧文档记的世界坐标 2366.53, −1162.47）⇒ 算得 world = (190.5+2176, −74.5−1088) = **(2366.5, −1162.5)**，x 完全吻合。

**Z 也直接沿用 blend 的 z（2026-11-10 用户裁定，恒等）**

```
① → ③    scene_z = loc_z            （整场抬/压用 --z-offset）
```

- **为什么不能按地形贴地**：RDR2 大量建筑、码头、栈桥的**桩基本来就插进地面**，贴地会把埋深抹平 —— 楼会整体浮起来、码头会离开水面。
- TRF 网格是对象局部坐标、枢轴不在底面，但**这就是 blend 里那个对象自己的枢轴** ⇒ 实体 `position` 填 pivot 的 z 即可，**不需要**任何 min_z 补偿。
- 旧办法（地形贴地 + 扣 min_z）保留成 `--z-mode snap`，只作对照：两者实测 **中位差 2.4 m、最大差 11 m**，不要用它交付。

**朝向**

- 摆位表的 `quat` 排列是 **(w, x, y, z)**（Blender `to_quaternion()` 的顺序）。
- `yaw(度) = 2 · atan2(q[3], q[0])`；写进 xscene 时 `rotation_euler` 第三项 = yaw 的**弧度**，**符号不变**（两边 Y 都朝北，无镜像）。
- 判据：拿包围盒反验，该公式 AABB 中位误差 **0.000**、96.7% 命中；若按 `(x,y,z,w)` 解只有 62.8%。

**对照实例（可照抄验证）**

| | 值 |
|---|---|
| Blender `loc` | (190.5, −74.5, **55.1**)，quat (1,0,0,0) ⇒ yaw 0° |
| ModKit 实体名 | `new_gar_05_house_a10` |
| ModKit 坐标 | x = 190.5+1664 = **1854.50** ；y = −74.5+1984 = **1909.50** ；z = **55.10** |

**怎么快速找同一栋楼**

1. ModKit 场景实体列表按名字搜（实体名 = metamesh 名，同名实例带 `_2`/`_3`）；
2. 或查逐实体清单 `Debug\RD2构造相关\scene_sdn_entities.csv`（列：entity / cls / model / x / y / z / yaw_deg / tris）；
3. 已知 ModKit 坐标反查 Blender：`loc = (scene_x − 1664, scene_y − 1984)`。

> ⚠️ 换算只对 **`rdr2_sanit_denis`** 这一张场景成立（它的地形矩形与 blend 一一对应）。其余场景各自有自己的 `rect_m`，换场景要重算常数。

## 5. 资产自动化（为什么不用 ModKit 手工导入）

- 唯一网格 **10,076 个**、贴图 **3,236 张**；ModKit 导入是「右键 → Import → 确认」，**没有批处理**，一万件 ≈ 8.3 小时纯点击。
- 三条路里选 **C. 直写 tpac**：`tools/tpactool` 是我们 fork 的 TpacTool，`makepack`（PNG → 贴图资产）已在游戏里跑通（立绘包 `lwnprof_*.tpac`）。

**现有工具链**：

| 命令 | 作用 |
|---|---|
| `tpaccli makepack` | PNG → Texture 资产包 |
| `tpaccli assetclone` | 克隆原版资产（metamesh + 材质 + 贴图）并改名 |
| `tpaccli texreplace` | 换贴图像素（支持任意尺寸、生成 mip） |
| `tpaccli meshmake` | RMDL1 网格 → Metamesh（`--lods 0,1,2,3` 出多档） |
| `tpaccli matflags` / `inspect` / `dump` | 改材质 flag / 看字段 / 导 OBJ→PNG |

**判定口径**：`tpaccli list` 资产数对得上；游戏里 `custom.spawn_prefab` 看得见、贴图对、无 `RGL CONTENT WARNING`；重跑两次字节一致。

## 6. LOD（只针对「真实城镇场景」，地图图标另算）

### 6.1 现状

- RDR2 交接包**没有 LOD 链**（每个原型只有最高精度网格）；全量按 LOD0 摆 = **3.36 亿面**。
- RDR2 自己的 `_slod` 是整片区域合并低模，不能当「一栋房子一套 LOD」用。

### 6.2 场景模型 LOD 规划

| 级别 | 距离 | 单件目标面数 | 做法 |
|---|---|---|---|
| LOD0 | 0~15 m | ~2,000 | 保留轮廓/门窗，削内部与背面 |
| LOD1 | 15~40 m | ~800 | 焊接顶点 + 减面 |
| LOD2 | 40~100 m | ~300 | 去栏杆/雨棚/招牌 |
| LOD3 | 100~250 m | ~100 | 体块 + 屋脊 |
| LOD4 | 250~600 m | 20~30 | 体块 + 屋顶 |
| LOD5 | 600~1,500 m | 6~12 | 双面片 / 交叉公告板 |
| LOD6 | >1,500 m | 2 | 单公告板 / 纯色块 |

**按 prefab 做，不按实例做**；先剔 `in_lib=0` 与 `cls=0`；单场景 LOD0 可见 ≤ 40 万面，配合 LOD1~2 ≈ 60 万面。

> 🔴 **LOD6 ≠ 大地图缩略**。LOD6 是场景里"远到看不见"的保底面片；大地图缩略直接用 LOD 大陆按据点分组切的碎片（§7.0），不另做资产。

### 6.3 引擎侧未验的一件事

骑砍 MetaMesh 每层网格带 `Lod` 序号，但**切换距离是引擎固定的**——P0 要量出"第几档在多少米切换"，再决定档位分配，不猜。

### 7.5 场景文件怎么来（三层分开，只有地形要进编辑器）

| 层 | 格式 | 谁生成 | 引擎怎么读 |
|---|---|---|---|
| 网格 metamesh | 二进制 `.tpac` | `tpaccli` | `AssetPackages/*.tpac` 启动自动加载，**不需注册** |
| 预制体 prefab | 纯文本 XML | 脚本生成 | `Prefabs/` 目录**自动扫** |
| 场景 xscene | 纯文本 XML | 脚本生成 | `SceneObj/<场景名>/scene.xscene`；由 `settlements.xml` 的 `scene_name` 指过来 |

**生成顺序（关键）**：① 脚本生成场景骨架（含 `<terrain>` 参数）→ ② 用户在 ModKit 导地形（编辑器写出 `terrain.bin` 并回填参数）→ ③ 脚本再把实体注入 xscene（不碰 terrain）→ ④ 验收。
**原因**：编辑器保存会重写整个 xscene，先导地形后注入实体，两边互不覆盖。

  - 水平尺寸 < 1.2 m 丢（路灯/路牌/栏杆）；

1. **共享网格只减了第一个实例** → 必须按"网格数据块"分组，先给属主单用户副本再减面（`modifier_apply` 对多用户数据直接失败，日志里是 123 条 SKIP）。
2. **图集太小**（255 格）→ 71% 物件落兜底灰格 → 扩到 1024 格。
3. **UV 没归一化** → RDR2 模型 UV 只占 0~1 的一小块，缩进格子后整栋楼采样同一个颜色（看着"没贴图"）→ 每栋楼 UV 先归一化铺满格子。
4. **z 基面被离群件带偏**（有 −179 m 的顶点）→ 用 2% 分位数 + 钳制 0~60 m。
5. **Python 逐行解析 250 MB OBJ**（十几分钟）→ Blender 直接导二进制 `MESH1`，numpy 秒级读取。

**已知未解**：Blender 的 `modifier_apply` 在个别网格上会**死锁**（CPU 归零，实测两次，分别卡在第 3,500 个物件 / 第 600 组）。当前规避 = 跳过 >2 万面的网格（原样保留）。

**下一步（建议顺序）**：
1. 跑完密集版看预览：`Debug/RD2构造相关/icon_blend/preview_render.png`；重点看**有没有贴图**（砖缝/窗框）。
2. 若 Blender 仍卡 → 放弃 Blender 减面，改**纯 numpy 顶点聚类减面**（不调 Blender ops，无死锁风险）。
3. 若要更真实的贴图 → 改成"每栋楼用自己的贴图 + 多材质"（需扩展 `tpaccli meshmake` 支持多材质），原版城镇正是这么做的。
4. 装包：`python Scripts/install_rdr2_city_icon.py --mdl Debug/RD2构造相关/icon_blend/rdr2_m_sdn.mdl --atlas Debug/RD2构造相关/icon_blend/atlas_d.png`

**内部验收（引擎侧）**：任意场景 `custom.spawn_mesh rdr2_m_sdn 30` 看得见、贴图对；大地图俯视截图无 `RGL CONTENT WARNING`；与「原版图标占位」在同相机高度 A/B，帧率 ≥90%。

**方法论教训（下次做同类任务先看这段）**：
- **先用 50~100 个物件跑通"带贴图的预览"，再放大到全量**——这次每一轮都是全量跑 10~30 分钟才发现一个本可以在小样本 1 分钟内发现的 bug。
- **每轮必须有可视化验收**（预览图），不要只看日志里的面数。
- **长任务必须有进度页**（`Scripts/build_progress.py`，浏览器 2 秒自刷新），并且时间戳要能看出"卡住"。

### 7.7 地图覆盖分三档（"每一栋房子都要看到"要定义清楚）

用户问过：**圣丹尼斯的经验能不能扩到全图，让说过的每一栋房子（如夏洛蒂的家）都在地图上有缩略版？**
能，但不是"逐栋摆"，要分三档：

| 档 | 范围 | 做法 | 预算 | 状态 |
|---|---|---|---|---|
| **A. 据点图标** | **44 个据点**（9 城 / 11 堡 / 11 村 / 5 营地 / 6 POI / 2 藏身处） | 每据点一个合并网格 + 图集（圣丹尼斯管线） | 城镇 ≤40 万面、村庄 0.5~2 万面；全图 44 个合计 ≤150 MB（暂定） | 圣丹尼斯在做，其余待 T10 |
| **B. 具名单点** | 夏洛蒂的家（= 威拉德之息）这类 | **它已经在 44 人名单里**（POI → 村庄），按 A 档做，图标只放 1~2 栋房、500~2,000 面 | 可忽略 | 含在 A 档 |
| **C. 全图建筑覆盖** | 18 万实例里剩下的房子 | **不逐栋摆**，改按 **2000 m 瓦片合并**：43 个瓦片各出一个"城外建筑群"低模网格 | 约 43 次绘制、**200 万面上下** | 未开始，先挑一个瓦片试点 |

**为什么不逐栋摆**：

1. **绘制次数**：地图相机一次要看全图，一个实体 = 一次绘制；几千栋独立房子直接掉帧。
2. **面数**：全图建筑 LOD0 是 3.36 亿面；就算每栋砍到 50 面，18 万栋 = 900 万面，仍太重。
3. **数据缺口**：约一半大件在解包模型库里没有网格，"每一栋"物理上做不到。
4. **交互**：不是据点的实体只是装饰——不能点、不能进；要有交互得挂 tag/组件，成本另算。

**建议顺序**：先把 A 档做完（44 个据点，含所有你点名的房子）→ 再看要不要 C 档（先做一个瓦片，看观感和帧率）。

#### C 档怎么做（"全图每一栋房子都能看到"的操作方案）

目标：18.2 万个建筑实例，地图上全都看得到缩略版。**不逐栋摆实体**，走"瓦片烘焙"：

| 步 | 做什么 | 产物 | 机器时间 |
|---|---|---|---|
| 1 | **替身网格库**：10,076 个有几何的模型各减面到 30~60 面；没几何的（约一半大件）用"同尺寸档最近模型"顶替 | 一张"模型 → 低模"映射 | 30~60 分钟（Blender 批量） |
| 2 | **按 2000 m 瓦片烘焙**：43 个瓦片，各把瓦片内实例按位置/朝向摆好、合并成一个静态网格 | 43 个 metamesh | 1~2 小时（机器） |
| 3 | **每瓦片 3 档 LOD**：LOD0 ~40k 面 / LOD1 ~12k / LOD2 ~4k | 43 × 3 档 | 同上 |
| 4 | **共用图集**：全图一张 2048²（或每瓦片一张），颜色取自原贴图 | 1~43 个 tpac | 快 |

**预算**：全图约 **240 万面 / 55 MB**；完全缩小看全图时 43 个瓦片都停在 LOD2 ≈ **17 万面**，与现在的大地图同量级。

**代价 / 风险**：
1. **一半建筑是替身**（不是真模型）——除非重新解包补几何；
2. 地图会变"满"，可能挡据点视认，需要按缩放淡出或只保留据点周边；
3. 仍是**纯装饰**：不能点、不能进；
4. 和 A 档会重叠（据点图标更精细，应该盖在瓦片层之上，或瓦片里挖掉据点范围）。

**先做试点**：挑一个 2000 m 瓦片（建议含瓦伦丁或黑水镇），量出观感 + 帧率，再决定要不要 43 个全做。

## 8. 地形链事实（省得重查）

### 8.0 坐标体系（唯一权威 —— 三套坐标怎么换算）

**三套坐标，各管一层，禁止混用**：

| 层 | 单位 | **X 方向** | **Y 方向** | Z | 范围 | 唯一数值来源 |
|---|---|---|---|---|---|---|
| ① **RDR2 世界**（源数据） | 米 | **东** | **北** | 上 | x ∈ [−6844, 3924]，y ∈ [−4800, 3224]；高程 −34.93 ~ 690.35 m | 解包 `README_骑砍2交接.md` §2 |
| ② **大地图**（战役沙盘） | 地图单位 | 东 | ⚠️ **未实机验证**（旧文档写"南"，与 ③ 的实测矛盾，等进图确认） | 上 | u ∈ [0, 768]，v ∈ [0, 576] | `terrain/terrain_meta.json` |
| ③ **Mission 场景**（1:1 米） | 米 | **东** | **北**（🔴 2026-10-26 实机确认，旧文档写的"南"是错的） | 上 | 每个场景自己的 0 ~ 边长（圣丹尼斯 0~1500） | `terrain_sdn/terrain_sdn_meta.json` |

**换算公式**

① → ②（地图单位；**注意不是 ÷14.5，是拉伸铺满**）：
```
u = (x − (−6844)) ÷ 10,768 × 768        # 横向 ≈ 14.021 米/单位
v = (3224 − y)      ÷ 8,024  × 576      # 纵向 ≈ 13.931 米/单位
```

① → ③（圣丹尼斯为例：中心 (2554.5, −1150.5)、边长 1500 m；**场景 Y+ 朝北**）：
```
scene_x = x − 1804.5            # 东 → 东，不变
scene_y = y + 1900.5            # 北 → 大 Y，不镜像
scene_z = 地形高度图采样（行 0 = 北 ⇒ 行号按 (1500 − scene_y) 取）
rotation_z = +yaw               # 无镜像 ⇒ 不取反
yaw = 2·atan2(qz, qw)           # glTF 节点四元数
```

**锚点（用来验证换算，2026-10-26 实测值）**

| 锚点 | 模型 | ① 世界 (x, y) | yaw | ② 大地图 (u, v) | ③ 场景 (x, y) | ③ 场景 z | ③ rz |
|---|---|---|---|---|---|---|---|
| A 西·民宅 | `new_gar_05_house_a10` | (2366.53, −1162.47) | 0° | (656.92, 314.88) | (562.03, **738.03**) | 19.47 | 0° |
| B 中·宅邸 | `new_gar_02_mansion04_a` | (2558.86, −1107.80) | 0° | (670.63, 310.96) | (754.36, **792.70**) | 20.07 | 0° |
| C 东南·船 | `new_boats_shp_05_ropes` | (2652.30, −1556.61) | 90° | (677.30, 343.17) | (847.80, **343.89**) | 8.46 | **+90°** |
| 据点中心 | — | (2554.50, −1150.50) | — | (670.32, 314.02) | (750.00, 750.00) | — | — |

三条可以互证的常识：据点中心落在场景正中 (750,750)；A 在 B 的西南、C 在 B 的东南偏南（**Y 越大越北，所以 C 的 Y 只有 343.89**）；C 的 yaw=90° 在场景里仍是 **+90°**（无镜像）。

**踩过的坑（别再犯）**

1. 手写"Y-up→Z-up"角度会写反 ⇒ 楼上下颠倒。正确做法：**直接取父级空物体的旋转矩阵**。
2. 场景高度用实例自带 z ⇒ **实测普遍高 4~6 米**（大件中位 +6.5 m，只有 22% 在 1 米内）——瓦片 z 不是地面接触点。必须采样地形高度图。
3. 🔴 **场景 Y+ 朝北**（2026-10-26 实机确认；旧文档写的"朝南"是错的）⇒ `scene_y = y + 1900.5`、`rz = +yaw`。判断依据：编辑器里越往北 Y 越大。
4. 大地图的 848 是 RDR2 自己那张图的尺度；**我们的地图是 768×576**，且 10,768 m 是**拉伸**铺进去的，所以"14.5 m/单位"只在名义上成立（实际 14.02 / 13.93）。
5. **地形生成只改"源图判定为水"的像素**（河床/碎塘填平），**陆地一律不动**——所以陆地高度和实例自带 z 的差异不是岸线平滑造成的，而是瓦片 z 本身不是地面高度。

## 18. 本轮实战沉淀（2026-10-25 · 地形 + 材质 + 建筑导入）

> 这一节是**踩过才知道**的事实，下次做任何内容包（三国/别的世界）直接照抄，别重走。

### 18.1 世界尺度与地形

1. **世界范围 = 解包高度图覆盖范围 ÷ 14.5**（大地图是缩微沙盘）。848 是 RDR2 自己那张图的尺度，不是我们的。
2. **ModKit 的 Import Heightmap 只有 `scale` / `offset`，地形底面固定 0，没有负高度**。所以高度图必须"满量程 = 完整高程范围"，参数 `scale = 50`、`offset = 0`。
3. **外圈不要掺第二份数据**：把 campaign 高度图（848²、自带台阶）补进解包图外圈，结果是**方框接缝 + 阶梯垃圾**。只用解包图。
4. **水面高度换算**：`场景单位 =（真实米 + 34.93）÷ 725.28 × 50`。例：−25 米 = 0.685、−23.3 米 = 0.8。
5. **全局只有一个水位**。西南盆地底 −25 米 ⇒ 水位必须低于它，否则 8.6% 的陆地变成湖。
6. **岸线做法（重要）**：水掩膜是权威 ——
   - 水区：整片压到水面以下，**边界 = 水面**，向内 90 米降到海床（这才叫"刻深"）；
   - 岸：做在**水掩膜之外的陆地**上，临水 45 米内"只降不抬"把地面斜到水面。
   - 只做前者 = 垂直悬崖；只做后者 = 水面被吃光。
7. **盆地抬升按“高度”做，不要按东南西北乘系数**（乘系数会把山一起拔高）：高程 ≤ −15 米抬满 10 米、≥ +15 米不抬、中间平滑过渡。
8. **验收口径**：水线相邻像素落差 —— 中位 0.5 米以内、最大 1 米左右算合格；几十米就是悬崖。

### 18.2 地形材质图层（大地图 vs 城镇）

| | 大地图 `Main_map` | 城镇场景 |
|---|---|---|
| 图层 | 8 层：default / flora_forest / rock / grass / dirt / dirt2 / forest2 / river | **每个城 13~15 层、各不相同**（有 `snow` / `road` / `soil` 等） |
| tileset | `vista_tileset="WorldMap"` | **空** |
| blend / layer_distance | 1 / 10000 | 0 / 35 |
| 雪 | **没有独立层**，靠 rock 的灰白岩贴图 + Vista 冷调 | 有 `snow` 层 |

9. 🔴 **注入图层后必须改节点 mask**：`layer_is_used_mask_{summer,fall,winter,spring}` 全改 **255**。不改 = 只渲染第 0 层（新建场景按"当时层数"写成了 1）。
10. 🔴 **编辑器里的 Remove Terrain / Generate Terrain 会把图层表打回 1 个 `default`** —— 图层和 mask 全白改。图层修好后**不要再点这两个按钮**。
11. 🔴 **空 `Assets/` 会整个遮蔽 `AssetPackages/`**（引擎按 `Assets → AssetPackages → …` 取第一个存在的）。所以手写的 tpac 在编辑器里看不见。
12. **水面默认是纯白**（`water_default` + shallow/deep 全 1,1,1）⇒ 一片惨白。要配材质 `wat_main_map_ocean_g` + 深浅色 + 强度 1.5 + choppiness。

### 18.3 外部模型进编辑器（本轮最硬的骨头）

13. **编辑器工程 `Assets/` 存的是元数据**（`_geo/_mtl/_tex.tpac`，各 400~5000 字节），**几何不在里面**；Publish 时从 `AssetSources/` 的 FBX 现编。
14. 🔴 **FBX 导入按"材质名"匹配已有 Material 资产，绑定发生在导入那一刻**；后补的材质**不会回填** → 必须先建材质再导 FBX（或删掉重导）。
15. **正确流水线**（四步）：
    ① 用户在编辑器**批量导入 albedo PNG**（多选）→ 生成 `_tex.tpac`；
    ② 脚本 `tpaccli editormeta --genmats` 克隆一份参考材质，逐个生成 `_mtl.tpac`；
    ③ Blender 导出 FBX（材质名先规范化）；
    ④ 用户导入 FBX → 材质按名字自动挂上。
16. 🔴🔴 **`RawMeta` 优先于类型化字段**：只改 `material.Textures[0]` 保存出来还是**旧贴图 GUID**（症状：所有材质显示同一张图）。必须**字节级替换 RawMeta 里的 16 字节 GUID**。
17. 🔴 **Blender 导 FBX 的三个坑**：
    - 重名材质自动加 **`.001`** → 对不上材质名 ⇒ 导出前统一合并回基名；
    - 无贴图槽的材质叫 **`gray`** → 工程里不存在 ⇒ 导出前替换成同楼有贴图的材质；
    - **坐标轴**：骑砍要 **Z-up**（`axis_forward='Y', axis_up='Z'`），Blender 默认 Y-up 会把楼放倒。
18. 🔴🔴 **源模型顶点带世界坐标**（X≈2500），直接导 ⇒ 网格离原点十万八千里、实体根本没法摆。必须在导出前**以"底面中心"为原点重新基准**（顶点世界化 → 对象变换清零 → 整体平移 −base）。
19. 🔴 Blender 导入 glTF 会带一层父级旋转（`RDR2_Zup`）⇒ 导出前 `transform_apply(rotation, scale)` 烘进网格。
20. **尺度自检**：与 `deliverable/manifests/model_manifest.csv` 的 `size_x/y/z` 逐项比对（本轮实测 20.7×55.1×20.5 vs 20.657×55.145×20.491，厘米级吻合）。
21. **贴图名 ≠ 材质名**时用**别名表**（`材质名=贴图资产名`，例：贴图导入成 `_abal`、FBX 要 `_ab`）。
22. **物体位置 = 底面在地形上**：实体 z 直接填该点地形高度（模型已以底面为原点）。

### 18.6 🔴 **脱离 ModKit 自动生成编辑器资产**（本轮实证，做材质已成功 / 贴图待补最后一步）

**先分清两类东西**

| | 运行期资产 | 编辑器资产 |
|---|---|---|
| 放哪 | `AssetPackages/*.tpac`（游戏读） | `Assets/<类>/<名>/` 下的 `_geo/_mtl/_tex.tpac`（**编辑器读**） |
| 内容 | 真几何 + 真像素 | **元数据**（400~5000 字节），几何/像素在 Publish 时从 `AssetSources` 现编 |
| ModKit 里可见 | ❌ 空 `Assets/` 会遮蔽它 | ✅ |

**材质资产：已能做到完全离线生成（实证 11 个，未经过任何手工建材质）**

一个 `_mtl.tpac` 里就是：`名字 + 材质 flags + blend + shader guid + 贴图槽(int index → 贴图 guid)`。
配方（`tpaccli editormeta --genmats`）：

1. 用户先在编辑器里正常建**一个**同类材质当模板（选好 shader / flags），这就是"参考材质"；
2. 脚本读 `_tex.tpac` 得到 `贴图名 + guid`；
3. 逐个**克隆参考材质** → 改 `Name`、改确定性 `Guid`、把 `Textures[0]` 指向该贴图；
4. 🔴 **同时按老 GUID → 新 GUID 做字节替换**（`RawMeta` 优先于类型化字段，只改字段等于没改）；
5. 存成 `Assets/<目录>/<材质名>_mtl.tpac`。

**贴图资产：还差最后一步（当前是手工导入的）**

- **不是 GUID 的问题** —— GUID 可以由名字确定性生成。
- 真正原因是：`_tex.tpac` 里除了我们能读写的字段（名字 / 源图路径 / 宽高 / 格式），还带着**两个我们没有类型化属性的东西**：
  ```
  用途 = albedo       像素格式 = B8G8R8
  ```
  它们存在贴图资产的**数据段（TypelessDataSegments）**里。
- 我第一次尝试克隆参考贴图时把数据段**清空了**（本想"编辑资产不存像素"），结果 507 B → 320 B，`albedo` / `B8G8R8` 一起丢了。
- **正确做法（下次直接做，别再摸索）**：
  1. **保留**参考 `_tex.tpac` 的数据段，不要清；
  2. 把段里的**源图路径字符串**替换成新路径（`$BASE/Modules/<模块>/AssetSources/...`，长度可变就重建段）；
  3. 改名字 + 确定性 GUID；
  4. 存成 `Assets/<目录>/<贴图名>_tex.tpac`。
- 判据：新文件大小与参考件同量级（约 500 B），且能读出 `albedo` 字样 —— 满足这两条即格式正确。

**为什么值得做**：贴图量是材质量的 1~2 倍（一栋楼 10~20 材质 / 12~33 张贴图），全城上千栋 ⇒ 手工导入是唯一剩下的瓶颈。

### 18.7 自动生成贴图资产的**实测结果**（2026-10-25 晚，未打通）

**已确认的结构事实**

- `_tex.tpac` 里存的是：`名字 + 源图路径 + 宽高 + 格式 + 用途(albedo) + 像素格式(B8G8R8)`，**全部在 `RawMeta`（184 字节）里**，数据段是空的。
- 字符串是 **`int32 长度 + 原始 UTF-8 字节`**（实测：路径 83 字节，前面 4 字节就写 83，无终止符）。
- 贴图的 GUID 可以确定性生成（`editormeta` 里已实现），**GUID 不是障碍**。

**试过但没成功的做法**：`editormeta --gentex` —— 克隆参考贴图、按"长度+字节"替换 RawMeta 里的源图路径、改名字/GUID。
结果：12 个文件生成了（303~329 字节），但**里面既没有源路径、也没有 `albedo`/`B8G8R8`** —— 说明**保存时没用上我们塞进去的 `RawMeta`**（库的 `AssetPackage.Save` 走了 `WriteMetadata()` 那条路）。
所以自动生成的贴图是空壳，编辑器不会认。

**下一步要查的一件事**：`TpacTool.Lib` 里 `RawMeta` 在什么条件下才会被写（`AssetItem.Save` 的 `RawMeta ?? WriteMetadata()` 判据、以及是否有 `DataLoaded`/`MetadataLoaded` 门控）。定位后 `--gentex` 应该就能通。

**在那之前**：贴图仍需**手工批量导入**（多选）。为了不让所有贴图堆在一个文件夹，导入时按**每栋楼一个源目录**（`AssetSources/ImortReady/<楼名>/tex/`）分别导入 —— 编辑器会在 `Assets/materials/` 下按导入时的名字建资产，后续我生成的 `_mtl` 也按楼名分目录放。
