# 太阁火器与移动大筒 — 实施计划

> **状态：待审批**（未开始实施）
> 覆盖范围：① 铁炮（火枪）② 移动大筒（士兵推着走的炮）
> 依据：2026-09-13 对 Shokuho / CA_BloodSmoke / BattleArtillery 三家的反编译对比

---

## 一、结论速览

**决定：两条线互不相干，分开做、分开验。**

| | 线 A：铁炮（火枪） | 线 B：移动大筒（炮） |
|---|---|---|
| 做成什么 | 弩换皮的单兵武器（`Type="Crossbow"` 的物品） | 场上的器械实体（`RangedSiegeWeapon` 子类） |
| 归属 | 兵种装备槽 | Mission 里的可操作器械 |
| 移动 | 不适用 | 士兵推着走 |
| 工期量级 | 中（卡在美术） | **重**（新系统，拆三阶段） |
| 风险 | 低 | 高（阶段 1 是未知数） |
| 建议顺序 | **先做** | 后做，且先做原型验证 |

**明确不做**（防范围蔓延）：

1. 不做手持大筒 —— 大筒只做需架设的移动炮
2. 不做蹲射 / 三段击轮放 —— 二期再说，一期不做
3. 不做「沿预设路径推行」方案 —— 理由见 §B4
4. 不做舰炮

## 二、线 A：铁炮（火枪）

### A1 数据（Taikou 侧，纯 XML，零 C#）

| 文件 | 动作 | 要点 |
|---|---|---|
| `ModuleData/item_usage_sets.xml` | 🔴 **新建**（Taikou 现在没有这个文件） | 定义 `tk_musket`。待机和走路的动作**直接复用原版弩**（`act_idle_crossbow_1` + `movement_set id="crossbow"`），开火/装填也先指向原版弩动作 |
| `ModuleData/action_types.xml` | 一期**不动**（保持空壳） | 只有引入自制动画时才需要填 |
| `ModuleData/action_sets.xml` | 一期**不动**（保持空壳） | 同上 |
| `taikou_items/weapons.xml` | 加铁炮物品 | `Type="Crossbow"`、`weapon_class="Crossbow"`、**`ammo_class="Cartridge"`**、`ammo_limit="1"`、`item_usage="tk_musket"`、`missile_speed="500"` |
| 同上 | 加铁炮弹药 | `Type="Bolts"`、`weapon_class="Cartridge"`、`stack_amount="20"` |
| `ModuleData/module_sounds.xml` | 加铁炮音效（三档 + 装填） | 名字由 Taikou 定，LWN 不认识 |
| `ModuleData/AssetRegistry/FirearmFx.xml` | 🔴 **新建** | 见 §A3 |
| `spnpccharacters.xml` + `taikou_equipment_sets.xml` | 加铁炮兵种 | 技能走 `Crossbow`（给高），装备槽配铁炮 + 弹药 |
| `ModuleSounds/` + `AssetPackages/` | 音效 wav + 枪模型 + 烟雾粒子 | **工期大头** |

**不需要改 `SubModule.xml`**：`item_usage_sets.xml` 按文件名自动加载（已核实：Native / Shokuho / CA_BloodSmoke 都没有在 SubModule.xml 里注册它）。

### A2 机制（LWN 侧）

| 文件 | 动作 |
|---|---|
| `Combat/FirearmFxRegistry.cs` | **新建**。读内容包的 `AssetRegistry/FirearmFx.xml`。写法照抄 [CampaignMode/HeroCatalogRegistry.cs](../../ExampleModVS/ExampleMod/ExampleMod/CampaignMode/HeroCatalogRegistry.cs)（扫全模块 → 懒加载 → 坏数据只记日志不抛） |
| `Combat/FirearmFxLogic.cs` | **新建** `MissionLogic`。挂 `OnAgentShootMissile`：判断是不是火器 → 查表 → 播音效 + 生成枪口粒子 |
| `ExampleMod.csproj` | 🔴 两个新 `.cs` **必须登记**。不登记 = 静默不编译，`dotnet build` 成功是假象 |

**`FirearmFxLogic` 要做三件事**：

1. **判定火器**：手持武器的 `PrimaryWeapon.AmmoClass == WeaponClass.Cartridge`
2. **播音效**：按射手到玩家（或相机）的距离选三档 —— 近 / 中 / 远
3. **生成枪口烟**：取主手骨骼，沿枪管方向前推 `PrimaryWeapon.WeaponLength / 100` 米（单位换算：物品表里 `weapon_length` 是厘米），在该位置生成粒子；粒子实体每帧清理

### A3 对接契约：`AssetRegistry/FirearmFx.xml`

LWN 定格式，Taikou 填值。**LWN 不认识任何世界观词汇**（铁律 3）。

```xml
<FirearmFx>
  <!-- ammoClass = 引擎枚举 WeaponClass 的名字（世界观无关）
       near/mid/far/particle = 内容包自己定义的声音与粒子名，LWN 只当字符串用 -->
  <Profile ammoClass="Cartridge"
           near="tk_teppo_fire_near" mid="tk_teppo_fire_mid" far="tk_teppo_fire_far"
           particle="tk_smoke_teppo"
           nearDist="22" farDist="75"/>
</FirearmFx>
```

`nearDist` / `farDist` 单位是米。距离小于 `nearDist` 用近档，大于 `farDist` 用远档，中间用中档。

**为什么按 `ammoClass` 分档而不是写死一个**：以后要加别的火器（不同口径、火箭）只加一个 `<Profile>`，LWN 一行代码都不用改。

### A4 三个必须避开的坑

**坑 1：火器标记用 `Cartridge`，不要用 `Bolt`**

织丰的判断是「`ItemType == Crossbow` 且 `AmmoClass == Bolt` 就播音效」。这在**内容包场景下会误判**——原版弩兵开火时这两个条件同样成立，会播成铁炮声。

织丰自己碰不到这个 bug，因为它是整体替换（全库一把普通弩都没有，已核实）。Taikou 是内容包，原版弩兵还在。

**做法**：火器的 `ammo_class` 写 `Cartridge`。原版全库零占用这个值（已核实），是显式声明不是猜。

**坑 2：音效名不能硬编码进 LWN**

织丰把 `teppo_fire_patch_close` 写死在 C# 字段里。LWN 里出现这种字串直接违反铁律 3。

**做法**：LWN 只认档位（近/中/远），名字从 `FirearmFx.xml` 读。

**附加要求**：音效名解析必须容错。内容包没装 / 名字拼错 / 音效文件缺失 → 跳过播音，**不能崩**（铁律 1 同理）。

**坑 3：弹速写在枪上，不是弹药上**

引擎取的是**手持武器**的弹速：

```csharp
float baseSpeed = shooterAgent.Equipment[shooterAgent.GetPrimaryWieldedItemIndex()]
                      .GetModifiedMissileSpeedForCurrentUsage();
```

（`GetPrimaryWieldedItemIndex()` 拿到的是枪占的槽位）。织丰在弹药上写 500、CA_BloodSmoke 写 10 —— 两者都不生效，实际听枪的。

**做法**：`missile_speed` 写在铁炮物品的 `<Weapon>` 上。

### A5 一期不做的部分（说清楚，免得误期待）

**一期没有火枪专用动画，装填动作是弩的拉弦。** 战场观感靠三样东西撑：枪的声音、枪口烟、手上的枪模型。装填动作与真枪不符，这是已知缺口，二期补。

这样安排的理由：有枪声 + 枪口烟 + 枪模型，整体观感已经成立；装填那两秒的动作差异是次要的。**资源优先级：音效 > 枪模型 > 粒子 > 动画。**

动画导入管线已有研究，见 [Knowledge/动画导入与UE5重定向_引擎能力与实现路径.md](../../Knowledge/动画导入与UE5重定向_引擎能力与实现路径.md)。

## 三、线 B：移动大筒（士兵推着走的炮）

### B1 三阶段（按顺序做，每阶段单独验收）

#### 阶段 1：prefab 原型 —— 最高风险，先做

**目标**：在场景里摆一门炮，士兵站上去能推着走，推动画正确，停下能开火。

**产出**：

- `Taikou/Prefabs/*.xml`（🔴 **新建目录**，Taikou 现在没有 `Prefabs/`）
- LWN `Combat/MobileSiegeArtillery.cs`（器械类）
- LWN `Combat/SiegeWeaponPushMovement.cs`（自写移动组件）

**验收（全部在一张测试场景里跑通）**：

1. 士兵站到推车位，播**推**的动画（不是站着发呆）
2. 手 IK 贴住炮身，不穿模
3. 轮子跟着转
4. 能推到指定位置并停下
5. 停下后士兵能操作炮开火，炮弹从炮口位置飞出

**这一阶段跑不通，后面两阶段没有意义。** 建议先只做这一步，验证通过再往下。

#### 阶段 2：动态生成

**目标**：随机生成的野战战场也能出炮（Taikou 的战场是随机生成的，没有预先摆好的东西）。

**做法**：`MissionLogic` 在 `OnBehaviorInitialize` 里查队伍带了多少大筒兵 → 按数量用 `Mission.Current.CreateMissionObjectFromPrefab(名字, 位置)` 生成 → 摆在我方阵前。

**验收**：带一队大筒兵打一场野战，炮按数量出现在我方阵前，位置贴地形高度。

#### 阶段 3：编队操作

**目标**：大筒兵自动去操作炮、自动瞄准开火，不需要玩家一个个点。

**做法**：大筒兵编成一个专门的 formation，配 `RangedSiegeWeaponAi` 让 AI 自己找人操作。

**验收**：开战后大筒兵自己走到炮位、自己瞄准敌军、自己开火。

### B2 技术要点：人推怎么实现

**核心事实：推动画是原版就有的，不需要自制动画。**

原版推器械的 ActionIndex 是 `act_usage_siege_machine_push`（Native `action_types.xml:12756`）。原版投石车/攻城塔用它，我们直接复用。

自写移动组件要做的推人逻辑（照抄原版 `SiegeWeaponMovementComponent` 的做法）：

```csharp
// 对所有站在 "move" 标签站位点上的士兵：
userAgent.SetActionChannel(0, act_usage_siege_machine_push, ...);   // 左手推
userAgent.SetActionChannel(1, act_usage_siege_machine_push, ...);   // 右手推
userAgent.SetCurrentActionSpeed(0, CurrentSpeed);                   // 动画速度跟着车速
userAgent.SetHandInverseKinematicsFrameForMissionObjectUsage(...);  // 手贴到炮身上
```

**要自己写的那部分**（原版组件不提供的）：轮子转动、车速插值、炮身朝向、滚动音效。这块参考 BattleArtillery 的 `BallistaMove` 类写法 —— 但**只作设计参考，不要抄代码**，理由见 §B4。

### B3 prefab 从哪来

**不从零建模，用两个原版文件拼**（已逐个核对标签）：

| 抄谁 | 拿什么 |
|---|---|
| `Native/Prefabs/props_siege_batteringrams.xml` | `move` 站位点 ×6、`wheel` 轮子 ×8 ← **移动底盘部分** |
| `Native/Prefabs/props_siege_ballistas.xml` | `projectile_leaving_position`（炮口出弹点）、`pilot` 站位、弹药堆 ← **炮身部分** |

炮的 3D 模型本身要自制（进 `Taikou/AssetPackages/`）。

### B4 为什么不用原版组件（`SiegeWeaponMovementComponent`）

**原版组件要求场景里有一个叫 `Path` 的路径实体，随机战场没有。**

追到的具体证据（1.2.12 引擎源码）：

```csharp
protected internal override void OnAdded(Scene scene)
{
    _path = scene.GetPathWithName(PathEntityName);   // ← 从「场景」找，不是从 prefab 找
    _wheels = MainObject.GameEntity.CollectChildrenEntitiesWithTag("wheel");          // ← prefab 内查找 ✓
    _standingPoints = MainObject.GameEntity.CollectObjectsWithTag<StandingPoint>("move");  // ← prefab 内查找 ✓
```

轮子和站位点可以放进 prefab，**`Path` 不行**。

**没有 `Path` 的后果**：不崩（`SetTargetFrame()` 有 `PathExists()` 守卫，会直接跳过），但**炮永远不动**——静默失效，比崩溃更难查。

**结论**：原版组件的优势（推动画白送）在我们自写组件里同样能拿到（就是 §B2 那几行），所以没有理由为它承担 `Path` 的不确定性。

## 六、风险与待验证

| # | 风险 | 影响 | 处置 |
|---|---|---|---|
| R1 | 自写移动组件与 `RangedSiegeWeapon` 基类的耦合点不明 | 阶段 1 可能推翻重做 | **阶段 1 就是为验证这个**，先做原型 |

| R4 | 美术工期（枪模型 / 炮模型 / 粒子 / 音效） | 决定整体交付时间 | 与代码并行，不阻塞 |
| R5 | 1.2.12 与 1.5.x 的 `RangedSiegeWeapon` 签名差异 | 编译不过 | 全部走 `Core/VersionCompat.cs`，禁止业务代码裸写版本 `#if` |

## 七、建议实施顺序

1. **线 A 数据层**（`item_usage_sets.xml` + 铁炮物品 + 一个铁炮兵种）—— 零代码就能跑通，先把兵种建起来
2. **线 A 机制层**（`FirearmFxRegistry` + `FirearmFxLogic` + 音效）—— 枪感成型
3. **线 A 美术**（枪模型 + 粒子 + 音效）—— 与 2 并行
4. **线 B 阶段 1**（prefab 原型）—— 独立开工，验证通过再排后两阶段
5. 线 B 阶段 2、3

线 A 的 1→2→3 与线 B 的阶段 1 之间没有依赖，可以并行。
