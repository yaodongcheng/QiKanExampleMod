# 时代剧本切换 — 先行验证（spike）

> **状态：📋 待开工**（2026-09-10 设计完成；用户提「先验再铺开」）
> **上游**：主 plan「四、」节（本文档从那里抽出）；剧本层路线见 [scenario-campaign-mode/06-玩家身份与时代重置](scenario-campaign-mode/06-玩家身份与时代重置.md)（该 plan 未审核，本 spike **不依赖**它）
> **一句话**：T4 要铺几百个据点、上千人物——**万一"多时代"这条路走不通，数据结构要推倒重来**。所以用最小成本先验一次。

---

## 要验的一件事

换了时代（如 1560 日轮 → 1582 转变），**据点归属 / 家族 / 王国 / 英雄**这四样能不能整套跟着变——世界建得出来、四项都对、两个时代互不污染。

## 候选机制（本次要验的就是它）

**一模块多 GameType + 每时代一套数据段**

- 引擎按 `<GameType value="…">` 过滤数据段（**现在就是这么工作的**：Taikou 的 30 个段挂在 `TaikouCampaign` 名下）→ 多时代 = 再注册一套段（换 GameType）+ 一个 thin 战役类 + 主菜单一个入口。
- **为什么不走官方 `worldscenarios` 扩展点**：那是 **1.5.1+** 的机制（06 号 plan 自己也标了"按其自身版本择用"），**我们的运行环境是 1.2.12**。

## 🔴 时序硬约束（决定了"选时代"只能放哪）

| 时序 | 发生什么 |
|---|---|
| ① 模块加载 | 只读 SubModule.xml 的段**清单**，数据还没加载 |
| ② **玩家点主菜单入口** | 启动对应 GameManager → new 出对应**战役类** |
| ③ 战役初始化 | 各段按 `IncludedGameTypes` **过滤加载**——过滤用的字符串 = **战役类名**（实证：官方 `Campaign` / 织丰 `ShokuhoCampaign` / 我们 `TaikouCampaign`） |
| ④ 建号流程 | 到这里数据早已加载完 |

**⇒ 两条推论**
- **「选时代」必须在主菜单层**（它决定加载哪套数据段，赶不上建号流程）。落地 = 主菜单一个「太阁」入口 → 展开剧本列表 → 点一个开局。技术上 = 6 个 `InitialStateOption`，**与现有 `CampaignModeActivator` 加"新游戏"入口同一机制**。
- **「选角色」可以留在建号流程内**（它只是运行期注入玩家身份：改名/换阵营/传送/配部队，**不决定加载哪套数据**）。
- ⚠️ **06 号 plan 要改形态**：它把"时代 → 角色"两层都放在建号流程里——**1.2.12 上第一层必须上移到主菜单**。等 06 审核时一并提。

**为什么不省掉多余的战役类**：引擎的段过滤就是拿一个**字符串**比对 `IncludedGameTypes`；该字符串来自战役类名（`GameType.GameTypeStringId => GetType().Name`，虚属性）。理论上可让一个类按变量返回不同串，但省下的只是几个 thin 小类（每个 3 行），换来的是**碰引擎内部的未知风险**——不划算。除非 U1 验证发现"一模块多 GameType"本身有问题，届时再议。

## 数据源结构（推荐 = 骨架 + 时代差异 → 生成器展开）

> **前提（用户给定）**：①**城池数量跨时代相同**（只是**改名 / 换归属**）②**人群是同一批**（一份人物池，各时代区别只在"未出生 / 已死 / 在世"与归属）。这两条成立 → **骨架可以共用**，每个时代只需要存"差异"。

**五张表（CSV，人维护 = 唯一真源）**

| 表 | 粒度 | 内容 |
|---|---|---|
| ① 据点骨架 | 每据点一行 | 据点 id / 地图场景 / 地图位置 / 组件类型 —— **跨时代不变** |
| ② 据点时代差异 | 据点 × 时代 | **显示名 / 归属家族** —— 每时代一行 |
| ③ 势力（家族·王国） | 势力 × 时代 | 是否存在 / 名称 / 统治家族 / 上级王国 —— 每时代一行 |
| ④ 人物池 | 每人一行 | 生年 / 卒年 / 属性技能 / 家系 —— **固有，跨时代不变** |
| ⑤ 人物时代差异 | 人物 × 时代 | **所属家族** —— 「在世 / 未出生 / 已死」**由生卒年自动推导，不用手填** |

**生成器（一次产出 = 引擎要的 XML，产出即每时代一套段）**
- 每个时代 → 一套 `settlements_<时代>.xml` / `spclans_<时代>.xml` / `spkingdoms_<时代>.xml` / `heroes_<时代>.xml`
- `SubModule.xml` 里按各时代 GameType 分别注册（引擎按 GameType 过滤，**运行期只加载所选时代那一套**）
- **「已死」怎么落地**：XML 表达不了"这人开局就已死" → 每个时代另生成一张**开局击杀名单**，由**一个**开局 behavior 走官方击杀流程（**运行期唯一要保留的一件事**）

**为什么推荐这个结构**
1. **差异集中在小表里**：几百据点 × 6 时代，每行只有"名字 + 归属"两个字段——改一处只改一处。
2. **符合数据优先三原则**：能 XML 不代码；**能离线查的绝不留给运行期**（每时代一套 XML → 十三件套能对**每套单独**跑）；运行期只剩"击杀已死"。
3. **绕开两个未知点**：运行期改据点归属、运行期改名——引擎接不接得住、UI 刷不刷新，**都不用验了**。

🔴 **一条关键纪律：据点 id 跨时代必须稳定（只改显示名，id 永不变）**——这就是铁律 20（引用一律用 StringId）。额外红利：**距离缓存天然可共用**（缓存按**据点 id** 存据点对）→ U4 风险**自动消解**。这正是"城池数量相同"这条前提的价值。（若某时代确有据点增减，表里加「启用」标记处理，缓存问题届时再议。）

**不推荐的两种**
- **每时代手写一套 XML**：6 倍手维护量、改一处要改 6 遍 —— 但**经上面生成器产出就没这个问题**（人只维护那 5 张表，别手写 XML）。
- **运行期覆盖 XML 设置**（自己搞 CSV、开新战役时改引擎已加载的数据）：违背"能离线查的别留给运行期"（离线查不了运行期改的结果），且引擎支持度未知——要额外验两件事：改归属接不接得住、改名 UI 刷不刷新。

**顺带：对 06 号 plan 的一处简化建议**
06 把「按时代改年龄、重算技能」放在**运行期**做；用生成期展开的话，每个时代的 `heroes_<时代>.xml` **直接写对生年**即可 → **06 那部分可简化为纯数据**，运行期只剩"击杀已死"。

**待核对一项**：「城池数量跨时代相同」需要在 TK5 布局表上核一遍（若不同，用「启用」标记处理——设计已留余地）。

## 主菜单与读档（反编译 + 实测存档案查证）

**① 主菜单：要屏蔽原版、显示我们自己的——而且已经在这么做**
`CampaignModeActivator.WireMainMenu()` 现在就剔掉原版三个按钮（`SandBoxNewGame` / `StoryModeNewGame` / `ContinueCampaign`）再加我们自己的。多时代 = 多加入口。
⚠️ **一个漏网的**：原版的「**Saved Games**（存档列表）」按钮（`CampaignResumeGame`，SandBox.View 注册）**没被剔掉**——它点我们的存档会走 SandBox 的 GameManager（见 ②）→ 错路径。多时代前必须一并处理。

**② 读档：GameType 能自动对上，但载入入口必须我们自己的**
- **存档不记 GameType，记的是"对象类型"**：战役对象按类型序列化（`SaveableTypeDefiner` 注册过——雷 32 就是为这个"Could not find type definition"而加）→ 读档时恢复出**同一个战役类** → `GameTypeStringId`（=`GetType().Name`）自然是它 → **对应那套数据段正确加载** ✓ **自动对号入座**。
- ⚠️ **原版载入按钮写死了自家 GameManager**（反编译实锤）：
  ```csharp
  ContinueCampaign(): SandBoxSaveHelper.TryLoadSave(info, StartGame);
  StartGame(LoadResult r): MBGameManager.StartNewGame(new SandBoxGameManager(r));  // ← 写死 SandBox
  ```
  → 我们的读档必须换成 `new LivingWorldCampaignGameManager(loadResult)`。
- ⚠️ **存档元数据里没有"时代"字段**（实测 dump `save041.sav`：只有 `Modules` / `Module_<名>` / `CharacterName` / `MainHeroLevel` … **无 GameType**）→ 读档列表显示不出"这存档是哪个时代"。
  🔑 **但 `MetaData` 是自由键值表**（`Dictionary<string,string>`）→ **我们可以自己写一个键**（如 `LWN_Era=1560`），读档列表就能显示年代。
- **现状**：我们的「继续战役」按钮是**禁用**的（写死"Save-loading is not implemented yet"）——**读档链还没打通**；要多时代得先把这条链做完。

## 执行步骤（5 步，做完就能跑）

> 思路：**共用的段照旧**（文化/物品/模板/文本…），**只给有差异的 4 个段各注册两份**（A 一份、B 一份）。`IncludedGameTypes` 本身就是**多值列表**（现有注册就是 `['Campaign','CampaignStoryMode','TaikouCampaign']`），共用的段把 `TaikouCampaign1582` 追加进去即可，不用复制。

| 步 | 做什么 | 产出 |
|---|---|---|
| 1 | **时代 B 的 4 份差异数据**（复制现文件 + 改）：据点归属（京 → `clan_g`）/ 家族（+`clan_g`）/ 王国（+`kingdom_g`）/ 英雄（+`lord_g`） | `settlements_1582.xml` · `spclans_1582.xml` · `spkingdoms_1582.xml` · `taikou_heroes_1582.xml` |
| 2 | **SubModule 注册**：4 个差异段各注册两份；其余共用段把新 GameType 追加进 `IncludedGameTypes` | `Taikou/SubModule.xml` |
| 3 | **时代 B 的 thin 战役类** + 现有类改名 | `CampaignMode/TaikouCampaign1582.cs` · `TaikouCampaign.cs`→`TaikouCampaign1560.cs` |
| 4 | **主菜单第二个入口** | `CampaignMode/CampaignModeActivator.cs` |
| 5 | **检查脚本 game-type 推断改对** + 编译 + 十三件套（两套数据各跑一遍） | `Scripts/*.py` + 验证报告 |

## 要一次验完的 5 个未知点

| # | 未知点 | 可能出什么问题 |
|---|---|---|
| U1 | **多 GameType 共存** | 一个模块里两套同名段（都叫 `Settlements`/`Factions`）按 GameType 分开注册——进时代 B 时时代 A 的段会不会漏进来（串档） |
| U2 | 据点归属差异生效 | 归属是 XML 属性，预期没问题——但要眼见为实 |
| U3 | 家族 / 王国 / 英雄差异生效 | 新建的家族/王国要过世界创建链的一堆假设 |
| U4 | 距离缓存 | **遵守「据点 id 跨时代稳定」纪律则自动消解**；spike 顺便验一遍确认无残留 |
| U5 | 存档 / 读档后归属保持 | 归属进存档；**但读档链目前未打通**，本 spike 先验前 4 条 |

## 验收（6 条，逐条打勾）

1. 主菜单出现**两个**时代入口
2. 进时代 B → 建号 → 进图 → 点京 → **归属显示 `clan_g`**
3. 氏族界面看到 `clan_g`、王国界面看到 `kingdom_g`、能找 `lord_g` 对话
4. 存档 → 读档 → 归属仍是 `clan_g`（⚠️ 需先打通读档链，否则本轮跳过）
5. **切回时代 A → 归属仍是 `clan_oda`**（互不污染 = U1 过关）
6. 十三件套对**两套数据分别**跑（各 0 错）

## 分叉

- **验通了** → T4 按「每时代一套段」铺开（生成器按时代批量产出数据），06 的选时代入口届时接上。
- **没验通（多半卡在 U1 或 U3）** → 回退方案 = **一份基线数据 + 运行期"改朝换代"**（建世界后按所选时代改据点归属与家族归属）。⚠️ 回退方案**自己也要先验一件事**：运行期改 `Settlement.OwnerClan` / 家族归属，引擎接不接得住（含存档与 UI 刷新）——同样要实测，不能想当然。
