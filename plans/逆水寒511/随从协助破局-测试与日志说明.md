## 3. 关键日志合同

### 3.1 每条记录必须能关联到真实对象

**决定：复用DebugLogger，在关键出口写`[Coop]`单行结构化记录，值与诊断原因使用英文。** 推荐JSON转义，不能拼接未转义台词导致多行；不记录密钥或完整LLM请求。玩家界面使用本地化自然文字，不直接显示日志。

| 字段 | 含义／要求 |
|---|---|
| `event/seq/run/sceneEpoch` | 事件、当前场景单调序号、玩法过程、场景代次；时间戳不能替代因果顺序 |
| `actor/agent/target` | 稳定身份、当前身体索引及实际对象；无Hero模板使用稳定场景身份，不借玩家ID |
| `activity/source/owner` | 本人活动、来源（新／旧／岗位／日常等）、实际身体持有编号；没有租约则明确空值 |
| `planRevision/stage/step` | 当前计划、阶段和步骤；重规划不能沿用旧修订号 |
| `request/attempt/receipt` | 请求、逻辑掷骰尝试、业务收据；没有时为null，不随日志另造编号 |
| `state/result/reason` | 当前状态、真实结果与可稳定检索的原因；成功／无解／触限／失败／取消／被打断分开 |
| `configVersion/configHash/factsVersion` | 活动固定数据及计算所用事实快照；过期结果应可核对 |
| `simTime/testMode/injection` | 游戏推进时间、是否测试、注入内容／来源；暂停期间simTime不增加 |
| `contractMode/operationId` | 小六为临时协作还是正式同伴、稳定招募／单次人情业务身份；原委托奖励与招募／人情不得共用操作身份 |

适用事件补参数：位置、目标、到位距离、同层检查、观察者与视线解释、技能／门槛／骰子、资源前后值、预留／提交、节点与CPU耗时、公共答复、文本key、消息编号、语言、展示渠道、接收资格与丢弃原因。未适用字段明确空值；完整合同由实施者维护清单，不能因为某日志“写起来麻烦”省关键证据。

### 3.2 必须记录的关键出口

| 日志事件（拟议固定名称） | 写入时机 | 能证明／不能证明 |
|---|---|---|
| `run.begin/run.end` | 实际过程开始／终止，end带各项目真实结果及未了事项 | 能区分协作成功、玩家单独越门、同伴牵制未收尾；不能把取消统称完成 |
| `identity.bound/recruit.committed` | 身份绑定；实际核入队与结算后 | 绑定不证明招募；招募提交需Hero／队伍／receipt和金币前后值 |

| `answer.published/answer.observed` | 对方公开答复／本人通过合法渠道收到 | published不表示玩家／发起者听到；等待方仅在observed后知晓 |

| `view.updated/view.discarded` | 同版本玩家摘要实际渲染／过期拒收 | 只有玩家已知内容；隐藏理由仍仅在开发trace |
| `polish.requested/polish.accepted/polish.discarded` | 文字请求／同版本受控文本接收／校验或过期拒绝 | accepted不触发动作；实际显示还要speech／view出口 |

**日志量与可靠性：**关键提交、失败、释放和版本丢弃不采样；只在状态变化写，不逐帧把全体视线刷盘。trace内存建议最多512条关键记录，超出显示截断与完整文件位置；活动收据另保留，不因trace淘汰丢幂等性。日志写盘错误不影响游戏安全收尾，但若关键证据缺失，验收标“证据不足”，不能自动通过。

### 3.3 正常链与失败链怎样判读

下列为**预期事件顺序示意，不是实测日志**。双方独立动作可交错，检查因果依赖和编号，不能要求所有线程／演员每次同一行序。

```text
随从：plan.ready → preview.shown → brain.granted → step.started(接近)
随从：step.ended(completed，真实到位) → interaction.received(守卫)
共享：roll.committed → interaction.resolved → answer.published
随从：answer.observed → 接后续步骤／调整；不知道结果之前不提前推进
守卫：goal.selected → guard.choice(留岗交谈) → 本人Brain动作
随从：opportunity.observed → speech.shown(有限信号)
玩家：gate.evaluated(全员真实视线／技巧) → player.crossed(实际跨线)
随从：留在诱离点牵制 → 目击实际过门 → step.ended(wait_player_cross)
过程：原companion活动run.end(success，目标passed已由真实回执提交) → 控制权释放
```

不需要检定的普通信息请求可以没有roll；拒绝职责的分支必须没有roll。失败骰子应是`roll.committed(result=failed)`→守卫留岗拒绝→公开答复送达→随从换已登记的新方法或撤回→终态；同一attempt后续只许`attempt.reused`。调查链必须在`post.replacement_arrived`之后才出现原守卫调查移动的`step.started`，且接替者仍参与门禁观察。

**成功证据必须有真实因果次序：**计划已发布→本人Brain真实开始→请求到达→资格及一次检定→对方真实答复→本人合法收到→真实机会被观察→信号实际显示→玩家真实跨线→小六实际看到过门→分项终态和控制权释放。排队不等于开始，公开不等于收到，同意不等于离岗，发信号不等于已跨线；不要求同伴再追到玩家身边。

**硬失败判据：**未真实到位却写completed；排队动作被清却写started；拒绝后仍出现随从来源派给守卫的移动；同一attempt出现两次roll；同一receipt实际扣款两次；旧owner在新owner获准后清新动作；看不见／无法接近的守卫隔空推回玩家；没有`player.crossed`却结束为全目标成功；没有展示出口却声称玩家收到说明。任一出现即阻止该阶段交付。

## 5. 用户可复现的验收案例

**决定：表内每例均交初始条件、操作、现场预期、日志证据和反例判据。** 同一DLL分别运行GOAP、HTN和组合模式；自然试玩使用默认模式。T01～T04使用第1.2节的当前场景诊断，其余需要在测试副本手工准备真实人物／点位与输入；经济／存档用正式玩法在副本存档操作。夹具支持清单由`test list`给出，不能把未支持案例写成已通过。

### 5.1 两条必须完整演示的链

**T03：两人分别接受、小六带离、原处牵制与实际越门。** 完整可复制步骤见[第5.7节](#quick-execution-test)。先核两卫实际姓名与办法已经展示，小六未动；批准后逐个交涉。每人真实答复且小六听到后才允许带路，两卫各走到门外核查点，观察真实空当后小六发手势。玩家看见手势后亲自蹲行过门，小六留在诱离点，确认实际过门即可成功。固定roll=1只保证合资格的新协作检定，不保证寻路／视线／门禁技巧；必须保留自然无注入复验。

**T04：第一人接受、第二人拒绝后收尾。** 完整命令见[第5.7节](#quick-execution-test)。两次实际技能检定分别为1和0，不合资格时零掷点。第一卫等待引路，第二卫拒绝；小六不得继续两卫带路或发安全信号。有限重规划无路后原活动失败，身体可用时启动独立报告活动，回来说明未说动并回门外原位；第一卫的本次邀请撤回，职责系统处理回岗。报告活动成功不等于协助入城成功。

**T01／T02仍保留：**分别只固定首个新合法检定成功／失败，后续使用种子；单卫留岗交谈是条件备选。它们不保证两卫都答应，不用它们代表两卫完整执行已覆盖。同条件重试须复用attempt或因已用人情拒绝，不能反复命令刷新骰子。

### 5.2 完整测试矩阵

表内“日志”指必须有的因果证据，**每例还须记录现场是否一致**。无UI／画面证据只能算程序层通过。

| T02 首检定失败 | 首次新合法检定失败，按已授权手段重规划或报告 | 同attempt只一次roll，不能刷新人情／无限刷成功 |
| T03 两卫诱离 | 按第5.7节分别交涉、带路、观察、手势、玩家跨线、小六原处牵制并确认 | 两卫实际到位才gap；actor=son role=companion成功且crossed=yes、signal=yes |

### 5.3 持续开发接入的具体复现顺序

**T31～T37先保存接入基线，不直接修改正式数据做夹具。** 在已有Debug测试域维护V1／V2／V3隔离内容，沿现有生成／加载／发布路径校验，记录DLL、源文件hash、目录版本与全部相关业务ID。正常内容改动另外在测试副本实机复验，不能把夹具目录当正式DesignData发布。

1. V1运行后执行`custom.story_probe cooperate catalog`、`custom.story_probe cooperate status`和`custom.story_probe cooperate trace`，保存目录、计划、实际结果与现有收据。
2. T31仅改内容源，生成V2，不改DLL。退出场景，在大地图执行`custom.story_probe reload`；按原规则再次进入，核新目录及新内容行为，纯GOAP、纯HTN和组合模式分别验。新增的是已有能力的组合，未实现的新token应被拒绝，不能作为本例通过。

### 5.4 小六招募的真实玩法复验

**T38～T43用原出场小六，不能用普通Wanderer替身代表通过。** 在正式测试副本自然进入二次场景，与小六接工具委托，到杜野处按现有合法路线办妥，再回小六完成交差；`custom.story_probe status/persona`和原对话／业务日志核当前状态，不用resolve／reset制造前置。若涉及他的当前老周群戏尚未收尾，先正常处理再谈合作；原奖励与合作分别保留收据。

2. 临时模式先看基础计划并取消，分别查看`custom.story_probe cooperate status`和`custom.story_probe cooperate trace`（均只读）：无正式入队、无30扣款、无favor.used；再正常开始，首个真实交涉started后只消费一次人情。失败报告、归位／待接应与旧人物身份都可观察。

4. 正式入队后离场／重进，并在可保存时读档；再验分兵、被扣／死亡等实际不可用状态。检查原Cast与已有同伴入口只绑定原Hero的合法身体，不造另一个小六，不把远方／被扣人物拖到墙头。

### 5.5 修复后的分批验收顺序

**第一批：程序和正式数据。** 本轮A01～A03及相关反例已加入正式C#合同测试；原样正式JSON必须保持通过。实际原生不可离线的部分如实保留未验。支持版本编译证据与用户实际DLL版本记录齐全；历史两端编译记录不能代替本轮修复验证。

**第二批：关闭LLM，自然小六路线。** 用正常存档副本进511二次场景，自然完成杜野委托并向小六交差，当前事件收尾；先临时帮助，再独立副本验30付费及魅力免招募费。看执行前计划、双方真实交谈和守卫动作，玩家亲自过门；小六原处确认过门后收尾，未获知则继续有限等待。对应T03、T10～T12、T38～T43，不能靠resolve/reset跳前置。

**第三批：失败与安全边界。** 在当前场景诊断或明确手工条件下验固定拒绝不重掷、两卫仍看、接替晚到／永不到、路径受阻、机会消失、战斗／拘捕抢占、每阶段叫停、新旧移交和暂停。对应T02～T09、T44～T45、T13～T18、T28～T30。失败时必须有模板原因与实际收尾，不能瞬移、无限等或误清别人的动作。

**第四批：持久与呈现。** 真存档往返核失败attempt／付款／一次人情保持，活动不自动续跑；换新战役不继承旧账。核玩家和NPC实际能力裁定、同版两种说明、迟到润色、远离听不到／回问及关闭辅助显示。对应T19～T24。

### 5.7 跳过工具委托，直接验两卫执行（Debug）

**准备：**使用初始测试存档副本，进入511二次场景，小六与两名守卫实际在场，守卫具有真实Brain与岗位。退出开场／正式对白、ESC和全屏菜单。玩家留在门外、靠近小六（12米内）以接收计划卡，直接输入下面指令；不必先看向守卫，也不必持续保持他们在画面中。身体不可被绑／扣押／战斗占用，没有旧活跃诊断。不需要完成工具任务；可以关闭LLM，保留交互功能。测试期间勿存档。

**第一条：建立两卫成功条件链的计划。**

```text
custom.story_probe cooperate test begin T03 hybrid 32003 quick
```

T03将本次小六协作所有新的合法检定设为roll=1；hybrid是本地组合算法；32003是种子；quick在诊断账本准备一次临时口头牵制关系，并用当前场景真实参与者准备起始计划，免除启动时的观察前置。命令创建待批准预览，应返回`OK`并带`actor=son algorithm=Hybrid preparation=quick`，另说明无需启动视线；关闭控制台后才推进异步求解。待批准期间小六不会开始协作动作。它不完成任务／事件、不发奖励、不正式招募、不发通行权、不移动玩家；执行中的真实接近、说话、岗位、到位、视线与门禁检查全部保留。批准后NPC会真实移动／说话，人情在合法交涉开始消费一次；玩家过门、伤害、拘捕等真实结果不回滚。

若返回`participant_unavailable:<id>:<reason>`，对应守卫缺失或身体不可用；`participant_without_duty:<id>`表示没有真实Brain／岗位。测试未启动，诊断账本自动恢复，不需要先执行结束命令；不能把缺少第二卫改算单卫成功。`quick`不再返回启动观察不足。普通start／preview及不带quick的test begin仍要求玩家或小六此刻在30米内真实看见参与者；这条正式玩法规则不用于本节的快捷准备。

日志应有每名真实参与者的`test.participant_prepared source=scene_setup`，活动来源为`test_scene_setup`。它们是测试准备记录，不是小六亲眼观察证据；实际到位、空当与手势仍须后续真实执行日志证明。

**第二条：打开完整计划卡。**

```text
custom.story_probe cooperate view open
```

已有本地卡时只打开IM完整面板并选“附近”，无LLM也可用，不批准、不掷骰、不移动。若刚建预览尚未完成求解，先关控制台等卡片出现再用。核两名实际守卫姓名、诱饵办法、逐人交涉、带路、观察、手势、留在诱离点等你过门、收尾与失败打算；待批准状态第0步也不能写“正在执行”。先确认小六没动，**点卡片“开始”**后面板关闭，才进入执行。不要另打start，也不要把后台plan当作读卡的替代。

**执行时按顺序观察：**小六分别走近两卫；每人都经过“小六报信→守卫质疑离岗与职责→小六补充说辞→守卫有条件同意”。每句从真实上屏算起至少3秒，长句按现有冒泡时长最多6秒，上一句结束才换人；说完最终答复才启动守卫自己的活动。T03只固定最终合法检定成功，不省略质疑、不改成守卫无条件轻信。

随后小六走向门外巷口核查点→两卫持续跟过去并真实到点→小六确认门口空当→玩家实际看见手势。此时应有**独立的“附近”消息和即时屏幕提示**，明确催你趁空当过门，不强开聊天面板；提醒来自你看到的手势，不是隔空私信。启动无需看守卫，但接收手势时必须能看到小六（30米内、视锥与遮挡仍检查）；背对或遮挡时不发提醒。先停5秒，确认不能假记越门，再亲自蹲行跨门，小六继续留在诱离点牵制，看到你过门后结束协助，不必再到你身边。

守卫正常核查的45秒从实际到点、核查对白读完后算；途中真实受阻、失能或协作取消仍可提前结束。不能走几秒就因两人间距离没缩小误判失败。T03不控制玩家门禁技巧骰子；若技巧失败，保留真实拦截后果，不能因此宣称协助已全目标成功。

**查询步骤（每条均只读）：**

```text
custom.story_probe cooperate plan
```

看实际小六步骤／对象及版本，不改身体、骰子、财物或剧情；关闭控制台后继续观察。

```text
custom.story_probe cooperate status
```

看当前run与各人状态。通过必须是`actor=son role=companion state=Success crossed=yes signal=yes`与现场吻合；`role=reporter state=Success`只代表报告做完。若主活动失败，可从trace／整轮日志找到原终态。

```text
custom.story_probe cooperate trace
```

看最近关键记录（当前实现最多最近20条），不改变游戏；完整因果证据必须另保存运行日志。核两人各一次`roll.committed`／合法`attempt.reused`；`speech.shown`／`dialogue.turn_shown`／`answer.published`的`duration`、`endsAt`证明接话间隔；答复读完后才有`guard.choice`，随后实际到位`movement.observed`、空当`opportunity.observed`、示意`speech.shown delivery=visual`、提醒`signal.received source=witnessed_gesture channel=nearby_and_notice`、跨线与小六原处确认过门。不能只有“受理／排队”。

**结束本例：**先按第2节保存完整日志，再执行：

```text
custom.story_probe cooperate test end
```

停止本诊断产生的活动，恢复原协作账本与随机来源；不返回地图、不恢复真实人物位置、剧情、伤害、财物。下一例回到初始测试副本，不在改变后的现场直接串测。

T04将第一处新合法协作检定设roll=1、第二处roll=0，后续使用32004；quick和副作用同T03。仍先看卡片并点开始。应见第一卫答应、第二卫拒绝，小六不带完两人、不发安全示意；有限重规划无路后失败，身体可用时回来报告并回门外原位，第一卫本次邀请撤回并按职责回岗。原companion失败不能被后续reporter成功覆盖。用上面完整查询命令核原因、保存日志，再执行上面的完整test end命令。

- **影响：**旧动作尚未结束也可能显示新活动已开始；取消可误打断其他活动，排队的旧移动仍可能以后出队。暂停只改Director状态，Runtime仍先Tick，Brain仍跑；恢复没有完整保存原等待状态和原生动作期限。
- **修复要求：**复用真实Brain占用／移交合同；仅由Brain出队开始才写started。取消只撤本人本次持有／排队动作，终态也收尾。所有身体表现，包括转向、发声的提交阶段，都尊重当前控制权。
- **复验：**T09／T14～T18／T30；特别验“已入队未开始就取消”和“旧停止晚于新owner到达”，不可误清新动作或继续旧移动。
