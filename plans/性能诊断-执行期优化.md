# 性能诊断 · 执行期（PlanExecutor）优化

## Context（为什么做）

perf 面板实测（2026-09-03）：`AIC_PlanExecutor 3.09ms/帧 · 33% · 340.3ms/s ×110 (峰 35.0ms)`——计划执行期间每秒吃掉 340ms CPU（三分之一秒），单次尖峰 35ms（每 0.1 秒一次）→ 表现 = 执行期随机顿挫性抖动。目标：**执行期 CPU 降到 ~100-150ms/s、峰值 35ms → ~15ms**，消除肉眼可见抖动，且**零语义损失**（LLM 计划玩法照旧）。

## 成本账（已读码确认）

每次节流通过（每 0.1s 一次，~34ms）的重活构成：

| # | 位置 | 成本 | 说明 |
|---|---|---|---|
| 1 | `_world.Tick` → `SceneSnapshot.Build`（RuntimeWorldState.cs:50） | **大头** | 全场景快照：遍历全部 agent 建列表/引用/名字（PlanExecutor 每 0.1s 调一次） |
| 2 | `TickContingencies` → `_world.Evaluate` | **大头** | 每个 contingency 谓词求值（RuntimeWorldState.cs:62）：`seeing(any)` → `GetWitnesses` 全场景视线判定；`alert_phase(any)` → 遍历全 agent；且**每次 Evaluate 无条件构建 ConditionKey 字符串**（字典查找用——即使无 sustained/was） |
| 3 | `TickTriggers` → `_world.Evaluate` | 中 | 同 2 |
| 4 | `TickGuardrails` | 轻-中 | IsAgentActive ×2 + 遍历 RoleAgents |
| 5 | `TickCursor` → 步骤 when 门控 Evaluate + 子动作 Tick | 中 | 步进敏感，保留 0.1s |
| 6 | `DetectPlayerModalUi`/`IsPlayerInCombat`（313/318 行） | 轻 | 已在节流后 ✓ |

## 优化方案（按序执行）

### P1 — 测量先行（1 次实机确认分账）

在 TickInner 节流通过段加 5 个**明细槽**（只进 TOP 不进 modShare）：
`PlanInner_World`（_world.Tick）/ `PlanInner_Guard` / `PlanInner_Contingency` / `PlanInner_Trigger` / `PlanInner_Cursor`。
跑一次偷窃计划执行 → `custom.perf_status` 看分账，确认 #1/#2 实际占比（防「认为是快照其实是目击判定」的误修）。

### P2 — 求值分档降频（核心，语义安全）

| 项 | 现在 | 改为 | 依据 |
|---|---|---|---|
| `_world.Tick`（SceneSnapshot.Build） | 0.1s | **0.5s** | 快照只服务**兜底解析**（角色/物件未注册时按名字找）——已解析产物全在 `NamedPositions`/`RoleAgents` 字典，动态 query 求值一次即注册；兜底滞后 0.5s 的后果 = 本轮诚实失败（既有路径），且引用本体会在 0.5s 内注册。**但**：RoleAgents 里的 Agent 引用每 tick 要复核存活？——快照降频期其余逻辑全走字典 + 使用时 SafeIsActive 现查（RuntimeWorldState 内全部现查）✓ 无死引用风险 |
| Contingencies 求值 | 0.1s | **0.25s** | 意外检测延迟 0.25s 不可感知（触发条件本身由 LLM 写成数秒级 sustained）；ask_player pending 冻结逻辑不受影响；force/超时等硬语义不动（它们是**步骤**驱动非 contingency） |
| Triggers 求值 | 0.1s | **0.25s** | signal_player 播报延迟 0.25s 无感 |
| Guardrails | 0.1s | **0.25s** | 目标敌对/死亡检测延迟 0.25s；顶部**死亡看门狗在节流前每帧拦**（TickInner 279 行），死亡/离场不受影响 |
| 步骤 when 门控（TickCursor） | 0.1s | **保留 0.1s** | 步进敏感（ask_player/force 跳转 + 门控等待判定需跟上节奏） |

实现：PlanExecutor 加 `_heaviesAccum`（与 `_tickAccum` 并列），节流通过后按重活 vs 轻活分两个计时器：`_tickAccum`（when 门控，0.1s）+ `_heaviesAccum`（快照/意外/触发/护栏，0.25s）。轻活每 0.1s、重活每 0.25s。

### P3 — ConditionKey 短路（GC 减负）

`Evaluate`（RuntimeWorldState.cs:62-94）开头：`if (c.SustainedS <= 0f && !c.Was) 跳过 key 构建`（当前**无条件** StringBuilder 构建 key——每 0.1s 数十次字符串分配，GC 停顿本身也贡献抖动）。时机敏感：was 状态记录需要 key——`Was=false && SustainedS<=0` 时真不用。

### P4 — 步内动作（atomic）层预留给第二阶段

MoveAction/FollowAction 的 0.2s 路径重算（寻路）属「Agent 动作域」，与执行器域分家；本 plan 不碰（改错域会牵连战斗/脑）。P2 完成后如果 340ms 还剩 >150ms（说明大头在原子动作而非求值），再开第二阶段 plan。

## 验证

1. **perf 对照**：优化前拍面板（AIC_PlanExecutor 340ms/s · 峰 35ms P0 基线）→ 优化后同一场景同计划：期望 ≤150ms/s、峰 ≤15ms
2. **玩法回归**（语义保真清单）：
   - 偷窃流程：接近→扒窃→目击 ask_player→玩家应答（contingency/force 语义正常，超时兜底没变慢）
   - BRING 计划：跟随掉线检测（seeing false 5s sustained）在 0.25s 档下仍正常触发（sustained 计时按 0.25s dt 积分——**注意 sustained 语义**：`_dt = tickDt`（0.1s 节流）现改为重活 dt（0.25s）→ sustained 积分步长变大、精度仍 OK（0.25s 粒度 < 触发阈值 5s 的 1/20）✓
   - 击晕/巡逻计划：Guardrails 0.25s 档下全流程
3. **无 LLM 调用回归**：优化后计划执行期日志无新异常；`custom.perf_status` 数据正常
