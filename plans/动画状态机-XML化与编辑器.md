## ⓪ 认知基线：这台状态机的**最终归属是 `SetActionChannel`**（用户 2026-09-25 裁定 · **先看这条**）

> **用户原话**：「别说什么没在游戏里验证过这种话，因为游戏的动画状态机都是我自己在骑砍2之外自己做的新建的，

### 三条（从此是**前提**，不再论证）

1. **这台动画状态机是自建层，不是骑砍2 的原生动画系统。** 整条链都在我们自己的代码里：
   `statemachine_flight.xml` → `Animation/AnimMachineLoader.cs`（装载 + 校验）→ `AgentAnimStateMachine`（求值）
   → **唯一的落点 `agent.SetActionChannel(0, idx, …)`** —— 引擎只负责"把某条 clip 写到 0 号通道"。
2. **`XML → 运行期` 这条路是用户的**：他自己解析、自己装载、自己看 clip 落得对不对。
   所以"写得对不对"的**最终判据 = 他跑一遍看落没落对**，**不是**"等一个外部条件成熟"。
3. 🔴 **"这台机从没在游戏里跑过" 不再是拒绝改动的理由，也不再是风险等级的判据。**
   风险只有一个正确度量：**改动会不会破坏 `XML → SetActionChannel` 这条链**。
   这条链的最坏情况 = **0 号通道被写上一条不对的 clip** —— **可观测、可回滚、不需要动引擎**。

### 由此产生的**行为修正**（对 AI 自己）

| 以前（错） | 现在（对） |
|---|---|
| 用"要先实机验证"把**运行时改动**挡回去 | 运行时求值类改动（Entry 条件分流、相位读边上条件…）**属正常功能范围**，该做就做 |

| 验收口径 = "编译通过 / 规则镜像通过" | 验收口径 = **跑完是不是落了正确的 clip 到 0 号通道** |

### 本轮（会话 2）最值钱的三条教训

1. **静态截图抓不到交互 bug**。双击进容器 / 拖绿点建边 / 拖状态进容器全是"看着有代码、点了没反应"，

## 十五、会话 2 补丁 8（同日）：去掉画布的"隐形边界"

用户实测：「为什么画布红框这一侧我这么拖都拖不过去？如果画布必然有边界，你为什么不把节点画在画布正中间」

**真因**：拖拽里写着 `Math.max(0, x)` —— 元素位置被卡在**世界坐标 x≥0 / y≥0**。
所以把节点/容器往画布左、上侧推时，推到世界 0 就再也过不去（看着就是"画布有左边界"）。

**修法**：拖拽 / 新建状态 / 容器 Entry 的自动摆位**全部不再钳制**（允许负坐标）；网格底色从 ±4000 扩到 ±20000。
世界本来就是无限的，网格只是视觉参考。

**"为什么不画在正中间"**：首次加载会跑 `fit()` 把内容居中（截图里就是居中的）；
用户看到偏移是自己拖过 / 平移过之后的状态。去掉边界后就不存在"够不到的那一侧"了。

| # | 缺 | 真因（改前） |

| 1 | **没有撤销 / 重做** | 全文件无 `undo` / `redo`。连错一条边只能手动改回来 —— 而这正是"自己重连"最痛的点 |

### 做了什么

**① 撤销 / 重做（快照栈）**

- 快照 = `{states, groups, edges, pos, gpos}` —— 🔴 **不含 `view`**：缩放平移是"浏览"不是"编辑"，撤销不该把镜头也倒回去
- 结构是**线性栈 + 指针**（不是双栈）：天生去重，也天生支持"改完再改回去"
- 🔴 **挂在 `commit()` 上**：`function commit() { save(); histPush(); render(); }` —— 所有结构性改动都走 commit，
  于是**自动全覆盖**（拖节点 / 改名 / 建边 / 面板下拉 / 右键菜单，一个都不用单独埋点）
- 入口：`Ctrl+Z` 撤销 / `Ctrl+Shift+Z`（或 `Ctrl+Y`）重做 + 顶栏 `↶ / ↷` 两个按钮（`disabled` 随栈状态更新）
- 上限 80 步；`histReset()` 在载入后把"初始结构"定为第 0 帧 ⇒ **第一次编辑也能撤回**

**② Delete 键能删 边 / 状态 / 容器**

- 状态 / 容器是**级联**删除（`removeState` 连带删掉所有引用它的边；`removeGroup` 连带删掉从它出发的边），
  删完给一条明确提示（含"连带删掉 N 条边 —— Ctrl+Z 可撤销"），**删错靠撤销兜底**
- ⚠️ **为什么不弹原生 `confirm()`**：它是**阻塞式**的，无头自检（`drive_pages.mjs`）会被对话框直接卡死

**③ 顺带修掉的显示缺陷**：`notice`（一次性提示）以前**只在"状态"分支里渲染** ⇒
撤销 / 删除的提示在没选中状态时**根本看不见**。现在统一提到面板顶部的 `#notice`。

## 二十三、会话 3 补丁 3（同日）：**一次性不写时长 + 剩余条件改百分比**（🔴 XML schema 变更）

> 🚨 **本轮动了 C# 与 XML 语义 —— 这是整份文档里第一次改运行期，必须实机验证（§二）。**
> 本节**取代 §二十二 ④**（那一版让用户从下拉里选"时长标量"；用户随后裁定：**连那个值都不该写**）。
> 关联：`tools/anim-statemachine/README.md`。

### 用户原话（两条，其实是一件事）

> 「animclip本身就有duration信息，引擎自己读到，所以这里不用写duration具体值。
> 　然后状态路径边有一个条件是当前动画波剩余多少，这里也填写百分比就行」

### 查证：两条合成一条主线

- 引擎早就在给 `agent.GetCurrentActionProgress(0)` —— **0~1 的播放进度**（`AgentAnimStateMachine.Enter` 里挂在 `_progressFn`）。

## 二十四、会话 3 补丁 4（同日）：🔴 **容器改名后拖不动**（用户实测 · 纯工具 hotfix）

> 只动**编辑器**（生成器 + 页面 + 自检）。XML 语义、C# **一行没动**。

### 症状（用户原话）

> 「我给两个容器改了名字之后 无法拖动了」

### 真因：一眼是"拖不动"，根子在**索引没重建**

`groupBox(i, g)` 第一行就是 `const p = gpos[g.name];` —— 它**必须拿到 g**。

而两处"容器改名"（面板的「容器名」输入框、右键「重命名…」）都只做了：

```js
g.name = nn;                                    // ← 只改了对象里的名字
edges.forEach(e => { if (e.from === oldName) e.from = nn; });
```

**没有重建 `groupByName` 索引**（旧键留着、新键根本不存在）。连锁反应：

1. `pointerdown` 里 `groupBox(groupIndexOf(gname), groupByName[gname])` ⇒ `groupByName[新名]` 是 `undefined`
2. `groupBox` 读 `gpos[g.name]` ⇒ **TypeError** ⇒ pointerdown **半路中断** ⇒ 连 `setPointerCapture` 都没执行 ⇒ **整个容器拖不动** ✅ 症状精确对上
3. 同一个索引还挂在 `anchorOf()` 上 ⇒ 它的边**画不出来**（返回 null 直接被跳过）
4. 顺带第二个 bug：`gpos` 还是**旧键** ⇒ 就算能拖，盒子也已经**跳回默认位置**

### 修法（治本 + 顺手清同源隐患）

| 改动 | 说明 |
|---|---|
| 新增 **`reindex()`** | 一处重建 `stateByName` / `groupByName`；凡是"整批换数据"或"改名字"的收尾都调它 |
| 新增 **`renameGroup(oldName, nn)`** | 容器改名**一条龙**：名字 + `reindex()` + 边来源 + **`gpos` 迁移** + tab + 选中 |
| 面板「容器名」/ 右键菜单 | 都改走 `renameGroup`（原来是两份重复实现，而且**两份都漏了索引**） |
| 🔴 右键「重命名…」不再用原生 **`prompt()`** | 它是**阻塞式**的，无头自检一碰就卡死。改成"去右侧面板输入" |
| `histApply` / 导入(`btn-apply`) / `恢复成文件里的样子` | 全部改走 `reindex()`。🔴 **导入那处原来只叠加不清空** ⇒ 旧名字会残留在索引里（同类隐患，一并清掉） |
| `renameState` | 也换成 `reindex()`（原来手写 delete/assign，等价但容易漏） |

### 自检（61 → **64**）

| 新增 | 断言 |
|---|---|
| ㉚ | 改容器名后：`groupByName[新名]` 在、`[旧名]` 没了，且 **`gpos` 跟着迁**（位置不跳） |
| ㉚b | 改名当帧 `groupBox(...)` **不再抛错**（拖动的起手就是这一句） |

### 补修 2（同轮）：从**容器端口**拉线时，预览线飞向画面外

**用户原话**：「悬浮飞行容器右侧的小圆点想连接时候 线条显示异常」
（截图：一条绿虚线从容器端口飞向**左上角画面外**）

**真因**：预览线一律按"**状态节点**"取起点：

```js
const r = nodeRect(pending);          // ← 这是给"状态"用的
...`M ${r.x+r.w} ${r.y+r.h/2} L ${mouse.x} ${mouse.y}`
```

但 `pending` 是「**状态名 / 容器名 / outside**」三选一。从容器端口拉线时 `pos["悬浮飞行"]` 不存在
⇒ `nodeRect` 走进兜底分支 `{x:0, y:0, w:240, h:50}` ⇒ 起点变成**世界坐标 (240, 25)**
⇒ 线就从画面外拉过来（截图里那条正是它）。

**修法**：起点改用 **`anchorOf(pending, 当前页)`** —— 和**边本身**用的是**同一套锚点规则**，必然一致。
（`anchorOf` 本来就正确处理三种来源：「容器 → 它的盒子」「outside → 机外盒」「状态 → 自己的节点 / 所属容器盒」。）

**自检（64 → 67）**：

| 新增 | 断言 |
|---|---|
| ㉛ | 容器盒右侧有出边端口（拉线的起点） |
| ㉛b | 预览线的 `d` **以容器盒右侧中点为前缀** —— 实测 `M 345.739 332.870 L …`，与 `groupBox(Upright)` 的右中点**逐位相等** |
| ㉛c | 这次拉线**没留下脏边**（截断回基线，别污染后面的断言） |

> 🔴 两轮 hotfix（§二十四 的 1 和 2）是同一类病：**"名字/锚点这类隐式约定"在改名或多来源路径上没走全**。

## 二十五、会话 3 补丁 5（同日）：**相位边的条件原来是"真的"** —— 出机时机搬进 XML

| `when="takeoff-trigger"` | **没人读** | 只是文档（写出来让"从哪进 / 从哪出"诚实） |
| `anim="remaining" anim-rem-pct="10"` | **相位（C#）读** | 🔴 **事实** —— 改它就是改时机 |

### 改动清单

| 文件 | 改动 |

**XML**

### ② 组合逻辑 —— 已经有了，只是没在界面上说清

**"同时按 W 和 Shift" = 现有的命名谓词 `sprinting`**：

```csharp
AnimConditions.Register("sprinting", c => C(c).Boost && C(c).Moving);   // 按着 Shift 且在动
```

`Upright → fastmoveStart when="sprinting"` 用的正是它 —— **那条就是"进快移"的边**。

**"离开快移"不需要写 `NOT(W && Shift)`** —— 状态机的边是**优先级阶梯**，离开由**另一条边命中**表达：

| 边 | 条件 | 什么时候成立 |
|---|---|---|
| `ProneFamily → fastmoveLeanL/R` | `sprint-lean-left/right`（after-finish） | 还在冲刺但压弯 |
| `ProneFamily → idle` | `at-rest` | 停住了 |
| `ProneFamily → hovermove` | `moving` | **松开 Shift 但还在动** ⇒ 这就是"离开快移" |

⇒ 松开 Shift ⇒ `sprinting` 不成立（`Boost` 假）⇒ `moving` 那条命中 ⇒ 回悬停。
**用"一条正向边"表达 `not`，比再造一条取反边安全** —— 取反边会和现有边**重叠**，
而 §八 记过"两条边互踢、动画永远播不起来"（boost↔cruise 每 5ms 互踢）。

**所以编辑器现在直接把这句写进面板**：要组合就用「命名谓词」，并点出 `sprinting` 的真身。

**要更多组合怎么办**（例如"W+Shift 且不在施法"）：**在 C# 登记一个命名谓词**，一行：
`AnimConditions.Register("名字", c => …);` → XML 里 `when="名字"`。
这就是既定的「**结构进 XML、判据留 C#**」边界，**不开字符串表达式**（那是另一种静默失败）。

> 用户截图 + 原话。查下来是**三件事叠在一起**，其中一件是**会让整台不注册**的真陷阱：

| # | 事实 | 处理 |
|---|---|---|
| 1 | Entry 那行显示的是**这个容器的 `entry` 属性**（进容器落到哪），不是"线拉到哪"。用户那一步做的是**建了一条边**（notice 里写的就是「已新建边 → 容器「子容器1」」），`entry` 根本没动 ⇒ 还是 XML 里的老值 `hovermove` | 文案澄清（README「怎么用」表里加一行） |
| 2 | 那条入口线**指到子容器盒**是对的：`hovermove` 被搬进了 `子容器1` ⇒ `anchorOf` 就近锚在装着它的盒子（§二十八 ⑧ 改的那条）。但"线指盒子、字写状态"看着就是矛盾 | 新增 **`entryPathOf(gname)`**：把入口写成**人话路径** `子容器1 → hovermove`，四处统一用它（Entry 盒 / 入口线标签 / 容器盒副标题 / 边列表的容器标注） |
| 3 | 🔴 **`entry="hovermove"` 这时已经失效** —— 装载器硬要求 `entry` 是**本容器的直接成员**（`Animation/AnimMachineLoader.cs`：`Array.IndexOf(kv.Value, ent) < 0` ⇒ 报错 ⇒ **整台不注册**）。用户在界面上"把状态拖进子容器"这个**完全正常的操作**，会**顺手把自己的 entry 弄失效** | 校验文案改成**可执行**：「…不是它的成员 —— 它已经被收进了子容器「子容器1」；**把 entry 改成「子容器1」即可**（装载期会继续解析到 hovermove）」。失效时路径前面还会带 `⚠` |
