### 当前怎么操作（🔴 **2026-09-21 实机验证版，与正文旧方案不同，以本节为准**）

| 操作 | 手势 |
|---|---|
| **起飞** | **跳跃中按空格**（二段跳）。不要求"刚跳过"，从高处坠落时按空格也能飞 |
| 起飞（后备） | 站着长按空格 0.65s（`tune longpressjump 0` 可关） |
| **飞行方向** | **W A S D** —— 方向 = **相机**方向（含俯仰）；机身朝实际移动方向（W 前 / A 左 / D 右 / S 转身朝镜头） |
| **转视角** | **鼠标**（接管相机后由我们读鼠标驱动） |
| **冲刺** | 左 Shift（26 m/s；巡航 9） |
| **瞄准机位** | **鼠标右键**（只在悬停/巡航生效，加速中不给进）—— 过肩近景、人物偏左 |
| **飞行中施法** | **按住右键蓄力**（右手上方出现能量球，越蓄越大、火越浓）→ **点左键放**（朝**相机中心**飞）· **松右键 = 取消**（不放）。见下方专节 |
| **落地 · 短按** | **贴地（≤8m）或俯冲时**按一下空格 —— 🔴 保持**待机姿势**下降，**触地当场**还控制权（不播落地动画） |
| **落地 · 长按** | 按住空格 = **持续下降**（松手停）—— 同上，属"主动放下"，不播落地动画 |
| 落地（自动） | 板顶触地（容差 0.25m）—— 🔴 **撞地不算主动放下**，照旧播落地动画 |
| 落地后 | 主动放下：**触地即**还控制权；撞地：**等动画播完 2 秒**（`tune landanim`）|
| 落地时镜头 | 🔴 一进落地阶段就切**悬停机位**（离得近），不再跟着巡航/加速机位收摊 |

### 🆕 飞行中施法（2026-09-24 落地 · 用户裁定）

**一句话**：飞行中**右键 = 蓄力键**（它本来就是瞄准机位键，一举两得），球挂在**右手上方**，
放出去的**方向 = 相机中心**（不是身体朝向）。飞行中**不要求装备法印/法术弹** ——
手里认得出法术就用它，认不出就用**飞行默认法术**（法术表里第一条 `projectile` 族，见 `SpellRegistry.DefaultFlightSpell`）。

| 动作 | 行为 |
|---|---|
| 按住右键 | 蓄力：右手上方出现能量球（网格 `charge_mesh`），随蓄力**长大**（数据 `charge_scale`）+ 粒子**变浓**（发射率倍数 0.08 → 1.5，走引擎的 `SetRuntimeEmissionRateMultiplier`） |
| 点左键 | **放**（按**当前**蓄力，不必等满 —— 满蓄力只是伤害最高档）；方向 = 相机中心 |
| 松右键 | **取消**（不发射，球与粒子当场清掉） |
| 引导型法术（`cast_type="channel"`） | 右键按住 = 持续放、松右键 = 停（引导中左键不参与） |
| 地面 | **本阶段停用**（2026-09-24 用户裁定）：地面有常规攻击模式，施法手势/动作会跟它打架 ⇒ 先只在空中施法，地面之后再谈兼容。`custom.spell cast`（控制台）与法印开火拦截**不受影响** |
| **瞄准偏移**（2026-09-24 落地） | 蓄力 / 引导期间**身体 + 头都朝相机方向**（"看相机无限远处"），压过"朝实际移动方向"那条；松手/取消/放完立刻回到原规则。⚠️ 这条**不看有没有移动输入**（站着不动也能瞄）。判据 = `SpellCastInput.IsPlayerAiming`（飞行那边读它，见第 ⑧ 条机身朝向那段） |
| **头的做法**（2026-09-24 查实） | 引擎**原生就有**：`Agent.SetLookToPointOfInterest(点)`（反编译 `Agent.cs:2170`）+ `DisableLookToPointOfInterest()`（`:3797`）。**POI 是粘性的** ⇒ 进瞄准设一次（`眼位 + 相机前向 × 200 m`）、退出关一次（`_headAimActive` 记账；**只撤我们自己设的**，原版对话也用这个口） |
| **蓄力球挂右手骨**（2026-09-24 落地） | 不再用"身体坐标近似"：`Monster.MainHandBoneIndex` + `AgentVisuals.GetBoneEntitialFrame(bone, useBoneMapping:false)`（当前动画帧的世界帧 ⇒ **手怎么动球怎么动**）+ 上抬 `HandAnchorUpOffset`（0.18 m）。取不到才退回近似位。诊断：`custom.spell hand` 打出**骨索引 / 骨世界位置 / 相对角色的三向偏移与距离**（这几个数就是要记进文档的） |
| **施法手势动画**（2026-09-24 落地） | FCS 的 `MagicIdle`（蓄力循环）+ `ProjectileSpell`（释放一次性）已由用户经 ModKit 发布 → **迁移进 `Taikou/AssetPackages/lwn_taikou_anim.tpac`** → 注册成 `act_magic_idle` / `act_magic_projectile` → 由**飞行那台动画状态机**播（`FlightAnimMachine` 的 `magicIdle` / `magicProjectile`）。🔴 **走通道 0、不是通道 1** —— 实机定案：通道 1 对我们导入的 clip 完全无效（证据与做法见 [wheels.d/agent.md](rules/wheels.d/agent.md)） |

### ✅ T1b 定案（2026-09-21 实机验证通过）：`aipause`

**现行做法 = `Controller = AI` + `SetIsAIPaused(true)`**（已设为默认档，起飞自动冻、落地自动还）。

**它为什么是答案**：飞行要同时满足三件事，只有这一档全中 ——

| # | 要求 | aipause 为什么满足 |
|---|---|---|
| ① | 玩家 WASD 被拿掉 | 切 AI 就成立（用户在地上实测：AI 档 WASD 完全无效） |
| ② | 板照样托人 | 切 AI 不影响碰撞承载（日志 `player.z - board.z` 恒为 **0.37** = 板顶面高度） |
| ③ | **不让"脚下平台在动"干扰 AI** | 🔴 这是 `ai` 档失败的原因：AI 有自己的**平台自适应**，板一动它跟着调整 ⇒ 在板上乱走/滑移。**暂停 AI = 那套自适应整个不跑** |

**实机判据**：`[Flight-Diag]` 里板停之后人与板**双双静止、偏移恒定不漂**（若是 AI 在走路，会往回收敛——它没有）。
WASD 已可正常用于飞行。

### 🔴 `ctrloff` 档的来历（2026-09-21 二次反编译，用户提问逼出来的）

**问题**：「`Controller=Player` 的时候，就拦不住 WASD 了吗？」—— 不是拦不住，是我第一次只找了一条路。

**答案**：`TaleWorlds.MountAndBlade.View.MissionViews.MissionMainAgentController` 上有
**`public bool IsDisabled { get; set; }`**（公开可写），而玩家输入就写在这个守卫里面：

```csharp
public bool IsDisabled { get; set; }

// OnPreMissionTick 里：
if (... && !Mission.MainAgent.IsAIControlled && !IsDisabled && _activated)
{
    InteractionComponent.FocusTick();
    ControlTick();          // ← 玩家的移动输入就写在这两行里
    LookTick(dt);
}
else { LockedAgent = null; }
```

**为什么它是甜点区**（三个条件同时成立，这是前几档都做不到的）：

| | `Controller` | 引擎写玩家输入 | AI 会驱动他 | 板托人（已验证的那套） |
|---|---|---|---|---|
| 第一版 `flags` | Player | **写**（清不掉，实机证伪） | 否 | ✅ |
| `ai` / `aipause` / `aidetach` | **AI** | 不写 | **会**（除非暂停/摘编队生效） | ❓ 未知 |
| **`ctrloff`** | **Player（不动）** | **不写** | **否** | **✅ 同已验证的那套** |

**代价**：`LookTick` 一起停（角色不再自动转向镜头）—— 对飞行无碍，机身朝向本来就由 `TurnBody` 每帧写。
**相机不受影响**（走 `Mission.OnTick` 的 `_missionState.Handler.UpdateCamera`，另一条路）。
`InteractionComponent.FocusTick`（互动提示）也一起停，飞行中不需要。

⚠️ **落地必须还回去**：`ExitFreeze` 里对 CtrlOff 档单独还原 `IsDisabled`（不还 = 落地后玩家永久不能走）。
它不依赖 agent 存活（控制器是 MissionView，与 agent 无关），所以放在归还逻辑最前面。

### 🔴 T1 第一版为什么失败（2026-09-21 实机，必读，别再走一遍）

**做法**：保留 `Controller=Player`，每帧把引擎刚写进去的 `MovementInputVector` / `MovementFlags` 清零。

**反编译依据**（看起来无懈可击，但结论错了）：

```
① OnPreMissionTick → MissionMainAgentController.ControlTick   ← 唯一的写入者
② OnMissionTick                                                ← 我们在这里清零
③ TickAgentsAndTeams → Agent.Tick                              ← 唯一的读取者
```

时序**确实**卡在 ① 之后、③ 之前 —— 但**玩家走路根本不看这两个量**。

**实机证据**（`Debug/StoryEngine_RuntimeLog.txt`）：

| 事实 | 数字 |
|---|---|
| 按着 W | `engineMove=0x0`（**恒为 0**，MovementFlags 全程没被写过） |
| 板速 | 8.95 m/s（与 `vel=9.0` 吻合 ✓） |
| **人速** | **11.2 m/s** —— 比板快 **2.25 m/s**（≈ 步行速度）= 他确实在自己走 |
| 人板距离 | 0.12 → 1.17 → 2.18 持续变大 |

**结论**：`MovementFlags` / `MovementInputVector` 对玩家是**被动镜像**，不是驱动源。
**真开关是 `Controller`** —— 用户在地上实测：切成 AI 后 **WASD 完全无效**（冻结成立）。

**新的怀疑对象**（用户提出，待验）：AI 档会「乱走」，可能不是没冻住，而是
**AI 有自己的一套「脚下平台在动」的自适应机制** —— 板每帧把人挪走，AI 要把 agent
带回它认定的位置，于是自己走回来。对症档 = `aipause` / `aidetach`。

### 🔴 转向接口：用 `SetMovementDirection`，**不是** `LookDirection`

**2026-09-21 用户纠正**：第一版用 `agent.LookDirection = 水平单位向量`，**转不动**（按 WASD 角色不转）。

```csharp

// 本飞行代码同款：

```

| 接口 | 结果 |
|---|---|
| **`Agent.SetMovementDirection(in Vec2)`** | ✅ **现行**。对应 getter = `GetMovementDirection()` |
| `Agent.LookDirection`（Vec3 属性） | ❌ 实测转不动，别用 |
| `Agent.LookDirectionAsAngle`（单浮点） | ❌ 未证实（单位是度还是弧度都不知道），仅作对照 |

> 所以"转不动"是 native 行为，C# 层看不出来 —— **以实测为准，别以反编译为准**。

## 三、动画体系：UE 有什么 / 骑砍能给什么 / 我们怎么做

### 3.1 UE 那边的事实（已导出取证，不是听说）

工程 = `SuperheroFlightAnimations`（**UE 4.26**，180 条飞行动画 + 20+ 混合空间 + 2 个动画蓝图）。

**`A`~`E` 是 5 种风格变体**（UE 里一个 `EFlightType` 枚举切换），不是 5 个方向。

**动画蓝图 `ABP_Player` 的骨架**（逐节点解析见 §附录）：

- **飞行本体只有 3 个状态**：`待机/悬停 →（按冲刺）→ 起飞过渡 → 巡航循环`；**复杂的地方不在状态机，在叠加层**。
- 🔴 **叠加层的"强度"不是变量控制的**：28 个叠加节点的强度**全是常量 1.0**，方向/倾斜的强弱来自
  **叠加层内部的混合空间** —— 把 `倾斜量(−1~1)`、`上下/水平速度分量(−1~1)` **直接当混合空间轴**采姿势。
- **升降那套混合空间是 1 维的，轴名就叫 `Speed`**（−1 = 俯冲姿势 / +1 = 爬升 / 0 = 中性）。
- 两个**引擎无关、可直接抄**的公式：
  - `速度分量 = 本地速度按 −最大速度~+最大速度 归一化到 −1~+1`（超范围钳住）
  - `倾斜量 = 平滑(角速度归一化到 −1~+1)`（平滑速度：左右 5 / 俯仰 15；角速度 = 相邻两帧速度方向转角 ÷ 时间）
- 瞄准用 `LookAt` 节点；闪避/落地走 **Montage**；特效挂时间轴（见 §四）。
- 🔴 **别照抄通知名字**：`AnimNotify_HoverStrat` / `StartFlightTrailVFX` / `StopFlightTrailVFX` 三个在 UE 里
  **图形体是空的**（不产生任何效果）—— 拿效果清单当依据，不拿名字当依据。

### 3.2 骑砍2 引擎能给什么（反编译核实）

| 能力 | 接口 | 有吗 |
|---|---|---|
| 播一条动画 | `SetActionChannel(通道, 动作, ignorePriority, …, blendInPeriod, actionSpeed, startProgress)` | ✅ |
| **交叉淡化** | 上面那个 `blendInPeriod` | ✅ |
| **播放速率** | `actionSpeed` / `SetCurrentActionSpeed` | ✅（"速度感"这个旋钮能真连续） |
| **读播放进度** | `GetCurrentActionProgress(通道)` 返回 0~1 | ✅（**特效时间轴要用它**） |
| 读混合权重 | `GetActionChannelWeight` / `GetActionChannelCurrentActionWeight` | ✅ 只读 |
| **按参数连续混合两个姿势** | — | ❌ **没有**（没有权重 setter） |
| **加法叠加通道** | — | ❌ **没有** |
| 引擎**内部**确实按参数混合 | 原版走/跑就是按速度混的（人形 4 档步态写死在 native）；clip flag `blends_according_to_look_slope` / `synch_with_movement` | ⚠️ **有，但 mod 没有入口** —— 只服务引擎的移动系统；飞行时人被冻住（速度 0），吃不到 |
| 每条 clip 的标记 | `cyclic` / `allow_head_movement`（头随视线）/ `enforce_all` / `affected_by_movement` … | ✅ 编辑器勾，或离线改 |
| 骨骼挂点粒子 | `MBAgentVisuals.CreateParticleSystemAttachedToBone` | ✅ |

### 3.3 结论：我们怎么做

| # | 决定 | 理由 |
|---|---|---|
| A | **每个姿态极端 = 一条已有动画 = 一个动作；极端之间用引擎自带的交叉淡化**（`blendInPeriod`） | 🔴 **2026-09-22 用户裁定**："我不需要你自己插值档位 —— ue 的动画有哪些已有资源代表哪些极端的情形，先用上，再端到端之间用原版自动过渡。" **不自造**驱动公式 / 档位 / 迟滞 / 骨骼合成 |
| B | **连"实时速度混合"也不自己造**：阶梯（悬停/巡航/冲刺）本身就够 —— 我们的速度只有两个值 | 飞行是**定速**（巡航 9 / 冲刺 26），没有中间速度可混；引擎也没权重接口 |
| C | 风格变体 `A~E`：**随机化**（每次起飞抽一种，俯冲结束/冲刺回巡航时可重抽） | 用户裁定；成本全在导入侧（见 §3.4） |
| D | 头随视线 = 用引擎自带 `allow_head_movement` 标记 | UE 那边是 `LookAt` 节点；引擎有开关，不用自己写 IK |
| E | **闪避（`Dodge_*` 20 条）先当"四方向位移的极端姿态"接进来**；要不要变成玩法（无敌帧/位移）另说 | 它们是**普通动画**（可直接播），正好代表四个方向 —— 见 §3.5 |
| F | UE 的**空壳通知不要抄** | 见 §3.1 最后一条 |
| G | 🔴 **不做烘焙**（本轮）：`_Add` / `Lean_*` / `Pose_*` 那些增量动画**先原样导 1~2 条实机看** —— 能用就用，不能用再说 | 用户裁定；"先不烘焙"是硬约束 |

### 3.5 姿态的"极端情形"对照表 —— 只用已有动画 + 原版过渡（2026-09-22 用户裁定）

> 🔴 **口径（用户原话）**："ue 的动画有哪些已有资源代表哪些极端的情形，先用上，再端到端之间用原版自动过渡。"
> ⇒ **不做**：自造的驱动公式 / 量化档位 / 迟滞 / 提前量 / 运行时骨骼合成 / 烘焙。
> ⇒ **只做**：一个极端 = 一条已有动画 = 一个动作名；**极端之间就是 `blendInPeriod` 交叉淡化**（引擎自带）。

**飞行的姿态空间 = 这些极端**（"已有没已有"是关键列）：

| 极端 | 已有可直用的动画（非增量） | 只有增量的 | 现状 |
|---|---|---|---|
| 悬停静止 | `Idle_A..E`（5） | — | 只接了 A |

| 起飞 | `Hover_Start_A..E`（5） | — | 只接了 A |
| 撞击落地 | `SuperheroLanding_A..E`（5） | — | 只接了 A |

| 抬头（爬升） | ✗ | `FM_*_Pose_U`（增量，参照 `FastMove`） | 没接 |
| 低头（俯冲） | ✗ | `FM_*_Pose_D`（同上） | 没接 |
| 左右压弯（banking） | ✗ | `FM_*_Lean_L/R`、`HoverLean_*_L/R_Add`（增量） | 没接 |

**由此得到的做法**（不发明任何东西）：

1. **能直用的都接上**：变体 A~E（见 §3.4 阶梯）+ **`FastMove_Start`（冲刺入姿）** + **`Dodge_*` 20 条**（四方向位移）。
2. **只有增量的那三类**（爬升 / 俯冲 / 压弯）：**先拿 1~2 条原样导进来看**——
   🔴 这是**唯一还没确定的事**：它们是 2 帧的**定格**动画，UE 里是"相对参照姿势的增量"；
   导进来当普通动画播，**看起来到底能不能用**（是"像那么回事"，还是"散架"）**只能实机看**。
   ⇒ **建议先导 `FM_A_Pose_U` + `FM_A_Lean_L` 两条试**（2 次导入，代价极小）：
   - 能用 ⇒ 这三类**零烘焙**直接接上（正好对用户"先不烘焙"的裁定）；
   - 不能用 ⇒ 再谈烘焙（那时是唯一的路），或者先不做这三类姿态。

### 3.6 动画状态机（**注册制**，2026-09-22 用户裁定后重构）

**为什么**：以前"什么时候播哪条动画"是散在 `TickTakeoff` / `TickAirborne` / `TickLanding` 三处的 if/else；
用户裁定要做成**通用件 + 注册制**（以后别的运动系统也要用），形制参照项目里的 `AtomicAction`。

**两级结构（读代码先认这两级）**：

| 级 | 管什么 | 在哪 |
|---|---|---|
| **① 相位** `Phase` | **物理与流程**（Grounded / Takeoff / Airborne / Landing） | `Flight/PlayerFlightBehavior.cs` 的四个 `TickXxx` |
| **② 动画状态机** | **播哪条动画**（状态表 + 转移表） | 定义在 `Flight/FlightAnimMachine.cs`，运行时引擎在 `Animation/AgentAnimStateMachine.cs` |

**"注册制"落在哪**：

```
Animation/                                 ← 通用件（以后任何运动系统都能用）
├─ AnimMachineRegistry.cs   定义类型（AnimState / AnimEdgeDef / AnimMachineDef / AnimContext）+ 注册表
│                             · AnimState.Loop(name, action)                  ← 循环状态
│                             · AnimState.Once(name, action, next, duration)  ← 一次性，播完自动去 next
│                             · def.Edge(from, to, ctx => 条件, blend)        ← 边：按**书写顺序**求值 = 优先级
│                             · AnimMachineRegistry.Register(def) / Create(name, ctx)
└─ AgentAnimStateMachine.cs 运行时：每帧 Tick(agent, dt) 按表流转；内建**防被引擎抢通道**、
                            未接状态自动跳过、Hold（相位自己掌控动画）+ Force（强制进状态）

Flight/FlightAnimMachine.cs               ← 飞行这份**定义**（唯一事实源）
    7 个状态 + 5 条边，一屏读完；Register() 由 MySubModule.OnSubModuleLoad 调一次
```

**加东西的代价（这就是重构的目的）**：

| 要做的事 | 改哪 |
|---|---|
| 改一条姿态规则 | `FlightAnimMachine.cs` 一行 |
| 加一个新姿态 | ① 定义里加一行状态 ② 需要的话加一行边 ③ 内容包接线 |
| 加一次性动作（冲刺入姿 / 闪避） | 用 `AnimState.Once(..., next:, duration:)`，播完自动接下一状态（结构已支持，只是还没接） |
| **别的运动系统也想要状态机** | 照 `FlightAnimMachine.cs` 写一份定义 + 在 `MySubModule` 加一行 `Register()` |

**行为保持**：重构是**逐字搬**（同样 clip、同样条件顺序、同样过渡时长、同样迟滞），没夹带新玩法。

### 3.7 本轮实机踩坑与教训（2026-09-21/22）

> **这一节是上面那次重构（+ 手感打磨）的代价清单** —— 全部**实机撞出来的**（不是推演）。按症状查，别按时间线读；第 9/10 条是状态机化之后才暴露的，直接关系下一阶段加姿态。

| # | 症状 | 根因 | 修法 / 纪律 |
|---|---|---|---|
| 1 | 起飞时角色朝向**抖一下、脸不在正前方** | 相机播种角**差 90°**（`RotateAboutUp` 的角约定 = `atan2(−x,y)`，旧代码写 `atan2(y,x)`） | 读**引擎相机视线**播种；删掉那个错约定的函数（留着必被复用） |
| 2 | 转镜头时人「啪」地跟过去 | `SetMovementDirection` 立刻生效 | **转向限速** `tune turnrate`（0 = 回旧行为） |
| 3 | 起飞像"**咔**一下卡上木板" | ① 板面其实在脚底**下方 8cm**（手调 0.45 对板面高 0.37）；② 更根本：**`Position` 不是脚底** —— 跳跃中真实碰撞体比它高 **0.43m**（实测） | 生成口径改**碰撞胶囊底面**；加**登板闸**（等人真站住再抬升） |
| 4 | 板会自己动（跟着人飘 / 自动抬升） | 我自作主张加的 | 🔴 **板只按 WASD 动**：删跟随、删自动抬升（用户裁定） |
| 5 | 起飞前多一段"脚踩平面" | 动作淡入吃全局 0.3s（那 0.3s 还是跳跃姿势）＋ 板与动作同帧出现 | 起飞动作**淡入 = 0（秒播）**；**板延迟 0.2s** 出现（两拍错开） |
| 6 | 落地"没有落地动作" / 落完还被定住 2 秒 | 收摊与动画抢帧 | **两种落地**（轻放不播 / 硬着陆播）＋**两段式**（先落地拆板、再演动画） |
| 7 | 落地瞬间镜头"甩回起飞方向" | 引擎相机在接管期间**冻结**（`CheckForUpdateCamera` 早退） | 撒手前**把当前朝向写回引擎**；可见参数按**接管时记录值**渐变回去 |
| 8 | 撞墙后人从板上掉下来 → **人被冻在地上走不动、板还在天上** | 板是逐帧 `SetFrame` **瞬移、会穿墙**，人却被墙挡住 | **离板判定**（三维距离 > 1.2m）⇒ 强制收摊（拆板/还相机/解冻） |
| 9 | 🔴 **按 Shift 冲刺看着像"前倾的巡航"** | 转移表求值写成"跳过自己那条**继续往下找**" ⇒ `boost↔cruise` **每 5ms 互踢**，动画永远停在淡化开头（实测日志 100+ 次/秒） | **命中即定**（优先级阶梯语义：第一条成立的边定输赢，"去你已在的地方"= 留原地收手）＋ **抖动自检**（1 秒 >10 次就报警） |
| 10 | 🔴 起飞瞬间 **NRE 崩** | 重构时 `Force` 把 agent 传了 `null`，而**起飞发生在首次 Tick 之前**（`TickGrounded`→`BeginTakeoff`） | `Force(agent, …)` **agent 必填**；机器记住 agent 兜底；真没有 = 不接管（不崩） |
| 11 | 起飞后 **2.9 秒**机身不跟镜头 | "无输入不写朝向"（N3，为的是悬停时绕看各面）**在起飞这一刻是错的** | 起飞那一刻**补写一次**朝向；之后仍按 N3 |

**两条方法论级别的教训**：

1. 🔴 **日志是这类 bug 的唯一出路**。第 9 条（每 5ms 互踢）靠肉眼看只会得出"动画资产有问题"的错误结论；
   是 `[Anim:flight]` 那行切换日志一眼看穿的。**所以每加一层新机制，先给它配一行切换日志。**
2. 🔴 **重构完必须实机走一遍冒烟，不能只跑编译**。第 10 条（NRE）编译期查不出、一进游戏第一步就炸 ——
   正好落在"编译过 ≈ 没问题"的盲区里。**顺序上：先让用户验完旧结构，再动手重构。**

**顺带测出来的两条"资产事实"**（下一轮扩充姿态要用，见 §3.5）：

- **起飞 clip 自带 25° 起手歪斜**：`Hover_Start_A` 首帧相对基线偏 **+24.8°**，**0.33 秒归零**（一闪而过，不是"没朝前"的主因）。
- **趴姿家族的根骨读数 ~90°**（`FastMove_*` / `Dodge_*` 全家族 +90.1，而 `Idle/HoverMove` 基线 65.2）——
  ⚠️ 但**趴姿下这个读数不可靠**（身体前倾 90° 时"yaw"不是朝向），要**实机视觉确认**再决定要不要修。

### 3.8 扩充动画姿态（✅ **已执行 · 2026-09-22 落地并实机可见**）

> 本节记的是**当时的施工清单**，现在已全部做完：冲刺入姿 ✓、四方向闪避 ✓、抬头/低头（两个家族分开）✓、左右压弯 ✓。
> 合成口径与那批坑见 **§3.8.1**；剩下的观感细节见 **§3.10**。下面的清单保留作"当时怎么想的"存档。

**目标**：把手上的动画都用起来 —— 风格变体、冲刺入姿、四方向位移、俯仰/压弯姿态。

### 3.8.1 增量合成的正确口径（2026-09-22 用户看图当场纠正后定案）

**结论**：增量（`Lean_*` / `Pose_*` / `_Add`）**必须合成成一条独立动画才能用**；
而且合成时**根骨那道增量要缩到 0**，否则会"把人整体转 90°"。

| 事 | 口径 |
|---|---|
| **合成公式** | `结果(t) = 基础(t) ∘ (增量 ∘ 参照⁻¹)` —— `trf_compose.py`（TRF→TRF，不回 Blender）。参照缺省 = 基础；这批素材的参照假设已验证（拿"中性"增量合成，与基础差 **0.010°**） |
| 🔴 **根骨** | `--root-scale 0`。这批增量在 **pelvis（骨 #0）上有 85°**（`FM_A_Lean_*` 85°、`FM_A_Pose_*` 85~90°、`HoverMove_*_Add` 5~74°），其它骨最大才 22°。照原样加 = **整个人被转 90°**；去掉后偏差落回**肩 / 臂 / 颈**（~20°，左右对称）= 用户要的"头带着肩膀倾" |
| **为什么会有这道量** | §3.7「趴姿家族根骨读数 ~90°」那条疑点在增量上的投影 —— **本次是它的首次实锤**（此前只是"读数存疑，待实机看"） |
| **A 套已合成 12 条** | 巡航：倾斜 L/R、抬头/低头、前倾/后仰、悬停左/右倾；冲刺：倾斜 L/R、抬头/低头（TRF 已进导入目录，与基准动画同帧号、同循环属性） |

### 3.11 🔴 腿部"硬"的根因定案（2026-09-22 夜 · 追了一整轮后归档）

> **一句话**：**引擎编译动画时会丢掉「相对静止姿势偏移很小」的骨骼轨道。**
> 飞行的趴姿靠**根骨转 90°** 摆出来，**腿自己几乎没动**（大腿只偏 5~10°）⇒ 大腿那条轨道被引擎削掉
> ⇒ 腿跟着骨盆趴着、但**摆动没了** = 观感"很硬"。**不是我们导出/合成的问题，是编译期的代价。**

#### 判据（三条实测，同包、同为 `cyclic`）

| clip | 大腿相对静止姿势的偏移 | 引擎实际渲染 |
|---|---|---|
| `flight_hovermove_a`（巡航） | **38.8 ~ 49.3°** | ✅ **0 帧丢失**（逐帧膝角 31→123→111 全程平滑） |
| `flight_fastmove_a_leanl / leanr`（压弯） | **14.2~20.7° / 2.8~7.5°** | ✅ 腿正常（用户实机） |
| `flight_fastmove_a`（冲刺/趴姿） | **5.3 ~ 10.8°** | ❌ **每圈约 47% 的帧塌回静止姿势**（膝角精确 0.00） |

**⇒ 与 `cyclic`、`Duration`、`Source1/2`、帧数全部无关**（这五个 clip 上它们完全一样）。

#### ⚠️ 顺手挖出的两个**独立**问题（都没修）

1. **`flight_fastmove_a_pitchu` / `_pitchd` 是废的** —— 逐骨偏差量与 `fastmove_a` **完全相同**。
   抬头/低头那对增量的动作**几乎全在根骨上**，而合成口径 `--root-scale 0` 正好摘掉根骨那道
   ⇒ **合成后 = 原封不动的 fastmove**。（`leanl/leanr` 的增量在腿上有真实动作，所以没被吃掉。）
2. **`flight_idle_a` / `hoverstart_a` / `superland_a` / `fastmove_a` 的 `Duration` 少 1 帧**。
   已用 `clipduration --duration auto` 在**产物包**上改过 → **仅供验证，ModKit 下次 Publish 会覆盖**。
   ModKit 输入框只有 2 位小数，**要向上取整**（1.04 / 2.04 / 3.04 / 1.54），四舍五入（1.03）仍然偏短。

#### 两条引擎 API 经验（跨工程通用）

- 🔴 **`Skeleton.GetAnimationParameterAtChannel(0)` 返回「已播秒数」，不是 0~1 归一化进度**（实测能到 1.26）。别当百分比用。

## 一、先回答架构判断（原第 5 问）

> 问题原文：*"飞行过程中需要屏蔽玩家原生控制移动是吧，然后通过木板设置位移，通过其他方式来控制角色动画，是否是这样？"*

**判断：三条全对，只有"屏蔽"的手法要换一个。**

| 判断 | 结论 | 说明 |
|---|---|---|
| 要屏蔽原生移动 | ✅ **对** | 不屏蔽的话，按 W 角色就自己走下木板了 |
| 用木板设位移 | ✅ **对** | 更准确的说法是我们**每帧改木板的坐标**，人跟着走 |
| 用其他方式控制动画 | ✅ **对** | 引擎只会在"走/跑"里挑动画，飞行姿势不在那张表里，必须我们直接指定 |

**屏蔽的手段 —— ✅ 已按"最小侵入"落地（2026-09-21 T1）**：

| 做法 | 用不用 | 说明 |
|---|---|---|
| 每帧把 `MovementInputVector` / `MovementFlags` / `EventControlFlags` 写成 0（保留 `Controller = Player`） | ✅ **本方案采用** | 最小侵入：引擎侧一切不变，只是"替玩家一直松着手"。帧序上必定生效（见交接节 T1 说明） |
| 不冻结，用**小键盘 8/2/4/6** 控制飞行 | ✅ **保留作备用** | 没绑任何游戏移动键 ⇒ 按了只影响板。现为"不冻结也不会误触走路"的隔离对照组 |
| `V.SetPlayerControlFrozen(agent, true)`（切 Controller = **AI**） | ❌ **已否掉** | 🔴 它的语义是"**把 agent 交给引擎 AI 驾驶**"，**不等于"原地不动"** —— 实测表现为角色在木板上走来走去、甚至被挪到离板 **41 米**外。别再用 |

**摄像机 / 朝向照常归玩家**，镜头手感跟平时一样。

> 🔴 **订正一条旧结论**：[Knowledge/骑砍2Agent运动与位置机制.md](../Knowledge/骑砍2Agent运动与位置机制.md) §5 与 §6 表 #2 记着"切控制权会丢镜头、agent 被搬到兜底坐标 `(-100, 10385, 15.06)`"——**那条是错的**。该次实验同时在写位置，变量没分离（文档自己也注了"该观察变量未完全分离"）。**实际表现：切 AI 后角色原地待机，镜头仍在玩家身上。**

### 为什么不用原版的走 / 跑 / 蹲状态机（2026-09-21 裁定）

**问题**：骑砍2 本来就有一套移动状态机（走 / 跑 / 蹲走 / 蹲跑），[自定义移动管线.md](自定义移动管线.md) 第二部分也确立了"换 action set = 换整套走跑外观"这条零代码的路。飞行为什么不走它？

**两条硬边界**：

| # | 边界 | 事实 |
|---|---|---|
| 1 | **只有 4 个模式，且全是水平** | `walking` / `running` / `crouch_walking` / `crouch_running` 名字写死在 native 里，数据层加不了第 5 个。**表达不了"抬头爬升、低头俯冲"** |
| 2 | **移动集运行时换不了** | 移动集挂在**物品用法**上（`item_usage_sets.xml` 的 `<movement_set id="..."/>`），物品用法来自**身上的武器**。反编译 `AnimationSystemData` 核实过：里面只有 `ActionSet` 和一个 monster usage 索引，**没有物品用法** —— C# 只能切 action set（动作名→clip 的映射），切不了移动集 |

**裁定**：**走纯代码路线** —— 封住原生移动，木板自己飞，动画由我们直接指定。

**理由**：本作要的是"像超人一样飞"，**方向跟镜头含俯仰**是核心体验；引擎那 4 个水平模式从根上表达不了它。与其把飞行硬塞进走路模型再打补丁，不如整体接管。代价是**过渡与混合要自己写**（几十行，用 `blendInPeriod` 做交叉淡化，见 §三）。

**保留的后路**：将来若要做"铁炮走路也换外观"那类需求，[自定义移动管线.md](自定义移动管线.md) 第二部分那条路仍然成立，与本方案不冲突。

> `A_FM_A_Pose_U` 是直立、`A_FM_A_Pose_D` 是**头朝下垂直**。

#### 🔴 `Lean_*` **不是**俯仰姿态，是另一整套体系（2026-09-21 用户纠正，本轮不导）

**曾经写错的说法**：「`Lean_U` 是爬升备选、`Lean_D` 是俯冲备选」—— **错的**，已作废。

**事实**（TRF 源目录实测，`D:\BrainMaker\骑砍2动画重定向\output	rf\`）：

```
fly_A_FM_A_Lean_{L,R,U,D}.trf     ← A 套的 4 个方向
fly_A_FM_B_Lean_{L,R,U,D}.trf     ← B 套
fly_A_FM_C_Lean_{L,R,U,D}.trf     ← C 套
fly_A_FM_D_Lean_{L,R,U,D}.trf     ← D 套
```

**`Lean` = 转向/倾斜体系**（L 左倾 / R 右倾 / U / D），**不是"抬头/低头姿态"**。
从这套里抠 `_U` / `_D` 两块当竖直姿态用 = **类别错了**。

**归属**：它服务的是本方案开头写的「**倾斜叠加**」—— 那是**下一轮**的功能（飞起来转向时身体跟着压弯）。
**本轮的处理**：**一条都不导**。等做「倾斜」时**成套**导（先设计要用哪几个变体，别零敲碎打）。

`AssetSources\animations\flight_lean_reserved\`（附 README 说明），

### 两条节奏规则

**动画切换**：**状态变了才调一次** `SetActionChannel(0, 动作名, ignorePriority: true, blendInPeriod: 0.2)`；**每帧重复调会把动画卡在第 0 帧**。靠 `blendInPeriod` 做交叉淡化 —— 这就是骑砍2 里能做到的"混合空间"。
> 但 0 号通道引擎的 locomotion 系统也有权写，所以**每 0.5 秒核对一次**有没有被抢回去，抢走了才重设（`ActionRecheckSeconds`）。

**朝向**：机身水平朝向 = 镜头的水平朝向（每帧写 `Agent.LookDirection`）；**俯仰由动画表现**。

## 五、三个必须提前知道的事

### 1. 🔴 现有那 130 条飞行 TRF 有已知缺陷，必须重跑

`output/trf/` 下所有 TRF 都是**旧版管线**产出的。旧版把"骨盆位置"按**绝对值**写进文件，而引擎读的是**增量** —— 症状是人整体被抬高。

**证据**：实测 `fly_A_Flight_Idle_A.trf` 的位置轨恒为 `0.020170 0.914520`（正常应是 ≈ 0）。而管线脚本 `pipeline/common/fbx_to_trf.py` 的修正时间是 **09-20 16:06**，这 130 条 TRF 的产出时间是 **09-20 15:25** —— 用的是有缺陷的旧版。

**修法**：重跑，并且**用 `--pelvis none`**：

```bash
cd /d D:\BrainMaker\骑砍2动画重定向
python pipeline/run_retarget.py --rig ue_mannequin \
  --clip A_Flight_HoverMove_A --name fly_A_Flight_HoverMove_A \
  --pelvis none --animdir input/source/ue_mannequin/clips_flight
```

**为什么是 `none`**：飞行动画必须**原地做**（位移由木板负责）。`--pelvis none` 的语义就是"不写位移轨"，正好 —— 而且它顺带**绕开了上面那个绝对值的坑**（不写就不会写错）。

**判据**：跑完看 `CHECK_POS` 一行，位置轨首帧应 ≈ 0。

> 管线**没有批量入口**，一条一条跑（9 条命令）。

### 2. 🔴 导入顺序不能反：先导入 → 读出真名 → 再写 XML

`animation=` 要填的是 **ModKit 给 clip 起的名字**，不是你给 TRF 起的名字，也不是 FBX 名字。

> 🔴🔴 **第 9 步不能提前做**（2026-09-21 实机崩过）：预制体里写着 `<meta_mesh_component name="lwn_flight_sigil"/>`，
> 而那个网格**还没进任何包**时就去 `GameEntity.Instantiate` = **native 访问违例，游戏当场崩**，
> `try/catch` 拦不住（AV 属"损坏状态异常"，.NET 默认不允许捕获）。
> ⇒ 预制体现在**暂存在 AssetSources 里**，等网格进包了再放回去。
> 代码侧也加了双保险：实例化之前先用 `MetaMesh.GetCopy(name, false, mayReturnNull:true)` 探网格在不在，不在就跳过。
> （已登记为坑点清单 **雷 149**）

> 🔴 **材质必须是【加法 / 自发光】档**，不能是不透明档 —— 贴图是**黑底 RGB**（无 alpha，因为本工程贴图管线只吃 8-bit RGB）。
> 黑底 + 加法 = 黑的地方加零 = 视觉上等于透明，亮的地方自己发光。**建成不透明档就会看到一块黑方块。**
> 想改成"透明底 + alpha 混合"也行，但那要另做一张带 alpha 的贴图并确认编辑器接受——**加法档更省事且观感更好**。
