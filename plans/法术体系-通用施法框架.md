### C. 三条"在游戏里看到它"的路径（从快到慢）

1. **控制台直放（不用任何装备，最快）** —— 进任意战场，敲：
   ```
   custom.spell cast projectile_yinmo_zhan
   ```
   从你的眼睛沿视线直接放一发。六条 id 见 §B 表；`custom.spell list` 列全部；
   全套调试命令 = `list / cast / npc / give / power / scale / hit / core / lead / hand / tilt / verbose / cap / probe`。
2. **自己装备**（走完整流程）—— 用控制台给物品，⚠️ **要敲显示名不是 StringId**（法印显示名 = `SpellSeal`，法术弹 = `SpellCrescent` 等，见附录 A.3 的两条坑）→ 装备法印 + 在**弹药槽**装法术弹 → 按 **X** 蓄力 → 松手放。
3. **看 NPC 放** —— `custom.spell npc`（让最近的人朝你放一发）或 `custom.spell give`（给最近的 NPC 装一套，它自己会打）。
4. **看冰冻**（2026-10-07 新）—— 进任意场景，站到一个兵面前敲：
   ```
   custom.ice on
   ```
   他会被**定格 + 全身换成冰**（甲 / 头盔 / 手脚 / 武器；脸除外）。`custom.ice list` 点名册，`custom.ice off` 全还原。
   细节与未验项见 **§25.9**。

### A4. 🔴 结案：施法动作在"通道 1（上身）"上不播 —— 根因 = **导入的 clip 缺元数据**（2026-09-24）

**一句话**：骑砍的两条动画通道里，**通道 1 会挑 clip 的元数据**；我们从 TRF 导入的 clip 那几项是空的/0，
于是"收下了、时长也读得到、就是不播"（零报错）。**照原版把四项填上就通了** —— 实机已验证（播了）。

**四项对照（原版参照 = 原版自己用通道 1 播的 `act_command_unarmed` → clip `anim_command_unarmed`）**：

| 字段（ModKit 的 Animation clip 面板） | 原版 | 我们的（导入后） | 修后 |
|---|---|---|---|
| **Priority** | 2.000 | **0.000** | 2.000 |
| **Right hand pose** | 4.000 | **3.000** | 4.000 |
| **Blend out period** | 0.500 | **0.000** | 0.500 |
| **Flags → `allow_head_movement`** | 勾 | **没勾**（`magic_idle` 只有 `cyclic`） | 勾 |
| （Left hand pose / Blend in period / Continue to action / Loading Type / Param1~3 本来就一致） | 3 / 0.3 / 空 / Always keep in memory / 0 | 同 | 同 |

**修法（编辑器里 4 步，一次一个 clip）**：打开 clip → Priority=2 · Right hand pose=4 · Blend out period=0.5 · Flags 勾 `allow_head_movement` → Publish →
产物改名拷进 `LivingWorldNpcs/AssetPackages/lwn_core.tpac`（见 §B 同款流程）。
⚠️ **蓄力那条要保留 `cyclic` 勾**（循环靠它）；`allow_head_movement` 对我们是加分项（配合"头看相机"那套，见 §A2）。

**两条我自己判断错的（记下来别再犯）**：
1. ❌ "带 `cyclic` 的 clip 会被通道 1 拒绝" —— **证伪**：`act_magic_projectile` 一个 flag 都没勾，一样不播。
2. ❌ "别传 `anf_enforce_lowerbody`（那是扩大覆盖面，与只改上身相反）" —— 那是**望文生义的猜测**，未经实测；正好相反的可能性同样成立（见下）。

**"只动上半身"还没做到**（现状与下一步见 **§A5**）：

| 事实 | 说明 |
|---|---|
| 🔴 **引擎没有"每骨权重/遮罩"接口** | `Agent` 上只有**只读**的 `GetActionChannelWeight`（整条通道，非每骨）；**没有 `SetActionChannelWeight`**；`SetActionChannel` 的参数里没有任何骨骼/权重项；`AnimFlags` 里那两个 `anf_animation_layer_flags_*` 是**无人消费的死常量**（全库检索过）。⇒ UE 的 `Layered Blend Per Bone` **在这引擎里不存在**，粒度只有"通道 0 全身 / 通道 1 上身"两档 |
| 唯一没试的旋钮 = 两个 flag | `custom.anim_ch 1 act_magic_idle lowerbody` / `all`（通道 1 现在能播了，**这两个开关位值得当场试**）|
| 还没搞清的一条 | 原版 clip 放通道 1 时**腿也跟着动了**（本该只有上身）⇒ 说明"通道 1 = 上身"不是无条件的：要么 flag 管，要么**clip 里含哪些骨就驱动哪些骨**（下层不接管缺失的骨）|
| 兜底方案（可靠） | **离线烘"只含上半身"的 clip**：把腿/骨盆的轨道剔掉（或让它们等于飞行基准），通道 1 播它时腿自然归通道 0 管。工具 = `tools/anim-retarget`（飞行那 20 条就是这么增量合成的），加一步"剔骨"是机械活 |

### A5. 🔴 施法手势「只动上半身」—— 交接（2026-09-24 收盘）

> ✅ **本节已被 §A5′ 取代**（2026-09-25 结案：`enforce_lowerbody` 写进资源包 ⇒ 实机验证分离）。
> 下面这段保留作**历史记录**——里面的判断（"通道 1 会把通道 0 挤掉"、"守通道 0"）**已被证伪**，别照着做。

**现状三句话**
1. 手势动画**能播了**（根因 = clip 元数据，见 §A4），当前播在**通道 1（上身层）**。
2. **但腿跟着动**：通道 0 / 通道 1 都试过，`affected_by_movement` / `lowerbody` / `all` 等 flag 也试过，**腿都保不住**。

### A5′. 🔴 机制查明 + 前一版测试无效（2026-09-24 晚）

**① 机制（写在官方 flag 文档里，不是猜）** —— 上下身分离是**引擎默认**，靠两条 flag 反向控制：

| flag | 官方原文 | 含义 |
|---|---|---|
| `enforce_lowerbody` | *Prevents previous channel and movement animations to be played during this animation* | 不带它 ⇒ **下半身继续由「上一个通道 + 移动动画」驱动**，只有上身归当前动作 |
| `enforce_all` | *Valid for channel 0 only. Prevents channel 1 and movement animations…* | 通道 0 的"我全占"开关 |

👉 **挥刀那几条 clip 都不带 `enforce_lowerbody`**（实测：`quick_release_slashright_1h` = `client_prediction` + `enforce_root_rotation`）
—— 这正是"边走边挥刀、腿照走"的机制：**刀只在通道/上身层，腿归移动动画**。
"移动动画"是一整套独立子系统：`movement_sets.xml`（每方向一套走/跑 + `*_adder` 叠加件）+ `full_movement_sets.xml`，由速度驱动。

`ItemUsage` 类型在 C# 侧根本不存在 ⇒ 攻击动画由 native 自己选通道（社区文档说是通道 1："channel 1 is for combat anims"）。

**③ 🔴 前一版测试（`custom.anim_ch 1 …` 看到"腿也变了"）证明不了任何事** —— 找到原因：

### B. 粒子为什么进不来 —— **根因已查明**（2026-09-24），**当天已解决**

**结论**：引擎**运行期**的粒子表来自 **AssetPackages 里的 `Particle` 资产**（编译产物）。

## 一、结论（先说做什么）

| # | 决定 | 理由 |
|---|---|---|
| 1 | **法术 = 四段拼装**：起手 / 瞄准 / 投送 / 结算 | DOS2 的 15 个形态不是 15 套系统，是这四段的组合；虚幻引擎里「投射物」也是同一个切法（Actor + 移动组件 + 碰撞 + 命中后效果） |
| 2 | **阶段 1 只做「投射物」一种投送方式** | 一阶段只做投射型法术 |
| 3 | **投射物不走引擎导弹，自管实体**（自己造、自己推、自己判命中） | 承接 2026-09-23 裁定：引擎导弹的渲染约 **110 米必定剔除网格**（证据链见法印计划 §16.2，七次实机实验） |
| 4 | **起手用「法印 = 远程武器」当脚手架**（抬起 → 瞄准 → 释放），🔴 **明确标为临时壳** | 引擎白送瞄准姿势、准星、弹药消耗、开火音效 —— 阶段 1 最快见效果的路径。**但自建投射物之后它不再必需**：阶段 3 换成我们自己的相位机（§5.1），换的时候投射物那一层一行不用改 |
| 5 | 🔴 **引擎那颗导弹要拦掉** —— 用 Harmony 前缀拦住 `Mission.OnAgentShootMissile`，改发我们的实体 | 不拦 = 有一颗**看不见的弩矢**同时飞出去，会撞到人、触发格挡与受击反应 = 出戏 |
| 6 | **伤害仍走引擎全管线** —— 复用现成轮子 `AgentDamageHelper.CastBlow` | 护甲、减伤、死亡判定都在 `RegisterBlow` 后面，白送；不用自己写伤害模型 |
| 7 | **法术数据放内容包** `ModuleData/AssetRegistry/Spells.xml`，格式照 `FirearmFx.xml` | 三单元架构（逻辑进 LWN、数据进内容包）；`AssetRegistry/` 是既有目录，不新开目录 |
| 8 | **阴魔斩 = 阶段 1 的验收件**，不新增法术 | 网格 / 贴图 / 材质 / 粒子四样都已做好，只差接线（见 §七） |
| 9 | 🔴 **三个接口的"契约"现在就写对**（见 §3.2）：瞄准产出**一张表**、投送**有生命周期**、结算**只认单次命中** | 龙之信条的多目标火球、艾尔登法环的彗星亚兹勒都卡在这三条上。**现在写对是免费的；阶段 2 才发现就是三轴同时返工** |
| 10 | **四段之上再加一层「法术族预设」**（见 §2.4）：常用组合固化成族，配表时选族填块 | UE 的 FlexibleCombatSystem 用 14 个族落地了整套法术系统 —— 证明这样配表最省、最不容易填错。**底层仍是可组合的四段**，所以比它灵活 |

**不做什么（本计划边界）**：不做地面瞄准圈 UI（**投射族不需要；等做放置族时它是必备件、不是打磨项**，见 §3.6）；不做技能槽与冷却（UE 那套里冷却属"组件级"，也不挂在法术行上）；不做 NPC 施法者（但核心函数从第一天就写成"不关心施法者是谁"，见 §十）。

**"以后要加"的，本阶段只负责把位置留对**：追踪、多发、软锁、落点、持续光束 —— 这些**不在阶段 1 实现**，但它们的接口契约在 §3.2 一次定死，阶段 2/3 只填实现、不动已写的代码。

**代价（一次说清）**：旧路线（把法术伪装成弹药）引擎包办了飞行、碰撞、插地、寿命 —— 代价是**全都不可调**（寿命写死、半径只有两档、朝向算不了），而且 110 米外直接隐形。换成自管之后，这些**全部由我们写**（约 250 行），换来的是**全部可调**。这是本计划唯一真正的取舍：**用一次性代码量，换全部参数的控制权**。

## 二、总模型：一个法术 = 四段拼装

### 2.1 四段（每段回答一个问题）

| 段 | 代码里的轴 | 回答的问题 | 大白话 | 阶段 1 实现 | 以后可加 |
|---|---|---|---|---|---|
| **起手** | Trigger | 谁、什么时候、什么姿势放出去 | 抬手结印 → 蓄力 → 推出 | 法印（远程武器的引擎流程） | **三种施法方式**（有前摇 / 按住持续 / 瞬发）、蓄力档位、被打断、输入缓冲、NPC 起手 |
| **瞄准** | Targeting | 法术往哪去 | 看哪打哪 / 锁谁打谁 / 点地打地 / 以自己为心 | **准星直视**（方向施法） | 软锁（可锁 N 个目标）、落点、自身为心 |
| **投送** | Delivery | 从施法者到落点之间怎么过去 | 直线飞 / 抛出去 / 追着跑 / 从天而降 / 一直照 | **直线飞行**（自管实体） | 追踪（一个参数）、多发、天降、持续光束、瞬时射线、位移 |
| **结算** | Payload | 到了之后发生什么 | 单体掉血 / 一片掉血 / 中毒减速 / 地上留火 / 召唤 | **单体伤害 + 半径伤害** | 状态、地面持续区域、光环、连锁传导、召唤 |

**为什么这么切**：DOS2 做 15 个形态用的是同一批字段的排列组合（`AreaRadius` / `Angle` / `Range` / `StrikeCount` / `Template`…），不是 15 套代码；虚幻引擎的投射物同样是「移动组件（怎么飞）+ 碰撞组件（撞到什么）+ 命中后的效果（撞了干什么）」的组合。按这个切法，**新形态 = 在某一轴加一个插件**，其余三轴原地不动。

### 2.3 四段各自的"参数长什么样"

| 轴 | 参数（都写在数据里，不写死在代码里） |
|---|---|
| 起手 | 用哪把法印、要几档蓄力（阶段 3） |
| 瞄准 | 准星 / 软锁（锁定的最大角度、锁定距离、**最多锁几个**）、落点（最远距离） |
| 投送 | 初速、重力（0 = 平飞）、最大飞行距离、最长存活时间、是否贴地滑行、命中半径、可穿透几个目标、**转向速率（>0 就是追踪弹）**、**发数（一发变 N 发）**、飞行朝向的倾斜角 |
| 结算 | 伤害值、伤害类型、作用半径、边缘衰减、**重复间隔**（持续型用）、是否给状态 |

### 2.4 四段之上：法术族预设（给配表用，不给代码用）

底层四段是**可自由组合**的；但配表时**不该让每一行都填八个轴字段** —— 把常用组合固化成"族"，一行选一个族、只填该族的块。

| 族 | 四段组合 | 该族专属参数 |
|---|---|---|
| **投射** | 准星或软锁 → 直线飞 / 抛物 / 追踪 → 命中结算 | 速度、重力、转向速率、发数、命中半径、可穿透数 |
| **引导** | 起手按住 → 持续存在 → 按间隔重复结算 | 引导粒子、转向 |
| **天降** | 落点 → 从上方落下 ×N → 范围结算 | 发数、散布、起落高度 |
| **放置 / 区域** | 落点 → 持续存在 → 按间隔重复 + 半径 | 半径、**重复间隔**、**持续时长** |
| **移动** | 落点 → 自己走 + 漂移 → 沿途结算 | 移动速度、漂移半径 |
| **符文** | 落点 → 留在世界上 → 踩中触发结算 | 触发半径、存不存档 |
| **增益** | 自身或软锁 → 瞬时 → 给状态 | 加什么属性、数值、时长 |
| **治疗** | 自身或软锁 → 瞬时或持续 → 回血 | 回血量、是否持续 |
| **召唤** | 落点 → 瞬时 → 生成实体或武器 | 生成什么、持续多久 |
| **变形** | 软锁 → 瞬时 → 换模型换属性 | 换成什么、时长 |
| **传送** | 落点或软锁 → 位移 → 落点效果 | 位移方式 |

🔴 **命名规约（抄 UE 那套）：族名当法术 id 的前缀** —— `projectile_yinmo` / `place_firepit`。
配表时一眼看出是什么族，也防止把 A 族的字段填进 B 族。

🔴 **我们的族比它粗**：它 13 个族各写一个类，其中「区域·一次性」和「区域·按间隔」是两个族（`PlaceDmg-*` / `PlaceTick-*`）；我们是**一个"放置"族 + 一个重复间隔参数**。因为它必须一个族一个类，我们的族只是预设。

**这条是从 UE 那套系统抄来的**（[FlexibleCombatSystem 分析](../Knowledge/FlexibleCombatSystem施法设计_UE实现分析.md) §二）：它用 13 个族落地了整套法术系统（60+ 个法术），配表一行选一个族、只填该族那一块。

🔴 **我们比它多一条**：它的族是**互斥单选**（一行只能填一个族块），我们的族只是**预设**，底层四段仍然可组合。所以它得写两个类来表达「区域·一次性」和「区域·按间隔」，而我们只是**一个"重复间隔"参数**。

## 三、三套外部设计的对照（龙之信条 · 艾尔登法环 · UE 实装工程）

### 3.1 结论先给

| 例子 | 当前四段框架兼容吗 | 要补什么 |
|---|---|---|
| 龙之信条 **多目标火球**（六连 / 十连，每发追一个目标） | ✅ 模型兼容 | 投送轴加「**多发 + 追踪**」两个参数；瞄准轴的产出必须是**一张表 + 目标引用**（§3.2 契约 1） |
| 龙之信条 **选定目标的雷电术**（软锁 → 天雷落到目标头上） | ✅ 模型兼容 | 瞄准轴加「软锁」；投送轴加「天降」。**阶段 2 本来就排了软锁** |
| 艾尔登法环 **彗星亚兹勒**（按住持续喷射的光束） | ⚠️ 模型兼容，但**三条契约要现在写对** | 不需要加第五段；要 §3.2 的三条契约 + 阶段 3 的"施法中"状态机（§3.5） |
| （顺带核对）陨石群 / 火墙 / 雷电领域 / 龙卷风 · 星雨 / 岩石弹 / 白金之雨 / 海马炮 / 夜雾 | ✅ 兼容 | 全是已有四段的参数组合，逐条见 §3.4 |

**一句话**：**四段模型本身一行不用改** —— 没有一个例子需要在轴上增加"第五段"。真正要改的是**三个接口的契约**（§3.2），而这三条**只有现在改才便宜**。

### 3.2 🔴 必须现在写对的三条契约

| # | 契约 | 写错了会怎样 | 现在怎么写 |
|---|---|---|---|
| **1** | **瞄准的产出 = 一张"施法意图"表，不是"一个方向"** | 做多目标火球时才发现瞄准接口只能产出一个方向 → **瞄准 / 投送 / 结算三处一起返工** | 产出 `List<SpellCastIntent>`，每条 = 起点 + 方向 + **可选的目标引用** + 序号。**阶段 1 恒为 1 条**，但接口形状按表写 |
| **2** | **投送 = 一个有生命周期的对象（进入 / 每帧 / 结束），不是"造一个飞出去的实体"** | 做持续光束时才发现"根本没有结束这一拍" → 投送接口返工 | 三拍接口：`Begin(意图)` / `Tick(dt)`（返回 false = 结束）/ `End()`。直线飞行只是其中一种实现 |
| **3** | **结算只认"收到一次命中"；"多久上报一次"归投送管** | 光束每帧都上报 → 每帧结算一次伤害 = **秒杀**；要改就得动结算接口 × 全部已写好的法术 | 投送负责节流（同一个目标最快每 X 秒上报一次），结算永远保持"来一次算一次" |

**第 1 条里"可选的目标引用"是关键**：软锁雷电要"雷落到**目标现在所在的位置**"，而不是"施法那一刻目标在的位置"。有了目标引用，投送和结算可以在**落地那一瞬间**重新取目标位置。

### 3.3 追踪弹的结论要反过来（旧计划的相反结论作废）

旧计划写的是「**追踪弹是陷阱，不做**」—— 那是**旧路线**的结论：那时飞行交给引擎，而引擎导弹没有追踪能力，自己做追踪等于放弃引擎的碰撞 / 伤害 / 插地。

**换成自管实体之后这条结论失效了**：飞行物本来就是我们在每帧推，**追踪 = 每帧把速度方向朝目标转一点（限速转弯），不到十行**，而且完全不影响命中判定与伤害管线。

所以：**「追踪」从"不做"升级为投送轴的一个参数**（转向速率 = 0 就是直线飞）。它是多目标火球与星雨的前提。

### 3.5 持续型法术（彗星亚兹勒）单独说清楚

它和阶段 1 的投射物**根本差别不在视觉，在三件事**：

| # | 差别 | 投射物（阶段 1） | 持续光束 |
|---|---|---|---|
| 1 | **起手** | 松手那一瞬间放出去，完事 | **按住期间一直在放**；松手 / 被打断 / 没资源才结束 |
| 2 | **投送** | 造一个实体飞出去，撞到就没了 | 没有"飞出去"这回事，**是一条一直在那儿的线** |
| 3 | **结算** | 撞到谁算谁一次 | **每帧都照到人，但只能隔一段时间结算一次**（否则每帧一次伤害 = 秒杀） |

**它需要的那台状态机，正好和阶段 3 的蓄力是同一台**：

- **蓄力** = 按住 → 档位往上走 → 松手发一发
- **引导** = 按住 → 一直在放 → 松手就停

两者都在读「按键是否按住 + 施法动作播到哪了」，**区别只在松手时是"发"还是"停"**。所以阶段 3 做蓄力的时候，顺手就把持续型的地基打了一半 —— 这也是把两者放进同一个阶段的原因。

**结论**：彗星亚兹勒**不需要改四段模型**。它要的是 ① §3.2 的三条契约现在写对 ② 阶段 3 的"施法中"状态机 ③ 投送轴补一个"持续"实现 + 结算轴补一个"地面区域 / 光环"实现。

### 4.2 一次施法的完整时序

```
释放（法印开火）
 ① 拦下引擎导弹          SpellSealFirePatch 前缀：认出手持武器是法印 → 不发导弹
 ② 定位                 瞄准轴：产出"施法意图表"（阶段 1 恒 1 条：准星方向 + 引擎给的出膛点）
 ③ 投送进入             取网格副本 → 造实体 → 挂上 → 缩放到目标尺寸 → 按飞行方向定向 → 挂拖尾粒子
 ④ 记账                 交给 SpellProjectileLogic，进"在飞"列表
每帧
 ⑤ 投送推进             位置 += 速度 × dt → SetGlobalFrame
 ⑥ 命中检查（每 0.05 秒一次，全部走引擎原生查询，见 §4.3）
       ├ 打到谁：`Mission.RayCastForClosestAgent(上一帧位置, 这一帧位置, …排除施法者, 命中半径)`
       └ 打到墙/地：`Scene.RayCastForClosestEntityOrTerrain(同一线段, …)`
       两条各给一个距离 → 取近的那个 = 这一步真正撞到的东西
命中
 ⑦ 结算                 单体伤害（复用 AgentDamageHelper.CastBlow）+ 半径伤害 + 命中爆散粒子

 ⑨ 回收                 飞满「最大飞行距离」或活满「最长存活时间」→ 删实体
```

### 4.3 命中判定：🔴 优先用引擎的查询 API，**不自己写**

**能不写就不写。** 引擎有三条现成的原生查询，而且都**带粗细**（`rayThickness`）—— 带粗细 = 沿线段扫一个球 = **天然就是连续碰撞**，正好顶掉"手写线段↔胶囊"那件事：

| 查什么 | 用什么 | 要点 |
|---|---|---|
| **打到谁** | `Mission.RayCastForClosestAgent(起点, 终点, out 距离, 排除谁, rayThickness)` | 返回 `Agent`；排除参数传施法者自己 |
| 打到哪根骨头 | `Mission.RayCastForClosestAgentsLimbs(...)` | 需要部位判定时才用 |
| **打到墙 / 地** | `Scene.RayCastForClosestEntityOrTerrain(起点, 终点, out 距离, out 命中点, out 实体, rayThickness, BodyFlags)` | 直接给命中点，喂给结算 |
| 形状更贴（可选） | `Scene.BoxCast(盒min, 盒max, …, 方向, 距离, out 距离, out 点, out 实体, BodyFlags)` | **扫掠一个盒子** —— 月牙是扁的，盒子比球更贴 |

**自己剩下要写的只有三件**：① 两条查询各给一个距离，**取近的那个** ② 命中**去重** ③ **穿透类**法术的循环（见下表第 2 条）。

🔴 **为什么不用"给实体挂个碰撞体"**：物理体 API 确实存在（`GameEntity.AddSphereAsBody` / `AddCapsuleAsBody` / `ApplyForceToDynamicBody`），**但引擎没有任何碰撞回调** —— `OnCollisionBegin` / `CollisionCallback` / `ContactPoint` / `BodyContact` 全 DLL 零命中，`MissionBehavior` 那四十多个钩子里也没有一个实体碰撞钩子。挂了物理体 = 它能推动别人、能挡住别人，**但永远不会告诉你它撞到了谁**。所以那条路不通，不用试。

**三个必须实测的点**（不能只看名字下结论）：

| # | 要验什么 | 不通过怎么办 |
|---|---|---|
| 1 | 🔴 `rayThickness` 是「**沿线段扫球**」还是「只在起点一个球」 | 只有前者等于连续碰撞。不是 → 退回手写线段↔胶囊 |
| 2 | `RayCastForClosestAgent` **只返回最近的一个** | 穿透类法术要自己循环：打到谁 → 排除它 → 从命中点再打一次，最多 `pierce` 次 |
| 3 | `Scene.RayCastForClosestEntityOrTerrain` / `BoxCast` **打不打 agent** | `BodyFlags` 看着是场景物件体系、agent 不是场景实体，**大概率不打** → 所以要两条查询配合；若实测打，可以合并成一条 |

**兜底路径已证可用**：SwordBeam 那套「遍历全场 agent + 自写线段↔胶囊距离」（[分析文档](../Knowledge/SwordBeam剑气_实现分析.md) §2.6）是跑通的 —— 实测不通过就退回去，不亏。

**顺带收益**：多发法术（一发变十发）的性能从「10 × 全场 agent 数」降到「10 × 2 次原生调用」，阶段 2 的性能估算因此好看得多（§4.4 那条"引入多发时重估"可以放宽）。

### 4.4 性能口径（和原版比，以及真正要守的纪律）

**结论：单发法术弹的开销大概率比原版一发弩矢更低。** 不是因为我们的代码更快，是因为**原版那颗导弹在做的绝大多数事情我们都不做**：

| 原版导弹每帧要做的 | 我们要做的 |
|---|---|
| 物理模拟（重力积分、空气阻力、旋转、角速度、反弹） | **位置 = 位置 + 速度 × dt**（一行乘法） |
| 物理宽相 + 窄相碰撞 | 🔴 **每 0.05 秒一次引擎射线查询**（= 原版 **1/3 的检查频率**） |
| 网络同步与回放记录 | 无 |
| 插盾 / 插骨 / 穿透 / 护甲结算 | 无（命中即消失） |
| 渲染 LOD 评估与网格剔除 | 场景实体，不走那条链 |

**量级也相当**：原版攻城战里几百个弓箭手同时抛射，天上可能有几十到上百发导弹；我们是玩家几秒一发，就算阶段 4 有二十个法师，同时在天上的也就几十发。

🔴 **真正该守的不是"别比原版慢"，而是"别写出算法上更蠢的东西"。** 五条纪律：

| # | 纪律 | 为什么 |
|---|---|---|
| 1 | 🔴 **绝不遍历全场 agent 去读 `CollisionCapsule`** | 每读一个就是**一次原生跨界调用**（`MBAPI.IMBAgent.GetCollisionCapsule`）。战场上 300~1000 个 agent × 20 次/秒 × 并发数 = **十万到百万次/秒**。这是唯一会把我们拖垮的写法 |
| 2 | **两条替代路径，都是「1 次原生调用」** | ① `Mission.RayCastForClosestAgent`（§4.3，引擎内部自己走空间索引）② 若走手写兜底，必须先 `Mission.GetNearbyEnemyAgents` 粗筛（一次原生调用返回附近几个），**只对筛出来的做精算** |
| 3 | **碰撞检查 0.05 秒一次，不是每帧** | 直接省 2/3 |
| 4 | **别每帧 new 容器** | 已命中名单、粗筛结果列表，一律**复用池**，不在热路径分配 |
| 5 | **并发上限默认 32，超出直接拒绝施放** | 宁可拒绝，也不要"加了再说" |

**什么时候必须重估**：阶段 2 引入**多发法术**（一发变十发 = 检查次数 ×10）、阶段 4 引入 **NPC 施法者**（并发数上去）。这两处到了就按"最坏情况：30 个施法者 × 每人 3 发 × 20 Hz"算一遍。

> **还有一个"最省"的选项，知道它存在就行**：保留引擎那颗导弹（它的碰撞、伤害、插地全是原版的），只把它的**视觉藏掉**、挂上我们自己的实体跟着它。纯性能上这是最省的。
> **不采用的理由**：导弹的寿命与失效距离不可控、有两套真相、形状与我们的月牙对不上（它的碰撞体是 47cm 弩矢）。**这是"性能换控制权"的取舍，我们选了控制权。**

## 五、起手路线：法印还要不要是「弩」

### 5.1 先把问题摆正

**自建投射物之后，"法印 = 弩"从"必需"降级成"脚手架"。** 引擎的弩只提供了三样东西，而这三样都不是非它不可：

| 弩给我们的 | 是不是非它不可 |
|---|---|
| 瞄准姿势 + 准星 | 不是 —— 可以用自建 `item_usage` 的姿势，也可以完全自建 |
| "按哪个键、什么时候放"这套输入 | 不是 —— 项目已有按键映射子系统，可以自己读 |
| **引擎开火事件**（我们现在的触发点） | 🔴 **恰恰是最想甩掉的** —— 为了它要写 Harmony 补丁、还要跟"装填"流程打交道 |

🔴 **所以真正的决定不是"要不要弩"，而是"起手怎么进入我们的代码"**。

### 5.2 关键设计：起手必须走**函数调用**，不能走**引擎事件**

| | 走引擎事件（现在） | 走函数调用（要改成） |
|---|---|---|
| 长什么样 | 引擎开火 → Harmony 拦下 → 调我们 | 我们自己的相位机 → 调我们 |
| 换壳的代价 | **要改投射物层**（因为触发点长在引擎上） | **投射物层一行不动**，只换调用者 |

**起手层的接口固定成一句话**：`(施法者 Agent, 法术 id, 起点, 方向, 蓄力档)` —— 谁调它都行。

- **阶段 1 的调用者** = Harmony 拦下引擎开火后的我们（脚手架）
- **阶段 3 的调用者** = 我们自己的相位机（§5.5：读输入 + 轮询动作进度）

**这样阶段 3 甩掉脚手架时，投射物那一层不需要改动。** 这是本计划把"临时壳"写清楚的全部意义。

### 5.3 三条路（阶段 3 要选一条）

| 路 | 起手怎么触发 | 动作从哪来 | 代价 | 评价 |
|---|---|---|---|---|
| **A. 弩当脚手架**（当前） | 引擎开火 → 拦下 | 弩的 `item_usage` | 要写补丁；装填流程会来捣乱；长期绑在远程武器语义上 | **阶段 1 用**，阶段 3 甩掉 |
| **B. 法印在，但它不发射** | 我们自己读输入 | 自建 `item_usage` 的姿势 | 要验一件事：**非远程武器能不能有"抬起瞄准"这个状态** | 待实验；成了就是长期形态 |
| **C. 完全不用物品**（FCS 那样） | 我们自己读按键 | `SetPose` 切自建动作集 | 丢瞄准姿势与准星；法术选择要自建 HUD（本来也排在阶段 5） | **NPC 侧的做法**（NPC 没有玩家 UI） |

**推荐：A 起步 → 阶段 3 做一次 B 的实验 → B 成则用 B，不成退 C。**

**为什么倾向保留"法印"这个物品**（而不是直接走 C）：龙之信条和艾尔登法环**都是手持法器施法**；而且有物品就有一套**专属动作集**，否则每个法术动作都要塞进各武器的动作集里；再加上弹药槽天然就是"选哪个法术"。

### 5.4 阶段 1 用弩时必须守的 Harmony 纪律（本项目已立过的规矩，逐条照办）

| # | 规矩 | 本补丁怎么落 |
|---|---|---|
| 1 | **目标必须在三个版本锚点都活着** | 已核对：`Mission.OnAgentShootMissile` 在 **1.2.12 / 1.3.15 / 1.5.1** 三个版本反编译出来**签名逐字相同**（`internal [MBCallback]`）。签名一致 ⇒ 补丁跨版本稳定 |
| 2 | **守卫要窄** | 只在「手持武器 ∈ 我们登记的法印集合」时拦截。别的 mod 射箭、原版射弩**一律不管** |
| 3 | **前缀内必须吞异常并放行** | 出错就 `return true` 让引擎照常发导弹 —— 顶多退回旧表现，绝不掐断游戏 |
| 4 | **要能被单独关掉** | 补丁类名进 `Settings.DisabledPatchClasses` 白名单即可（本项目已有这套逐类开关，改完重启即生效、零重编） |
| 5 | **补引擎跳过的记账** | 引擎原方法末尾有一句 `UpdateLastRangedAttackTimeDueToAnAttack`（AI 的"刚射击过"计时）—— 前缀里要自己补一次 |
| 6 | 🟢 **兜底天然优雅** | 补丁关掉 / 认不出弹药 → 引擎照常发导弹，弹药的 `flying_mesh` 还在，**表现退回旧路线**（月牙照飞，只是 110 米外会隐形），不会崩 |

### 5.5 🔴 动画相位：照 FCS 的模型办

FCS 把「**什么时候播什么**」和「**法术什么时候真的出来**」分得很干净 —— 这是本项目要照抄的部分。

| FCS 的做法 | 干什么 | 骑砍怎么落 |
|---|---|---|
| **蓄力蒙太奇** | `BeginMagicCharge` 时起播，循环到出手 | 法印的「抬起 / 维持」姿势（阶段 1 靠 `item_usage`，阶段 3 靠自建动作） |
| 🔴 **出手帧通知** `AN_TriggerMagicAbility` | 挂在动画"法术真正放出"那一拍 → `TriggerMagicSpell` | 🔴 **骑砍没有动画通知** → **每帧轮询 `GetCurrentActionProgress(通道)` 过阈值**（本项目已有技法：[自定义战斗.md](../Knowledge/自定义战斗.md) §3「进度阈值打点表」） |
| **收尾帧通知** `AN_TriggerNextAbility` | 挂在动画末尾 → `NextSpell`（接下一发 / 连招） | 同一个轮询，取第二个阈值 |
| **引导三件套** `Start / Mid / End` | 引导法术的三段（起 / 持续循环 / 收） | `SetActionChannel` 切段播 |
| 🔴 **瞄准俯仰三变体**（`Aim-Offset`：`SpellChannel1_Down / Mid / Up`） | 仰角不同播不同姿势 | **我们也该有** —— 三套姿势按视角俯仰切 |
| **手势按投送方式分** | `M_Projectile`（投掷）/ `M_SkyfallSpell`（举天）/ `M_EruptionSpell`（下压）/ `M_SpellChannel1·2`（引导） | 每种投送方式一套动作（`tools/anim-retarget` 的素材库正好对得上） |

🔴 **三条纪律**（都来自 FCS 的实现）：

| # | 纪律 | 为什么 |
|---|---|---|
| 1 | **"何时放出法术"交给动画那一拍，代码不自己计时** | 换动作、改动画时长都不影响出手时机。骑砍没有通知 → 用"进度过阈值"做等价物，**阈值写在数据里**（一个法术一个），不写死在代码里 |
| 2 | 🔴 **出手阈值必须防重入** | "过阈值"这个条件是**持续成立若干帧**的，不挡就会连发同一个法术（FCS 用 `IsPlayingMontage` 挡） |
| 3 | **收尾帧开输入缓冲窗口** | 松手到动作结束之间按下的下一次施法要接住（FCS 是 `AN_TriggerNextAbility` + `InputBuffer`） |

**阶段 1 怎么落**：阶段 1 用引擎的弩流程当脚手架，**它的开火事件就是"出手帧"** —— 所以阶段 1 不需要轮询，但**数据表里要先把「出手阈值 / 收尾阈值」两个字段留出来**，阶段 3 换相位机时不用改表结构。

### 5.6 阶段 1 一次实机要顺带确认的三件事

| # | 问题 | 为什么重要 |
|---|---|---|
| 1 | 拦掉导弹后，**弹药还照扣吗** | 扣 = 白送；不扣 = 要自己扣（走 `AgentControlHelper`，铁律 4） |
| 2 | 开火**音效**还响吗 | 音效在 native 侧，理论上照响；不响就自己补一条 `module_sounds` |
| 3 | 引擎的"装填"流程还走吗 | 走 = 白送一个施法后摇；不走则阶段 3 自己做（FCS 对应物 = 收尾帧接下一发） |

## 六、数据契约（内容包侧）

### 6.1 一个法术一行

文件：`Modules/Taikou/ModuleData/AssetRegistry/Spells.xml`（照现有 `FirearmFx.xml` 的放法）。

```xml
<Spells>
  <Spell id="lwn_yinmo_zhan"                 <!-- 法术 id（StringId，铁律 20） -->
         ammo="lwn_spell_crescent"        <!-- 哪个弹药物品 = 这个法术（选择器 + 消耗品） -->
         family="projectile"                 <!-- 🔴 法术族（§2.4）：选它 = 一次填好下面三轴的默认搭配 -->
         targeting="aim"                     <!-- 瞄准轴：准星直视（不写就按族的默认） -->
         delivery="projectile"               <!-- 投送轴：直线飞行 -->
         payloads="damage,area"              <!-- 结算轴：单体伤害 + 半径伤害 -->
         cast_type="normal"                  <!-- 起手轴：Normal / channel / instant（阶段 3 用） -->
         release_at="0.42" end_at="0.80"     <!-- 🔴 动画相位阈值（§5.5）：出手帧 / 收尾帧。阶段 1 引擎开火即出手，字段先留着 -->
         mesh="lwn_yinmo_crescent"           <!-- 飞行网格 -->
         trail_particle="lwn_yinmo_trail"    <!-- 拖尾 -->
         impact_particle="lwn_yinmo_burst"   <!-- 命中爆散 -->
         damage="60" damage_type="Cut"
         speed="60" gravity="0"              <!-- 重力 0 = 平飞；>0 = 抛物线下坠 -->
         turn_rate="0"                       <!-- 转向速率：0 = 直线飞；>0 = 追踪弹（阶段 2） -->
         count="1" spread_deg="0"            <!-- 发数 + 散布角（阶段 2） -->
         max_distance="120" max_lifetime="4"
         hit_radius="1.2" pierce="1"
         radius="3.5" radius_falloff="0.5" />
</Spells>
```

### 6.2 对应规则

| 规则 | 说明 |
|---|---|
| **先选族（`family`），再按需覆盖三轴** | 族 = 常用搭配的预设（§2.4）。不写 `targeting`/`delivery`/`payloads` 就按族的默认；写了就是覆盖 |
| 🔴 **`family` 认不出 → 整个法术不加载**（记日志、不崩） | 数据填错的兜底；不是"退回引擎导弹"那条路径 |
| **一个法术 = 一个弹药物品 = 一个视觉** | 禁止让多个法术共用一个弹药（DOS2 踩坑 #10：元素错配就是"火球模板"类错误的根源） |
| **认不出的弹药 = 不管** | 弹药 id 不在表里 → 引擎照常发导弹（兜底路径，见 §5.3 第 6 条） |
| **法印集合也登记在同一张表** | 表里出现过的 `ammo` 所属的法印，自动进"要拦截"的集合；不需要另立名单 |
| **数值一律数据化** | 速度、寿命、半径、可穿透数、转向速率**都是参数**——这正是自管路线白赚的（旧路线的爆炸半径写死在引擎里，只有 1.2 / 2.8 米两档，改不了） |
| **阶段 2 的字段现在先留空** | `turn_rate` / `count` / `spread_deg` 阶段 1 写了也不读，但**表结构不用再改** |

### 7.2 旧路线解决不了、新路线自动解决的三个问题（法印计划 §15.3 的待办）

| # | 旧待办 | 新路线的答案 |
|---|---|---|
| 1 | 🔴 **"寿命"** —— 飞多远 / 活多久（旧路线查到 `WeaponComponentData` 没有寿命字段、引擎里写死，**无解**） | **变成我们自己的两个参数**：`max_distance` / `max_lifetime` |
| 2 | **飞行朝向**（旧结论：朝向由 native 按速度算，**没有运行时手段**，只能改网格几何） | **朝向由我们算**：飞行方向 + 我们自己定的姿态倾斜 |
| 3 | **爆炸半径**（旧路线写死 `isBigExplosion ? 2.8 : 1.2` 米，数据改不了） | **变成我们的参数**：`radius` + `radius_falloff` |

### 7.3 迁移时唯一要重新实测的几何项

**网格本地朝向 → 我们算的 frame 之间的换算关系。**

- 旧路线里，朝向由引擎决定，生成器用一个 `-90°` 的烘焙去迁就它；现在换成我们定，必须重标一次。
- 做法最省：诊断件已有 `alt_mesh` 子命令（造一个陪飞的场景实体）。**摆 3~4 个候选朝向，一次实机看哪个对**，把对的那个写进代码的常驻定向函数。
- 为什么必须先标：2026-09-23 之前的教训 —— 朝向错了整个法术就废，但**资产做完了才发现**要重来一整轮（法印计划 §14.5）。

| 2 | 月牙**朝向对**（薄刃立着、凸面朝前）、**尺寸对**（约 3.8 米宽，不是 19 米） |

### 12.5 阶段 2（2026-09-23，同批落地）

**一句话**：四段各加了新实现，**阶段 1 写好的那四段一行没改** —— 这就是"接口切对了"的判据（本阶段自己的验收标准）。

| 轴 | 新增实现 | 数据参数 |
|---|---|---|
| 瞄准 | `ground`（落点）· `locked`（软锁，可锁 N 个，一个目标一条意图） | `lock_max` / `lock_angle` / `lock_range` |
| 投送 | `projectile` 扩容：**追踪**（`turn_rate`）· **天降**（`start_height`，从落点上方砸下来）；**多发**在瞄准轴摊成 N 条意图（`count` / `spread_deg`） | 同上 + `count` |
| 投送 | **`place`**（新）：留在落点上，活 `duration` 秒、每 `repeat_interval` 秒上报一次（**节流在投送手里** —— 契约 3 的第一次实装）；首次生效带 `start_delay` ± 抖动 | `duration` / `repeat_interval` / `start_delay` / `start_delay_variance` |
| 结算 | **`status`**（新）：给目标挂持续伤害（燃烧/中毒/流血…），由 `SpellStatusManager` 每帧推进（跳伤害 + 跟随视觉），**同目标同法术 = 刷新时长不叠伤害** | `status` / `status_damage` / `status_duration` / `status_interval` / `status_particle` |
| —— | **落点指示圈**（放置/天降族的必备件）：手上有落点类法术弹时，在准星指向的地面画圈 | `indicator` / `indicator_scale` |

**三个验收件**（都是机制验收，不是正式法术；复用月牙网格，所以"看起来一样、行为不同"）：
`projectile_multi_bolts`（锁 3 + 追踪 + 中毒）· `skyfall_meteor`（落点上方 25 m 砸下来）· `place_firezone`（地上留 8 秒、每秒烧）。
控制台免装备直放：`custom.spell cast projectile_multi_bolts`。

**新落的两条硬事实**（都写进代码注释，避免下次再查）：
1. `lwn_flight_sigil`（法阵网格）**平面法线 = 本地 +Y** —— 它在 Taikou 的 prefab 里必须补 `rotation_euler="1.571,0,0"` 才躺得平（2026-09-21 实机确认）。放置区域与指示圈都按这个约定定向（`SpellMath.BuildGroundRotation()`）。
2. `SpellCastIntent` 加了 **`AimPoint`**（落点）—— 天降与放置靠它；这是契约 1 的自然加宽（阶段 1 的直线飞不读它，所以那三个类一行没动）。

**刻意没做的两件**（说明理由，免得被当成漏）：① **落地随机抖动只做在"首次生效延迟"上**（不是随机落点）—— 落点由玩家瞄，抖落点会让人觉得"法术不准"；② **区域不区分敌我**（自己站进去照样烧）—— 与 DOS2 同款直觉，且避免"施法者免疫"这类隐藏规则。

### 12.8 阶段 3（2026-09-23，同批落地）—— "施法中"那台状态机

**一句话**：起手轴从此**自己读键、自己管节奏**（数据 `cast_type` 一个字段切三种施法方式），
而**投送与结算那一层一行没动** —— "甩掉脚手架"这件事的全部代价就是多了一个 `SpellCastInput`。

| 件 | 说明 |
|---|---|
| **起手键** | `InteractionIds.SpellCast`（默认 **R** / 手柄 **RT**，走既有 `ModInput` 键位系统，改键照旧走 config.json）。**按住蓄力、松手放**。 |
| **三种施法方式** | `normal`（按住 → 手上核长大 → 松手发一发）· `channel`（攒够 `charge_time` → 一直放 → 松手停）· `instant`（按下即出，无前摇） |
| **蓄力档位改效果** | 起手算出 `Power`（0~1）→ 随意图/命中一路传到结算 → 伤害按 `1 + charge_bonus × Power` 放大。**投送与结算没为它加过一行"蓄力专用"代码**。 |
| **蓄力视觉** | 手心的核（`charge_mesh` = `lwn_yinmo_core`）+ 蓄力粒子（`charge_particle` = `lwn_yinmo_charge`），随 `Power` 长大。⚠️ 位置是**身前近似手位**，不是骨骼挂点 —— "法阵 prefab"接上后换挂点即可（数据字段不用改）。 |
| **打断 / 输入缓冲** | 换武器、换法术、施法者倒下、场景结束 → 当场清干净（核与粒子一起）；松手后 0.35 s 内再按 = 直接接下一发。**按住不放不连发**（要松一次手才认下一发）。 |
| **投送轴「持续」** | `channel`：每 `repeat_interval` 秒沿朝向打一条射线 → 打到人报"命中那个人"、打到墙/地报"打到那里" → **契约 3 的完整实装**（每帧都照着，但每 0.4 s 才结算一次）。 |
| **结算轴「光环」** | `aura`：与 `area` 同款，**圆心改成施法者自己**（雷电领域/加护）；`self` 瞄准轴一条意图落在自己身上。 |
| **两条起手并存、不双发** | 引擎开火（鼠标）那条路**保留**（阶段 1/2 的习惯不用改）；**相位机正在施法时，法印补丁只拦不放**。 |

**验收件**：`channel_beam`（按住持续喷射 + 灼烧状态）· `aura_field`（以自己为圆心持续电周围）。
控制台：`custom.spell cast channel_beam`；**验蓄力不用按键盘** → `custom.spell power 0.2` 再 `cast`（对比伤害）。

**三处要你出手的（我不做，做了也是白做）**：

| # | 事 | 为什么现在就能用 |
|---|---|---|
| 1 | **"法印在但不发射"实验**（§5.3 路 B：非远程武器能不能有抬起瞄准状态） | 现在走的是"**我们的键 + 保留法印当姿势来源**"（路 C 的变体），不依赖该实验；实验只为决定**要不要把法印从弩换成自建 usage**（手感差异） |
| 2 | **蓄力法阵 prefab** | 现在用"核网格 + 粒子"顶替（同一套数据字段）；prefab 做好后换 `charge_mesh` 指过去即可 |
| 3 | **蓄力/引导动作**（结印/举天/下压，`tools/anim-retarget`） | 现在**没有施法动作**（人站着放）—— 动作接上后，用 `release_at`/`end_at` 阈值驱动动画相位（§5.5 的 FCS 模型） |

**没做的一件**（明说，免得被当成漏）：**手上发光**（SwordBeam 的 `Material.CreateCopy` + `self_illumination`）。
理由：它要碰"手持武器实体 → 网格 → 材质"这条链，而这条链在 1.2.12 与 1.3.0+ **类型不同**
（`GameEntity` vs `WeakGameEntity`，见 version-compat-plan 的 1.3.0 变更表）—— 纯观感打磨，
等施法动作定了再一起做，比现在写一个跨版本分支划算。

### 12.9 阶段 4（2026-09-23，同批落地）—— NPC 施法者

**一句话**：NPC 放法术 = **同一套 `SpellCastFlow`**，差别只有触发源（`SpellNpcCaster` 每秒扫一次附近，
而不是按键）。铁律 18 的"判定与结算共用"从阶段 1 就是这么写的，这一阶段只是把调用者补上。

| 纪律 | 怎么落 |
|---|---|
| 谁是施法者 | **手里是「法印 + 法术弹」的 NPC**（与玩家同一条判据：弹药 = 法术）；不需要另立名单 |
| 只开 7 类 | 框架侧白名单 `{projectile, channel, skyfall, place, buff, heal, teleport}`；数据侧还能 `ai="false"` 单独否掉 |
| 带权随机 | `SpellNpcCaster.PickWeightedForAi()` 按 `ai_weight` 抽（现在 NPC 手上只有一个法术，所以它主要给"发法印"用；有法术书之后就是选法术的入口） |
| 防重入 | 每个 NPC 一个冷却（数据 `ai_cooldown`，默认 5 s） |
| 施法期间照常走位 | **本类从不碰移动/行为**，只管调 `SpellCastFlow` |
| 性能 | 扫 `Mission.GetNearbyAgents`（1 次原生调用 / 秒，半径 45 m），**不遍历全场 agent** |

**验证钩子**（一条命令让 NPC 变成法师）：
`custom.spell give` → 给最近的 NPC 装一套「法印 + 法术弹」（按 `ai_weight` 带权随机抽一个），
它下一拍就会自己找敌人放法术 —— 之后看：**判定/飞行/命中/掉血与玩家一模一样**，
且**不会连发**（5 s 冷却）、**不会站着不动**（我们从不碰它的移动）。

⚠️ 已知边界（如实说）：NPC 现在**没有施法动作**（同 §12.8 第 3 条），法术从它手上飞出去但人站着；
另外若 NPC 自己的原版远程 AI 也开火，补丁会**另外**放一发（两条触发源各自成发）—— 真实玩法里
施法 NPC 会由 `AgentBrain` 接管，届时把这一条收口。

## 十三、结论

> **本部分状态：待审批**（2026-09-26 立 / 09-27 修订）。**只做战斗** —— 战役层的获取、学习、名声、后果不在本部分内。
> **一句话**：忍术**不是"更强的远程武器"，而是"改造战场 + 组合实验"** —— 龙之信条给**下注的勇气**（蓄力/打断），神界原罪给**战场的语法**（地表/反应），Noita 给**装配的自由**（宝石组合）。

### 13.1 融合命题

三套参考是**三个时间尺度上的同一件事**，不是三个并列功能：

| 尺度 | 来源 | 玩家在干嘛 |
|---|---|---|
| **秒** | 龙之信条 | 蓄力 → 赌注 → 释放；被打断就白费 |
| **战** | 神界原罪 | 用地表**改造战场**：切断阵型、连锁反应 |
| **役** | Noita | **出击前装配**：基础术 + 宝石 → 决定这次带什么 |

三个环互为因果：配装决定你能造什么地表 → 地表决定你站哪里、赌多久 → 打出来的结果反过来改配装。

**一句话**：**忍术是放大器，不是替代品** —— 它不让你一人打赢一支军队，它让你决定**这场仗在什么地方、以什么方式打**。

### 13.2 决定表

| # | 决定 | 理由（一句） |
|---|---|---|
| 1 | **四段框架一行不改**，新东西全加在四段**之上或之外** | 三条契约当初就是为今天留的口子；改四段 = 把已验收的 6 条法术全拖回重测 |
| 2 | **修正 = 对法术数据的一组增量**，解算成「有效定义」再走原管线 | 修正本质是"改数值"，而我们的法术数据本来就是一张数值表 —— **组合不预设、全由解算得出**（玩家自创法术的基础） |
| 3 | 🔴 **修正挂四段的任意一段**，不只挂投射物 | 四段是四个挂点，**包括"落地留地表"**（Noita 没有、神界原罪独有）—— 这是三套真正咬合的地方 |
| 4 | **承载 = 施法手环 + 宝石槽** | 用户裁定（09-26）：修正靠装配获得，配装即玩法 |
| 5 | **代价 = 自建查克拉条**，上限挂已有的忍术技能等级（0~4） | 引擎没有耐力条（已核实）；忍术技能数据链已在跑，天然是上限来源 |
| 6 | **元素立成一等数据**（火水风雷土），挂法术 / 状态 / 地表 / 修正四处 | 地表反应、五遁、元素修正三者共用同一个轴；没有这层就要造三套 |
| 7 | **招式表 = 太阁5 忍术卡**（库里 20+ 张）+ 少量彩蛋（火影/凡人系，现有阴魔斩属此） | 零新造词、与世界观同源；忍术技能等级天然是学习门槛（294 人有值、17 人满级） |
| 8 | 🔴 **地表按战场尺度做**：条形（火墙切阵型）+ 同类合并 + 总量上限 | 小队尺度的 4 米火圈在几百人战场里等于不存在 |
| 9 | 🔴 **本期不做 AI 避让**，先做攻击者视角 | 战场里 `AgentBrain` 关闭，引擎只剩"预制阻挡件硬挡"一条路（是资产工作 + 要开 ModKit）—— 见 §19.4 末条 |
| 10 | **首期只做修正机制**（用户裁定） | 唯一"不依赖任何其他层、且直接决定玩法深度"的一块 |

| **3** | **无限组合 × 持久战役** | 地上随便捡宝石 → 平衡崩坏 | ① 获取有门槛（战役层，不在本部分）② **装配有上限**（槽位 = 手环品质 + 忍术等级）③ **代价有梯度**（修正越猛查克拉越贵）④ **不做随机性** |
| **4** | **法术实体 × 千人同屏** | 几十个实体乱走 → 卡、看不懂 | ① **实体预算**（沿用并发上限）② **可读性铁律**：一眼看懂什么元素、会不会动 ③ **不做隐形杀手**（看不见的范围伤害一律不要） |

### 14.2 修正挂四段 —— 比 Noita 多的地方

Noita 的修正只有"投射物"一个目标。我们的四段是**四个挂点**：

| 挂哪段 | 宝石举例 | 改变什么 |
|---|---|---|
| **起手** | 缩短前摇 / 瞬发化 / 连放两次 / 静默施法 | 什么时候放、以什么代价放 |
| **瞄准** | 多发 / 锁定数 +N / 目标间跳（链） | 打谁、打几个 |
| **投送** | 追踪 / 弹跳 / 钻地 / 分裂 / 触发器 / 定时器 | 怎么过去 |
| **结算** | 伤害 / 贯穿 / 附加状态 / 🔴 **留地表** / 范围扩大 | 到了之后发生什么 |

🔴 **"留地表"是三套参考真正的咬合点**：Noita 有材质但没有组合式地表，神界原罪有地表但不能装配。**宝石能让火球变成"先铺油、再点燃"**。
🔴 **触发器让组合爆炸**：命中时释放另一个术 → 玩家能配出"火球命中后原地放水弹"这类链条，**这才是"自创法术"的实际形态**。

### 14.3 一局的形状（战斗的五个节拍）

| # | 节拍 | 用到什么 |
|---|---|---|
| 1 | **接敌前**：你不在阵中 —— 找掩体、绕侧翼、或升空占高度 | 位置是忍者的第一资源 |
| 2 | **开局**：敌骑冲锋 → 你在冲锋路线上横一道**火墙** → 骑兵受伤 + 减速 → **冲锋被打散** | 神界原罪的地表 × 骑砍玩家一眼就懂的价值 |
| 3 | **中局**：敌方法师浇水灭火 → 你补一发**雷** → 水面带电 → 半队人麻痹 | 元素反应（水 + 雷） |
| 4 | **危机**：弓手盯上你，咏唱到一半被击中 → **掉一档**（不是全废）→ 用**空蟬之術**脱身 | 龙之信条的赌注 + 打断分级 |
| 5 | **收尾**：残兵溃散，**亂苦無**（多发 + 追踪宝石）清场 | Noita 的组合 |

### 14.4 有意不抄的

| 参照 | 它的毒 | 为什么不搬 |
|---|---|---|
| 龙之信条 | 法术同步 · 随从仇恨 | 骑砍没有小队施法编队；仇恨系统会跟原版 AI 打架 |
| 神界原罪 | 回合制 / 行动点 · 地表"等级"覆盖 | 骑砍是实时；地表强度改为**尺寸 + 时长叠加**（大覆盖小、久覆盖短），更好懂 |

## 十六、首期：投射物模型与修正机制（Noita）

### 16.1 投射物运行时模型：先定义属性，再谈修正

🔴 **这一节回答的是"修正凭什么能任意组合"** —— 修正**不是功能，是对属性的操作**。所以属性必须在开工前**定义完备且正交**，否则每加一条修正就得加一段代码（这正是"能抄 Noita 的系统很多、做到 Noita 的只有一个"的原因）。

**八个作用点**（每帧循环；属性**只在这八处被读**）：

| 点 | 干什么 | 在这里被读的属性 |
|---|---|---|
| **① 推进** | 速度 ← 重力 / 阻力 / 沿程加速 / 追踪；位置 ← 速度 × dt | `speed` · `speed_scale` · `gravity` · `drag` · `accel` · `turn_rate` · `turn_delay` · `homing_target` |
| **② 定向** | 网格朝向 ← 速度方向 + 横滚 + 定向模式 | `orient_mode` · `tilt_deg` |
| **③ 命中查询** | 上一帧 → 这一帧的线段扫掠（默认 0.05 秒一次） | `hit_radius` · `sweep_interval` · `collide_terrain` · `collide_agent` |
| **④ 命中裁决** | 地形与目标各给一个距离 → 取近的 → 去重 → 穿透 / 弹跳 / 钻地 | `pierce` · `bounce_count` · `bounce_damping` · `drill` · `hit_same_team` |
| **⑤ 触发** | 命中 / 定时 / 弹跳 / 分裂 → 派生子法术、留地表 | `on_hit_cast` · `on_timer_cast`(+`timer_seconds`) · `on_bounce_cast` · `on_expire_cast` · `split_at`(+`split_count`) · `trigger_depth` · `leave_surface` |
| **⑥ 到期** | 距离 / 寿命 / 命中数耗尽 → 结束（或转成放置物） | `max_distance` · `max_lifetime` · `duration` · `repeat_interval` · `start_delay`(+`_variance`) |
| **⑦ 表现** | 拖尾跟随、命中爆散、音效 | `mesh` · `scale` · `trail_particle` · `impact_particle` · `impact_sound` · `sound_release` |
| **⑧ 结算** | **交给结算轴**（不是投射物自己的事） | `damage` · `damage_type` · `element` · `crit` · `crit_mult` · `area_radius` · `area_falloff` · `status_*` · `power` |

🔴 **第一条硬纪律：没有读取点的字段不许进表。** 每个属性都必须能说出它在①②③④⑤⑥⑦⑧哪一处被读；说不出来 = 这个字段是装饰品，删掉。

**修正 = 对属性的五种操作（只有这五种）**：

| 操作 | 写法 | 例 | 适用属性类型 |
|---|---|---|---|
| **设定** | `field = v` | 元素改成火 | 数值 / 布尔 / 枚举 / 引用 |
| **增减** | `field += v` | 穿透 +2 | 数值 |
| **乘** | `field *= v` | 伤害 ×1.5 | 数值 |
| **开关** | `field = 开/关` | 钻地 = 开 | 布尔 |
| **追加引用** | `field = <id>` | 挂拖尾粒子 / 挂子法术 | 引用（粒子/法术/地表/网格） |

🔴 **身份型属性不许被修正改**（法术 id / 族 / 瞄准轴 / 投送轴 / 弹药物品）—— 修正改的是**行为**，不是"这是什么法术"。
🔴 **一条修正可以同时改多个属性**（Noita 的"轻/重互换"就是"伤害 × 与 速度 ×"两条操作），但**必须是显式列出的两条**，不许有隐藏耦合。
🔴 **新增一条修正不许加代码分支** —— 只能用上面五种操作。做不到 ⇒ 说明**属性表缺东西**，**补属性，不是加特例**（这是这套系统几年后还能用的唯一原因）。

**完备性判据（= "属性表设计好了没有"的验收）**：拿 Noita 的招牌修正逐个对照，**全部能用现有属性 + 五种操作拼出来**才算完备：

| Noita 修正 | 落到哪些属性 |
|---|---|
| 伤害强化 | `damage` += |
| 暴击 + | `crit` / `crit_mult` |
| 加速 / 减速 | `speed_scale` × |
| 轻 / 重互换 | `damage` × **与** `speed_scale` ×（两条显式操作） |
| 弹跳 | `bounce_count` + `bounce_damping` |
| 穿透 | `pierce` |
| 钻地 | `drill` 开关 |
| 追踪 | `turn_rate` + `homing_target` |
| 反重力 | `gravity` += / × |
| 延长寿命 | `max_lifetime` × |
| 元素拖尾（火/冰/雷/毒） | `trail_particle` 引用 + `element` 设定 |
| 伤害场 | `leave_surface` 引用 |
| 爆炸 | `area_radius` + `impact_particle` |
| 触发器 / 定时器 | `on_hit_cast` / `on_timer_cast`（**载荷 = 一个子装配块**，语义见 §16.4 末尾） |
| 伤害均分 | `count` × **与** `damage` ×(1/N) |
| 巨大化 | `scale` × + `hit_radius` × |
| 多重施法 | 瞄准轴的 `count`（**已有**） |
| ❌ 回旋 / 环绕 / 链式 / 闪避 | **先不做** —— 它们要的是**新的运动模式**（`orient_mode` 的扩展），不是新属性；做的话单独排期 |

**要补的属性清单**（当前 `SpellDef` 没有、首期必须补齐）：
`speed_scale` · `drag` · `accel` · `turn_delay` · `orient_mode` · `collide_terrain` · `collide_agent` · `hit_same_team` · `bounce_count` · `bounce_damping` · `drill` · `on_hit_cast` · `on_timer_cast` · `timer_seconds` · `on_expire_cast` · `on_bounce_cast` · `trigger_depth` · `leave_surface` · `split_at` · `split_count` · `crit` · `crit_mult`
（`element` 等元素层属性在阶段 7 补；`power` 蓄力已有。）

🔴 **这张表是唯一真源**：`SpellDef` 填它 · `Modifiers.xml` 改它 · 代码读它 · 本文描述它 —— **加一个属性 = 改这张表 + 在对应作用点接线，三处必须同步**。

### 16.2 公式

> **有效法术 = 基础术 ⊕ 修正₁ ⊕ … ⊕ 修正ₙ**

**修正** = 一行数据：**改哪个字段、怎么改、改多少**（加 / 乘 / 覆盖 / 追加）。解算结果**仍是同一个 `SpellDef`** ⇒ 四段一行不用改。

### 16.3 数据与承载

**`Modifiers.xml`**（内容包 `ModuleData/AssetRegistry/`，既有目录）一行一颗宝石：

| 类 | 字段 | 说明 |
|---|---|---|
| 身份 | `id` / `name` / `icon` / `desc` / **`stage`（挂哪一段）** | 名字走本地化（铁律 13） |
| 数值 | 目标字段 + 运算 + 值（`damage ×1.5` / `pierce +2`） | **一张通用表**，不给每颗宝石写代码 |
| 行为 | `on_hit_cast` / `on_timer_cast` / `bounce` / `drill` / `split` / `leave_surface` | 见 §16.4 |
| 代价 | `chakra_cost_add` | 修正越猛越贵 |

**承载**：现有法印 `lwn_spell_seal` 升级为**施法手环**（不改名不改用途，只加槽位）。**槽位数量 = 手环品质 + 忍术等级**；装备槽位 = 能叠几层修正。

🔴 **技术要点**：骑砍的物品**没有实例状态**（背包只有"某物品 × 个数"）⇒ "哪颗宝石插在哪个槽"必须**存在角色身上 + 存档**；宝石物品只当解锁凭证。（另外两个走不通的方案：一套配装=一个物品定义 → 定义爆炸；扫背包 → 玩家无法表达"装 3 颗里的这 2 颗"。）

**宝石按四段分四类**不只是分类好看 —— 它是**装配界面的组织方式**：打开手环一眼看出"这条术缺起手、结算已经很猛"。

### 16.4 需要新作用点的修正（五条）

| 修正 | 用到哪些属性 | 新作用点要写什么 |
|---|---|---|
| **弹跳** | `bounce_count` + `bounce_damping` | **④ 命中裁决**：撞地形时按命中法线**反射速度**而不是结束；次数用光再结束 |
| **钻地** | `drill` | **③④ 命中过滤**：地形命中**忽略**（飞行距离仍算），只撞人 |
| **触发器** | `on_hit_cast` + `trigger_depth` | **⑤ 触发**：命中那刻派一条新意图（复用 `SpellCastFlow` 入口 → 天然套娃，**必须限深**）。载荷形态见下 |
| **定时器** | `on_timer_cast` + `timer_seconds` | **⑤ 触发**：条件从"命中"换成"计时"。载荷形态同下 |
| **分裂** | `split_at` + `split_count` | **⑤ 触发**：飞到行程的百分之几时派 N 条新意图（与"多发"同机制，只是延迟到中途） |

**🔴 触发类修正的语义 —— 把"触发之后到底发生什么"说死**（2026-09-27 补）

| 问题 | 答 |
|---|---|
| **触发之后发生什么** | **在触发点派一条新的施法意图**：起点 = 投射物**当时的位置**，方向 = 继承原飞行方向（或按子法术自己的瞄准轴重瞄）—— 走的是**同一条 `SpellCastFlow`**。⇒ "**召唤一颗新子弹**""**炸一片**""**留一地火**"**全都是它**，因为子法术自己能带范围 / 留地表 / 追踪，不需要为每种效果新造机制 |
| 🔴 **载荷的形态** | **不是一个法术 id，是一个「装配块」** = 基础术 + **它自己的修正列表** + 一个缩放系数（伤害 / 发数）。理由：Noita 的触发器里可以塞"**带修正的法术**"；只填一个 id ⇒ 这半个能力直接丢掉 |
| **触发点（四个）** | `on_hit_cast` 命中时 · `on_timer_cast` + `timer_seconds` 飞行 N 秒后（在空中）· `on_bounce_cast` 每次弹跳时 · `on_expire_cast` 到期 / 飞完时 |
| **每个触发点能做三类动作** | ① **派子法术**（重项 = 上表两行）② **落地表**（`leave_surface`）③ **放表现**（`impact_particle` / `impact_sound`）—— 后两类**不派新意图**，成本低 |
| **子装配块继承外层修正吗** | ❌ **不继承**（独立解算）—— 要什么**显式写在子块里**。否则"外层一颗伤害宝石，里面子法术也跟着变"会变成一团乱账 |
| **套娃** | 允许，但 `trigger_depth` **默认限 3 层**（防无限递归） |
| 🔴 **两个容易混进来的东西，明确划出去** | **传送 ≠ 触发器** —— 那是**投送轴的位移实现**，移动的是**施法者自己**；**召唤 ≠ 触发器** —— 那是**结算轴的一种效果**（生成一个单位），可以被触发调起、也可以直接由法术调起。<br>**触发器本身只做一件事：把"投射物所在的位置"当作一次新的施法起点。** |

数据形状（写在宝石里；子块独立成节，便于解算与限深）：

```xml
<Modifier id="gem_trigger" stage="投送">
  <Set field="on_hit_cast" sub="sub_fireball" />
  <Sub id="sub_fireball">
    <Base spell="projectile_yinmo_zhan" />        <!-- 子法术的基础术 -->
    <Gems>gem_homing gem_pierce</Gems>            <!-- 子法术自己的修正（不继承外层） -->
    <Scale damage="0.5" count="1" />              <!-- 子法术自己的缩放 -->
  </Sub>
</Modifier>
```

**完备性判据（§16.1：拿 Noita 招牌修正逐个对照）** —— **全部能用现有属性 + 五种操作拼出来**：
伤害强化 / 暴击 / 加速减速 / 轻重互换 / 弹跳 / 穿透 / 钻地 / 追踪 / 反重力 / 延长寿命 /
元素拖尾 / 爆炸 / 触发器 / 定时器 / 伤害均分 / 巨大化 / 多重施法 —— 均已落成宝石（`Modifiers.xml`）。
**没做的只有两样**，都在计划里明说不做：**回旋 / 环绕 / 链式**（要的是新的运动模式，不是新属性）。

**与计划的偏差（4 条，都带理由）**

| # | 偏差 | 理由 |
|---|---|---|
| 1 | **浮动与暴击做成"数据开启"**（默认关），而不是像 §24 第 6 条那样直接改公式 | 阶段 5 验收第 2 条是"**旧 6 条法术行为零变化**"——直接改公式会当场破这条。机制照采纳（`damage_variance` 0.75~1.0 随机 + 暴击 ×2），开关交给数据 |
| 2 | `leave_surface` **字段已登记，但没有读取点会真的造地表** —— 命中时打一条"要等阶段 8"的告警 | §16.5 把"留地表"归到 D 组（等后面的层）。字段先进表是为了数据能写、拼错的字段能被体检抓到；**告警是刻意的**：免得数据作者以为自己配错了 |
| 3 | 补了一个计划没列的字段 `damage_variance` | 第 1 条那个"浮动"要有地方放（属性表缺东西 ⇒ 补属性，不是加特例） |
| 4 | 触发口径写死：**`on_hit_cast` 只在"真的停下来的那一击"响**，弹跳那一拍响的是 `on_bounce_cast` | 不然一颗弹跳弹会把命中触发器连响 N 次（§16.4 没说这一条，这是落地时发现的语义空洞） |

**顺手修掉的一类坑（"有效定义是副本"带来的引用比较陷阱）**
阶段 5 之后，手里拿的 `SpellDef` 可能是**解算出来的副本**（配了宝石时）—— 代码里原来有两处拿**引用**比法术，两处都会静默失效：

| 在哪 | 原来的写法 | 后果 |
|---|---|---|
| `SpellCastInput`（蓄力/引导中） | `wielded != _spell` = "换法术了 = 打断" | **一蓄力就被当成换了法术、当场打断** —— 配了宝石的人**完全放不出法术** |
| `SpellStatusManager`（持续状态） | `_active[i].Spell == spell` = "同法术刷新时长不叠伤害" | 永远判为"不同法术" ⇒ **同一条 DoT 连打几发叠成秒杀**（契约 3 的同源问题） |

修法 = 统一走 `SpellDef.SameAs(other)`（**比 id 不比引用**，一处实现两处用）。
🔴 **教训**：给一个 DTO 加"解算副本"这条路之后，凡是拿它做身份判断的地方都要复查一遍。

**还修了一个"反重力根本不存在"的坑（2026-09-28，用户试出来）**
`ProjectileDelivery` 里原来写的是 `-_velocity += -Math.Abs(gravity)` —— **负号被绝对值吃掉**，
`gravity="-25"` 写进去照样往下掉（当初的注释还写着"免得有人写负号还以为是反重力"）。
⇒ 阶段 1 那条"重力恒向下"的旧决定**与 §16.1 的 Noita 对照表冲突**（那儿反重力是 `gravity += / ×`），已改成**带符号**：
**正 = 往下掉 · 0 = 平飞 · 负 = 往上飘**；`SolveLaunchVelocity` 对负重力**不平抛解算**（直接照瞄准方向打出去，
让向上的加速度自然把弹道抬起来；硬解抛物线会算出一个"先往下压"的发射角）。
配套宝石三颗：`gem_gravity`（+25 抛物线）/ `gem_zerog`（0 平飞）/ **`gem_antigrav`**（`Mul -1` 反向 + `Add -20` 保底抬升
—— 只反向的话，平飞法术的 0 × (-1) 还是 0，"反重力"看上去什么也没发生）。

**还没做的（按计划就是后面的事）**：装配界面（阶段 10）· 查克拉（阶段 6，`cost_add` 已在数据里登记但没人读）·
解锁凭证检查（代码已写，`Modifiers.xml` 的 `item=` 还空着 —— 填了物品就自动生效）· 宝石的物品定义（阶段 9）。

**这一版必须实机验的（下次进游戏按顺序）**

| # | 验什么 | 判据 |
|---|---|---|
| 1 | 三条命令能跑 | `custom.spell mods` 打出 30 颗宝石 · `custom.spell gem` 打出 `slots=3 (bracelet 3 + ninjutsu 0)` |
| 2 | **配装 → 放法术 → 行为变了** | `custom.spell gem 0 gem_multi` → `custom.spell build projectile_yinmo_zhan` 打出 `count=3(was 1)` → 按 X 放一发是**三发** |

## 二十五、元素状态（燃烧 / 冰冻 / 触电 / 中毒）

> 2026-10-07 立。**这一节回答"一个人身上着火 / 结冰 / 触电 / 中毒"怎么做。**
> 法术只是触发它的一种方式（陷阱、地表、环境将来走同一条路）。
> 冰冻的**实机部分已完成**（§25.5），这一节把它和另外三个收进同一套。

### 25.1 先回答"粒子够不够"

**视觉上够 —— 但"状态"不只是视觉。** 四种里只有冰冻要动材质（整个人换成冰），
另外三种观感全靠粒子 + 光 + 动作，**不需要任何新资产**。

粒子给不了的三件事，才是这一节真正要写的：

| # | 缺口 | 不管会怎样 |
|---|---|---|
| 1 | **挂载**：粒子得挂在**骨头上**，不是跟着坐标飘 | 现在 `SpellStatusManager` 是"空实体跟坐标走"——人一转身 / 爬梯子 / 骑马，火就在旁边飘 |
| 2 | **光**：燃烧、触电要**照亮周围** | 不发光 = 夜里看着像贴上去的纸片 |
| 3 | **动作**：触电抽搐、中毒踉跄、燃烧拍打 | 粒子只管外观，人该有的反应得动画给 |

第四条是状态本身（掉血 / 减速 / 禁行动 / 叠层 / 免疫 / 存档），现在是硬编码在法术上的，要改成读表。

### 25.2 四种状态各长什么样（一张表写完）

| | **燃烧** | **冰冻**（已落地） | **触电** | **中毒** |
|---|---|---|---|---|
| **视觉** | 火焰粒子，挂胸 / 头 / 手三处 | 材质换冰（甲 / 头盔 / 手脚 / 武器） | 电弧粒子，短促爆发反复播 | 绿雾 + 气泡，低空绕身 |
| **光** | 暖橙跟随光，带闪烁 | 不要 | 冷白跟随光，高频闪 | 不要 |
| **动作** | 慌乱：拍打 / 乱跑，打断当前行为 | **定格**（骨架暂停 + 停 AI） | 抽搐：短动作反复打断 | 踉跄 / 捂腹 |
| **机制** | 快而疼的每秒掉血 + 移速乘子 + 点燃脚下地表 | 不能动、不能施法 | 麻痹（不能行动）+ 短时减速 | 慢速长时 DoT + 命中 / 视野减益 |
| **怎么收尾** | 火苗熄灭 + 留焦痕（走地表） | 解冻 + 碎冰粒子 | 电弧消失 | 毒雾散去 |

**一句话**：三种靠粒子，冰冻靠材质；四者共用同一套"挂载 / 光 / 动作 / 结算"。

### 25.3 共用件（做一次，四种状态全通用）

| 件 | 做什么 | 现状 |
|---|---|---|
| **挂载件** | 骨挂粒子 + 摘除 | 🔴 要新写。`MBAgentVisuals.CreateParticleSystemAttachedToBone(粒子, 骨索引, 骨局部帧)` —— **本项目已实机验证可见**（飞行腿上的特效用过）；摘的时候 `Skeleton.RemoveComponent(组件)`，不摘会残留 |
| **光件** | 跟随光源实体（跟着"视觉中心"走，不是原点） | 做法现成（`Knowledge/SwordBeam剑气_实现分析.md` 里那份） |
| **动作件** | 每种状态一组动作 + 优先级 | 接现有 `Animation/` 状态机（注册制，加状态=加一行）；抢通道的问题按它已有的纪律处理 |
| **结算件** | 掉血 / 移速 / 禁行动 / 叠层 / 免疫，全部读表 | 把 `SpellStatusManager` 从"值写在法术定义上"改成"值读 `Statuses.xml`" |

### 25.4 数据（`AssetRegistry/Statuses.xml`，一行一状态）

| 列 | 说明 |
|---|---|
| `id` / 显示名 / 图标 / 颜色 | 状态身份与 UI |
| `duration` / `tick_interval` / `damage_per_tick` / `damage_type` | 结算 |
| `speed_multiplier` / `can_act` / `can_cast` | 机制限制（`Agent.SetMaximumSpeedLimit(倍率, true)`；清掉传 `(-1, false)`） |
| `particles`（可多条：粒子名 + 骨 + 局部帧） | 视觉 |
| `light`（颜色 / 强度 / 闪不闪） | 光 |
| `actions`（动作名 + 优先级 + 间隔） | 动作 |
| `stack_rule`（刷新时长 / 叠层 / 上限） | 叠层 |
| `immunity_tags`（免疫标签，如"火元素抗性"） | 免疫 |

**判据**：加一种新状态 = 加一行 XML，不改代码。改观感 = 改 XML。

### 25.5 与现有代码怎么接

| 现状 | 目标 |
|---|---|
| `SpellStatusManager`：值写在 `SpellDef`（`StatusDamage` / `StatusInterval` / `StatusParticle`…）、粒子挂**空实体** | 值读 `Statuses.xml`；粒子改**骨挂**；一套管理器服务所有状态 |
| 🔴 **冰冻（`Combat/IceFxBehavior.cs`，今天做的）**：独立一套，走 `custom.ice` | **收编成表里的一行**：`freeze` = 定格件 + 材质件 + 霜粒子。控制台命令保留（`custom.ice` 继续能用），但内部改走同一张表 |
| 无叠层 / 无免疫 / 不存档 | 按 §25.4 的 `stack_rule` / `immunity_tags` 补；**是否存档按"状态要不要跨战斗"逐条定** —— 战场内状态（燃烧、触电）不存档，跨战斗的长期状态（中毒）才存 |

**清理纪律**（照抄别处踩过的坑）：agent 死亡 / 离场必须摘粒子与光；场景卸载全清；状态到期与被打断都要走到同一条"摘干净"的路上。

### 25.6 分几步做

| 步 | 内容 | 做完能看到 |
|---|---|---|
| **A** | 挂载件 + 结算件读表（先不动动作和光） | 四种状态的**粒子**都能挂在人身上跟着动，掉血/减速按表走 |
| **B** | 光件 | 燃烧的人夜里真的照亮周围 |
| **C** | 动作件接 `Animation/` | 触电抽搐、中毒踉跄、燃烧拍打 |
| **D** | 冰冻收编 + 叠层 / 免疫 / 存档口径 | `custom.ice` 变成"状态系统的一个入口" |

### 25.7 验收命令

```
custom.status on  burn|freeze|shock|poison [目标]    ← 上状态（默认目标 = 准星指着的人）
custom.status off burn|freeze|shock|poison [目标]    ← 单独摘一个
custom.status off                                    ← 全部摘干净
custom.status list                                   ← 谁身上有什么 + 剩余时间
custom.status probe  [目标]                          ← 只查不改：粒子/光/动作各自挂上没有
```

分步可见（这是纪律）：`probe` 必须能分别报出**粒子挂没挂、光挂没挂、动作有没有抢到通道**，
否则出了问题只能看"整体像不像"，没法定位。

### 25.9 实验记录：冰冻（2026-10-07 · 实机）

> 这一节是**已经跑出来的事实**，不是设想。代码落点：
> `Combat/IceFxBehavior.cs`（本体）+ `CampaignMode/Tools/IceFxCommands.cs`（控制台入口），命令 `custom.ice`。

**做成了什么**

| 项 | 结果 | 用的机制 |
|---|---|---|
| **只冻他一个**（动作停住、旁边的人照常走打） | ✅ 实机通过 | 三条一起上：`GameEntity.PauseSkeletonAnimation()` + `Skeleton.Freeze(true)` + `Agent.SetIsAIPaused(true)`；目标是玩家时再加 `V.SetPlayerControlFrozen`。四条都有逆操作，`off` 逐项还原 |
| **把他身上的甲 / 头盔 / 手脚 / 武器换成冰** | ✅ 实机通过（截图确认） | 复制原材质 → 换 diffuse **两个槽** + 法线 + 高光（用游戏自带的 `ice_a_d/_n/_s`）→ 加 `self_illumination` → `mesh.SetMaterial(副本)`。25 个网格、**4 份材质副本**、耗时 1ms |
| **头 / 脸也变冰** | ❌ 判死（见下） | — |

**今天的硬事实（写下来省得重挖）**

1. **角色网格挂在三处，缺一不可**：① 实体树的 MetaMesh 组件 ② **骨架自己的组件**（甲 / 头盔在这一处）③ 逐骨挂件。
   第一次只走了① —— **只找到 3 个网格，甲一个都没扫到**，所以"看着没反应"。
2. **"身体 + 头"那件在 native 私有区**：三处都枚举不到（手 `hands_male_a`、脚 `feet_male_a` 枚举得到，身体和头不行）。
   native 接口只有 `AddMultiMesh` / `RemoveMultiMesh`，**两个都要指针、没有 getter** ——
   引擎自己加 banner 标签也是自己存字典（`_agentMeshes[agent]`）。
3. **`MBAgentVisuals.ReplaceMeshWithMesh(old, new, type)` 的真身 = "删一个 + 加一个"**，两边都能传 null
   ⇒ **不交出旧指针也能往某个部位"加"网格**（冰头就是这么贴上去的）。
4. **每个角色的网格是各人一份的副本**（引擎建角色视觉走 `MetaMesh.GetCopy`，反编译实证）⇒ 换材质理论上不串。
   ⚠️ 但有反证线索：日志里见过 `xxx(copy)(copy)` 这种材质名（说明复制时它已经是副本了）——
   **负向检查还没做**，见下面的未验清单第 1 条。
5. 🔴 **别给网格写帧**：`MetaMesh.Frame` / `Mesh.SetLocalFrame` 会把**蒙皮绑定冲掉**
   （实机：整颗头飞到半空，不跟骨头了）。缩放这条兜底路就此判死。
6. **换上去的一瞬间角色透明一下**：CPU 侧只花 **1ms**（有计时日志），所以不是我们在算东西，
   是渲染管线重建 —— 多半是 `self_illumination` 造出的 **shader 新组合要现编**。
   想验：`custom.ice tint .72 .88 1 0`（关掉发光）再上一次，看还闪不闪。

**头为什么判死**：抄来的头副本**形状跟真头对不上**（真头带捏脸数据；自定义头更是整套换过）⇒ 真脸从冰头里穿出来；
想放大兜住又踩了第 5 条。**查真名这条路也堵着**：皮肤的 `race → 头网格` 映射在 native 里，
且换头模块是拿 `skins.xslt` 改写 Native 的 skins.xml 的 ⇒ 照原文件查表只会查到被改之前的名字。

## 附录 D · 为什么弃 `flying_mesh`：**约 110 米必定剔除网格**（2026-09-23 裁定 ✓ 已落地为自管实体）

> 本文 §一 第 3 条与 wheels 都引用这条 —— **原文保留**，别再重推一遍。

**D.1 证据链（七次实机，每条都实测过）**

| # | 实验 | 结果 | 得到什么 |
|---|---|---|---|
| 1 | 月牙（1 档 LOD）当弹 | 飞出一小段就看不见 | 起点 |
| 2 | 放大 5 倍（19 米） | 照样消失 | ❌ 排除"太小看不见" |
| 3 | 加 `MissileWithPhysics="true"` | 照样消失 | ❌ 排除"非物理刚体" |
| 4 | 补 LOD 到 7 档 | 消失点从 ~8 米推到 ~110 米 | 方向部分有效 |
| 5 | 补 LOD 到 8 档（含表尾档） | 仍是 ~110 米 | ❌ **表尾之外不看资产** |
| 6 | 拿原版建筑网格当弹（LOD 链完整） | 同样消失 | ❌ 排除"我们月牙资产的问题" |
| 7 | 原版网格挂**场景实体**（诊断件的"陪飞影子"） | 一直可见 | ✅ **场景实体路径没这个上限** |

⚠️ 第 7 条有一次测量污染：影子默认带火焰拖尾粒子，**粒子不受剔除影响** —— 复验时先关（`alt_particle off`）。

**D.2 机制（反编译 + 实机实证）**

- 引擎有一张**全局 LOD 距离表**：`GameEntity.GetLodLevelForDistanceSq` 在 9.6 / 15.4 / 21.1 / 32.5 / 43.6 / 88 / 116 米处依次返回 1..7
  ⇒ 阈值约 **8 / 12 / 17 / 24 / 35 / 51 / 74 / 108 米**（随画质设置缩放）。
- **表尾之外（返回值 7）= 剔除**；`Meta Mesh Editor` 第 8 档显示 `until -2147483648m`（未初始化哨兵）说的是同一件事。
- **原版弹丸网格全部只有 1 档 LOD**（`bolt_bl_flying` / `projectile_rock` / 霰弹碎片，实测均 1 子网格 @LOD0）
  ⇒ "档数"从来不是我们与原版的差别：**原版只是从没飞过 110 米**，这个上限从不显形。
- 结论：**别在导弹管线上跟 LOD 表较劲**（补档只能把撞表尾的时间往后推，推不出表）。

## 附录 E · 原版参照机：`RangedSiegeWeapon` 的完整阶段机（反编译实见）

原版器械上有一台完整分阶段状态机（`RangedSiegeWeapon.cs:40` 定义，推进在 `OnTick :951`，
`AddCustomMissile` 在 `:1641`）：

```
Idle → LoadingAmmo → Reloading ↔ ReloadingPaused     ← 装填可暂停 = **蓄力保持的原生对应物**
     → WaitingBeforeProjectileLeaving                ← 发射前一刻 = **放爆发/枪口特效的钩子**
     → Shooting（AddCustomMissile 在这）→ WaitingAfterShooting → Idle
```

**怎么用**：
① 我们的相位机（`SpellCastInput`）已经自己实现了「蓄力 / 引导 / 瞬发」，**不用抄它**；
② 但它的两个**语义对应物**值得记住 —— **能暂停的装填**就是"蓄力保持"，**发射前一刻那个状态**是该挂爆发特效的地方
（我们现在把爆发挂在"松手 / 左键"那一拍，等价）；
③ 真要做**多段法术**（蓄力→发射→二段）时，照它的**结构**抄（状态枚举 + `OnTick` 推进 + 每状态副作用），
**别抄类** —— 那台机器挂在 `UsableMachine` 上，是攻城器械，不是法术。
