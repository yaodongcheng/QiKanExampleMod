### A4. 🔴 结案：施法动作在"通道 1（上身）"上不播 —— 根因 = **导入的 clip 缺元数据**（2026-09-24）

**一句话**：骑砍的两条动画通道里，**通道 1 会挑 clip 的元数据**；我们从 TRF 导入的 clip 那几项是空的/0，
于是"收下了、时长也读得到、就是不播"（零报错）。**照原版把四项填上就通了** —— 实机已验证（播了）。

**四项对照（原版参照 = 原版自己用通道 1 播的 `act_command_unarmed` → clip `anim_command_unarmed`）**：

| 字段（ModKit 的 Animation clip 面板） | 原版 | 我们的（导入后） | 修后 |
|---|---|---|---|
| **Priority** | 2.000 | **0.000** | 2.000 |
| **Right hand pose** | 4.000 | **3.000** | 4.000 |
| **Blend out period** | 0.500 | **0.000** | 0.500 |
| **Flags → `allow_head_movement`** | 勾 | **没勾**（`magic_idle` 只有 `cyclic`） | 勾 |
| （Left hand pose / Blend in period / Continue to action / Loading Type / Param1~3 本来就一致） | 3 / 0.3 / 空 / Always keep in memory / 0 | 同 | 同 |

**修法（编辑器里 4 步，一次一个 clip）**：打开 clip → Priority=2 · Right hand pose=4 · Blend out period=0.5 · Flags 勾 `allow_head_movement` → Publish →
产物改名拷进 `Taikou/AssetPackages/lwn_taikou_anim.tpac`（见 §B 同款流程）。
⚠️ **蓄力那条要保留 `cyclic` 勾**（循环靠它）；`allow_head_movement` 对我们是加分项（配合"头看相机"那套，见 §A2）。

**两条我自己判断错的（记下来别再犯）**：
1. ❌ "带 `cyclic` 的 clip 会被通道 1 拒绝" —— **证伪**：`act_cast_projectile` 一个 flag 都没勾，一样不播。
2. ❌ "别传 `anf_enforce_lowerbody`（那是扩大覆盖面，与只改上身相反）" —— 那是**望文生义的猜测**，未经实测；正好相反的可能性同样成立（见下）。

**"只动上半身"还没做到**（现状与下一步见 **§A5**）：

| 事实 | 说明 |
|---|---|
| 🔴 **引擎没有"每骨权重/遮罩"接口** | `Agent` 上只有**只读**的 `GetActionChannelWeight`（整条通道，非每骨）；**没有 `SetActionChannelWeight`**；`SetActionChannel` 的参数里没有任何骨骼/权重项；`AnimFlags` 里那两个 `anf_animation_layer_flags_*` 是**无人消费的死常量**（全库检索过）。⇒ UE 的 `Layered Blend Per Bone` **在这引擎里不存在**，粒度只有"通道 0 全身 / 通道 1 上身"两档 |
| 唯一没试的旋钮 = 两个 flag | `custom.anim_ch 1 act_cast_charge lowerbody` / `all`（通道 1 现在能播了，**这两个开关位值得当场试**）|
| 还没搞清的一条 | 原版 clip 放通道 1 时**腿也跟着动了**（本该只有上身）⇒ 说明"通道 1 = 上身"不是无条件的：要么 flag 管，要么**clip 里含哪些骨就驱动哪些骨**（下层不接管缺失的骨）|
| 兜底方案（可靠） | **离线烘"只含上半身"的 clip**：把腿/骨盆的轨道剔掉（或让它们等于飞行基准），通道 1 播它时腿自然归通道 0 管。工具 = `tools/anim-retarget`（飞行那 20 条就是这么增量合成的），加一步"剔骨"是机械活 |

### A5′. 🔴 机制查明 + 前一版测试无效（2026-09-24 晚）

**① 机制（写在官方 flag 文档里，不是猜）** —— 上下身分离是**引擎默认**，靠两条 flag 反向控制：

| flag | 官方原文 | 含义 |
|---|---|---|
| `enforce_lowerbody` | *Prevents previous channel and movement animations to be played during this animation* | 不带它 ⇒ **下半身继续由「上一个通道 + 移动动画」驱动**，只有上身归当前动作 |
| `enforce_all` | *Valid for channel 0 only. Prevents channel 1 and movement animations…* | 通道 0 的"我全占"开关 |

👉 **挥刀那几条 clip 都不带 `enforce_lowerbody`**（实测：`quick_release_slashright_1h` = `client_prediction` + `enforce_root_rotation`）
—— 这正是"边走边挥刀、腿照走"的机制：**刀只在通道/上身层，腿归移动动画**。
"移动动画"是一整套独立子系统：`movement_sets.xml`（每方向一套走/跑 + `*_adder` 叠加件）+ `full_movement_sets.xml`，由速度驱动。

**② 战斗挥刀那条链在 native 里，读不到** —— `TaleWorlds.MountAndBlade.dll` 与 `SandBox.dll` 全库搜 `SetActionChannel`：
命中的只有器械（弩炮/投石机/冲车）、嘲讽、喊命令、欢呼、胜利欢呼，**没有任何"攻击动作"的调用点**；
`ItemUsage` 类型在 C# 侧根本不存在 ⇒ 攻击动画由 native 自己选通道（社区文档说是通道 1："channel 1 is for combat anims"）。

**③ 🔴 前一版测试（`custom.anim_ch 1 …` 看到"腿也变了"）证明不了任何事** —— 找到原因：
`PlayerFlightBehavior` 的"守通道 0"（把飞行姿势补回通道 0）原来**只在 `SpellCastInput.IsPlayerAiming`（我们自己施法）期间跑**，
`custom.anim_ch` 手验**根本不走这条路** ⇒ 通道 0 被清掉也没人补，腿当然变。
**已改**：只要在空中就每帧守（新开关 `FlightTuning.GuardChannelZero`，默认开），日志改成
`[Flight] 通道 0 空了，已补回飞行姿势（第 N 次）`。**改完才谈得上"通道 1 是否遮罩"**。

⚠️ **编译踩坑记录**：这个老式 csproj（`ToolsVersion=15.0`，非 SDK 风格）用 `dotnet build` 是**假成功**
（0.8 秒返回 "Build succeeded"，其实什么都没编）；真编译用
`D:\Program Files (x86)\VSIDE\MSBuild\Current\Bin\MSBuild.exe <csproj> -p:Configuration=Debug`。

**④ 候选动画（离线量测，见 §A5 的"第 2 步怎么敲"表）** —— 全库 5623 条里，"窗口内腿不动"的人形动画只有 81 条；
其中绑了动作名、像施法的已列出。**参考量**：原版自己用在通道 1 的 `act_command_unarmed` 腿动 **68°**、
`act_cheer_1` 腿动 **36°** ⇒ 原版并没有"通道 1 专用、只写上身的动画"。

**⑤ 🔴 飞行中"腿被挥手动作抢走" = 优先级（2026-09-25 实机 + 离线改包）**

**⑦ ✅ 结案：`enforce_lowerbody` 加在【下层】= 上下身分离（2026-09-25 实机验证通过）**

```
飞行姿势（通道 0）带 enforce_lowerbody  →  它的下半身归它（腿 = 飞行姿势）
施法手势（通道 1）                     →  照旧管上身（手在动）
结果：上下身分离 ✓（用户实机确认）
```

**机制全貌（这一轮把所有错解都排除后的定论）**：

| 事实 | 证据 |
|---|---|
| 通道 1 固定在通道 0 上面（默认覆盖全骨） | 状态探针：两条都 w=1.00 时腿跟通道 1 |
| 优先级与分层无关 | 改 clip Priority 0→30 无效 |
| 通道 0 从没被清、权重一直满 | 状态探针 `ch0 w=1.00` 全程不变 ⇒ **"守通道 0 / 补写"是治不存在的病** |
| 地面能分离 = 因为还有一层"移动动画"压在最上面管腿 | 地面挥手腿照走 |
| 🔴 **flag 必须写进 clip 元数据才被引擎认**；运行时用 `additionalFlags` 传（`lowerbody`/`all`/`prio=NN`）**从未生效** | 三次实机都无反应 vs 写进包立刻生效 |
| `enforce_all`（加在下层）= 把通道 1 **整个挡住**（"谁都别动我"） | 实机：全身动作都不显示 |
| `enforce_lowerbody`（加在下层）= **"我的下半身归我"**，上层照旧管上身 | ✅ 本轮结案 |

**落地的两件收尾**：

**✅ 最终验收（2026-09-25 用户实机）**：飞行中**按住右键蓄力 ⇒ 腿保持飞行姿势、上身做施法手势**（不再被抢）。

### B. 粒子为什么进不来 —— **根因已查明**（2026-09-24），**当天已解决**

> ✅ **2026-09-24 晚结案**：不再走"编辑器 Publish"那条路 —— 改成**纯离线编译**：
> `tpaccli particleimport --xml … --packdir <原版包目录> [--split]` 直接把我们的 XML 编成
> tpac 里的 `Particle` 资产（编辑器里已看到 `lwn_yinmo_trail` 的 5 个 emitter 全部正常）。
> **完整链路、XML→二进制字段映射表、踩的七个坑** → [Knowledge/骑砍2粒子系统.md](../Knowledge/骑砍2粒子系统.md) **§十二**。
> 下面这段保留作"为什么要这么干"的证据链。

**结论**：引擎**运行期**的粒子表来自 **AssetPackages 里的 `Particle` 资产**（编译产物）。
`ModuleData` 的粒子 XML + `project.mbproj` 的 `soln_particle_systems` 注册只是**编辑器源**，运行时**不读** ——
所以我们那份 XML 挂得再对，游戏里也永远查不到名字（实测正是如此：零报错、静默失败）。

## 一、结论（先说做什么）

| # | 决定 | 理由 |
|---|---|---|
| 1 | **法术 = 四段拼装**：起手 / 瞄准 / 投送 / 结算 | DOS2 的 15 个形态不是 15 套系统，是这四段的组合；虚幻引擎里「投射物」也是同一个切法（Actor + 移动组件 + 碰撞 + 命中后效果） |
| 2 | **阶段 1 只做「投射物」一种投送方式** | 一阶段只做投射型法术 |
| 3 | **投射物不走引擎导弹，自管实体**（自己造、自己推、自己判命中） | 承接 2026-09-23 裁定：引擎导弹的渲染约 **110 米必定剔除网格**（证据链见法印计划 §16.2，七次实机实验） |
| 4 | **起手用「法印 = 远程武器」当脚手架**（抬起 → 瞄准 → 释放），🔴 **明确标为临时壳** | 引擎白送瞄准姿势、准星、弹药消耗、开火音效 —— 阶段 1 最快见效果的路径。**但自建投射物之后它不再必需**：阶段 3 换成我们自己的相位机（§5.1），换的时候投射物那一层一行不用改 |
| 5 | 🔴 **引擎那颗导弹要拦掉** —— 用 Harmony 前缀拦住 `Mission.OnAgentShootMissile`，改发我们的实体 | 不拦 = 有一颗**看不见的弩矢**同时飞出去，会撞到人、触发格挡与受击反应 = 出戏 |
| 6 | **伤害仍走引擎全管线** —— 复用现成轮子 `AgentDamageHelper.CastBlow` | 护甲、减伤、死亡判定都在 `RegisterBlow` 后面，白送；不用自己写伤害模型 |
| 7 | **法术数据放内容包** `ModuleData/AssetRegistry/Spells.xml`，格式照 `FirearmFx.xml` | 三单元架构（逻辑进 LWN、数据进内容包）；`AssetRegistry/` 是既有目录，不新开目录 |
| 8 | **阴魔斩 = 阶段 1 的验收件**，不新增法术 | 网格 / 贴图 / 材质 / 粒子四样都已做好，只差接线（见 §七） |
| 9 | 🔴 **三个接口的"契约"现在就写对**（见 §3.2）：瞄准产出**一张表**、投送**有生命周期**、结算**只认单次命中** | 龙之信条的多目标火球、艾尔登法环的彗星亚兹勒都卡在这三条上。**现在写对是免费的；阶段 2 才发现就是三轴同时返工** |
| 10 | **四段之上再加一层「法术族预设」**（见 §2.4）：常用组合固化成族，配表时选族填块 | UE 的 FlexibleCombatSystem 用 14 个族落地了整套法术系统 —— 证明这样配表最省、最不容易填错。**底层仍是可组合的四段**，所以比它灵活 |

**不做什么（本计划边界）**：不做地面瞄准圈 UI（**投射族不需要；等做放置族时它是必备件、不是打磨项**，见 §3.6）；不做技能槽与冷却（UE 那套里冷却属"组件级"，也不挂在法术行上）；不做 NPC 施法者（但核心函数从第一天就写成"不关心施法者是谁"，见 §十）。

**"以后要加"的，本阶段只负责把位置留对**：追踪、多发、软锁、落点、持续光束 —— 这些**不在阶段 1 实现**，但它们的接口契约在 §3.2 一次定死，阶段 2/3 只填实现、不动已写的代码。

**代价（一次说清）**：旧路线（把法术伪装成弹药）引擎包办了飞行、碰撞、插地、寿命 —— 代价是**全都不可调**（寿命写死、半径只有两档、朝向算不了），而且 110 米外直接隐形。换成自管之后，这些**全部由我们写**（约 250 行），换来的是**全部可调**。这是本计划唯一真正的取舍：**用一次性代码量，换全部参数的控制权**。

## 二、总模型：一个法术 = 四段拼装

### 2.1 四段（每段回答一个问题）

| 段 | 代码里的轴 | 回答的问题 | 大白话 | 阶段 1 实现 | 以后可加 |
|---|---|---|---|---|---|
| **起手** | Trigger | 谁、什么时候、什么姿势放出去 | 抬手结印 → 蓄力 → 推出 | 法印（远程武器的引擎流程） | **三种施法方式**（有前摇 / 按住持续 / 瞬发）、蓄力档位、被打断、输入缓冲、NPC 起手 |
| **瞄准** | Targeting | 法术往哪去 | 看哪打哪 / 锁谁打谁 / 点地打地 / 以自己为心 | **准星直视**（方向施法） | 软锁（可锁 N 个目标）、落点、自身为心 |
| **投送** | Delivery | 从施法者到落点之间怎么过去 | 直线飞 / 抛出去 / 追着跑 / 从天而降 / 一直照 | **直线飞行**（自管实体） | 追踪（一个参数）、多发、天降、持续光束、瞬时射线、位移 |
| **结算** | Payload | 到了之后发生什么 | 单体掉血 / 一片掉血 / 中毒减速 / 地上留火 / 召唤 | **单体伤害 + 半径伤害** | 状态、地面持续区域、光环、连锁传导、召唤 |

**为什么这么切**：DOS2 做 15 个形态用的是同一批字段的排列组合（`AreaRadius` / `Angle` / `Range` / `StrikeCount` / `Template`…），不是 15 套代码；虚幻引擎的投射物同样是「移动组件（怎么飞）+ 碰撞组件（撞到什么）+ 命中后的效果（撞了干什么）」的组合。按这个切法，**新形态 = 在某一轴加一个插件**，其余三轴原地不动。

### 2.2 DOS2 十五形态 = 四段组合（这张表就是"以后兼容更多类型"的凭据）

| DOS2 形态 | 起手 | 瞄准 | 投送 | 结算 | 本框架要新增什么 |
|---|---|---|---|---|---|

### 2.3 四段各自的"参数长什么样"

| 轴 | 参数（都写在数据里，不写死在代码里） |
|---|---|
| 起手 | 用哪把法印、要几档蓄力（阶段 3） |
| 瞄准 | 准星 / 软锁（锁定的最大角度、锁定距离、**最多锁几个**）、落点（最远距离） |

### 2.4 四段之上：法术族预设（给配表用，不给代码用）

底层四段是**可自由组合**的；但配表时**不该让每一行都填八个轴字段** —— 把常用组合固化成"族"，一行选一个族、只填该族的块。

| 族 | 四段组合 | 该族专属参数 |
|---|---|---|
| **投射** | 准星或软锁 → 直线飞 / 抛物 / 追踪 → 命中结算 | 速度、重力、转向速率、发数、命中半径、可穿透数 |
| **引导** | 起手按住 → 持续存在 → 按间隔重复结算 | 引导粒子、转向 |
| **天降** | 落点 → 从上方落下 ×N → 范围结算 | 发数、散布、起落高度 |
| **放置 / 区域** | 落点 → 持续存在 → 按间隔重复 + 半径 | 半径、**重复间隔**、**持续时长** |
| **移动** | 落点 → 自己走 + 漂移 → 沿途结算 | 移动速度、漂移半径 |
| **符文** | 落点 → 留在世界上 → 踩中触发结算 | 触发半径、存不存档 |
| **增益** | 自身或软锁 → 瞬时 → 给状态 | 加什么属性、数值、时长 |
| **治疗** | 自身或软锁 → 瞬时或持续 → 回血 | 回血量、是否持续 |
| **召唤** | 落点 → 瞬时 → 生成实体或武器 | 生成什么、持续多久 |
| **变形** | 软锁 → 瞬时 → 换模型换属性 | 换成什么、时长 |
| **传送** | 落点或软锁 → 位移 → 落点效果 | 位移方式 |

🔴 **命名规约（抄 UE 那套）：族名当法术 id 的前缀** —— `projectile_yinmo` / `place_firepit`。
配表时一眼看出是什么族，也防止把 A 族的字段填进 B 族。

🔴 **我们的族比它粗**：它 13 个族各写一个类，其中「区域·一次性」和「区域·按间隔」是两个族（`PlaceDmg-*` / `PlaceTick-*`）；我们是**一个"放置"族 + 一个重复间隔参数**。因为它必须一个族一个类，我们的族只是预设。

**这条是从 UE 那套系统抄来的**（[FlexibleCombatSystem 分析](../Knowledge/FlexibleCombatSystem施法设计_UE实现分析.md) §二）：它用 13 个族落地了整套法术系统（60+ 个法术），配表一行选一个族、只填该族那一块。

🔴 **我们比它多一条**：它的族是**互斥单选**（一行只能填一个族块），我们的族只是**预设**，底层四段仍然可组合。所以它得写两个类来表达「区域·一次性」和「区域·按间隔」，而我们只是**一个"重复间隔"参数**。

## 三、三套外部设计的对照（龙之信条 · 艾尔登法环 · UE 实装工程）

### 3.1 结论先给

| 例子 | 当前四段框架兼容吗 | 要补什么 |
|---|---|---|
| 龙之信条 **多目标火球**（六连 / 十连，每发追一个目标） | ✅ 模型兼容 | 投送轴加「**多发 + 追踪**」两个参数；瞄准轴的产出必须是**一张表 + 目标引用**（§3.2 契约 1） |
| 龙之信条 **选定目标的雷电术**（软锁 → 天雷落到目标头上） | ✅ 模型兼容 | 瞄准轴加「软锁」；投送轴加「天降」。**阶段 2 本来就排了软锁** |
| 艾尔登法环 **彗星亚兹勒**（按住持续喷射的光束） | ⚠️ 模型兼容，但**三条契约要现在写对** | 不需要加第五段；要 §3.2 的三条契约 + 阶段 3 的"施法中"状态机（§3.5） |
| （顺带核对）陨石群 / 火墙 / 雷电领域 / 龙卷风 · 星雨 / 岩石弹 / 白金之雨 / 海马炮 / 夜雾 | ✅ 兼容 | 全是已有四段的参数组合，逐条见 §3.4 |

**一句话**：**四段模型本身一行不用改** —— 没有一个例子需要在轴上增加"第五段"。真正要改的是**三个接口的契约**（§3.2），而这三条**只有现在改才便宜**。

### 3.2 🔴 必须现在写对的三条契约

| # | 契约 | 写错了会怎样 | 现在怎么写 |
|---|---|---|---|
| **1** | **瞄准的产出 = 一张"施法意图"表，不是"一个方向"** | 做多目标火球时才发现瞄准接口只能产出一个方向 → **瞄准 / 投送 / 结算三处一起返工** | 产出 `List<SpellCastIntent>`，每条 = 起点 + 方向 + **可选的目标引用** + 序号。**阶段 1 恒为 1 条**，但接口形状按表写 |
| **2** | **投送 = 一个有生命周期的对象（进入 / 每帧 / 结束），不是"造一个飞出去的实体"** | 做持续光束时才发现"根本没有结束这一拍" → 投送接口返工 | 三拍接口：`Begin(意图)` / `Tick(dt)`（返回 false = 结束）/ `End()`。直线飞行只是其中一种实现 |
| **3** | **结算只认"收到一次命中"；"多久上报一次"归投送管** | 光束每帧都上报 → 每帧结算一次伤害 = **秒杀**；要改就得动结算接口 × 全部已写好的法术 | 投送负责节流（同一个目标最快每 X 秒上报一次），结算永远保持"来一次算一次" |

**第 1 条里"可选的目标引用"是关键**：软锁雷电要"雷落到**目标现在所在的位置**"，而不是"施法那一刻目标在的位置"。有了目标引用，投送和结算可以在**落地那一瞬间**重新取目标位置。

### 3.3 追踪弹的结论要反过来（旧计划的相反结论作废）

旧计划写的是「**追踪弹是陷阱，不做**」—— 那是**旧路线**的结论：那时飞行交给引擎，而引擎导弹没有追踪能力，自己做追踪等于放弃引擎的碰撞 / 伤害 / 插地。

**换成自管实体之后这条结论失效了**：飞行物本来就是我们在每帧推，**追踪 = 每帧把速度方向朝目标转一点（限速转弯），不到十行**，而且完全不影响命中判定与伤害管线。

所以：**「追踪」从"不做"升级为投送轴的一个参数**（转向速率 = 0 就是直线飞）。它是多目标火球与星雨的前提。

### 3.4 三家游戏的法术 → 四段逐条核对

**龙之信条**

### 3.5 持续型法术（彗星亚兹勒）单独说清楚

它和阶段 1 的投射物**根本差别不在视觉，在三件事**：

| # | 差别 | 投射物（阶段 1） | 持续光束 |
|---|---|---|---|
| 1 | **起手** | 松手那一瞬间放出去，完事 | **按住期间一直在放**；松手 / 被打断 / 没资源才结束 |
| 2 | **投送** | 造一个实体飞出去，撞到就没了 | 没有"飞出去"这回事，**是一条一直在那儿的线** |
| 3 | **结算** | 撞到谁算谁一次 | **每帧都照到人，但只能隔一段时间结算一次**（否则每帧一次伤害 = 秒杀） |

**它需要的那台状态机，正好和阶段 3 的蓄力是同一台**：

- **蓄力** = 按住 → 档位往上走 → 松手发一发
- **引导** = 按住 → 一直在放 → 松手就停

两者都在读「按键是否按住 + 施法动作播到哪了」，**区别只在松手时是"发"还是"停"**。所以阶段 3 做蓄力的时候，顺手就把持续型的地基打了一半 —— 这也是把两者放进同一个阶段的原因。

**结论**：彗星亚兹勒**不需要改四段模型**。它要的是 ① §3.2 的三条契约现在写对 ② 阶段 3 的"施法中"状态机 ③ 投送轴补一个"持续"实现 + 结算轴补一个"地面区域 / 光环"实现。

### 4.2 一次施法的完整时序

```
释放（法印开火）
 ① 拦下引擎导弹          SpellSealFirePatch 前缀：认出手持武器是法印 → 不发导弹
 ② 定位                 瞄准轴：产出"施法意图表"（阶段 1 恒 1 条：准星方向 + 引擎给的出膛点）
 ③ 投送进入             取网格副本 → 造实体 → 挂上 → 缩放到目标尺寸 → 按飞行方向定向 → 挂拖尾粒子
 ④ 记账                 交给 SpellProjectileLogic，进"在飞"列表
每帧
 ⑤ 投送推进             位置 += 速度 × dt → SetGlobalFrame
 ⑥ 命中检查（每 0.05 秒一次，全部走引擎原生查询，见 §4.3）
       ├ 打到谁：`Mission.RayCastForClosestAgent(上一帧位置, 这一帧位置, …排除施法者, 命中半径)`
       └ 打到墙/地：`Scene.RayCastForClosestEntityOrTerrain(同一线段, …)`
       两条各给一个距离 → 取近的那个 = 这一步真正撞到的东西
命中
 ⑦ 结算                 单体伤害（复用 AgentDamageHelper.CastBlow）+ 半径伤害 + 命中爆散粒子
 ⑧ 投送结束             实体删掉（贯穿类法术按"可穿透几个目标"参数决定继续飞）

 ⑨ 回收                 飞满「最大飞行距离」或活满「最长存活时间」→ 删实体
```

### 4.3 命中判定：🔴 优先用引擎的查询 API，**不自己写**

**能不写就不写。** 引擎有三条现成的原生查询，而且都**带粗细**（`rayThickness`）—— 带粗细 = 沿线段扫一个球 = **天然就是连续碰撞**，正好顶掉"手写线段↔胶囊"那件事：

| 查什么 | 用什么 | 要点 |
|---|---|---|
| **打到谁** | `Mission.RayCastForClosestAgent(起点, 终点, out 距离, 排除谁, rayThickness)` | 返回 `Agent`；排除参数传施法者自己 |
| 打到哪根骨头 | `Mission.RayCastForClosestAgentsLimbs(...)` | 需要部位判定时才用 |
| **打到墙 / 地** | `Scene.RayCastForClosestEntityOrTerrain(起点, 终点, out 距离, out 命中点, out 实体, rayThickness, BodyFlags)` | 直接给命中点，喂给结算 |
| 形状更贴（可选） | `Scene.BoxCast(盒min, 盒max, …, 方向, 距离, out 距离, out 点, out 实体, BodyFlags)` | **扫掠一个盒子** —— 月牙是扁的，盒子比球更贴 |

**自己剩下要写的只有三件**：① 两条查询各给一个距离，**取近的那个** ② 命中**去重** ③ **穿透类**法术的循环（见下表第 2 条）。

🔴 **为什么不用"给实体挂个碰撞体"**：物理体 API 确实存在（`GameEntity.AddSphereAsBody` / `AddCapsuleAsBody` / `ApplyForceToDynamicBody`），**但引擎没有任何碰撞回调** —— `OnCollisionBegin` / `CollisionCallback` / `ContactPoint` / `BodyContact` 全 DLL 零命中，`MissionBehavior` 那四十多个钩子里也没有一个实体碰撞钩子。挂了物理体 = 它能推动别人、能挡住别人，**但永远不会告诉你它撞到了谁**。所以那条路不通，不用试。

**三个必须实测的点**（不能只看名字下结论）：

| # | 要验什么 | 不通过怎么办 |
|---|---|---|
| 1 | 🔴 `rayThickness` 是「**沿线段扫球**」还是「只在起点一个球」 | 只有前者等于连续碰撞。不是 → 退回手写线段↔胶囊 |
| 2 | `RayCastForClosestAgent` **只返回最近的一个** | 穿透类法术要自己循环：打到谁 → 排除它 → 从命中点再打一次，最多 `pierce` 次 |
| 3 | `Scene.RayCastForClosestEntityOrTerrain` / `BoxCast` **打不打 agent** | `BodyFlags` 看着是场景物件体系、agent 不是场景实体，**大概率不打** → 所以要两条查询配合；若实测打，可以合并成一条 |

**兜底路径已证可用**：SwordBeam 那套「遍历全场 agent + 自写线段↔胶囊距离」（[分析文档](../Knowledge/SwordBeam剑气_实现分析.md) §2.6）是跑通的 —— 实测不通过就退回去，不亏。

**顺带收益**：多发法术（一发变十发）的性能从「10 × 全场 agent 数」降到「10 × 2 次原生调用」，阶段 2 的性能估算因此好看得多（§4.4 那条"引入多发时重估"可以放宽）。

### 4.4 性能口径（和原版比，以及真正要守的纪律）

**结论：单发法术弹的开销大概率比原版一发弩矢更低。** 不是因为我们的代码更快，是因为**原版那颗导弹在做的绝大多数事情我们都不做**：

| 原版导弹每帧要做的 | 我们要做的 |
|---|---|
| 物理模拟（重力积分、空气阻力、旋转、角速度、反弹） | **位置 = 位置 + 速度 × dt**（一行乘法） |
| 物理宽相 + 窄相碰撞 | 🔴 **每 0.05 秒一次引擎射线查询**（= 原版 **1/3 的检查频率**） |
| 网络同步与回放记录 | 无 |
| 插盾 / 插骨 / 穿透 / 护甲结算 | 无（命中即消失） |
| 渲染 LOD 评估与网格剔除 | 场景实体，不走那条链 |

**量级也相当**：原版攻城战里几百个弓箭手同时抛射，天上可能有几十到上百发导弹；我们是玩家几秒一发，就算阶段 4 有二十个法师，同时在天上的也就几十发。

🔴 **真正该守的不是"别比原版慢"，而是"别写出算法上更蠢的东西"。** 五条纪律：

| # | 纪律 | 为什么 |
|---|---|---|
| 1 | 🔴 **绝不遍历全场 agent 去读 `CollisionCapsule`** | 每读一个就是**一次原生跨界调用**（`MBAPI.IMBAgent.GetCollisionCapsule`）。战场上 300~1000 个 agent × 20 次/秒 × 并发数 = **十万到百万次/秒**。这是唯一会把我们拖垮的写法 |
| 2 | **两条替代路径，都是「1 次原生调用」** | ① `Mission.RayCastForClosestAgent`（§4.3，引擎内部自己走空间索引）② 若走手写兜底，必须先 `Mission.GetNearbyEnemyAgents` 粗筛（一次原生调用返回附近几个），**只对筛出来的做精算** |
| 3 | **碰撞检查 0.05 秒一次，不是每帧** | 直接省 2/3 |
| 4 | **别每帧 new 容器** | 已命中名单、粗筛结果列表，一律**复用池**，不在热路径分配 |
| 5 | **并发上限默认 32，超出直接拒绝施放** | 宁可拒绝，也不要"加了再说" |

**什么时候必须重估**：阶段 2 引入**多发法术**（一发变十发 = 检查次数 ×10）、阶段 4 引入 **NPC 施法者**（并发数上去）。这两处到了就按"最坏情况：30 个施法者 × 每人 3 发 × 20 Hz"算一遍。

> **还有一个"最省"的选项，知道它存在就行**：保留引擎那颗导弹（它的碰撞、伤害、插地全是原版的），只把它的**视觉藏掉**、挂上我们自己的实体跟着它。纯性能上这是最省的。
> **不采用的理由**：导弹的寿命与失效距离不可控、有两套真相、形状与我们的月牙对不上（它的碰撞体是 47cm 弩矢）。**这是"性能换控制权"的取舍，我们选了控制权。**

## 五、起手路线：法印还要不要是「弩」

### 5.1 先把问题摆正

**自建投射物之后，"法印 = 弩"从"必需"降级成"脚手架"。** 引擎的弩只提供了三样东西，而这三样都不是非它不可：

| 弩给我们的 | 是不是非它不可 |
|---|---|
| 瞄准姿势 + 准星 | 不是 —— 可以用自建 `item_usage` 的姿势，也可以完全自建 |
| "按哪个键、什么时候放"这套输入 | 不是 —— 项目已有按键映射子系统，可以自己读 |
| **引擎开火事件**（我们现在的触发点） | 🔴 **恰恰是最想甩掉的** —— 为了它要写 Harmony 补丁、还要跟"装填"流程打交道 |

🔴 **所以真正的决定不是"要不要弩"，而是"起手怎么进入我们的代码"**。

### 5.2 关键设计：起手必须走**函数调用**，不能走**引擎事件**

| | 走引擎事件（现在） | 走函数调用（要改成） |
|---|---|---|
| 长什么样 | 引擎开火 → Harmony 拦下 → 调我们 | 我们自己的相位机 → 调我们 |
| 换壳的代价 | **要改投射物层**（因为触发点长在引擎上） | **投射物层一行不动**，只换调用者 |

**起手层的接口固定成一句话**：`(施法者 Agent, 法术 id, 起点, 方向, 蓄力档)` —— 谁调它都行。

- **阶段 1 的调用者** = Harmony 拦下引擎开火后的我们（脚手架）
- **阶段 3 的调用者** = 我们自己的相位机（§5.5：读输入 + 轮询动作进度）

**这样阶段 3 甩掉脚手架时，投射物那一层不需要改动。** 这是本计划把"临时壳"写清楚的全部意义。

### 5.3 三条路（阶段 3 要选一条）

| 路 | 起手怎么触发 | 动作从哪来 | 代价 | 评价 |
|---|---|---|---|---|
| **A. 弩当脚手架**（当前） | 引擎开火 → 拦下 | 弩的 `item_usage` | 要写补丁；装填流程会来捣乱；长期绑在远程武器语义上 | **阶段 1 用**，阶段 3 甩掉 |
| **B. 法印在，但它不发射** | 我们自己读输入 | 自建 `item_usage` 的姿势 | 要验一件事：**非远程武器能不能有"抬起瞄准"这个状态** | 待实验；成了就是长期形态 |
| **C. 完全不用物品**（FCS 那样） | 我们自己读按键 | `SetPose` 切自建动作集 | 丢瞄准姿势与准星；法术选择要自建 HUD（本来也排在阶段 5） | **NPC 侧的做法**（NPC 没有玩家 UI） |

**推荐：A 起步 → 阶段 3 做一次 B 的实验 → B 成则用 B，不成退 C。**

**为什么倾向保留"法印"这个物品**（而不是直接走 C）：龙之信条和艾尔登法环**都是手持法器施法**；而且有物品就有一套**专属动作集**，否则每个法术动作都要塞进各武器的动作集里；再加上弹药槽天然就是"选哪个法术"。

### 5.4 阶段 1 用弩时必须守的 Harmony 纪律（本项目已立过的规矩，逐条照办）

| # | 规矩 | 本补丁怎么落 |
|---|---|---|
| 1 | **目标必须在三个版本锚点都活着** | 已核对：`Mission.OnAgentShootMissile` 在 **1.2.12 / 1.3.15 / 1.5.1** 三个版本反编译出来**签名逐字相同**（`internal [MBCallback]`）。签名一致 ⇒ 补丁跨版本稳定 |
| 2 | **守卫要窄** | 只在「手持武器 ∈ 我们登记的法印集合」时拦截。别的 mod 射箭、原版射弩**一律不管** |
| 3 | **前缀内必须吞异常并放行** | 出错就 `return true` 让引擎照常发导弹 —— 顶多退回旧表现，绝不掐断游戏 |
| 4 | **要能被单独关掉** | 补丁类名进 `Settings.DisabledPatchClasses` 白名单即可（本项目已有这套逐类开关，改完重启即生效、零重编） |
| 5 | **补引擎跳过的记账** | 引擎原方法末尾有一句 `UpdateLastRangedAttackTimeDueToAnAttack`（AI 的"刚射击过"计时）—— 前缀里要自己补一次 |
| 6 | 🟢 **兜底天然优雅** | 补丁关掉 / 认不出弹药 → 引擎照常发导弹，弹药的 `flying_mesh` 还在，**表现退回旧路线**（月牙照飞，只是 110 米外会隐形），不会崩 |

### 5.5 🔴 动画相位：照 FCS 的模型办

FCS 把「**什么时候播什么**」和「**法术什么时候真的出来**」分得很干净 —— 这是本项目要照抄的部分。

| FCS 的做法 | 干什么 | 骑砍怎么落 |
|---|---|---|
| **蓄力蒙太奇** | `BeginMagicCharge` 时起播，循环到出手 | 法印的「抬起 / 维持」姿势（阶段 1 靠 `item_usage`，阶段 3 靠自建动作） |
| 🔴 **出手帧通知** `AN_TriggerMagicAbility` | 挂在动画"法术真正放出"那一拍 → `TriggerMagicSpell` | 🔴 **骑砍没有动画通知** → **每帧轮询 `GetCurrentActionProgress(通道)` 过阈值**（本项目已有技法：[自定义战斗.md](../Knowledge/自定义战斗.md) §3「进度阈值打点表」） |
| **收尾帧通知** `AN_TriggerNextAbility` | 挂在动画末尾 → `NextSpell`（接下一发 / 连招） | 同一个轮询，取第二个阈值 |
| **引导三件套** `Start / Mid / End` | 引导法术的三段（起 / 持续循环 / 收） | `SetActionChannel` 切段播 |
| 🔴 **瞄准俯仰三变体**（`Aim-Offset`：`SpellChannel1_Down / Mid / Up`） | 仰角不同播不同姿势 | **我们也该有** —— 三套姿势按视角俯仰切 |
| **手势按投送方式分** | `M_Projectile`（投掷）/ `M_SkyfallSpell`（举天）/ `M_EruptionSpell`（下压）/ `M_SpellChannel1·2`（引导） | 每种投送方式一套动作（`tools/anim-retarget` 的素材库正好对得上） |

🔴 **三条纪律**（都来自 FCS 的实现）：

| # | 纪律 | 为什么 |
|---|---|---|
| 1 | **"何时放出法术"交给动画那一拍，代码不自己计时** | 换动作、改动画时长都不影响出手时机。骑砍没有通知 → 用"进度过阈值"做等价物，**阈值写在数据里**（一个法术一个），不写死在代码里 |
| 2 | 🔴 **出手阈值必须防重入** | "过阈值"这个条件是**持续成立若干帧**的，不挡就会连发同一个法术（FCS 用 `IsPlayingMontage` 挡） |
| 3 | **收尾帧开输入缓冲窗口** | 松手到动作结束之间按下的下一次施法要接住（FCS 是 `AN_TriggerNextAbility` + `InputBuffer`） |

**阶段 1 怎么落**：阶段 1 用引擎的弩流程当脚手架，**它的开火事件就是"出手帧"** —— 所以阶段 1 不需要轮询，但**数据表里要先把「出手阈值 / 收尾阈值」两个字段留出来**，阶段 3 换相位机时不用改表结构。

### 5.6 阶段 1 一次实机要顺带确认的三件事

| # | 问题 | 为什么重要 |
|---|---|---|
| 1 | 拦掉导弹后，**弹药还照扣吗** | 扣 = 白送；不扣 = 要自己扣（走 `AgentControlHelper`，铁律 4） |
| 2 | 开火**音效**还响吗 | 音效在 native 侧，理论上照响；不响就自己补一条 `module_sounds` |
| 3 | 引擎的"装填"流程还走吗 | 走 = 白送一个施法后摇；不走则阶段 3 自己做（FCS 对应物 = 收尾帧接下一发） |

## 六、数据契约（内容包侧）

### 6.1 一个法术一行

文件：`Modules/Taikou/ModuleData/AssetRegistry/Spells.xml`（照现有 `FirearmFx.xml` 的放法）。

```xml
<Spells>
  <Spell id="lwn_yinmo_zhan"                 <!-- 法术 id（StringId，铁律 20） -->
         ammo="taikou_spell_crescent"        <!-- 哪个弹药物品 = 这个法术（选择器 + 消耗品） -->
         family="projectile"                 <!-- 🔴 法术族（§2.4）：选它 = 一次填好下面三轴的默认搭配 -->
         targeting="aim"                     <!-- 瞄准轴：准星直视（不写就按族的默认） -->
         delivery="projectile"               <!-- 投送轴：直线飞行 -->
         payloads="damage,area"              <!-- 结算轴：单体伤害 + 半径伤害 -->
         cast_type="normal"                  <!-- 起手轴：Normal / channel / instant（阶段 3 用） -->
         release_at="0.42" end_at="0.80"     <!-- 🔴 动画相位阈值（§5.5）：出手帧 / 收尾帧。阶段 1 引擎开火即出手，字段先留着 -->
         mesh="lwn_yinmo_crescent"           <!-- 飞行网格 -->
         trail_particle="lwn_yinmo_trail"    <!-- 拖尾 -->
         impact_particle="lwn_yinmo_burst"   <!-- 命中爆散 -->
         damage="60" damage_type="Cut"
         speed="60" gravity="0"              <!-- 重力 0 = 平飞；>0 = 抛物线下坠 -->
         turn_rate="0"                       <!-- 转向速率：0 = 直线飞；>0 = 追踪弹（阶段 2） -->
         count="1" spread_deg="0"            <!-- 发数 + 散布角（阶段 2） -->
         max_distance="120" max_lifetime="4"
         hit_radius="1.2" pierce="1"
         radius="3.5" radius_falloff="0.5" />
</Spells>
```

### 6.2 对应规则

| 规则 | 说明 |
|---|---|
| **先选族（`family`），再按需覆盖三轴** | 族 = 常用搭配的预设（§2.4）。不写 `targeting`/`delivery`/`payloads` 就按族的默认；写了就是覆盖 |
| 🔴 **`family` 认不出 → 整个法术不加载**（记日志、不崩） | 数据填错的兜底；不是"退回引擎导弹"那条路径 |
| **一个法术 = 一个弹药物品 = 一个视觉** | 禁止让多个法术共用一个弹药（DOS2 踩坑 #10：元素错配就是"火球模板"类错误的根源） |
| **认不出的弹药 = 不管** | 弹药 id 不在表里 → 引擎照常发导弹（兜底路径，见 §5.3 第 6 条） |
| **法印集合也登记在同一张表** | 表里出现过的 `ammo` 所属的法印，自动进"要拦截"的集合；不需要另立名单 |
| **数值一律数据化** | 速度、寿命、半径、可穿透数、转向速率**都是参数**——这正是自管路线白赚的（旧路线的爆炸半径写死在引擎里，只有 1.2 / 2.8 米两档，改不了） |
| **阶段 2 的字段现在先留空** | `turn_rate` / `count` / `spread_deg` 阶段 1 写了也不读，但**表结构不用再改** |

### 7.2 旧路线解决不了、新路线自动解决的三个问题（法印计划 §15.3 的待办）

| # | 旧待办 | 新路线的答案 |
|---|---|---|
| 1 | 🔴 **"寿命"** —— 飞多远 / 活多久（旧路线查到 `WeaponComponentData` 没有寿命字段、引擎里写死，**无解**） | **变成我们自己的两个参数**：`max_distance` / `max_lifetime` |
| 2 | **飞行朝向**（旧结论：朝向由 native 按速度算，**没有运行时手段**，只能改网格几何） | **朝向由我们算**：飞行方向 + 我们自己定的姿态倾斜 |
| 3 | **爆炸半径**（旧路线写死 `isBigExplosion ? 2.8 : 1.2` 米，数据改不了） | **变成我们的参数**：`radius` + `radius_falloff` |

### 7.3 迁移时唯一要重新实测的几何项

**网格本地朝向 → 我们算的 frame 之间的换算关系。**

- 旧路线里，朝向由引擎决定，生成器用一个 `-90°` 的烘焙去迁就它；现在换成我们定，必须重标一次。
- 做法最省：诊断件已有 `alt_mesh` 子命令（造一个陪飞的场景实体）。**摆 3~4 个候选朝向，一次实机看哪个对**，把对的那个写进代码的常驻定向函数。
- 为什么必须先标：2026-09-23 之前的教训 —— 朝向错了整个法术就废，但**资产做完了才发现**要重来一整轮（法印计划 §14.5）。

### 7.4 迁移后的验收（一次实机看全）

| # | 看到什么算过 |
|---|---|
| 1 | 装备法印 + 法术弹 → 抬手 → 瞄准 → 释放 → **月牙飞出去**（且**没有弩矢同时飞出去**） |
| 2 | 月牙**朝向对**（薄刃立着、凸面朝前）、**尺寸对**（约 3.8 米宽，不是 19 米） |
| 3 | 有**拖尾**；命中处有**爆散** |
| 4 | 命中敌人 → **掉血**；周围 3.5 米内的敌人**一起掉血** |
| 5 | 打墙/打地 → 爆散消失（不穿地飞走） |
| 6 | 飞满 120 米或活满 4 秒 → 消失，**没有残留实体**（反复射 50 发后实体数不涨） |

### 12.8 阶段 3（2026-09-23，同批落地）—— "施法中"那台状态机

| 件 | 说明 |
|---|---|

| **蓄力档位改效果** | 起手算出 `Power`（0~1）→ 随意图/命中一路传到结算 → 伤害按 `1 + charge_bonus × Power` 放大。**投送与结算没为它加过一行"蓄力专用"代码**。 |

| **打断 / 输入缓冲** | 换武器、换法术、施法者倒下、场景结束 → 当场清干净（核与粒子一起）；松手后 0.35 s 内再按 = 直接接下一发。**按住不放不连发**（要松一次手才认下一发）。 |
| **投送轴「持续」** | `channel`：每 `repeat_interval` 秒沿朝向打一条射线 → 打到人报"命中那个人"、打到墙/地报"打到那里" → **契约 3 的完整实装**（每帧都照着，但每 0.4 s 才结算一次）。 |
| **结算轴「光环」** | `aura`：与 `area` 同款，**圆心改成施法者自己**（雷电领域/加护）；`self` 瞄准轴一条意图落在自己身上。 |
| **两条起手并存、不双发** | 引擎开火（鼠标）那条路**保留**（阶段 1/2 的习惯不用改）；**相位机正在施法时，法印补丁只拦不放**。 |

**验收件**：`channel_beam`（按住持续喷射 + 灼烧状态）· `aura_field`（以自己为圆心持续电周围）。
控制台：`custom.spell cast channel_beam`；**验蓄力不用按键盘** → `custom.spell power 0.2` 再 `cast`（对比伤害）。

### 12.9 阶段 4（2026-09-23，同批落地）—— NPC 施法者

**一句话**：NPC 放法术 = **同一套 `SpellCastFlow`**，差别只有触发源（`SpellNpcCaster` 每秒扫一次附近，
而不是按键）。铁律 18 的"判定与结算共用"从阶段 1 就是这么写的，这一阶段只是把调用者补上。

| 纪律 | 怎么落 |
|---|---|
| 谁是施法者 | **手里是「法印 + 法术弹」的 NPC**（与玩家同一条判据：弹药 = 法术）；不需要另立名单 |
| 只开 7 类 | 框架侧白名单 `{projectile, channel, skyfall, place, buff, heal, teleport}`；数据侧还能 `ai="false"` 单独否掉 |

| 防重入 | 每个 NPC 一个冷却（数据 `ai_cooldown`，默认 5 s） |
| 施法期间照常走位 | **本类从不碰移动/行为**，只管调 `SpellCastFlow` |
| 性能 | 扫 `Mission.GetNearbyAgents`（1 次原生调用 / 秒，半径 45 m），**不遍历全场 agent** |

**验证钩子**（一条命令让 NPC 变成法师）：

它下一拍就会自己找敌人放法术 —— 之后看：**判定/飞行/命中/掉血与玩家一模一样**，

另外若 NPC 自己的原版远程 AI 也开火，补丁会**另外**放一发（两条触发源各自成发）—— 真实玩法里
施法 NPC 会由 `AgentBrain` 接管，届时把这一条收口。

**一句话**：把法术的"结算"从**一次性掉血**升级成**世界会记住**的东西 —— 角色身上挂状态、地上留地表、

### 13.1 三块新东西，以及它们各挂在四段的哪一段

| 块 | 是什么 | 挂在哪一段 | 已有的地基 |
|---|---|---|---|

### 13.2 关键设计点（现在定下来，免得以后返工）

1. **状态是数据表，不是代码分支** —— `ModuleData/AssetRegistry/Statuses.xml`：一行一个状态
   （id / 时长 / 每跳效果 / 移速乘子 / 能否行动 / AI 修正 / 粒子 / 叠层规则 / 免疫标签）。
   加"冻伤" = 加一行，代码不动。
2. **地表 = 会施加状态的一片区域**，不是"另一种伤害" —— `place` 投送生成地表并登记进世界表；
   每 `repeat_interval` 对圈内每个 agent 施加**它携带的状态**。伤害只是状态的一种效果。
3. **反应表也是数据** —— `(元素A, 元素B) → 结果` 一行一条（水+火=蒸汽 / 油+火=爆燃 / 水+电=导电水面 /
   冰+火=化水 / 毒+火=爆炸…）。触发时机 = 两张地表/状态的空间重叠。
4. **传播是状态的字段**（天照的核心）—— `spread_radius` + `spread_interval` + `spread_chance`：
   每跳检查附近有没有别人，有就传过去（或在他脚下留一小片地表）。
   **"水浇不灭" = 免疫标签里排除 water**（天照在原作里就是不灭之炎）。
5. 🔴 **存档是前提不是收尾** —— 地表与状态一旦要跨场景存在（战役地图 / 城镇里布置），
   必须同期走 `SaveableTypeDefiner`（计划 §九-9 与 FCS §12 都点名）。
   战场内可以只做任务级；**做战役层地表时必须一起做**。
6. **性能口径沿用既有纪律** —— 地表 × 每跳 × 圈内 agent 走 `Mission.GetNearbyAgents` 粗筛，
   每 `repeat_interval` 一次；**地表两两相遇的检查要限量**（每片地表每拍最多查 N 片）。
7. 🔴 **两个已核实的引擎事实**（2026-09-24 反编译 1.2.12，省得开工时再查）：
   · **减速有原生 API**：`Agent.SetMaximumSpeedLimit(float, bool isMultiplier)` —— 传
     `(0.8f, isMultiplier: true)` = 减速 20%；清掉用 `(-1f, false)`（原版自己就这么清，
     `Agent.cs:1183`）。**所以"减速"是最便宜的一种状态**。
   · **引擎没有"角色着火"状态**：全客户端搜 `Burning` 只有 `WeaponFlags.Burning`（那是弹药的
     属性，不是 agent 状态）⇒ 燃烧 / 中毒 / 冻伤这些**全由我们的状态系统自己实现**（DoT 走既有
     `SpellWorld.Damage`，视觉走挂粒子的跟随实体 —— 与现有 `status_particle` 同一套）。

### 13.5 地表的**表现层**怎么落 —— 不是改地形贴图（2026-09-24 定）

**结论**：地表 = **贴地为"载体" + 贴图动画为"活"**，载体从引擎现成的三种里挑；
**逻辑与表现分离**：逻辑是纯数据（零引擎对象），表现才挂引擎对象。

**① 先说不能做的：改地形材质图（materialmap）**
地形材质图是**烘焙的图层系统**（Taikou 的地图 13 层：草/林/沙/雪…），运行期写它是错路：
贵（改纹理）、只对地形有效（室内地板 / 屋顶 / 水面 / 木台全不适用）、且与地图烘焙流程打架。
**DOS2 / BG3 也不是改地形** —— 它们那些血/火/水/油表面是**贴地的贴花或薄片**。

**② 三条能做的载体（引擎都现成）**

| 载体 | 引擎入口 | 适合 | 成本 |
|---|---|---|---|
| **贴花 Decal** | `Decal.CreateDecal(name)` + `SetMaterial` + `SetFrame` + `SetVectorArgument` + `SetFactor1`（染色）；内容包可**自己注册贴花集**（Native 挂了 5 条 `soln_decal_textures` + `soln_decal_sets` —— soln 体系，跟粒子同一条通路） | 大面积、形状随地面的（血/焦痕/水渍）；**原版血迹与焦痕就是这个** | 低（引擎自己批） |
| **贴地平片网格 + 贴图动画** | 我们已有：`lwn_flight_sigil`（2.6 m 平片，躺平靠本地 +Y 对齐世界上）+ **月牙材质正在用 `use_texture_sweep`** | 需要**精确轮廓**、明显流动的火墙/法阵 | 低-中（一个 quad 实体，骑砍里是白菜价） |
| **粒子贴地**（+ 粒子生成贴花） | 粒子 flag 里现成有 `emit_on_terrain` / `enable_collision` / `fixed_billboard_direction` / **`create_decal_on_collision` / `create_decal_only_once` / `permanent_collision_decals` / `randomize_collision_decal_rotation`** | 火苗、蒸汽、飘逸的细节层；**"烧过留焦痕"零代码**（原版血迹/焦痕就是这么来的） | 最低（纯数据） |

**实际用法 = 叠着用**：`decal`（底：烧焦的地面）+ 平片或粒子（面：流动的火）+ 粒子（细节：火星）。
**"天照烧地"的组合**：平片网格带 sweep 的黑炎 + 粒子 `create_decal_on_collision` 留永久焦痕 ✓。

**③ "都是 mesh 会不会算不过来" —— 要分开看**

- **渲染**：一个贴地 quad 在骑砍里**不贵**（原版遍地箭矢/石头/树/血迹都是场景实体，成千上万）。
- **逻辑**（真正要守的）：地表登记处**只存纯数据**（位置 / 半径 / 元素 / 寿命 / 携带状态），
  谁在圈里用 `Mission.GetNearbyAgents` 粗筛（1 次原生调用）、按 `repeat_interval` 节流、
  地表两两相遇的检查**限量**。50 片地表 ≈ 每秒几十次原生调用 —— 与"每帧遍历全场 agent"是不同量级。
- ⇒ 一句话：**贵不贵取决于你怎么写逻辑，不取决于你用不用 mesh**。

**④ 贴图动画的两个已知坑**（见 `Knowledge/骑砍2网格贴图动画_引擎能力与实现.md`，别踩第二次）

- **漂移（sweep）与翻页（page-flip）互斥**，且与**自发光强度**抢同一个 `Vector Argument 1`
  （`.x/.y/.z/.w` 三种读法，两个同开 = 9.6Hz 硬闪）。
- **漂移会把贴图里的空间遮罩一起漂走** ⇒ **"圆形边界 + 会动"只能走翻页**（地表常要圆形边界，这条直接相关）。
- ⚠️ **未验一条**：decal 的材质能不能吃 sweep / 翻页这两个 flag（跟网格是两套 shader 路径）——
  开工时一次实测即可定性；不行就让 decal 只做静态底、动画交给平片/粒子。

## 附录 D · 为什么弃 `flying_mesh`：**约 110 米必定剔除网格**（2026-09-23 裁定 ✓ 已落地为自管实体）

> 本文 §一 第 3 条与 wheels 都引用这条 —— **原文保留**，别再重推一遍。

**D.1 证据链（七次实机，每条都实测过）**

| # | 实验 | 结果 | 得到什么 |
|---|---|---|---|
| 1 | 月牙（1 档 LOD）当弹 | 飞出一小段就看不见 | 起点 |
| 2 | 放大 5 倍（19 米） | 照样消失 | ❌ 排除"太小看不见" |
| 3 | 加 `MissileWithPhysics="true"` | 照样消失 | ❌ 排除"非物理刚体" |
| 4 | 补 LOD 到 7 档 | 消失点从 ~8 米推到 ~110 米 | 方向部分有效 |
| 5 | 补 LOD 到 8 档（含表尾档） | 仍是 ~110 米 | ❌ **表尾之外不看资产** |
| 6 | 拿原版建筑网格当弹（LOD 链完整） | 同样消失 | ❌ 排除"我们月牙资产的问题" |
| 7 | 原版网格挂**场景实体**（诊断件的"陪飞影子"） | 一直可见 | ✅ **场景实体路径没这个上限** |

⚠️ 第 7 条有一次测量污染：影子默认带火焰拖尾粒子，**粒子不受剔除影响** —— 复验时先关（`alt_particle off`）。

**D.2 机制（反编译 + 实机实证）**

- 引擎有一张**全局 LOD 距离表**：`GameEntity.GetLodLevelForDistanceSq` 在 9.6 / 15.4 / 21.1 / 32.5 / 43.6 / 88 / 116 米处依次返回 1..7
  ⇒ 阈值约 **8 / 12 / 17 / 24 / 35 / 51 / 74 / 108 米**（随画质设置缩放）。
- **表尾之外（返回值 7）= 剔除**；`Meta Mesh Editor` 第 8 档显示 `until -2147483648m`（未初始化哨兵）说的是同一件事。
- **原版弹丸网格全部只有 1 档 LOD**（`bolt_bl_flying` / `projectile_rock` / 霰弹碎片，实测均 1 子网格 @LOD0）
  ⇒ "档数"从来不是我们与原版的差别：**原版只是从没飞过 110 米**，这个上限从不显形。
- 结论：**别在导弹管线上跟 LOD 表较劲**（补档只能把撞表尾的时间往后推，推不出表）。

## 附录 E · 原版参照机：`RangedSiegeWeapon` 的完整阶段机（反编译实见）

原版器械上有一台完整分阶段状态机（`RangedSiegeWeapon.cs:40` 定义，推进在 `OnTick :951`，
`AddCustomMissile` 在 `:1641`）：

```
Idle → LoadingAmmo → Reloading ↔ ReloadingPaused     ← 装填可暂停 = **蓄力保持的原生对应物**
     → WaitingBeforeProjectileLeaving                ← 发射前一刻 = **放爆发/枪口特效的钩子**
     → Shooting（AddCustomMissile 在这）→ WaitingAfterShooting → Idle
```

**怎么用**：
① 我们的相位机（`SpellCastInput`）已经自己实现了「蓄力 / 引导 / 瞬发」，**不用抄它**；
② 但它的两个**语义对应物**值得记住 —— **能暂停的装填**就是"蓄力保持"，**发射前一刻那个状态**是该挂爆发特效的地方
（我们现在把爆发挂在"松手 / 左键"那一拍，等价）；
③ 真要做**多段法术**（蓄力→发射→二段）时，照它的**结构**抄（状态枚举 + `OnTick` 推进 + 每状态副作用），
**别抄类** —— 那台机器挂在 `UsableMachine` 上，是攻城器械，不是法术。
