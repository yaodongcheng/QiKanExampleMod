## 〇、结论先行（决定清单）

1. **决定：翻译 = 两个脚本 + 一个校验闭环 + agent 只做收尾审核**，不让 LLM 逐句手抄。理由：手抄不可校验也不可回放（09b 实测：自称 55 行全落点、实际漏 15+ 行；注释写了 25 条条件、JSON 只落 5 条）。
2. **决定：机械翻译只认 `16a-DSL翻译总表.csv`；查不到就报错停机**，既不猜译，也不产出「🔴待注册」凑数。理由：表外 = 生成器缺陷（铁律 22），正确动作是回填映射表重跑，不是在产物里打补丁。
3. **决定：名字 → StringId 的对照表同样是生成物**，由 `gen_entity_maps.py` 从《骑砍2太阁Mod表.xlsx》机器生成（§九）。理由：手写表只够桶狭间用，全量 2594 事件必漏，而且漏了不报错——直接生成哈希占位，静默错到底。
4. **决定：产物放 `story_event_json/<剧本>/`**，与手写 plan 文档分开；定稿后整体迁去补充包 ModuleData（裁定 24）。
5. **决定：初版按「一个源事件 = 一个事件 JSON」直译，不做合并**。多契機合并、机位拆线是设计判断，留给 §七 审核阶段。
6. **决定：每行源原文自动写成行注释并自动编 T# 号**。理由：注释由程序从源行生成，「源文每行都有落点」这条铁律从源头成立，不靠人工数号。
7. **决定：09b/09c 手工产物留作「参照答案」，不废弃**——机械初版是素材，手工产物是终态样板，审核时两相对照。
8. **决定：旧脚本（TK52Json5.py / TK52Json_SpiltFile_v2.py）只批判继承**——继承词法与块解析思路，废弃其输出格式与删注释做法（§十）。

## 一、机械翻译纪律（23 条）

> 每条都是一次实机踩坑（用户抓包或自审发现）→ 已固化成脚本行为。**翻新事件、换新题材之前先过一遍这 23 条**，这是本文件最有用的部分。

1. **条件必须逐条对上 TK5 原文**（用户裁定）——「注释说 25 条、JSON 只写 5 条」是手抄的必然结果。机械翻译 = 逐条查 16a CSV（§3.4），查不到就停机（§六）。**禁止「注释写摘要、JSON 写简化版」两条腿走路**。
2. **指令名必须落 JSON 第一字段**（用户裁定）——演绎剧本每行 `cmd` ∈ 05 指令流权威（`dialogue` / `narrator` / `choice`），骨架每步 `step` ∈ 01 步骤表。**禁止靠别的字段在不在来推断这行是什么**（曾用「有没有 speaker」推断是不是对白，被抓包）。對話→`dialogue`+speaker+listener；自語→`narrator`+speaker（内心独白有归属）；旁白→`narrator`（上帝视角）；選擇→`choice`。
3. **對話 的两个参数都要落字段**（用户裁定）——`對話:(說話人,對象)` 的 param1=speaker、param2=listener 都结构化落盘，禁止只收 speaker、让「对谁说」靠注释反推。舞台注入靠 listener 字段推导沉默观众位（§四）。
4. **代入 = 局部变量赋值，不是静态展开**（用户裁定）——`代入人物Ｄ:(旅人)` → 骨架 `ctx_set`（slot=`hero_D`），后续引用写 `Ctx::hero_D`（16 §一 Ctx 三档）。**唯一例外：条件块里的代入要静态展开**——条件求值时没有执行流可以跑 ctx_set（EFF0C300_159 的「據點Ｂ = 織田本城」即此例）。槽名一律 ASCII：人物Ｄ→`hero_D`、城Ａ→`settlement_A`、據點Ａ→`place_A`、ａ→`var_a`、忍者衆Ａ→`ninja_A`。
5. **中文和 emoji 禁止进 ID**（用户裁定）——占位 ID 必须是合法 StringId 形态（`Hero::tk5_dosan` / `Agent::tk5_traveler` / `Settlement::tk5_city_083`），配一张「占位 ID → 中文名」对照表进报告，供 07 审核时全局替换。兜底 fallback = 确定性哈希 ID（`tk5_uXXXXXX`）+ 登记中文名。**「🔴待07」只允许出现在注释和清单里，不允许出现在引用位置**。
6. **本地化键必须全局唯一**（铁律 13 的脚本落地）——行计数器是事件内的，键必须带事件号前缀（`LWN_SCN_okehazama_EFF0C300_159_7`）。裸序号跨事件必撞（实机：`_7` 撞了 22 次）。
7. **文本变量占位符语义化**（用户裁定）——TK5 变量翻成 TextObject 占位符，键从角色 ID 派生（`(今川義元)` → `{IMAGAWA.NAME}`），风格照抄引擎内置的 `{PLAYER.NAME}`。**TextObject 键只收大写字母、数字、下划线、点**——`::` 和小写字母不合法，写不出 `{Hero::lord_1_imagawa.name}` 这种东西。类型与源角色另记在报告的「文本变量注入表」。
8. **称呼属性体系**（用户裁定，全语料扫描 2026-08-27）——圆括号两种：`(X.姓)`→`{X.FIRSTNAME}`（**姓 = FirstName**，骑砍2 的 FirstName 显示在前，日本名正好姓在前）、`(X.名)`→`{X.LASTNAME}`。花括号三种：`{X.名前}`→`{X.NAME}`（全名）、`{X.姓名}`→`{X.FULLNAME}`（运行时拼接）、`{X.代名詞}`→槽人称。人称：`{一人稱}`→`{SELF_PRONOUN}`、`{二人稱}`→`{OTHER_PRONOUN}`、`{二人稱名前}`→`{OTHER_PRONOUN_NAME}`。`{未知NN}`→`{UNKNOWN_NN}`（唯一需要人工定语义的一类，全语料约 1500 次）。槽显示：`<城Ａ>`→`{SLOT_A.NAME}`、`<ａ>`→`{SLOT_A.VALUE}`、`<年>`→`{TIME.YEAR}`、`<月>`→`{TIME.MONTH}`。**禁止自造属性词**（曾把「姓」写成 CLAN，被纠正）。
9. **源里的重复拷贝自动去重**——TK5 源大量整块复制粘贴（EFF0C300_159 的四组 ＯＲ 里两组逐字重复；性别变体文本也常常逐字相同）。**条件翻译在顶层去重**（顺序敏感，保留第一个）。**执行块里的重复照翻不删**——那可能是机位变体，不是纯重复。
10. **循环和容器必须完整保留语义，禁止降级**（2026-08-27 用户裁定修订）——`循環:{...}` → `loop` 步骤（body 递归，运行时对容器逐个执行）；`脫出模塊` → `break`；容器命令（設定/篩選/排除/排序/選擇/清理）→ `container_*` 步骤（参数按序语义化：domain / attr / value / slot / mode）。**实机教训**：曾把循环「线性展开一次」、把容器标成「🔴待注册」，用户裁定「翻译必须原原本本保留意思，指令不够 = 查 16a CSV 回填 + 补实现，不准自作主张删减」。166 号案例：`循環:{容器選擇→脫出模塊→人物登用→容器清理}` → `loop{container_pick → break → spawn_hero → container_clear}`，从 0 效果变成全语义。**顺带查出 CSV 参数列漏项**：`人物登用` 源里实参是三个 `(人物Ｅ,直臣,德川家康)`（actor / status / clan），CSV 原来只写了 (actor, clan)——已回填。
11. **注释恢复必须按 `cmd` 字段配对**——`stage_inject.py` 恢复 T# 注释时，原来用「这行里有没有 narrator 三个字」配对；v4 改成 `cmd: "narrator"` 之后旁白行错位、T# 全丢，覆盖率从 22/22 掉到 15/22。**凡是「读进来、改写、再写回」的二次处理脚本，都必须自证注释和锚点没丢**。
12. **全角字符禁止进任何键或 ID**——全角 Ａ-Ｅ / ａ-ｚ 在槽名、占位符、ID 里一律转 ASCII（`ninja_Ａ`→`ninja_A`、`SLOT_Ｃ`→`SLOT_C`）。**推论**：占位符前缀从槽名派生时也要走同一条转换——曾经直接把「人物Ｄ」按「只留 ASCII」清洗，全角字被清光，生成出 `{___.NAME}` 这种空前缀；现在槽走 `slot_cname()` 得到 `{HERO_D.NAME}`，正好和 `Ctx::hero_D` 对得上。validator 应加全角检查。
13. **块结构：开块 append 一次，闭合只出栈**——实机：块头 append 进父节点、闭合行又 append 一次 = 每个块翻倍（EFF0C300_159 的 4 个 ＯＲ 变成 16 个）。闭合行 `}//塊名` 只 pop，不 append。**解析器写完先跑一次「源里几个块 vs 树里几个块」自证**。
14. **CSV 侧名要按主体的域取段**——16a 的属性侧名是 `Hero.clan / Settlement.clan` 这种多域共用格式，翻译时必须按「域::主体」的域取对应那一段（人物::X 取 `.clan`、城::X 取 `.clan`），**禁止把整段侧名拼进 DSL**（实机错拼成 `(Hero::X.Hero.clan / Settlement.clan)`）。域对不上（大名家.本城 vs Hero.home）→ 停机报缺，不硬拼。
15. **分支语义三件套**——①`分歧:(N)` 指的是**最近一次 調查**（pending_cond 保留到被覆盖为止，不消费就清掉——EFF0C300_159 主流程的 分歧:(0) 与尾部守城的 分歧:(1) 共用同一次调查）；②相邻的 分歧:(1) / 分歧:(0) 配成 if/else（顺序是 [0块,1块] 时 then 条件取反）；③`主人公分歧:(其他)` = 已出现机位取反（`not(A) and not(B)`）；④not 嵌套化简（`not(not(X))`→X）。
16. **结算命令的参数按 CSV 参数列语义化**——世界结算命令（武將死亡 / 城主變更 / 家督讓位…）的参数按 16a「参数」列映射成字段（`kill_hero actor` / `set_owner settlement+clan` / `teleport party+pos`）。TK5 参数不带域前缀（`武將死亡:(今川義元)`）→ 按参数名推断域再翻（actor→人物→`Hero::lord_1_imagawa`）。多参数逗号切分。参数位不够 → 记进未结清清单（§六）。**禁止只落原文、把参数丢掉**。
17. **代入槽的参数在命令名里**——`代入人物Ｄ:(旅人)` 的槽名写在命令名上（cmd=`代入人物Ｄ`，括号里是值），**不是参数列表的第二项**；`代入ｃ:(狀況::年)` 是单参数（曾误判成「至少两个参数」，造出 89 条假待注册）。
18. **未知NN 分两类，属性类不许当碎片丢掉**（2026-08-27 用户裁定：先记录，处理留到全量翻译）——`未知NN` 是 **TK5 内部编号属性系统**（数字 = 属性系统内部 ID，反编译器没映射出属性名就留了占位），**不是反编译 bug**；同族还有 `主命屬性::5288.80`、`遊戲通關種類::5830.134`。两类：
    - **属性类（有完整语义结构）**：`域::X.未知NN(参数)` 形式的带参调用或赋值——`大名家::X.未知8(勢力::Y)` 出现 173 次（`更新:(大名家::織田信長.未知8(勢力::齋藤義龍))(59)`：这是大名家对某势力的数值属性，值有 0 / 6 / **59 反复出现**（织田→斋藤、長宗我部→島津 都是 59）→ 疑似外交好感一类的数值。**编号→属性名要拿 TK5 属性表（太阁表 125 列）核对，禁止猜译**。`地方::X.未知2` 出现 43 次。
    - **命令类（真的是字节碎片）**：行首 `未知NN:(2B 00 00 00)` 这种字节命令（未知43 出现 379 次、未知44 出现 321 次）→ 解析成碎片忽略。
    - **待办**：全量 2594 事件翻译之前，给属性类的未知NN 做结构保留翻译（`(Clan::X.attr_8(Faction::Kingdom.Y)) == (59)` 形态，语义标「待核对」）；07/08 阶段用太阁表回填编号→属性名。
19. **🔴 完整语义优先（2026-08-27 用户裁定，本节最高优先级）**——翻译器**必须完整保留 TK5 语义**：循环就是循环、容器就是容器、参数就是参数。**指令/函数/域不够用 = 先查 16a CSV 是不是漏了 → 漏了就回填（改 `gen_registry_tables.py` 映射规则 → 重跑 `build_registry_csv.py`）+ 01/16 注册 + 引擎实现**。「标个待注册推给 agent」只允许用于**确实查证过、表里真没有**的词条（流程：先 grep CSV 确认 → 才记录并注明「已查证表外」）。**禁止**：把已注册命令降级成注释、把参数丢成一串原文、把循环展开成一次、把容器当静态列表——「结构在、效果待补」不是设计，是欠账。
20. **🔴 「原文 → 翻译」注释纪律（2026-08-27 用户裁定，四连抓包后固化）**——每段翻译结果必须**紧贴它的源原文注释**，正文保持纯翻译：
    - **正文 = 纯翻译结果**（引擎要吃的数据）；TK5 原文一律进注释（`// 源：` / `// [N]` / `// T#`）。**禁止把原文当 JSON 字段**（曾把 `"src": "ＢＧＭ變更:..."` 塞进正文被抓包；引擎调试要源行 = 编译阶段注入，源文件不背这个）。
    - **注释位置 = 紧贴对应字段的正上方**：id 贴事件块头、trigger/facility 贴發生契機、once/priority 贴屬性；条件逐条 `[N] 原文 → DSL` **严格贴在 condition 字段上方**；步骤贴 `// 源：`；演出行贴 `// T#`。**禁止把注释堆在 JSON 对象开头**（曾把 39 条 [N] 堆在 `{` 前面被抓包）。
    - **每条原文只出现一次**——禁止「顶部整块原文 + 字段级注释」两处拷贝（两处拷贝就是「注释和 JSON 对不上」的温床）。
    - **覆盖全字段**：id / trigger / once / priority / facility / condition 每条 / script 每步 / story 每行——**任何翻译内容没有贴源注释 = 欠账**。
21. **🆕 据点表两列语义不同，混用会造出假身份**（2026-08-28 查表实证）——织丰《CityTaikou》表有两列：`MatchSettlement` = 骑砍地图上就是这座城（99 条），`NearSettlement` = 骑砍地图上没有这座城、只给了最近的一座（81 条）。原来的写法是「Match 查不到就用 Near」，结果**太阁「鳴海城」被翻成了那古野的村子**——鸣海攻防会打到那古野去。现在的规则：Match 命中 → 直接用真 ID；只有 Near → **自己发一个 `tk5_city_NNN` 占位 ID**，同时把 Near 记进 `SETTLEMENT_ANCHOR`（只表示「事件大概在地图这一带」，不是同一个地方），报告里点名让 07 数据包补真城。同名异写（清洲/清須、河越/川越、阪本/坂本…）走白名单，直接认作同一座城。
22. **🆕 校验器必须能吃自己的生成物，而且跨文件合池**（2026-08-28）——`verify_tk5_coverage.py` 原来只认手写的 md 计划文件，拿生成的 `.jsonc` 喂进去会「声明源事件：（空）→ 通过」，**空转还报绿**。v2 两处改造：①加一层 `read_doc` 适配，把 `// ==== 事件 XXX ====` 横幅当标题、其余当代码块，生成物直接可校验；②**条件注释块与落点行池跨全部入参合并**——本流水线把一个事件拆成两个文件（events.jsonc 放条件、story.jsonc 放台词），按单文件查必然一半落空，误报「没找到 condition 注释块」「缺失 N 行」。**推论：校验器自己也要有「空输入即失败」的自证**，绿灯不等于查过。
23. **🆕 改这些脚本时的 shell 陷阱**（2026-08-28，连踩三次）——在 Git Bash 里用 heredoc 往 py 文件里写代码，**反斜杠会被吃掉**（即使用了 `<<'PY'` 引号形式）：`"\n".join(...)` 落地变成真换行，py 直接语法错误。写脚本里的字面反斜杠一律用 `chr(92)` 拼，或改用文件写入工具，改完拿 `ast.parse` 验一遍再跑。
24. **🆕 生成器必须是确定性的——同样输入，两次重跑必须一字不差**（2026-08-28 当场抓到）——`tk5_to_json.py` 把「已见机位」存在 `set` 里，「主人公分歧:(其他)」这一支要把已见机位逐个取反拼成 `and(not(A), not(B))`，拼的顺序就随 Python 哈希随机化每次都变。后果不是产物错，是**没法复核**：重跑一次 diff 就一片红，人分不清哪些是真改动。**规矩：凡是会写进产物的集合，一律用有序容器**（保留源码出现顺序，或显式 `sorted`），禁止让 `set`/`dict` 的迭代序流到输出里。**自证办法**：连跑两遍、比 md5，不一致就是缺陷——这一步应进发布清单。

25. **🆕 一座城的不同区不能拆成两个地点**（2026-08-28 当场抓到）——太阁把「岡崎城」（城）和「岡崎之町」（町区）当两个地点写，骑砍这边 `town_CHUB10` 一个据点就把城和町都包了。归一表原来只登记「岡崎城」，「岡崎之町」查不到就发了个独立占位 `tk5_okazaki`，**后果是事件里「筛选所属据点 = 岡崎之町的浪人」一个人都筛不到**（所有人的所属据点是 town_CHUB10），事件表面跑通、实际空转。**规矩：据点归一必须把「城/之町/町/之砦/砦/館/港」全套后缀变体都注册到同一个 ID**。反例边界：釜山之町/那覇之町/寧波之町/呂宋之町 是**真的**不在骑砍地图上（织丰据点表里查无此地），它们发占位是对的——**区分标准是「去掉后缀后的城名在不在表里」，不是「名字里有没有『之町』」**。


### loop 的执行模型（2026-08-27 全量数据定稿）

> 全量扫描：TK5 共 1823 个循環块，块里的命令 100% 是机制操作（容器選擇/清理/脫出模塊 每块标配，加上 更新 1103 次、人物解雇 440、城主解任 396、人物登用 69、武將死亡 17、代入若干），**没有一条演出命令、没有一次等待**。

- **执行模型 = 同步批量跑完**：`loop` 一帧内跑完所有轮次，不需要暂停/续跑机制（玩家不介入）。
- **每轮的上下文**：每轮进 body 之前 `container_pick` 覆盖槽（如 `Ctx::hero_E`），body 里的引用 = 当轮那个元素；容器空（pick 失败）或显式 `break`（脫出模塊）→ 循环结束。
- **validator 要拦的**：`loop` body 里**禁止出现演出类步骤**（dialogue / choice / perform / scene_enter）——全量数据证明合法循环不含演出，出现了就是翻译或题材出了 bug，直接阻断打包。
- **容器域** = 运行时集合：`container_set`（按类别初始化）→ `container_filter`（叠条件）→ `container_sort` → `container_pick`（取一个进 Ctx 槽）/ `container_clear`（清空）；引擎侧 = 内存集合 + 世界查询填充（01 调度器/执行器注册）。

### 称呼怎么定（`{二人稱名前}` 的运行时规则，2026-08-27 用户裁定：称呼取决于双方地位差）

> 全语料扫描：`{一人稱名前}` **0 次，不存在**；`{二人稱名前}` 1863 次，说话人→对象的模式**绝大多数是低位对高位**（人物Ｂ→主人公 180、忍者→主人公 131、人物Ａ→主人公 120、小姓→主人公 54、人物Ｂ→上杉謙信 57、福島正則→德川家康 22），少量平级（主人公→人物Ａ 50）。

- **运行时侧（🔴 待设计落地）**：注入 `OTHER_PRONOUN_NAME` 时**按说话人↔听话人的地位差查一张称呼规则表**：
  - **判定输入**：说话人、听话人（v4 已把 listener 落成字段，运行时直接取）、两人关系（17 主公/家臣、同势力、亲密度、性别）。

  - **表结构**：`{说话人角色, 听话人角色, 语境} → 称呼模板`，模板里可以再套 `{LASTNAME}` / `{NAME}`。
  - **兜底链**：主公様/殿 → 「〇〇殿」通用敬称 → 直呼其名（查不到不许崩，铁律 1）。

## 三、步骤 1 规格：`tk5_to_json.py`

### 3.1 输入

- `--events` 事件号清单（带前缀，如 `EFF0C300_159`）
- `--scenario` 剧本名（决定输出子目录与本地化键前缀）
- `--source` TK5 合并源（默认 `Knowledge/太阁事件包/TK5AllEvents_merged.txt`）
- `--registry` 翻译总表（默认 `16a-DSL翻译总表.csv`）
- 实体归一表：直接 import `tools/entity_maps.py`（§九 的生成物，不再走命令行参数）
- `--out` 输出目录（默认 `story_event_json/`）

### 3.2 解析器（批判继承旧脚本）

| 旧脚本做法 | 结论 | 我们怎么做 |
|---|---|---|
| 正则删 `//.*` 注释再解析 | ❌ 批判：原文被丢，T# 无处可锚 | **不删行**：每行留原文 + 行号，注释由原文自动生成 |
| 字符流 tokenizer（按 `{`、`}`、换行切块） | ✅ 继承思路 | 同思路，但**必须处理 `//size=xxx` 块尾注释和 `}//块名` 闭合标记**（源格式实测，旧脚本没处理会误判） |
| 非贪婪正则取括号参数 | ❌ 批判：嵌套括号被截断（v1 的 bug） | 平衡括号提取（继承 v2 的 `_extract_balanced_params` 思路） |
| 输出「太阁5 中间 JSON」（cmd 保持原名） | ❌ 批判：等于没翻译，还得再译一遍 | **直接输出 01 DSL**，查表在解析时完成 |
| `[[文本]]` 里的花括号先替换成占位再还原 | ✅ 继承（防块解析器误判） | 同思路，还原时写回原文注释 |
| 性别变体（相邻 分歧:(1)/分歧:(0) 双行） | ⚠️ 旧脚本没处理 | 识别「相邻两块逐字相同、只差性别词」→ 合并成一行 + 性别 when 门控 |

### 3.3 事件头（發生契機 / 屬性 → JSON 字段）

- `屬性:一次` → `"once": true`；`屬性:多次` → `false`；`｜弱` → `"priority": "weak"`。
- `發生契機:X(参数)` → `"trigger"`，值查 08 时机对照表（settlement_enter / house_enter+facility / field_battle_* / siege_battle_* / council_start / daily 兜底）。**表外时机 = 停机报缺，禁止自造 trigger**（README 纪律 8）。
- 契機第二参数（自宅 / 評定間 / 城主間…）→ `"facility"` 字段（01 facility 注册表 v1）。

### 3.4 条件翻译（發生條件 → condition DSL）——本脚本的核心

1. **逐条查表**：每条 `調查:(...)` 拿「太阁原词」列查「我们侧名 / 实现锚点」列：
   - 域：`人物`→`Hero::`、`大名家`→`Clan::`、`城`/`據點`→`Settlement::`、`狀況`→`Time::`、`事件標誌`→`Flag::`、`國`→`Settlement.region`。
   - 属性：`存在`→`exists(...)`、`死亡標誌`→`(Hero::X.alive)`、`所屬大名家`→`(Hero::X.clan)`、`城主`→`(Settlement::X.owner)`、`外交同盟`→`isAllied(...)`、`鄰接大名家`→`isNeighbor(...)`、`事件参加可能`→`(Hero::X.available)`。
   - 值：角色名/城名 → StringId（查 §九 归一表）；`真偽::真/偽` → `true/false`；枚举值（`身份::城主`）→ 16 §四 枚举 token。
2. **结构 1:1 保持**：`ＡＮＤ調查` → `and(...)`、`ＯＲ調查` → `or(...)`，**禁止拍平**（拍平 = 漏条件 = 静默语义错）。
3. **代入槽**：见纪律 4（条件块内静态展开，执行块内 ctx_set）。
4. **查不到就停机**：见 §六。
5. **防重复条件不生成**：`not(Flag)` 这类防重复写法不落（01 三层纪律：调度器自动记 `Event::<id>.done`）；事件顺序依赖 → 自动生成 `(Event::<前置事件号>.done) == true`。
6. **输出**：单条 = 直接表达式；多条 = `and(...)` 包裹。

### 3.5 执行翻译（→ script 骨架 + 演绎剧本 lines[]）

| 源命令 | 落位 | 说明 |
|---|---|---|
| `對話` / `自語` / `旁白` | 演绎剧本 `lines[]`（cmd + speaker + listener + textKey + T# 注释） | 说话人查归一表；本地化键自动分配（`LWN_SCN_<剧本>_<事件号>_<序>`），同时写 i18n XML（中文 = 原文，英文 fallback 待翻译） |
| `ＢＧＭ變更` / `ＳＥ開始` | 演绎剧本对应字段（05 注册表） | — |
| `進入設施` / `離開設施` | 骨架 `scene_enter` / `scene_exit` | 成对出现（进设施演 3D 段、出来回大地图） |
| `代入` 系列 | `ctx_set` 步骤 | 纪律 4 |
| 执行块里的 `調查` | `when` 门控或 if 条件 | 同条件翻译规则 |
| `分歧:(N)` | 演绎剧本 choice + 骨架 `if ((Ctx::<槽>) == "值")` | 选项序 = TK5 索引序；值用可读语义词（`accept` / `reject`），禁止数字索引 |
| `場合別` / `場合分歧` | 骨架 `if` 块（1:1 嵌套） | 禁止拍平 |
| `主人公別` / `主人公分歧` | 机位选路：`if ((Hero::MainHero) == (Hero::lord_X))` | 有对白 → 机位块；纯效果 → 串行 if |
| `循環` / `脫出模塊` / 容器命令 | `loop` / `break` / `container_*` | 纪律 10 + loop 执行模型 |
| 结算命令（武將死亡/勢力滅亡/城主變更/宣戰/改名/軍團指令…） | 骨架 `effect` 步骤 | 参数按 CSV 参数列语义化（纪律 16）；同语义结算只生成一处，跨事件引用时注明「结算在 X 事件」 |
| `選擇:[[…]][[…]]` | 演绎剧本 choice 节点 | 选项文本进 i18n |
| 纯机制行（士气/义理更新等无演出价值的） | 不落 lines[]，在注释里标「机制行 → 承接系统」 | 承接系统按 CSV 分组落 02/03/13/14/17 |

**演出段怎么切**：一个源事件的执行块，按「進入設施 / 離開設施 + 主人公分歧机位块」切成若干演出段，每段一个演绎剧本 JSON（id = `<剧本>_<事件号>_seg<N>`）。合并/改名留给 §七 审核（09b 参照物：159 → first_audience + departure 两段）。

### 3.6 输出清单

## 六、查不到怎么办（🔴 v2：查不到 = 生成器缺陷，2026-08-27 用户裁定）

**两道闸，把「表外」堵在产物之前**：

## 八、与 16b 落点裁定表怎么对接

**一句话：16a 告诉翻译器「这个词翻成什么」，16b 告诉它「这个词将来由谁实现、存哪儿」。翻译器两样都读，但只把后者写进报告，不写进 JSON。**

翻译器实际消费 16a 的 13 列里的这几列：

| 列 | 翻译器拿它干什么 |
|---|---|
| 类别 / 所属域 / 太阁原词 | 查表主键（三元组）——同一个词在不同域里是不同的东西 |
| 我们侧名 | 直接拼进 DSL 的 token（`Hero.clan` → `(Hero::X.clan)`） |
| 参数 | 结算命令的参数位 → 字段名映射（纪律 16）；参数位不够就记未结清 |
| 值类型 | 决定值怎么写（布尔 → true/false、数字 → 裸数、枚举 → token、对象 → StringId） |
| **档** | 只进报告分档统计，不进 JSON |
| **载体 / 存档键** | 只进报告的「落仓清单」，告诉实现方这个字段将来存哪个仓 |
| **实现锚点** | 只进报告，告诉实现方读写落在哪个模块 |

**四档在运行时分别是什么行为**（16b 权威，翻译器只是转述）：

| 档 | 含义 | 运行时 | 桶狭间用到 |
|---|---|---|---|
| T1 | 引擎直取 | 直接读写骑砍原生字段 | 25 |
| T2 | 引擎改造 | 走引擎，但要本 mod 补一层（如 loop、facility 进出） | 21 |
| T3 | 本 mod 新造 | 落外置仓 / 13主命 / 17功勋 等，本 mod 自己实现读写 | 35 |
| T3-预留 | 可解析、可落仓、**行为空执行** + `[Scenario][TODO]` 日志 | 存得下读得出，动作本期不做 | 1（所屬海賊衆） |
| T0 | 降级 | 只作注释保留，不生成步骤 | 0 |

**落仓清单**（本剧本要存档的字段，报告自动汇总）：`lwn_scn_attr` 29 个、`lwn_scn_state` 6 个、`13` 2 个、`17` 4 个。这张清单就是 11-存档与配置 的输入——存档键必须在 11 的登记表里写清「存在哪」和「新档怎么清」，`fill_registry.py` 自检⑥ 会卡。

## 九、名字 → StringId 的对照表从哪来（`gen_entity_maps.py`）

**决定：对照表是生成物，不手写。** 理由：手写六张表（人物/模板角色/家族/势力/据点/地方）只覆盖桶狭间那几十个人，全量 2594 事件必漏，而且**漏了不报错**——直接生成哈希占位，静默错到底。

**生成链**：

```
Knowledge/骑砍2织丰角色ID对应/骑砍2太阁Mod表.xlsx   （用户指定的事实源）
  + Modules/Shokuho/ModuleData/**.xml                （存在性核对）
  → tools/gen_entity_maps.py
  → tools/entity_maps.py                             （生成物，禁止手改，铁律 22）
  → tk5_to_json.py import
```

**三条纪律**：产出全是 StringId，中文只作查找键（铁律 20）；要改映射 → 改脚本的对照字典再重跑（铁律 22）；每个 ID 都拿模块 XML 核过存在性，核不到的进 `MISSING_IN_XML`，翻译器照常用（数据包可能后补）但报告点名（铁律 5）。

**🔴 数据源在哪：活数据在基础 mod，不在扩展包。** `Modules/Shokuho/ModuleData/` 才是真数据（`settlements.xml` 847 座据点，另有港口/寺社/决斗三个补充据点文件；`spkingdoms/` 39 个势力；heroes/lords/spclans 全量）；`ShokuhoTaikouExpansionPack/ModuleData/Shokuho/` 下的同名文件是样例桩（settlements.xml 只有 5 条、spkingdoms.xml 只有 1 条），扩展包实际放的是 `DesignData/` `StoryJson/` `Patches/`。**扫错目录会误报几百条「缺失」。**

**繁简**：太阁源是繁体（織田信長），织丰表是简体（织田信长）。生成期用 zhconv 转一次，**两种写法都进表**，运行时不需要这个依赖。

**当前产出规模**：人物 1049 行 → 1052 个 ID / 1835 个查找键；家族 605、势力 134、据点 764。太阁城 180 条 → 对上骑砍真城 106 座、占位 74 座（其中 8 座连最近据点都没有：出石城、白鹿城、三原城、山口城、宇和岛城、久留米城、八代城、佐伯城，07 阶段要连位置一起定）。134 个势力里 95 个在模块 XML 里没注册（IsShokuho=0 的预备势力）；31 个「势力」在 Kingdom 表里没有条目，那是组织（水军/众/屋）→ 走 `Org::` 占位（16b 判 T3-预留）。
**但组织不是数据缺口**：织丰表另有一张 `ForceTaikou`（202 条），把组织按类型分好了——武家 132、商家 42、海贼众 15、忍者众 12，我们用到的 31 个组织**全部命中**（100%）。
缺的只是「组织 → StringId」这一列（该表只有名字和类型），由 07 数据包定 ID 后回填生成器。

**已知缺口**（07 阶段要补）：

- 令制国：织丰表**有**分区数据，但不是一张独立的表——它是 `CityTaikou` 的 `Area` 列，
  62 个分区（三河、尾张、骏河…）。**不能直接当令制国用**：太阁把小国合并了（`伊势志摩`、`相模伊豆`、
  `丹后若狭` 各是两国合一），也把大国拆了（`北信浓`/`南信浓`、`北近江`/`南近江`）。
  所以还是缺一张「令制国 ↔ Area」的对照（多对多），目前由脚本手维护 12 个令制国占位（`tk5_owari` 等）兜住桶狭间。
  **07 阶段的活儿是补这张对照表，不是补数据** —— 分区数据本身织丰表已给全。
- 桶狭间三个配角（服部小平太、毛利新介、簗田政綱）太阁有、织丰没有 → `TK5_ONLY_HERO` 占位。
- 几个容易认错的 ID：`lord_1_saito_dosan` 实际是太原雪齋（不是斋藤道三）；德川家康 = `lord_1_tokugawa` / `clan_tokugawa_1`。
