### 反编译证据（2026-08-25 实测，TaleWorlds.Library.dll 的 AssemblyLoader.LoadFrom 全文）

```csharp
public static Assembly LoadFrom(string assemblyFile, out AssemblyLoadResult result, bool showError = true)
{
    Assembly assembly = null;
    try { assembly = Assembly.LoadFrom(assemblyFile); result = Success; }
    catch (Exception ex) { if (showError) Debug.ShowMessageBox(...); result = CriticalError; }
    if (ApplicationPlatform.CurrentRuntimeLibrary == Runtime.DotNetCore
        && assembly != null && !_loadedAssemblies.Contains(assembly))
    {
        _loadedAssemblies.Add(assembly);
        AssemblyName[] referencedAssemblies = assembly.GetReferencedAssemblies();
        for (int i = 0; i < referencedAssemblies.Length; i++)
        {
            string text = referencedAssemblies[i].Name + ".dll";   // ← 相对文件名
            if (!text.StartsWith("System") && !text.StartsWith("mscorlib") && !text.StartsWith("netstandard"))
            {
                LoadFrom(text, out result);                        // ← 递归，游戏 bin 找不到 → LoadedWithErrors
                if (result != 0) result = LoadedWithErrors;
            }
        }
    }
    return assembly;
}
```

**关键结论**：
- 补丁点：`AssemblyLoader.LoadFrom(string, out AssemblyLoadResult, bool)` 静态方法，public，递归调用也走补丁
- 相对名 = 从游戏 bin（当前目录）找 → 实测游戏 bin 85 个 DLL **无** 0Harmony/ButterLib/MCMv5/UIExtenderEx/Serilog → 必然失败
- 织丰 bin 自带：0Harmony **2.2.2.0**（本机 Bannerlord.Harmony = **2.4.2.0**，强名版本精确匹配 → 必须加载 2.2.2 副本）/ Serilog / ColorMinePortable / System.Windows.Forms / System.Xml / System
- 织丰依赖的外部库在各模块 bin（已实测）：Bannerlord.ButterLib.dll（ButterLib 模块）、MCMv5.dll（MBOptionScreen 模块）、Bannerlord.UIExtenderEx.dll（UIExtenderEx 模块）
- `System.*` 前缀被原方法跳过相对名加载 → System.Windows.Forms.dll 等靠 `OnAssemblyResolve`（AssemblyLoader 静态构造挂的事件）→ 预加载织丰 bin 后事件可命中

### 实施步骤

#### 🔴 设计修正（2026-08-25 二轮反编译，实机验证失败后定位）

第一轮实施（OnSubModuleLoad 打补丁）真机失败（织丰仍报 dependency conflict）。二轮反编译（TaleWorlds.MountAndBlade.dll + TaleWorlds.ModuleManager.dll）发现**两处原 plan 未掌握的机制**，全部修正：

1. **OnSubModuleLoad 时机太晚——补丁必须在构造函数打**：
   - 游戏 `Initialize()` 流程 = `LoadSubModules(modules)` 先把**所有**模块 DLL 加载完（循环内 `AssemblyLoader.LoadFrom`，织丰的递归相对名失败发生在此）→ **循环结束后**才 `InitializeSubModuleBases()` 统一调各模块 `OnSubModuleLoad`
   - 结论：任何 OnSubModuleLoad 里的补丁都赶不上织丰加载——**必须在 MBSubModuleBase 构造函数打补丁**（`AddSubModule` 在加载循环内立即 `constructor.Invoke` 实例化，补充包在织丰前实例化即可抢跑）
2. **游戏内不解析 SubModule.xml 排序声明，启动器拓扑排序决定顺序**：
   - `ModuleHelper.GetModules()` 按 `_loadedModules`（Dictionary）插入序返回 = native `Utilities.GetModulesNames()`（`GetModulesCode().Split('*')`）顺序——**游戏内完全由启动器写好的顺序驱动，SubModule.xml 声明只在启动器排序时被解析**
   - 启动器排序 = `MBMath.TopologySort(modules, GetDependentModulesOf)`：**`DependedModules` 语义 = 依赖必须在前；`ModulesToLoadAfterThis` 语义 = 被引用模块在后**
   - 修正：**织丰必须移出 `DependedModules`**（放那里 = 启动器强制织丰先加载 = 补丁永远来不及），"织丰在后"只由 `ModulesToLoadAfterThis` 表达；`DependedModuleMetadata` 不参与排序（只作启动器 UI 提示），织丰条目删除
   - 排序结果：`… Bannerlord.Harmony < 补充包 < 织丰 < …`（拓扑无环）

### 🔴 验收结论（2026-08-25，实机五轮测试）

**方案 A 在 1.5.1 上不可行——织丰 DLL 与 1.5.1 API 签名硬不兼容（非 AssemblyLoader 问题）**：

| 轮次 | 观测 | 结论 |
|---|---|---|
| 1-2 | OnSubModuleLoad 打补丁 → 弹窗依旧 | OnSubModuleLoad 晚于所有 DLL 加载（反编译实锤），补丁必须构造函数打 |
| 3 | 构造函数补丁 → 弹窗依旧 | 排序声明矛盾（DependedModules 织丰在前 vs ModulesToLoadAfterThis 在后）→ 织丰移出 DependedModules |
| 4 | 三补丁全打（AssemblyLoader 3 参 / BCL LoadFrom / OnAssemblyResolve）→ 弹窗依旧 | compat_log 实锤：织丰.dll LoadFrom **Success**、递归未发生、OnAssemblyResolve 未触发——弹窗来自 AddSubModule |
| 5 | GetTypes 复现（BCL Postfix） | **GetTypes 抛 ReflectionTypeLoadException：86 个类型加载错误** |
| 6 | 签名对比（1.2.12DLL vs 1.5.1DLL 反编译） | 全部为 1.2.12→1.5.1 API 签名演进：`OpenBattleMission(string,bool)` → `(string,bool,string)`（1.5.1 新增 sceneLevels）等——**织丰 IL 引用旧签名 → Method not found / does not have an implementation** |

- **排序机制**（TaleWorlds.ModuleManager.dll `GetDependentModulesOf`）：启动器拓扑排序中 `DependedModules` 语义 = 依赖必须在前、`ModulesToLoadAfterThis` 语义 = 被引用模块在后；游戏内 `GetModules()` 按 Dictionary 插入序（= native `GetModulesCode()` 顺序，启动器排序产物），**SubModule.xml 排序声明只在启动器解析**
- **AssemblyLoader.OnAssemblyResolve**（TaleWorlds.Library.dll）：.NET Core 分支**只做已加载程序集全名精确匹配**（含版本号）——预加载织丰 bin 的 0Harmony 2.2.2 后其引用才能命中
- **Harmony self-call 机制**：方法体内的递归调用（`LoadFrom(text, out result)`）被 Harmony IL 重写指向 Original 方法、**不经过补丁**——外部调用经补丁（compat_log 有"绝对路径经过"）、递归零日志
- **1.2.12 形态差异**（1.2.12DLL 副本）：`LoadFrom(string, bool show_error = true)` **2 参**（无 out AssemblyLoadResult），递归 `LoadFrom(text)`，失败弹 "Cannot load" 窗；1.4+/1.5+ 为 3 参带 out——兼容层因此做**运行时探测**（3 参 → 2 参 fallback）

**④ 签名对比**（1.2.12DLL vs 1.5.1DLL 反编译，方法名二进制 UTF-8 定位——🔴 方法名在元数据 #Strings 是 UTF-8，CLAUDE.md 的 UTF-16LE 教训只适用于字符串字面量）：
```
1.2.12：IMission OpenBattleMission(string scene, bool usesTownDecalAtlas)          ← 2 参
1.5.1 ：IMission OpenBattleMission(string scene, bool usesTownDecalAtlas, string sceneLevels)  ← 3 参（新增 sceneLevels）
```
其余 85 个同类（`MaximumSeeingRange` / `GetBannerLootChanceFromDefeatedHero` / `GetVillageTaxRatio` / `GetGoldCostForUpgrade` / `get_MaxWagePaymentLimit` / `IsStartAllianceDecisionAllowedBetweenKingdoms` / `OnDeploymentPlanMade` / `GetDescriptionText`…）。

**⑤ 版本匹配说明**：织丰引用 ButterLib 2.9.10.0 / UIExtenderEx 2.12.0.0 / MCMv5 5.10.2.0，环境（1.2.12 与 1.5.1 同款）装 2.10.4 / 2.13.2 / 5.11.4——LoaderError 中**没有**库版本不匹配错误 → .NET Core 宽松版本匹配（higher 满足 lower 引用）生效，**报错纯为方法签名差异**。

**用户裁定（2026-08-25）**：织丰在 1.2.12 上**原生可运行**（1.2.12 = 织丰设计环境；用户 1.2.12 客户端库模块版本全部满足织丰声明——Harmony 2.4.2≥2.3.3 / ButterLib 2.10.4≥2.9.9 / MCM 5.11.4≥5.10.1 / UIExtenderEx 2.13.2≥2.11.0），**无需兼容层**。plan 07 记录"1.2.12 真机报 dependency conflict"系另一台机器环境问题（缺库模块），非普遍现象。

**兼容层最终定位：无使用场景**——1.5.1 救不了签名（GetTypes 86 个差异，加载路径之外）、1.2.12 原生可跑用不上。**代码已于 2026-08-25 删除**（用户确认：补充包回归剧本层定位，SubModule.xml 排序声明还原为织丰在前、MySubModule 回空壳、残留目录清理）——实现细节全部保留在上文「排查证据链实录」；兼容层未跟踪的编译产物与 compat_log 原始日志存档于主仓库 `Debug/compat_log_20260825.txt`。补充包的实际用途 = **剧本层**，等剧本工程 plan 审核后在 1.2.12 上基于织丰原生实施。
