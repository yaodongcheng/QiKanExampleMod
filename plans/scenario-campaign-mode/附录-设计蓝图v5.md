## Context

**🔴 项目定位（用户最终裁定，2026-08-24）**：LivingWorldNpcs **始终是通用玩法框架**——权游/三国玩家将来也要能用。日本战国只是前期实验题材。因此：
- **LWN 核心 = 可复用的机制性内容**：剧本引擎框架、程序化战斗编排器、条件原语、Quest 结合、转化管线通用部分——全部题材无关
- **日本战国数据层 = TaikouContent 数据包**：剧本 JSON、角色/城池映射、太阁5 转化产物、织丰适配、战国本地化——全部在内容包
- **机制验证纪律**：每个新机制先在卡拉迪亚演示剧本（通用世界观）验证，再进战国数据（Phase 0/1 = 机制，Phase 2/3 = 战国数据）
- **延伸目标**：权游/三国剧本 = 未来内容包，复用同一引擎（引擎的"剧本"/"actor 映射"/"条件原语"/"布局函数"天然题材无关——城池归属/角色存活/战争状态/营寨方阵在任何题材都成立）

**问题**：现有的日本战国世界观 mod（织丰 Shokuho 等）只是换美术/兵种/地图，缺历史战役剧情。玩家想体验类似太阁立志传/信长之野望/三国志的剧本模式：扮演历史角色（信长/光秀）经历桶狭间之战、本能寺之变等事件，且**不自己造任何地图和兵种美术**——全部依赖织丰前置 mod。本方案 = 通用剧本引擎（LWN）+ 战国数据包（TaikouContent）双轨。

**已确认的设计决策**（2026-08-24 用户裁定，含 v3 新增）：
1. **事件触发模型** = 条件驱动 + 时间窗（城池归属/角色归属/存活/战争状态等条件满足才触发），**且触发后王国战略级 AI 按事件纠正**（今川军锁定上洛、光秀军锁定进京）
2. **玩家扮演历史角色本人**（StartAsAnyone / 官方 ASO 开局机制）
3. **支持 IF 线**：玩家行为可以改变历史结局（救今川/救信长）
4. 🔴 **程序化战斗编排（v3）**：不手工制作场景/点位——场景内静态美术资源位置、每个 agent 位置与 AI 逻辑、所属阵营，全部由代码按数据参数程序化生成；但**符合叙事**（布局/氛围/溃散等叙事元素由数据表达）
5. 🔴 **资源只组合不造（v3）**：场景/装饰/兵种/角色/过场全部复用原版 + 织丰现有资源，对已有资源做组合
6. 🔴 **剧本内容来源 = 太阁立志传5 剧本转化（v3）**：织丰人物不全、城池与太阁5 不一致 → 需要转化管线（太阁5 剧本 → ScenarioJson），复用并优化已有 TaikouContent 转化

**关键事实**：
- 游戏 v1.5.1（开发机）；**织丰完整解压版在 1.2.12 客户端**（`MB2_Version\MB2_1.2.12\...\Modules\Shokuho\` + `Shokuho_CNs` 汉化），1.5.1 主目录只有 11GB 未解压的 Shokuho.7z；织丰 = `Shokuho.dll`（4MB）+ ModuleData XML + 场景 + GUI prefab
- 织丰是自定义 `GameType=ShokuhoCampaign` 的整体替换战役（日本大地图 + 40 王国 + 848 聚落 + 100+ 日式场景 `sho_battle_plain_a~k` / `sho_castle_map_a~k` / `meeting_castle_sho_a` + 全套日式兵种装备）
- 🔴 **worldview 铁律**：LWN 是通用 mod，核心禁止硬编码织丰/日本战国字串 → **架构 = LWN 核心放"剧本引擎框架"（通用数据驱动）+ 独立内容包 mod 放"剧本数据 + 织丰资源引用"**
- 项目已有 `Story/StoryEngine`（JSON 指令剧情演出引擎）+ `WorldEvent`（OccurredDay 时间线 + ScheduleCascadeEvent 延迟链）+ IM 私聊（LLM 人格化）+ `ActionRegistry`（45 动作）等成熟轮子

## 三、剧本引擎核心设计

### 3.1 剧本定义 JSON Schema（ScenarioJson/*.json）

```jsonc
{
  "id": "okehazama",
  "nameKey": "LWN_scn_okehazama_name",        // 铁律 13：本地化 key
  "playerRole": "oda_nobunaga",
  "eraYear": 1560,                             // 时代（驱动开档年龄/生死重置）
  "actors": [ {                                 // 铁律 5 两轮策略
    "id": "oda_nobunaga",
    "heroIds": ["sho_oda_nobunaga", "oda_nobunaga"],   // ①预设 ID 列表
    "fallbackPredicate": "HeroNameContains:信長",        // ②predicate 兜底（数据里写，代码无字串）
    "required": true,
    "eraAge": 26, "eraAlive": true, "clanIds": ["sho_clan_oda"],
    "spawnIfMissing": true,                     // 织丰角色不全 → HeroCreator.CreateSpecialHero 补造（v3）
    ...
  }],
  "initialWorldState": [                        // 开局世界纠正（ASO 应用后执行）
    { "action": "set_war", "a": "kingdom:sho_oda", "b": "kingdom:sho_imagawa", "value": true },
    { "action": "set_owner", "settlement": "sho_owari", "clan": "sho_clan_oda" } ],
  "events": [...], "endings": [...]
}
```

**事件字段**：`id / once / priority / when（条件树）/ effects[] / goto / onPlayerChoice（IF 分支挂点）/ delayDays（链式延迟，仿 ScheduleCascadeEvent）`

**条件原语**（ConditionEvaluator，对缺失对象安全返回 false + `[Scenario]` 日志）：

| 原语 | 语义 | 实现 |
|---|---|---|
| `SettlementOwner(settlement, clan)` | 城池归属 | `Settlement.Find(id)?.OwnerClan` |
| `HeroAlive/HeroDead(actor)` | 角色存活 | `hero.IsAlive` |
| `HeroClan(actor, clan)` | 角色归属 | `hero.Clan.StringId` |
| `AtWar(a, b, value)` | 战争状态 | `faction.IsAtWarWith(faction)` |
| `DateAfter/DateBefore(days)` | 相对开局时间窗 | `CampaignTime.Now.ToDays - startDay` |
| `FlagSet(flag)` | 剧本变量 | GlobalVariableBehavior `狀況::` 通道（StoryContext 既有） |
| `ArmyAt(leader, settlement, dist)` | 部队就位 | 纠正器到达感知缓存（<3f 同款） |
| `PlayerNear(settlement, dist)` / `PlayerIs(actor)` | 玩家 | `V.Pos(MobileParty.MainParty)` / ScenarioState |
| `EndingReached(id)` | 结局达成 | ScenarioState 查询 |

**结局**：`id / nameKey / when（条件树）/ effects / epilogue（演出）`，与事件同通道每日求值。

### 3.2 调度器（照抄 WorldEvent 双件套）

- `ScenarioStore`（static）：AllScenarios / ActiveScenario / ScenarioState（事件指针、已触发集合、分支 flag、锁定 party 登记表）+ `ResetAll()`（**必须补进 `MyBehavior.ResetAllCampaignState()`**）+ Serialize/Deserialize
- `ScenarioDirector : CampaignBehaviorBase`：DailyTick → `EvaluateScenarioTick()`（过滤 → 逐条条件求值 → priority 排序 → `TriggerEvent`，全部 try/catch 铁律 1）；Tick → 到达扫描（5s 低频）；OnNewGameCreated → 应用剧本；HeroKilled → 玩家死亡处理
- **演出挂起队列**：玩家在战斗/囚禁/演出中 → 演出类 effects 入队挂起，状态纠正类立即执行（防竞态）
- 延迟链：`delayDays>0` 事件入等待表（`dueDay = now+delayDays` 每日检查，逐字复用 `ScheduleCascadeEvent` 模式）

### 3.3 🔴 战略 AI 纠正器（用户特别要求）— ScenarioWarStateCorrector

```
CorrectWarState(a, b, war)      → DeclareWarAction.ApplyByDefault / MakePeaceAction(dailyTribute:0)
                                  ⚠️ 剧本导演动作非对话路径，不受 KingdomPoliticsFlow 对话铁律；
                                     但走原版 Action 类，事件总线（OnWarDeclared）照常广播
LockParty(leaderHero, targetRef, behavior)
  → ① leader 无 party：复用 SpawnEventParty「征用真人部队/新建」双路径（抽取为私有 PartyMobilizer）
  → ② GatherArmyAction.Apply(party, targetSettlement)  大军集结（"数万大军" = army 多 party 集结）
  → ③ V.BesiegeSettlement / V.EngageParty + party.Ai.SetDoNotMakeNewDecisions(true)  锁定
  → ④ 登记 LockedPartyRegistry
ReleaseParty(leader, reason)    → SetDoNotMakeNewDecisions(false)；剧本新建 party → 删
ReleaseAll()                    → 剧本结束/玩家死亡/abort 兜底
CleanupStaleLocks()             → 每日：party 消失/leader 死亡解锁；expiresAfterDays 到期自动释放（防死锁）
ArrivalScanTick()               → 每 5s 扫登记表，Distance<3f 到达 → 写 ArmyAt 缓存
```

### 3.4 效果 action 全集（ActionExecutor）

`set_flag/unset_flag`（`狀況::` 通道）、`war_correct/peace_correct`、`lock_party/release_party/army_gather`、`set_owner`（ChangeOwnerOfSettlementAction）、`change_hero_clan/change_clan_leader`、`kill_hero`（KillCharacterAction）、`spawn_hero`（CreateSpecialHero 补缺角色）、`teleport_party`、`scenario_notification`（过场）、`story_perform`（演出）、`im_message`、`spawn_army_near`（战场遭遇前置）、`grant_troops`（兵种经 ActorResolver 两轮解析）、`battle_mission`（🔴 程序化编排战斗，§四·3）

### 3.5 演出编排（四通道 + Quest 结合 + 演出强度）

1. **StoryEngine（PlaybackEngine 执行器化，见 3.8.7）**：运行时顺序执行**预编译演出产物**（分幕/站位/镜头/进出场已编译期算好）；保留新指令注册（写 handler + `CommandManager.Register("SCN_xxx", handler)`，禁止改 Execute）：`SCN_SET_WORLD`（内嵌 effects）/ `SCN_CUTSCENE`（过场）/ `SCN_IM`（私聊投递）/ `SCN_MEET`（SpawnHeroInFrontOfPlayer）/ `SCN_BATTLE`（程序化战斗触发）/ `SCN_FLAG` / `SCN_CHOICE_BRANCH`（IF 分支选择）；场景切换走既有 `進入設施` 指令
2. **🔴 演出面板 = StoryDialogVM 升级版（3.8.6）**：UI 重构为原版对话流风格 + StoryEngine 升级多 agent 互动（对话轮转/旁听者/镜头跟随说话人）；玩家可中断；**斩断 OnDialogClosed 旧链 + IM confirmFight 不碰它（铁律 16）**
3. **过场**：`ScenarioSceneNotificationData : SceneNotificationData`，角色槽位 `CampaignSceneNotificationHelper.CreateNotificationCharacterFromHero`
4. **对话四通道（按 intensity 分配）**：①通知横幅/IM（campaign 层）②Quest 化推进（L3，亲自前往）③原版对话流注入 + Persuasion 检定（`AddPlayerLine/AddDialogLineMultiAgent` 绑 `ScenarioQuest : QuestBase` 作为 relatedObject 清理锚点）④`SpeechChannel.SayPolished`（场内冒泡，无 LLM 走 Say 直出）
5. **🔴 Quest 结合（回应问 4）**：每个剧本阶段 = 一个 `StoryModeQuestBase` 子类实例（仿 CommissionQuest 自动创建、不可失败）：
   - `JournalLog` 写剧情日志（当前阶段目标 + 历史脉络），玩家在任务面板随时查看"我在剧本哪里、下一步做什么"
   - `QuestManager.TrackedObjects` 加地图标记（今川大军位置/京都/本能寺/目标 NPC）
   - 阶段推进 = `CompleteQuestWithSuccess` 完成当前 + 创建下一阶段（`onPlayerChoice` 分支走不同子类）；主命（3.8.2）复用同一 Quest 载体
   - 剧本完结 = `CompleteQuestWithBetrayal`/`Success` 五通道收束 → 结局通知

### 3.6 玩家身份注入

- 开局选择器：`[StartOptionsProvider]`（`#if MB2_GE_150`；`#else` MCM 下拉 + `custom.scenario_start <id>` 兜底）
- **时代重置应用链**（问 2 的核心，OnNewGameCreated 后执行，官方 API 已实证）：
  1. 遍历 `Hero.All` 按剧本 `eraYear` 生死年龄表：`SetBirthDay(CampaignTime.YearsFromNow(-age))` / `ChangeState(Active/NotSpawned)`（🔴 设未出生必须把生日设未来，防 OnHeroComesOfAge 拉活）/ `KillCharacterAction.Apply`（死）
  2. 技能/等级重算：先 `SetBirthDay` 再 `GetDefaultSkillsForHero` + `SetSkillValue` + `InitializeHeroDeveloper`（🔴 顺序依赖：GetDefaultSkillsForHero 判 Age；🔴 UnspentAttributePoints 可能变负，重算前确认；只开档做，存档中会掉级）
  3. 玩家身份：改名 → `ChangeKingdomAction.ApplyByJoinToKingdom` 换阵营 → 传送 `TeleportHeroAction`/`V.SetPos` + 部队填充（兵种两轮解析）→ 装备
  4. **角色补缺（v3）**：织丰角色不全 → 按剧本 actors 表 `spawnIfMissing` 用 `HeroCreator.CreateSpecialHero` 补造（名字/阵营/装备数据化），时代重置同管线

- 玩家死亡：`HandlePlayerDeath()` → 死亡结局过场 或 **换扮演继承者**（`HeroCreator.CreateSpecialHero` 新 Hero + 注入身份；🔴 **不替换 MainHero 对象**——引擎全局引用迁移风险）

### 3.8 🔴 体验设计（玩家视角，每阶段玩什么，2026-08-24 用户裁定补）

> 目标：以玩家对 3A 游戏的体验要求设计每个阶段——不事件时玩什么、事件如何营造叙事、演出在哪个层、玩家有没有操作。题材无关（权游/三国同样成立）。

#### 3.8.1 体验全景（三阶段循环）

```
【间隙期】自由沙盒 + 主命目标 + 背景推进
   主命系统派发阶段任务（Quest 化，有目标/追踪/报酬）→ 玩家自由选择接/不接
   背景剧本持续修正世界（战争状态/角色动向）→ 世界在"推进"，玩家感知时代压力
        ↓ 触发条件满足
【事件触发】叙事分级触达
   轻：通知横幅（大事发生）→ 中：IM 私聊（人物视角信息/立场）→ 重：Quest 引导（去 X 找 Y）
        ↓ 玩家亲自前往 / 条件达成
【演出期】mission 层亲历（演出强度谱系，见 3.8.5）
   多 NPC 演出 / 对话流检定 / 程序化战斗 / 过场 → 战果与选择写回世界 → 新状态进入下一循环
```

#### 3.8.2 🔴 主命系统（ScenarioOrders）——间隙期的目标感

- **数据**：剧本定义 `orders` 表（主命池：攻城/防守/讨伐/护送/领地治理/外交，按阶段与势力关系解锁）
- **派发**：剧本节拍（每周/月）由 ScenarioDirector 向玩家派发 1-2 条主命（来源 = 当前主公 actor，太阁式）
- **形态**：主命 = ScenarioQuest 阶段任务（JournalLog 目标 + TrackedObjects 地图标记 + 报酬 + 期限）；拒绝有代价（关系/剧本推进滞后——设计哲学原则二：给压力不剥夺选择）
- **与剧本的关系**：主命是"可选推进器"——接了加速剧本走向（如攻城成功 → 触发条件提前），不接则等时间窗/条件自然成熟（自由感）
- **题材无关**：主命池 = 数据，权游剧本换"领主命令"语义即可

#### 3.8.3 🔴 背景剧本（BackgroundScenario）——战略 AI 塑造时代背景

- **间隙期世界维护**：剧本定义背景修正表（`background` 段：战争状态维持、角色动向调防、势力消长节拍），每日由 ScenarioWarStateCorrector 施加——玩家做任何沙盒事都不破坏历史前提（织田-今川保持战争、光秀按动向调防）
- **乱世氛围**：既有 WorldEvent 系统降频保留（犯罪/冲突/社交事件），配合背景剧本塑造"战国乱世持续运转"感
- **与玩家行为的关系**：玩家可以改变背景（提前灭掉今川 → 桶狭间触发条件永久不满足 → 剧本分支/IF 判定），背景修正器只维护"未被玩家干预"的前提（设计哲学：自由感优先，修正器是叙事保险丝不是牢笼）

#### 3.8.4 叙事层级（campaign 层 vs mission 层，各用什么载体）

| 层 | 载体 | 用途 |
|---|---|---|
| **Campaign 层**（大地图） | IM 私聊/群聊（历史人物 LLM 消息）| 人物立场/密谋铺垫/日常关系（光秀苦闷线） |
| | 通知横幅（SceneNotification 轻量/InformationManager）| 大事发生（"今川大军集结北上！"） |
| | 🔴 **大地图交互**（靠近军团/聚落 → 触发对话流或 IM——**三国志式"军团头上人物说话"的骑砍2 实现**：地图上军团 party 可靠近、可互动、发言走 IM/冒泡） | 军团动向可视化 + 就地获取情报 |
| | Quest 引导（JournalLog + 地图标记）| 玩家下一步去哪（"去清洲见信长"） |
| **Mission 层**（场景内） | StoryEngine 预编译演出（登场/站位/镜头/多 NPC 对话）| 会议/密谋/重要时刻的情感演出 |
| | 原版对话流（深度一对一 + Persuasion 检定）| 谈判/劝降/审讯 |
| | AgentSay 冒泡 | 即时反应台词 |
| | 程序化战斗编排器 | 战役亲历 |
| | 过场（SceneNotificationData）| 章节点题（出征/胜利/死亡） |

**原则**：campaign 层给"信息与目标"，mission 层给"亲历与情感"。同一事件（如桶狭间）两层层层递进：通知（今川北上）→ IM（信长问计）→ Quest（集结部队/选择战术）→ mission 演出（前夜会议）→ 战斗 → 战果过场 → campaign 后果（停战/洗牌）。

#### 3.8.5 🔴 演出强度谱系（玩家操作设计——禁止纯点点点）

每个剧情节点数据标 `intensity`（转化管线按事件类型自动分配，人工可调）：

| intensity | 形态 | 玩家操作 | 例子 |
|---|---|---|---|
| L1 | 通知横幅/过场标题 | 阅读 | 大事发生播报 |
| L2 | IM 对话 | 可回复/选择立场 | 光秀日常铺垫 |
| L3 | 🔴 Quest 化推进 | **亲自位移**（去 X 找 Y）+ 标记指路 | "去清洲见信长" |
| L4 | 原版对话流 | 对话 + 说服检定（d20）| 劝降今川将领 |
| L5 | 演出面板（DialogCutsceneVM）| AVG 式对话/选择，**但玩家可走动/拔剑/中断** | 敦盛之舞、本能寺前夜 |
| L6 | 程序化战斗 | 亲自战斗（奇袭/巷战/溃散）| 桶狭间、本能寺 |
| L7 | 操作型节点（小游戏/检定）| 技能检定/限时操作 | 潜入、开锁 |

🔴 **Quest 化推进纪律（用户核心要求）**：关键剧情节点优先走 L3（玩家亲自前往目标 NPC 触发），**禁止全部 AVG 切场景**——骑砍2 的代入感在"玩家是世界的角色"，不是"看剧的观众"。

#### 3.8.6 🔴 演出 UI 决策（多 NPC 互动剧情的载体，2026-08-24 用户裁定）

- **判断**：原版对话流 = 玩家↔单 NPC 状态机，**不足以演绎多 NPC 互动**（会议/密谋/多方表态）
- **方案：升级 StoryDialogVM + StoryEngine 管理多 agent 互动**（废弃 = 无现行调用链 = 可自由重制的安全地盘）：
  - 🔴 **StoryDialogVM UI 重构**：视觉风格**接近原版对话流**（原版对话面板的视觉语言：说话人名字/头像/文本区、底部选项列表样式——玩家零学习成本），保留复用其现成组件模式（`StoryOptionVM` 选项/预测/置灰、继续提示、`StoryTraitVM` 特质）
  - 🔴 **StoryEngine 升级**：管理**多 agent 互动**——对话轮转（说话人切换：`對話` 指令带说话人，UI 自动切名字/头像/镜头）、旁听者（在场但未发言的 agent 站立/坐下/注视）、多方表态（分歧节点多 NPC 依次发言）、镜头跟随说话人（SpringArmCameraView 模板按说话人切换）
  - 🔴 **斩断旧链**：`OnDialogClosed → OnDialogueEnded → GenerateEventAsync`（无当面对话时 `_memory` null 必崩）——升级时彻底移除该回调链；🔴 IM 弹窗确认回调（ATTACK/DUEL/KNOCKOUT/STEAL 的 confirmFight）**禁止**改调重制版 `Close()`（沿用 IM 面板自己的关闭路径，铁律 16）
  - 运行时执行器 = StoryEngine 预编译产物（3.8.7）；Mission 层演出期间玩家输入不锁死（可 Esc/走动/拔剑——设计哲学自由感）
  - UI 纪律：按 wheels.d/ui.md（GauntletLayer 摘层守卫/输入门控/手柄兼容/层序表）

#### 3.8.7 🔴 StoryCompiler 预生成（消除运行时动态分析，回应 StoryEngine 批评）

- **问题**（用户指出）：现有 StoryEngine 运行时解析太阁 JSON——`ExecutionContext.RefreshSceneScope`/`GetCurrentSceneParticipants` 每幕扫描后续节点、站位/镜头运行时推断（`AssignSlots`/镜头模板动态选），重复计算且质量不稳
- **方案：内容包侧 `StoryCompiler`（编译器，Python/C# 工具）**：太阁 JSON → 中间表示 → **编译产物**（预计算的：分幕表、每幕参与者清单、站位分配（StageSlot）、镜头序列（SpringArmCameraView 模板+机位）、出场/退场指令展开、时间轴、选项树展开）
- **编译产物可人工导演标注**（`_director_notes.json` 覆盖层：指定某幕用某镜头/某站位——质量人工可调，编译时合并）
- **StoryEngine 改造 = 执行器化**：运行时只顺序执行编译产物（`PlaybackEngine`），移除动态分析路径（RefreshSceneScope/AssignSlots 等移出运行时）；保留场景切换/等待/阻塞语义
- **收益**：运行时零扫描（稳定+性能）、镜头/站位质量可控可调、无 LLM 时同管线（编译产物兜底文本）

### 4.4 🔴 程序化战斗编排器（v3 核心）— Scenario/Battle/

**定位**：通用"战斗演出编排"系统。剧本 JSON 声明编排参数 → 代码程序化生成整个 mission（场景选择/装饰/agent 位置/AI 逻辑/阵营/阶段/叙事钩子）。**新战役 = 写 JSON，零美术工作。**

```
Scenario/Battle/
├─ BattlePreset.cs        编排参数模型（JSON 反序列化：场景/Atmosphere/布局/兵力/阶段/叙事钩子）
├─ BattleLayouts.cs       🔴 布局函数库（纯数学计算，叙事表达核心）：
│     环形营寨(camp_raid) / 方阵(square) / 队列(column) / 哨站链(outposts) / 突入方向(entry_side)
│     每个布局 = 函数(center, radius, counts) → 位置清单（主将位/卫队位/装饰位/入口位）
├─ ProceduralSpawnLogic.cs  MissionLogic：按布局清单 Mission.SpawnAgent 放置全部 agent
│     + 所属阵营（Team 分配）+ 初始被动（沉睡/警戒状态）
├─ ProceduralDecorLogic.cs  MissionLogic：CreateMissionObjectFromPrefab 摆装饰
│     素材表 = 原版/织丰 prefab 清单（营帐/篝火/火把粒子/栅栏），铁律 5 两轮策略
├─ PhaseWaveLogic.cs      分阶段波次（替代 HideoutPhasedMissionController 的场景实体依赖）
│     阶段表（JSON）：每阶段敌人位置（布局函数）/数量/兵种 → 程序化生成，支持叙事阶段推进
├─ NarrativeBattleLogic.cs 叙事钩子：
│     主将死→Panic() 溃散 / 战斗内事件点（SCN_CHOICE_BRANCH 挂接）/ 战果写 flag（battle_won/lost）
└─ BattleScenes.cs        场景选择（两轮策略）：剧本 sceneIds → 织丰 sho_battle_*/sho_castle_map_* / 原版 battle_* 兜底
```

**编排参数 JSON 示例**（剧本 events effects 里 `battle_mission` 引用）：

```jsonc
{
  "sceneIds": ["sho_battle_plain_a", "battle_plain_a"],     // 铁律 5 两轮
  "atmosphere": "TOD_photo_02_30_rainy_night",              // 雨夜预设
  "layout": {
    "type": "camp_raid",                                     // 布局函数：营地突袭
    "camp": { "center": "map_center", "radius": 25,
              "tents": 6, "campfires": 3, "guards": 8,
              "generalAtCenter": true },                     // 今川义元在营中（叙事核心）
    "attacker": { "entrySide": "north_east", "distance": 60 }
  },
  "forces": {
    "defender": { "troopIds": ["sho_imagawa_guard", "sho_ashigaru"], "counts": [20, 80], "general": "imagawa_yoshimoto" },
    "attacker": { "troopIds": ["sho_oda_kiheitai", "sho_ashigaru"], "counts": [30, 120], "general": "player" }
  },
  "initialState": { "defender": "sleeping" },                // 沉睡营地（初始被动）
  "phases": [                                                 // 本能寺式分阶段
    { "name": "gate",  "defender": [ { "pos": "gate_left", "count": 10 } ] }, ...

```

**叙事保真原则（v3）**：程序化 ≠ 平庸。叙事元素全部数据表达——主将位置（营中央+卫队）、突入方向（雨夜侧翼）、氛围（雨/夜/火）、溃散触发（主将死→Panic）、阶段推进（叙事节点）——布局函数库就是"叙事位置的数学表达"。

### 4.5 🔴 桶狭间演绎链（七步，全程序化，无新美术）

1. **大军压境（大地图）**：`army_gather` 效果——今川义元集结多 party（GatherArmyAction）→ `lock_party` 锁定围攻尾张（SetDoNotMakeNewDecisions + BesiegeSettlement）；织田军锁防守。画面 = 数万军（大 roster）向尾张推进
2. **"没发现织田军"（隐蔽模拟）**：今川 army AI 被锁定只向尾张移动，**无视贴身织田 party**——玩家带少量兵力贴着今川军走不被攻击（引擎无天气视野，这是唯一可靠模拟；配合雨夜叙事铺垫）
3. **雨夜氛围**：Atmosphere `TOD_photo_02_30_rainy_night`（凌晨 2:30 + 大雨 + 浓雾）贯穿演出与战斗
4. **突袭触发**：玩家主动 Engage 今川本阵 party（EncounterManager.StartPartyEncounter 或直达 `battle_mission` 效果）→ 程序化 mission
5. **雨夜突袭 mission（程序化）**：场景 = 织丰通用平原 `sho_battle_plain_a`（两轮兜底）→ 布局函数 `camp_raid` 程序化生成：营帐/篝火/火把粒子摆一圈（prefab 数据表）、今川义元营中央 + 卫队环形、织田军从地图边缘雨夜侧翼出生；**敌方初始沉睡**（AI 冻结，触发点激活）；`CustomBattleCombatant` 注入双方兵种；`InitWithSinglePhase` 定兵力
6. **义元死→溃散（原生）**：`NarrativeBattleLogic.OnAgentRemoved` 检测 `affectedAgent == 敌方 Team.GeneralAgent` → 敌方全员 `CommonAIComponent.Panic()` → `BattleEndLogic` 判 EnemyRetreated 胜利。玩家亲手击杀义元则自然触发（击杀主将士气 ×2 是原生公式）
7. **战后世界纠正**：其余今川 party 溃逃回远江（`SetPartyAiAction.GetActionForVisitingSettlement`）+ `ReleaseParty` 解锁 + 停战/尾张洗牌（史实或 IF）

### 4.6 🔴 本能寺演绎链（六步，全程序化）

1. **前奏（IM 铺垫）**：光秀苦闷私聊线（3-4 条）+ 织田家内政状态纠正
2. **大军进京**：光秀 party `lock_party` 锁定向京都移动（EngageParty/VisitingSettlement）；玩家扮演信长在京都能看到光秀军接近
3. **本能寺之夜 mission（程序化）**：场景 = 织丰城堡 `sho_castle_map_a`（两轮兜底）→ `PhaseWaveLogic` **分阶段逐波（大门→回廊→大殿→本堂，阶段表 JSON）**，光秀军逐波进攻，信长（玩家）率少数卫队且战且退；`SCN_CHOICE_BRANCH`（死守/突围/召集家臣 → flag）
4. **大火氛围（程序化）**：布局函数在殿堂/回廊摆 `fire_big`/`torch_fire` 粒子（CreateMissionObjectFromPrefab/挂粒子）+ `AmbientColor` 橙红 + 夜 atmosphere；`FireSpreadLogic` 按 MissionTime 递增粒子密度——**氛围级大火**（引擎无真实燃烧蔓延，诚实边界）
5. **战果分流**：信长败/亡（史实）→ 死亡过场 + `HandlePlayerDeath`（换扮演秀吉或光秀，IF 展开）；信长突围成功（IF）→ 全局 IF 线
6. **战后纠正**：光秀败/降（ChangeKingdomAction 纠偏 + ReleaseParty）→ 秀吉继任（ChangeClanLeader + 结局过场）或 IF 结局

## 八、🔴 织丰接入方案（Shokuho.dll 反编译实锤，2026-08-24）

**实锤结论**：Shokuho.dll 是 1.2.12 专属产物，**在 1.5.1 硬失败**：
- ❌ 引用 `TaleWorlds.MountAndBlade.CustomBattle.dll`——1.5.1 程序集不存在（二进制 grep 0 命中），加载即崩
- ❌ `SetPartyAiAction.GetActionFor*(2参)` 约 20 处——1.5.1 签名已改 4~5 参 → MissingMethodException
- ✅ 世界生成 **100% 靠 XML**（聚落/角色/氏族/王国全走 SubModule.xml Xmls 列表，无代码生成逻辑）；场景/prefab/粒子/汉化全部版本无关
- ✅ 不用 MissionGameStarter（用 MissionState.OpenNew + BattleSideEnum，与现代一致）

**🔴 结论：克隆注册层 = 唯一主方案**（数据全用织丰，不要 Shokuho.dll）：

```
新建内容包 DLL（ScenarioCampaignGameManager 体系，替代 ShokuhoCampaign）：
  ├─ 注册 GameType 入口（主菜单"历史剧本战役"选项——替代 Shokuho 的 CustomSandBoxNewGame）
  │    🔴 同时解决年代问题：不锁 1568（织丰 CampaignStartTime=1568-04-05 是反射写入的静态字段），
  │        由剧本选择（ASO/主菜单）决定初始世界状态（1560 桶狭间/1582 本能寺）
  ├─ CampaignGameStarter.AddModel：织丰 60 个 GameModel 中【与剧本/战斗相关的】选择性复刻或跳过
  │    （织丰 models 是 1.2.12 面，逐一评估；首版可只挂最小集——战斗奖励/晋升等，其余跳过）
  ├─ 注册织丰行为（AddBehaviors）：同理选择性；原创 Issue Quest/抽卡/海战等跳过（与剧本无关）
  ├─ 加载织丰 XML：SubModule.xml Xmls 列表（IncludedGameTypes=ShokuhoCampaign 门控自动加载
  │    ——我们的 GameType 若命名为 ShokuhoCampaign 或兼容值则织丰 XML 零改动）
  └─ LoadSPBattleScenes(sho_sp_battle_scenes.xml)（地形索引→场景映射 31 条目，程序化选场数据模型）
  放弃（数据替代不了或与剧本无关）：内嵌 Diplomacy（启动弹窗 AbortGame 逻辑必须绕开）、
  抽卡 Gacha/海战/港口/寺庙/决斗模型（首版跳过）、UIExtenderEx 自定义 ViewModel（首版跳过）
```

**1.2.12 回退路线**（若克隆注册层受阻）：三锚点支持（MB2_V1212），代价 = ASO 不可用退 MCM 下拉 + 开发机降级/双客户端。
