## 结论（审批人只看这七条也够）

1. **分四档，不是三档。** 用户提的三点之外必须有第四档「做不了」——太阁有、骑砍2 没有、且硬做体验反而更差（小游戏、数字输入框）。第四档**不是丢弃**：每条都写死降级形态，剧情流程一步不少。
2. **新增字段只加一个新类别：剧本外置属性仓。** 骑砍2 没有的 ~175 个字段（功勋、技能、各种标志位、组织字段）全部住进一张「对象 → 字段 → 值」的稀疏表，**共用一个存档字段（引擎原生字典，非 JSON 字符串）、一行清档**。不给每个字段单写存档字段。
3. **命令不是"存下来"，是"演出来"。** 154 条命令逐条给出玩家在骑砍2 里**真能看到的**落地形态；实在没有对应物的 14 条给降级形态（技能检定代替小游戏等），并在事件 JSON 里留痕。
4. **本文件是唯一事实源。** 现在散在 `gen_registry_tables.py` / `build_registry_csv.py` 两个脚本里的手写字典，凡属"落点裁定"的部分全部搬进本文件；脚本从本文件生成 `registry_verdicts.py`，16a 照旧重跑（铁律 22：生成物不手改）。
5. **现在 CSV 里的 ✅/🔴 有假阳性，必须重判。** 根因：备注不是裁定，是「这个属性有没有被 `ATTR_TYPES` 收录」反推出来的。反例：`軍團.使用狀況`、`軍團.結果`、`大名家.戰略`、`大名家.大方針`、`城.訓練度` 都标着「✅ 引擎查询器」，骑砍2 里**根本没有这些字段**。本表用显式裁定替换反推。
6. **"没有遗漏"靠机器保证，不靠人保证。** 注入脚本做扣除法：16a 每一行必须被本表某条裁定认领，剩一行就 `exit 1`；反向也查——本表有裁定但语料里查无此词，同样报错（防表里长草）。
7. **本文件只是方案，不写代码。** 审核通过后按 §十 的六步实施。

## 三、T3 的落地底座：三个仓、两个存档键

**先说结论**：所有 T3 的东西只往三个地方放，多一个都不许加。

| 仓 | 存什么 | 谁写 | 进存档？ |
|---|---|---|---|
| **外置属性仓** `ScenarioAttrStore` | 对象上骑砍2 没有的字段（功勋/技能/标志位/组织字段/主命字段） | 剧本运行时 | ✅ 一个键 |
| **旗标计数仓** `ScenarioStateStore` | `Flag::` 172 个旗标、`Time::counter_N` 85 个计数器、`Variable::` 剧本变量、`GlobalSlot::` 全局槽 | 剧本运行时 | ✅ 一个键（并入 11 已有的剧本进度段） |
| **数据包表** `ScenarioDataPack` | 卡/流派/组织/物品/身份链/官职链/CG/BGM/设施/区域定义 | 作者写文件，加载期只读 | ❌ 不进存档 |

**为什么数据包不进存档**：它是定义（"世界上有哪几张卡"），不是状态（"谁持有这张卡"）。状态一律进外置属性仓。这样数据包能随版本更新而不弄坏老存档。

### 3.1 外置属性仓怎么存

- **形状**：`域:StringId` → `字段名` → `值`。例：`Hero:lord_1_oda` → `merit_samurai` → `120`。
- 🔴 **逐实体 key，不是全局单值**（2026-08-27 用户确认）：每个人物 / 每个大名家 / 每个据点 / 每个组织**各自一行**，互不干扰。
  「一个存档键」说的是**存档字段只声明一个**（避免 175 个 `SaveableField` 爆炸），那个键里装的是整张二维表：

  ```
  lwn_scn_attr = {
    "Hero:lord_1_oda":        { "merit_samurai": 120, "flag_ambition": true },
    "Hero:lord_1_imagawa":    { "merit_samurai": 340 },
    "Settlement:town_CHUB11": { "kokudaka_base": 45000 },
    "Clan:clan_oda_1":        { "strategy": "上洛" }
  }
  ```

  加一个新字段 = 表里多一个格子，存档结构零改动、老档不用迁移。
- **全局的东西不进这个仓**：`Flag::` / `Time::counter_N` / `Variable::` / `GlobalSlot::` 是无主状态，进旗标计数仓（3.2）。判据一句话：**这条状态是"某个人/某座城的"，还是"整个世界的"**——前者进属性仓带 key，后者进旗标仓不带 key。
- **key 只能用 StringId，禁止显示名**（铁律 20）：`Hero:lord_1_oda`，不是 `Hero:织田信长`。理由：显示名是本地化产物且可被改名（玩家改据点名 / 不同语言不同名），拿名字当 key 会在改名或换语言后丢状态。
- **对象暂时不存在时的 key**（孤儿键）：读取时对象查不到 → 返回空值，**但不删这一行**。理由：对象可能只是"这个时代还没登场"或"某个 mod 没加载"，删了就永久丢剧情状态；保留则对象回来后状态自动接上。清理只走控制台命令（人工确认），不自动执行。
- **值只有四型**：数字 / 布尔 / 字符串 / 对象引用。对象引用存 `域:StringId` 字符串，**不存实例**——存实例会跟着引擎对象销毁而悬空。
- **稀疏**：只存「被写过且不等于默认值」的格子。没写过的读出来 = 数据包默认值；数据包也没有 = 空值。
- **默认值来源**：06 时代重置时从数据包（人物总表 125 列）灌入，所以「武力」「忍术」一开局就是真实数值，不是全 0。
- **读的顺序**（DSL 引用解析）：① 原生适配器（T1/T2 走引擎）→ ② 外置仓 → ③ 空值。**任何一步失败都返回空值，永不抛异常**（铁律 1/2；空值参与比较一律为假）。
- **写的唯一入口**：`set_attr(对象, 字段, 值)`。太阁的 `更新:` 命令统一编译到它。写之前查类型（16 §四 值类型体系），类型不符 = **加载期报错**，不是运行期静默。
- 🔴 **存档：走引擎原生字典，禁止用 JSON 字符串键**（2026-08-27 修正，原方案会毁存档）：

  | 存档字段 | C# 类型 | 装什么 |
  |---|---|---|
  | `lwn_scn_attr` | `Dictionary<string, Dictionary<string,string>>` | 外层 key = `域:StringId`，内层 = 字段名 → 值 |

  - **为什么不能用 JSON 字符串**：存档 Strings 表每条字符串的长度字段是 16 位 signed short（上限 32767 字节），单条超了溢出成负数 → 整张表错位 → **读档必崩**。项目为此立了 `SaveStringGuard.GuardJson`（阈值 30000 字节，超了裁剪，见 `Debug/SaveGuard.cs`）。本仓估算 400 KB，塞进一个字符串键 = **被一刀裁到 30000 字节，93% 的剧情状态静默丢失**——正是本节明令禁止的事。
  - **字典为什么安全**：32767 是**每条字符串**的限制，不是每表。字典里每个字符串都是小串（字段名几十字节、值几字节），各自独立计长，两万格子无压力，**且没有裁剪逻辑参与**。
  - **类型注册**：`SaveableTypeDefiner` 必须注册 `Dictionary<string,string>` 和 `Dictionary<string,Dictionary<string,string>>`——**项目已注册**（`Story/StoryContext.cs` 的 `SaveDefiner`），零新增。
  - **值统一存字符串**：数字/布尔/引用一律序列化成字符串，读时按 16a「值类型」列解析。类型是注册表已知的，不靠猜。
  - **清档**：`ResetAllCampaignState()` 里加一行清空——**新开档不清 = 串档红线**（11 已立此规矩）。
- **体积**：估算 2000 人 × 平均 8 个非默认格 + 据点/家族/组织若干 ≈ 2 万格。字典形态下无单条上限风险；仍在超过 5 万格时打日志告警并提供控制台命令导出排查（排查异常膨胀，不是防崩）。

**为什么不给每个字段单独写存档字段**：175 个字段 × 手写 `SaveableField` = 存档定义爆炸；以后加一个字段就要动存档结构、老档还要写迁移。一张表 = 加字段零存档改动。

### 3.2 旗标计数仓怎么存

- `Flag::flag_N`（172 个）：布尔集合。`set_flag` / `clear_flag` 写，条件里裸引用读。
- `Time::counter_N`（85 个）：整数计数器，**每日 +1**（挂 Campaign 层日 tick，不挂 `OnApplicationTick`），`counter_reset` 归零。太阁的"距那件事过了几天"全靠它。
- `Variable::` / `GlobalSlot::`：16 §一 已定义，本表不重复。
- **存档字段 `lwn_scn_state`**，类型 `Dictionary<string,string>`（同样已注册，零新增）：key 带前缀区分四类（`Flag::flag_88` / `Time::counter_3` / `Variable::x` / `GlobalSlot::y`），值统一字符串。
- **11 的剧本进度段并入这个字段**（当前剧本 / 事件指针 / 已触发集合 / 锁定部队登记），不另开键。理由：它们与旗标同生共死（剧本停止一起清空），一个键 = 一处清档、一处排查。
- 新开档在 `ResetAllCampaignState()` 一并清空。

### 4.5 塌缩拆分裁定（必须拆，不拆翻译器写回会串）

## 九、本文件的机器格式（脚本怎么读它）

**原则：正文表就是数据，不另开一份数据块。** 一份内容两处写 = 迟早分叉。

### 9.1 两种表，固定表头

**① 行裁定**（针对单个太阁原词）——表前一行放标记 `<!-- verdict:row 类别=属性 -->`：

| 太阁原词 | 侧名 | 档 | 值类型 | 载体 | 读实现 | 写实现 | 存档键 | 降级 | 待核实 |
|---|---|---|---|---|---|---|---|---|---|

**② 组裁定**（针对一整组，按 `类别 + 所属域`（可加前缀）匹配）——标记 `<!-- verdict:group -->`：

| 匹配（类别/域/前缀） | 档 | 值类型 | 载体 | 侧名规则 | 存档键 | 降级 | 说明 |
|---|---|---|---|---|---|---|---|

**解析规则**：行裁定优先于组裁定；两者都没命中 = 报错退出。

### 9.2 列的取值约定（避免自由文本）

- **档**：`T0` / `T1` / `T2` / `T3` / `T3-预留`，只此五值。
- **载体**：`引擎` / `外置仓` / `旗标仓` / `计数器仓` / `数据包` / `Ctx` / `Variable` / `GlobalSlot` / `13主命` / `17功勋` / `02战略` / `03战斗` / `05演出` / `无`。
- **存档键**：`lwn_scn_attr` / `lwn_scn_state` / `13` / `17` / `无`。
- **降级**：新增取值 `空执行`——解析通过、参数落仓、不改世界、打 `[Scenario][TODO]` 日志（T3-预留专用）。
- **值类型**：必须 ∈ 16 §四 的值类型体系（布尔 / 数字 / 字符串 / `枚举:XX` / 空 / `对象:XX`）。
- **侧名**：纯 ASCII（现有 `side_ok` 断言继续生效）；多域侧名用 ` / ` 分段，翻译器按主语域选段（08b 踩坑⑮）。
- **降级**：档 = `T0` 时必填，其余留空。
- **待核实**：填写待反编译确认的 API 名；非空的条目**禁止判 T1**。

### 9.3 与两个生成脚本的分工（清楚的边界）

| **裁定** | 档 / 载体 / 读写实现 / 存档键 / 降级 / 侧名 / 值类型 | **本文件（16b）** |

这条边界就是"设计"与"解析"的分界。搬错了会让两边都难改。

## 十一、与 08b 的对接：可执行 + 还原度
