# plan 审计轮子（写作纪律 + 矛盾核对，2026-08-26 登记）

> 场景：写完 plan 自查 / 审 plan 前预检 / 大改后全量复核。
> 来源：2026-08-26 全文件夹审计（23 份 plan，4 组并行 + 核心交叉核对）产出本清单；当次实测抓到硬矛盾 21 条、不说人话 11 条、存疑 15 条。

## 一、人话五问（铁律 21 可执行版，每条结论过一遍）

1. **结论先行？**「决定：X」打头，理由 ≤1 句；禁止大段铺陈再引结论
2. **无思考史？**正文无「先 A → 发现 B → 定 C」推导；历史踩坑不进正文（存档类文档除外）
3. **中文直白？**术语首次出现括注大白话；英文 token 只出现在代码/API/文件路径/JSON
4. **名词有实义？**读者不查代码能理解；抽象名词堆砌 = 没想清楚
5. **四问自答？**「结论是什么/凭什么/代价/要做哪几件事」答不上就重写

## 二、矛盾核对锚点（按序查，多文件场景用）

1. **README 总纲**：21 条裁定 + 审核表 + DSL 要点速查 + 横切纪律 ← 所有 plan 的准绳；改 plan 不改 README = 必查项
2. **单所有权文件**：16（注册表/trigger/facility/谓词/token）、01（语法/调度/validator 编号）、05（步骤类型/演绎指令）——**两处对同一 token 的定义冲突 = 以单所有权文件为准改另一处**（2026-08-26 实测：16 的 field_battle_start 监听点与 01 冲突）
3. **跨文件数字/编号**：事件号（`文件名_事件ID`）、行数自称 vs 实际、数量口径（169 分文件 vs 2594 事件号、30 种 vs 19 项、1385 vs 1051 vs 1381 类）
4. **状态标记**：审核表 vs 文件自称状态；「废弃/折叠/禁止实施」标注 vs 正文还当现行方案写（12:38 克隆注册层实测残留）
5. **README 计数**：总纲自称的 plan/附录数量 vs 审核表/索引实际行数（2026-08-26 实测 15+2 vs 实际 17+3）
6. **剧本文件 ↔ 源事件**：逐句核对 `Knowledge/太阁事件包/TK5AllEvents_merged.txt`——工具 = `plans/scenario-campaign-mode/tools/verify_tk5_coverage.py`（强检查演出行、弱检查触发/条件）

## 三、剧本写作纪律核对（七条，写剧本前先过）

1. token 先查 16 注册表再写，注册表外禁止落 JSON
2. 注释描述的可执行动作必须落 JSON 字段（actor_action/action/face/camera）
3. 无机制消费方的字段禁止（tone 教训）
4. 台词三态标注：【原文】/【原文改编】/【演绎补写】，禁止无标注编造
5. 旁白走 inquiry，禁止改编成角色台词（史官腔 = 上帝视角违规）
6. TK5 行完整性：源事件每一行必须有对应，**禁止省略/转述/丢弃**；删行不行，`🔴待XX` 占位可以
7. trigger/once/priority 落 JSON 字段，禁止只写注释

## 五、审计分工法（多文件场景的标准动作）

1. **先读锚点**：README 总纲 + 单所有权文件（01/16）——所有 agent 的准绳
2. **按组分派**：机制组 / 验证组 / 剧本组 / 附录组，每组一份固定输出格式（不说人话 / 逻辑矛盾 / 纪律违反 / 存疑 / 每文件定性），行号必须 Read 后真实
3. **汇总抽查**：对每条发现独立验证（grep/Read 行号）后才入报告——agent 报告不可全信（2026-08-26 实测 agent 也有误报：ECF00000 曾被疑为 EFF0C300 笔误，实为两个真实事件文件）
4. **修复派单**：修复 agent 按「文件:行号 + 目标 + 修法」逐条派单，禁止超范围发挥；改完 git diff 复验

## 六、修复顺序建议（2026-08-26 实测优先级）

1. 会导致实现出错的规格错误（flag 双义 / 重复键 / 条件漏分支 / 断链）→ 先修
2. 机制权威文件冲突（01 vs 16 的 trigger 表）→ 次修
3. 数字/计数/状态标记同步 → 再修
4. 人话问题 → 最后统一过
