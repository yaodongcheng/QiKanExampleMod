## 一、核心架构：Issue → Quest 双层模型

原版骑砍2 的 NPC 委托任务使用**两层分离设计**，这是理解整套系统最关键的概念：

```
┌─────────────────────────────────────────────────────────────────┐
│  Issue (IssueBase) — 问题/事件层                                 │
│  "某NPC遇到了一个问题，希望有人帮忙解决"                            │
│  - 独立于玩家存在（AI领主也能接）                                   │
│  - 有时效性（过期自动消失）                                        │
│  - 对定居点产生负面效果（IssueEffect）                              │
│  - 三种解决方式：Quest / Alternative / Lord                       │
├─────────────────────────────────────────────────────────────────┤
│  Quest (QuestBase) — 任务/委托层                                  │
│  "玩家接受了这个Issue，现在变成了一个活跃的任务"                     │
│  - 玩家专属（QuestManager 追踪）                                   │
│  - 有任务日志（JournalLog）                                        │
│  - 有任务子步骤（QuestTaskBase）                                   │
│  - 五种完成方式：Success / Cancel / Fail / Timeout / Betrayal     │
└─────────────────────────────────────────────────────────────────┘
```

### 1.1 IssueBase（问题基类）

**文件位置**：`TaleWorlds.CampaignSystem.dll` → `TaleWorlds.CampaignSystem.Issues.IssueBase`

```csharp
public abstract class IssueBase : MBObjectBase
{
    // ═══ 生命周期状态 ═══
    internal enum IssueState { Ongoing, SolvingWithQuestSolution, 
                               SolvingWithAlternativeSolution, SolvingWithLordSolution }

    // ═══ 核心属性 ═══
    Hero IssueOwner;           // 谁有这个Issue（任务发布者）
    CampaignTime IssueDueTime; // 过期时间
    QuestBase IssueQuest;      // 关联的Quest（玩家接受后才创建）
    
    // ═══ 三种解决路径的文本定义 ═══
    abstract TextObject IssueBriefByIssueGiver;          // NPC的"我有一个麻烦"开场白
    abstract TextObject IssueQuestSolutionExplanationByIssueGiver; // NPC解释"你亲自去办"
    virtual TextObject IssueAlternativeSolutionExplanationByIssueGiver; // NPC解释"派人去办"
    virtual TextObject IssueLordSolutionExplanationByIssueGiver; // NPC解释"请领主出面"
    
    // ═══ 关键方法 ═══
    abstract QuestBase GenerateIssueQuest(string questId); // 工厂方法：每个Issue创建自己的Quest
    abstract IssueFrequency GetFrequency();                // VeryCommon / Common / Rare
    abstract bool CanPlayerTakeQuestConditions(...);       // 前置条件检查
    abstract bool IssueStayAliveConditions();              // Issue是否仍然有效
    abstract void HourlyTick();                            // 每小时更新（超时/状态检查）
    
    // ═══ 三种解决路径的启动 ═══
    bool StartIssueWithQuest();            // 玩家亲自接任务
    void StartIssueWithAlternativeSolution(); // 派同伴+士兵去解决
    void StartIssueWithLordSolution();     // 花影响力请附近领主解决
}
```

### 1.2 QuestBase（任务基类）

**文件位置**：`TaleWorlds.CampaignSystem.dll` → `TaleWorlds.CampaignSystem.QuestBase`

```csharp
public abstract class QuestBase : MBObjectBase
{
    Hero QuestGiver;                 // 发布者
    CampaignTime QuestDueTime;       // 时限
    int RewardGold;                  // 奖励金
    MBList<QuestTaskBase> TaskList;  // 子任务列表（如"找到目标"→"说服目标"→"护送目标"）
    MBList<JournalLog> JournalEntries; // 任务日志
    
    // ═══ 对话流 ═══
    DialogFlow OfferDialogFlow;      // 接任务时的对话
    DialogFlow DiscussDialogFlow;    // 进行中的讨论对话
    DialogFlow QuestCharacterDialogFlow; // 与任务目标的对话
    
    // ═══ 五种完成方式 ═══
    void CompleteQuestWithSuccess();
    void CompleteQuestWithCancel(TextObject log);
    void CompleteQuestWithFail(TextObject log);
    void CompleteQuestWithTimeOut(TextObject log);
    void CompleteQuestWithBetrayal(TextObject log); // 背叛任务发布者
    
    // ═══ 生命周期回调 ═══
    abstract void OnStartQuest();
    virtual void OnCompleteWithSuccess();
    virtual void OnCanceled();
    virtual void OnFailed();
    virtual void OnTimedOut();
    virtual void OnBetrayal();
    abstract void SetDialogs();      // 注册对话选项
}
```

### 1.3 管理类分工

| 类 | 职责 | DLL |
|----|------|-----|
| `IssueManager` | Issue 的创建、派遣、每日Tick（过期/失效检查）、冷却管理 | CampaignSystem |
| `QuestManager` | Quest 的追踪、日志、地图标记、超时检查 | CampaignSystem |
| `IssueModel` | 难度系数、替代解决方案的成功率/伤亡/持续时间计算 | CampaignSystem |
| `DefaultIssueModel` | IssueModel 的具体实现（难度=玩家进度0.1~1.0，冷却=30天） | CampaignSystem |

### 1.4 一条Issue的完整生命周期

```
1. 生成阶段
   NPC Hero 到达条件 → CampaignBehavior.OnCheckForIssue 触发
   → IssueManager.AddPotentialIssueData(hero, issueData)
   → IssueManager.CreateNewIssue(issueData, hero)
   → CampaignEventDispatcher.OnNewIssueCreated

2. 待接阶段 (IssueState.Ongoing)
   玩家进定居点 → 菜单显示蓝色感叹号 "!"
   → 对话中显示 "Is there anything I can do for you?"
   → 玩家选择 "Go on." 进入任务介绍

3. 接受阶段（三选一）
   ┌─ Quest Solution: 玩家亲自去 → StartIssueWithQuest() → GenerateIssueQuest()
   ├─ Alternative Solution: 派同伴 → StartIssueWithAlternativeSolution()
   └─ Lord Solution: 请领主 → StartIssueWithLordSolution()

4. 执行阶段
   Quest: 玩家在大地图/场景中完成 QuestTask 链
   Alternative: 倒计时结束自动结算（成功/失败掷骰）
   Lord: 进入对话流（可能有CounterOffer）

5. 完成阶段
   Quest成功 → 奖励+关系变更 → CompleteIssueWithQuest()
   超时 → CompleteIssueWithTimedOut()
   NPC死亡/条件失效 → CompleteIssueWithStayAliveConditionsFailed()
   背叛 → CompleteIssueWithBetrayal()

6. 清理阶段
   IssueFinalized() → IssueManager.DeactivateIssue()
   → ConversationManager.RemoveRelatedLines()
   → VisualTrackerManager.RemoveTrackedObject()
```

## 三、任务触发机制

### 3.1 两个触发路径

原版由 `IssuesCampaignBehavior` 统一调度，分两条路径触发：

**路径 A：定居点路径（Notables → Issue）**
- 通过 `OnSettlementTick()` 周期性触发，每天分摊到 N 个定居点（每个 Tick 处理 1 个定居点）
- 城镇：1~3 个 Issue
- 村庄：1~2 个 Issue
- 开局初始分布：70% 村庄、80% 城镇获得 Issue（加权洗牌均匀分布）

**路径 B：家族路径（Lords → Issue）**
- 通过 `DailyTickClan(Clan)` 每天触发
- 每个家族 10%~20% 的符合条件的领主获得 Issue
- 开局初始：12% 的领主获得 Issue

### 3.2 生成概率公式（指数衰减）

```csharp
// IssuesCampaignBehavior.GetIssueGenerationChance:
float GetIssueGenerationChance(int currentIssueCount, int maxIssueCount)
{
    float ratio = 1f - (float)currentIssueCount / (float)maxIssueCount;
    return 0.3f * ratio * ratio;  // 指数衰减
}
// 0个Issue → 30%概率 → 填满50%后 → 7.5% → 越接近上限越难生成
```

### 3.3 触发流程

```
游戏每日Tick / 定居点周期Tick
  ↓
IssuesCampaignBehavior.OnSettlementTick / DailyTickClan
  ↓ 判定生成概率（指数衰减）
  ↓
对每个符合条件的 Hero（无现有 Issue）：
  CampaignEventDispatcher.OnCheckForIssue(hero)
  ↓ 所有 IssueBehavior 响应此事件
  ↓ 检查该 Hero 类型是否匹配（Headman / GangLeader / Lord / Artisan...）
  ↓ 检查冷却时间是否已过（IssueCoolDownData: 30天冷却）
  ↓ 检查是否有相同类型的活跃 Issue（IssueQuestCanBeDuplicated）
  ↓
IssueManager.AddPotentialIssueData(hero, potentialIssueData)
  ↓ （如果 ConditionsHold 不满足，注册无效的 PotentialIssueData 作为标记）
  ↓
IssueManager.CreateNewIssue(pid, hero)
  → hero.OnIssueCreatedForHero(issue)
  → CampaignEventDispatcher.OnNewIssueCreated(issue)
  → 地图上出现蓝色感叹号 "!"
```

### 3.4 频率评分系统

```csharp
// IssuesCampaignBehavior 内部：
// IssueFrequency → 分值映射:
//   VeryCommon → 6
//   Common     → 3
//   Rare       → 1

// 评分公式（简化）:
score = frequencyRatio × (1 + bonus - existingRatio/frequencyRatio)
// - frequencyRatio = 该类型的频率分 / 所有候选的总频率分
// - existingRatio = 当前世界上已有的同类型Issue / 目标总数
// - bonus = 正常游戏时 0.2，初始分配时 -0.4
// 惩罚已过度代表的类型（某种Issue太多→该类型评分被压低）
```

- **定居点选 Issue**：加权随机（`MBRandom.ChooseWeighted`），按分数加权抽取
- **家族选 Issue**：最高分优先（`OrderByDescending(x => x.Score).First()`）

### 3.5 前置条件系统（PreconditionFlags）

每个 Issue 通过 `CanPlayerTakeQuestConditions()` 返回 14 种可能的拒绝原因：

| Flag | 含义 | 玩家的拒绝文本 |
|------|------|--------------|
| `AtWar` | 你我在交战国 | "我们正在交战，不便交谈" |
| `NotInSameFaction` | 不是同一阵营 | "我只和本王国领主或忠诚佣兵合作" |
| `MainHeroIsKingdomLeader` | 你是国王 | "不敢劳烦陛下" |
| `PlayerIsOwnerOfSettlement` | 你是城主 | "不敢劳烦城主大人" |
| `ClanTier` | 家族等级不够 | "没听说过你的家族" |
| `Renown` | 声望不够 | "我需要更有声望的人" |
| `Relation` | 关系太差 | "你我的过去不太愉快" |
| `Skill` | 技能不够 | "你需要{SKILL_NAME}方面的经验" |
| `Money` | 钱不够 | "我需要有钱的人" |
| `Influence` | 影响力不够 | "你需要有点影响力" |
| `Wounded` | 你受伤了 | "你应该养好伤再来" |
| `NotEnoughTroops` | 兵力不足 | "你手下的兵不够" |
| `PartySizeLimit` | 部队上限不够 | "你没法再接收更多士兵了" |
| `ClanIsMercenary` | 你是雇佣兵 | "这个任务不适合雇佣兵" |

### 3.3 冷却系统（IssueCoolDownData）

- **类型冷却**：每个 Issue 类型完成任务后有 30 天冷却（`IssueModel.IssueOwnerCoolDownInDays`）
- **NPC 冷却**：同一个 NPC 在冷却期内不会再产生新 Issue
- **关联冷却**：某些任务共享冷却（如 `SnareTheWealthy` / `EscortMerchantCaravan` / `CaravanAmbush` 共享）
- **失效检查**：`DailyTick` 中通过 `ExpireInvalidData()` 清理过期冷却

### 3.4 地图标记

- **蓝色感叹号 `!`**：有可用 Issue 的 NPC（`IssueQuestFlags.AvailableIssue`）
- **蓝色问号 `?`**：有进行中 Quest/Alternative 的 NPC（`IssueQuestFlags.ActiveIssue`）
- 通过 `IssueManager.CheckIssueForMenuLocations()` 在进入定居点时刷新

## 四、三种解决路径（玩家体验阶段）

### 4.1 Quest Solution（亲自执行）— 标准玩家体验

```
阶段 1：发现与接洽
  - 进入定居点，看到 NPC 头顶蓝色 "!"
  - 对话 → "Is there anything I can do for you?"
  - NPC 叙述 IssueBriefByIssueGiver（"我遇到一个麻烦..."）
  - 玩家选择 IssueAcceptByPlayer（"说下去"）
  - NPC 详细解释 IssueQuestSolutionExplanationByIssueGiver
  - 玩家选择 IssueQuestSolutionAcceptByPlayer（"交给我吧"）

阶段 2：任务激活
  - IssueManager.StartIssueQuest(issueOwner)
  - Issue.StartIssueWithQuest()
    → 设置难度系数
    → 调用 GenerateIssueQuest() 创建具体 Quest
    → 状态变为 SolvingWithQuestSolution
    → 触发 OnIssueUpdated(PlayerStartedIssueQuestClassicSolution)
  - Quest.StartQuest()
    → OnStartQuest() 回调（添加追踪对象、创建初始JournalLog）
    → RegisterEvents() 注册事件监听
    → questGiver 加入 QuestManager.TrackedObjects
    → 触发 OnQuestStarted(quest)
  - 任务日志（JournalLog）添加到玩家日志面板

阶段 3：任务执行
  - 玩家在大地图上按日志指引行动
  - QuestTask 链驱动：定位目标 → 到达 → 对话/战斗 → 推进
  - 每个任务步骤由一个 QuestTaskBase 子类管理：
    · ArenaDuelQuestTask — 竞技场决斗
    · BeginConversationInitiatedByAIQuestTask — NPC主动找你对话
    · FollowAgentQuestTask — 跟随某个Agent
    · (各Issue都有自己的专用QuestTask)
  - 地图追踪：QuestManager.TrackedObjects 显示目标位置

阶段 4：任务结算
  - Quest 达成条件 → CompleteQuestWithSuccess()
    → OnCompleteWithSuccess()
    → 给予奖励（Gold + Relation + 可能的物品/经验）
    → FinalizeQuest() → 清理追踪/日志
    → 触发 OnQuestCompleted(Success)
    → Issue.CompleteIssueWithQuest() → IssueFinalized()
  - 失败路径：超时/条件失效/主动取消
```

### 4.2 Alternative Solution（派同伴代办）— 简化体验

```
阶段 1：接洽（同上）
  - NPC 解释 IssueAlternativeSolutionExplanationByIssueGiver
  - "如果能派一个能干的人和几个好兵，{DAYS}天应该能解决"
  - 玩家选择 IssueAlternativeSolutionAcceptByPlayer
  - 选择一个同伴（Hero）+ 分配士兵

阶段 2：派遣
  - Issue.StartIssueWithAlternativeSolution()
    → 计算成功率（基于同伴技能 vs 需求技能）
    → 计算伤亡率（基于部队数量vs 需求数量）
    → 同伴 + 士兵从玩家部队移除
    → 同伴标记 DisableHeroAction（不可使用）
    → 设置返回时间 AlternativeSolutionReturnTimeForTroops
    → 状态变为 SolvingWithAlternativeSolution
    → 日志显示 "你的士兵将在{X}天后返回"

阶段 3：等待
  - 每日 Tick 更新进度条（JournalLog progress）
  - 到达返回时间前1天：IssueEffect 消除
  - 同伴不可用（在任务外执行任务）

阶段 4：结算
  - 到达返回时间 → CompleteIssueWithAlternativeSolution()
    → 掷骰：MBRandom.RandomFloat > failureChance
    → 成功：
      · 同伴获得技能经验
      · 士兵获得 XP（可能升级）
      · 部分士兵受伤
      · 给予金钱奖励
      · AlternativeSolutionEndWithSuccessConsequence()
    → 失败：
      · 士兵阵亡（根据 casualtyCount）
      · 同伴受伤
      · AlternativeSolutionEndWithFailureConsequence()
    → 同伴+剩余士兵返回部队
```

**关键公式（DefaultIssueModel）**：

```
成功率 = 1 - min((需求技能 - 同伴技能) × 0.5 / 100, 0.9)
       = 1 - failureChance
       ≈ 同伴技能越高，成功率越高（最高90%）

伤亡率 = clamp(ceil(需求部队 × value), 1, 需求部队)
       where value = clamp((需求技能 / 同伴技能) × 0.1, 0.2, 0.8)
       ≈ 同伴技能越高，伤亡越少（最低20%）

实际天数 = 基础天数 + 2 × clamp(需求技能 / 同伴技能, 0, 10)
         ≈ 同伴技能越高，耗时越短

实际部队 = 基础部队 × clamp(需求技能 / 同伴技能, 0.2, 1.2)
         ≈ 同伴技能越高，需要部队越少
```

### 4.3 Lord Solution（请领主帮忙）— 仅 FamilyFeudIssue

```
阶段 1：接洽
  - NPC 解释 IssueLordSolutionExplanationByIssueGiver
  - "如果您能说服附近的{领主}出面，20影响力应该够了"
  - 玩家选择 IssueLordSolutionAcceptByPlayer
  - 消耗 Clan 影响力

阶段 2：执行
  - Issue.StartIssueWithLordSolution()
    → 状态变为 SolvingWithLordSolution
    → 监听 BeforeGameMenuOpenedEvent
    → 玩家下次进入大地图时自动触发与 CounterOfferHero 的对话

阶段 3：CounterOffer（可能有）
  - CounterOfferHero 提出条件：
    · 如果接受 → 背叛原 NPC，帮 CounterOfferHero
    · 如果拒绝 → 保持对原 NPC 的承诺
  - 如果 CounterOfferHero == null → 直接完成

阶段 4：结算
  - 拒绝 CounterOffer → CompleteIssueWithLordSolutionWithRefuseCounterOffer()
    → 消耗影响力 → 获得金钱奖励 → 成功
  - 接受 CounterOffer → CompleteIssueWithLordSolutionWithAcceptCounterOffer()
    → 背叛原 NPC → CompleteIssueWithBetrayal()
```

## 六、IssueEffect 惩罚系统

当一个 Issue 未解决时，会对 NPC 所在定居点产生持续负面效果。

### 6.1 架构

```
IssueEffect (MBObjectBase, XML定义)
  ↓
IssueBase.GetActiveIssueEffectAmount(issueEffect)
  ↓ 各 Issue 重写 GetIssueEffectAmountInternal()
  ↓
DefaultIssueModel.GetIssueEffectsOfSettlement(issueEffect, settlement)
  → 遍历定居点所有 Notables 的 Issue
  → 累加每个 Issue 的 effect amount
  → 返回 ExplainedNumber（含修饰符）
```

### 6.2 常见 IssueEffect 类型

| Effect ID（示例） | 效果 | 影响的游戏数据 |
|-------------------|------|---------------|
| `security` | 治安下降 | 定居点 Security 值 |
| `loyalty` | 忠诚度下降 | 定居点 Loyalty 值 |
| `prosperity` | 繁荣度下降 | 定居点 Prosperity 值 |
| `militia` | 民兵减少 | 定居点 Militia 值 |
| `food` | 食物短缺 | 定居点 Food 值 |

### 6.3 Effect 应用时机

- 玩家进入定居点时实时计算（通过 `GetIssueEffectsOfSettlement`）
- Alternative 模式下在返回前 **1 天**自动清除 Effect（`_areIssueEffectsResolved = true`）
- Issue 完成后 Effect 自动清除

## 七、与对话系统的集成

### 7.1 对话 Token 体系

原版使用 **5 个对话 Token** 将 Issue 系统挂接到对话引擎：

| Token | 用途 | 在何处被检查 |
|-------|------|------------|
| `hero_main_options` | NPC 主选项列表（"我能帮你做什么？"） | ConversationManager |
| `issue_offer` | 显示 "Is there anything I can do?" 选项 | IssueManager |
| `issue_classic_quest_start` | "我亲自去" 选项 | IssueManager |
| `issue_discuss_alternative_solution` | "换个方式解决" 选项 | IssueManager |
| `quest_offer` | 进行中 Quest 的对话（"关于那个任务..."） | QuestManager |

### 7.2 对话优先级

```csharp
// IssueBase 中定义
public const int IssueRelatedConversationPriority = 125;
```

当玩家进入定居点与 NPC 对话时：
1. 先检查 NPC 是否有 Quest（进行中的任务） → 显示 `quest_offer` token
2. 再检查 NPC 是否有 Issue（可用任务） → 显示 `issue_offer` token
3. 上面都处理完后，再显示常规对话选项

### 7.3 DialogFlow（对话流）

每个 Quest 通过 `SetDialogs()` 方法注册三个 DialogFlow：

```csharp
protected DialogFlow OfferDialogFlow;        // 接任务时的对话分支
protected DialogFlow DiscussDialogFlow;      // 进行中的讨论分支
protected DialogFlow QuestCharacterDialogFlow; // 与任务目标NPC的对话分支
```

`DialogFlow` 是骑砍2的对话树系统，支持：
- 条件分支（基于游戏状态）
- 说服检查（Persuasion）
- 选项后果（关系/金钱/战斗等）
- 嵌套对话（一个选项触发子对话）

## 九、对 LivingWorldNpcs 委托系统的启示

### 9.1 原版系统值得借鉴的设计

1. **Issue/Quest 双层分离**：这是个优雅的设计——Issue 是"世界中的问题"，Quest 是"玩家的任务"。NPC 可以有 Issue 但玩家还没接，Issue 有自己的生命周期（过期/条件失效），不依赖玩家存在。**我们的 CommissionHubIssue 应该对标 IssueBase。**

2. **三种解决路径**：Quest/Alternative/Lord 三种方式给了玩家选择权，降低了对特定技能树的强制依赖。尤其 Alternative Solution 的计算公式（成功率/伤亡/时长基于同伴技能）设计精巧。

3. **PreconditionFlags 系统**：用 Flags 枚举表示拒绝原因，配合对应的 TextObject 说明。这是一种干净的前置条件 → 玩家反馈映射。

4. **IssueCoolDownData**：类型+目标冷却，防止玩家反复刷同类任务。`SnareTheWealthy` / `EscortMerchantCaravan` / `CaravanAmbush` 共享冷却是个好模式。

5. **IssueEffect 惩罚**：未解决的任务对定居点产生持续负面影响，给了玩家动力去解决。这个机制让任务不只是"赚外快"，而是"维持世界运转"的一部分。

### 9.2 原版系统的不足（我们该做得更好的地方）

1. **没有叙事深度**：原版 40 种任务都是模板化的文本替换（`{TARGET_HERO.LINK}` / `{BASE_REWARD}`），没有人物弧光、没有情感深度、没有长期后果。做完了就是做完了，世界不会记住。

2. **没有 NPC 记忆**：任务发布者不会记得你帮他做过什么（除了冰冷的关系值+5），第二次见面就是"我能帮你做什么？"的复读机。**这正是 LivingWorldNpcs 的 NPC 记忆系统可以发力的地方。**

3. **没有动态生成**：所有任务都是预定义的 Issue 子类，无法根据世界状态动态组合。没有"因为 A 领主和 B 商人有了恩怨，所以产生了一个独特的委托"。

4. **Lord Solution 几乎没用**：40 种任务只有 1 种有 Lord Solution，设计空间巨大。

5. **背叛后果不充分**：SnareTheWealthy 的三选一虽然设计好，但后续影响太弱——没有 NPC 网络传播你的恶名，没有报复链。

6. **莫得感情的任务文本**：TextObject 是纯静态的，不支持根据玩家关系/历史/性格动态变化（除了少数 persona 检查）。

### 9.3 我们可以复用的原版基础设施

如果我们想要兼容原版系统（可选），以下是可以直接 hook 的点：

| 原版入口 | 我们能做什么 |
|---------|------------|
| `IssueManager.AddPotentialIssueData()` | 注入我们自己生成的 Issue |
| `CampaignEventDispatcher.OnCheckForIssue` | 通过事件响应添加自定义 Issue |
| `ConversationManager` + `issue_offer` token | 挂接自定义对话选项 |
| `QuestManager.TrackedObjects` | 为自定义 Quest 添加地图追踪 |
| `IssueBase` 子类化 | 创建自定义 Issue 类型 |
| `QuestBase` 子类化 | 创建自定义 Quest 流程 |

### 9.4 我们已有的轮子与委托系统的契合

| 我们的系统 | 能增强委托任务的方面 |
|-----------|-------------------|
| `CommissionHubIssue` / `CommissionQuest` | 对标 IssueBase/QuestBase，已有基本框架 |
| `NPCProfile` / `SingNpcMemorySystem` | NPC 记忆 → 任务发布者记住你的帮助 |
| `TrustSystem` / `InfamySystem` | 信任度影响任务可用性，恶名度传播后果 |
| `CommissionNarrative` | LLM 生成动态任务叙事 |
| `ComplicationTable` | 任务中途的意外/转折（动态事件注入） |
| `JourneyEvents` | 任务执行过程中触发的事件 |
| `NotificationPipeline` | 任务相关通知的递送 |
| `WorldEventSimulator` | 世界事件驱动的任务生成（而不是死板的冷却计时） |
| `HeroNemesisTracker` | NPC 对玩家的长期恩怨追踪 |
