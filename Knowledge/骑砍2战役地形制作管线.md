## 一、编辑器里没有"PNG 导入"这种单独功能——在 Terrain 面板，参数是四件套

已核实：引擎 DLL 里没有 ImportHeight/TerrainTools 字符串；导入功能藏在场景编辑器 Terrain Properties 面板。

| 面板字段 | 含义 | 换算关系 |
|---|---|---|
| **X** | 横节点数 | 世界宽(m) = X × Size |
| **Y** | 纵节点数 | 世界高(m) = Y × Size |
| **Single Node Size** | 每节点边长(米) | 世界尺寸的真正控制者 |
| **Single Node Dim** | 每节点分辨率 | 总顶点 = X×Dim × Y×Dim；**PNG 必须与之 1:1** |

**三条铁律**：
1. 世界尺寸（米）**只由 X×Size / Y×Size 决定**，与 PNG 分辨率无关
2. **PNG 像素数 ≡ 地形顶点数**（1:1 强制，错像素=错位/形变）
3. 节点数与 Dim 可互换：X=16, Size=128, Dim=256 与 X=32, Size=64, Dim=128 等价（同世界体、同顶点、不同单节点分辨率；原版可参考量≈4096×4096 顶点）

按钮（同一面板，自上而下）：`Import Heightmap` / `Import Materialmap` / `Import Normalmap from Heightmap`（可选）/ `Export Heightmap`（导出核对）。

### 🔴 官方导入流程（2026-09-05 moddocs 原文确认，与你实测的"直接成功"无矛盾）

1. **先有图层**：Terrain Paint 面板"Add Layer"建一个图层 → **选中该图层** → 属性面板 → `CTRL+A` 选中全部节点 → 点导入按钮
2. **新场景自带 `default` 图层**（`terrain_materials.xml` 第一个条目）且默认选中 → 所以导入高度图/材质图**不需要手动 Add Layer**，直接成功（2026-09-05 用户确认："因为有 default，所以高度图直接成功了"）
3. 材质精度官方原文：高度图 **8/16 位（PNG 或 raw）**；材质图 **8bit**
4. 官方"四件" = **四类图层**（碎屑图 debris / 水流图 flowmap / 植被图 vegetation / 基岩图 bedrock）—— ⚠️ 与我们文档用语"四件套"（X/Y/Size/Dim）撞名，是两码事

## 二、Python 管线（2026-09-05 版，替换旧「亮度差分吃整图」）

旧版被废弃的原因：道路黄线/河蓝线被抬成山脊与刻槽、海上航路白点线变成小岛、雪山(灰白/蓝白)混进滩、平原亮度方向搞反。**现管线 = 元素语义分层**：

| 元素 | 判据（源图色域采样） | 高度 |
|---|---|---|
| 海（深浅湾） | blueish & lum≤165 | 0（统一） |
| 湖 | 陆上大块蓝 | 0（=海） |
| 航路/浪花 | 海上低饱和亮色 + 开运算线状/点状 | 归海 → 0 |
| 滩/岩墙/雪 | 粗白 & 距海 d 连续映射（灰白/淡蓝白/淡绿白）| 0.05+d/1200（贴海0.05→岩0.14→雪0.55+雪脊差分，上限0.95） |
| 平原 | 绿区亮度分段低位（Koei 画法：平原亮黄绿、山地暗绿 → 亮度与山高**反向**）| ~0.2 |
| 山地 | 绿区亮度分段高位 + 山影高斯差分（亮度门控增益）| 0.25~0.5+细节 |
| 富士蓝白雪 | 蓝判 + 最大白点簇 → 雪帽；PEAKS 地标锥体豁免海清零 | 0.6-0.88 |
| 道路/河线 | 黄色判/细蓝判 + 开运算线状 | 中值替换底色（不抬山不刻槽） |

**⚠️ 关键裁定（用户亲报 2026-09-05）**：富士山 == 源图坐标 (10500,7000)（山顶白点=格线交点）。
- 富士雪是「蓝白 + 中心白点 + 绿地包围」——**蓝白雪≠水**（与海同色系），曾被三次当湖泊判 0 → 黑斑/蓝湖 bug
- 修复 = 雪帽检测（**最大白点簇**判定：全图最大白点簇=雪顶；浪花/礁石白点都是小簇自动排除）+ **PEAKS 地标区豁免海清零**（高度图、材质图两边同源，禁止分叉）

**材质图四通道**（RGBA 256，与高度图同尺度 1:1）—— ⚠️ 见「三·七官方流程」：**官方做法 = 每图层一张 8bit 灰度 mask**；下图 RGBA 拼图层是我们当时实测的**捷径形式**（引擎侧存在整图导入路径，具体以"三·八 待验证"为准）：
- R 草（平原档，h_base<0.30）/ G 林（山地档）/ B 沙土（白系离海≤400）/ A 雪（白系离海>400 且 **hm≥0.42**（高度先决，防海岸白带误判）+ 雪帽 + 地标峰锥）
- 海/湖 = 全 0（引擎材质层 water/河层覆盖，并非"引擎自动铺水面"——见「三·六水系统」）
- ⚠️ 查看器不认 RGBA 四通道（A=雪 被当 alpha → 变半透明黑）；**用 `matpreview_*.png` 人看**

**脚本内部五段**：①语义分类（海陆/白/黄/河 + 雪帽）②高度合成（分层 + 山影）③地标层（`PEAKS` 表 =(cx, cy, 锥半径, 峰高, 山体基底高, 山体半径)）④材质派生 ⑤预览/QA。改素材/改参数 → 重跑一条命令。

> 🔴 2026-09-05 晚（用户裁定「普通地表压平、富士独大」）：`HEIGHT_GAMMA=1.4` 压平曲线（平 0.2→0.105 / 普通山 0.45→0.30 / 顶值保留）+ PEAKS 富士峰高 `0.88→1.00` 顶格；场景 min/max 定稿 **0 / 21**（富士≈19.6m=3.1× 普通山；平滑中值把尖顶磨 1.0→0.933，正常）。雪 mask 0.3%→0.1%（γ 后 0.5~0.55 白脊降破 0.42 阈值转沙，属预期）。

## 🔴 三、素材分辨率 × Terrain 四件套：不同分辨率的图适配同一世界的方法论

**问题**：为什么给两张分辨率不同的日本地图（japanmap_hires 15840×10080 / TaikouMap2 704×448），都能生成同一世界尺寸、同一语义内容的地形，精细度如何换算？

**回答（三层）**：

### 第一层：世界尺寸只由四件套决定
```
世界宽(m) = X × Size；世界高(m) = Y × Size    ← 与 PNG 分辨率无关
总顶点    = X×Dim × Y×Dim                      ← PNG 必须 1:1 等于顶点数
```

### 第二层：PNG 分辨率只决定"网格能装多细"，不决定世界有多大
| 管线输出 PNG | X | Y | Size | Dim | 顶点 | 世界尺寸 | 每顶点代表 |
|---|---|---|---|---|---|---|---|
| 4096×2560（hires 主档） | 16 | 10 | 128m | **256** | 4096×2560 | **2048×1280m** | 0.5m |
| 1024×640（小素材推荐档） | 16 | 10 | 128m | **64** | 1024×640 | **2048×1280m** | 2.0m |
| 704×440（Taikou 原生近似） | 16 | 10 | 128m | **44** | 704×440 | 2048×1280m | ≈2.9m |
| **4096×4096（原版规格档，2026-09-05 新）** | 16 | 16 | **53m** | **256** | 4096×4096 | **848×848m** | 0.207m |

**规律**：Size 与节点数不动 ⇒ **世界尺寸不变**；Dim × 节点数 = PNG 分辨率；**PNG 越高 ⇒ Dim 可以越大 ⇒ 同世界体网格越细**。

### 第三层：素材分辨率如何换算成"精细度上限"
```
素材有效像素率 = 素材宽 / 世界宽(m)     ← 素材能支撑多少"真细节"
精细度上限 = min(素材像素率, 引擎顶点预算)
```
- japanmap_hires 15840 宽 / 2048m ≈ 7.7 源px/m → 撑得起 4096 顶点网格（0.5m/顶点），细节是真材实料
- TaikouMap2 704 宽 / 2048m ≈ 0.34 源px/m → **只能撑 1024 档（2m/顶点）**；强行 4096 = 顶点全插值 → "假细节"（碎斑振铃），观感反而劣化
- **"同一世界"的保证**：管线输出是**语义图层**（海/陆/山影/雪），语义与分辨率无关；素材经裁剪→语义→按目标顶点重采样，所以两素材输出**图上每个像素映射到世界上同一点**（山脉/海岸/富士同位置），仅网格粗细不同

### 实践规约
1. 正式产出用 **hires 4096 主档**（Dim=256）；小素材（704 级）只配 **1024 档预览**（Dim=64），两档可共用同一场景在世界坐标逐位置对齐
2. **不要**给小素材强行套大 Dim（顶点=插值假纹）
3. 换素材后**四件套只需要改 Dim**（节点数/Size 不动），世界尺寸自动一致
4. 素材原生分辨率不整除不是问题（如 704×448→440）：管线以"世界比例裁切后重采样到目标顶点"输出任意尺寸 PNG

### 直接参数表（照抄用，2026-09-05 实测）

**当前 Output/ 两档现成图 → 参数**：

| 要导入的 PNG（tools/ExportHeightMatMap/Output/） | X | Y | Single Node Size | Single Node Dim | 顶点 = PNG | 世界尺寸 |
|---|---|---|---|---|---|---|
| `hm_japanmap_hires_4096x2560_16bit.png` + `mat_japanmap_hires_4096x2560.png` | 16 | 10 | 128.000 | **256x256** | 4096×2560 ✓ | 2048m × 1280m |
| `hm_TaikouMap2_1024x640_16bit.png` + `mat_TaikouMap2_1024x640.png` | 16 | 10 | 128.000 | **64x64** | 1024×640 ✓ | 2048m × 1280m（同） |

**脚本输出档 → 四件套通用表**：

| 脚本输出的 PNG | 四件套（X / Y / Size / Dim） |
|---|---|
| 4096×2560 | 16 / 10 / 128 / **256x256** |
| 2048×1280 | 16 / 10 / 128 / **128x128** |
| 1024×640 | 16 / 10 / 128 / **64x64** |
| 704×440（Taikou 原生比例） | 16 / 10 / 128 / **44x44** |
| **4096×4096（原版规格档）** | **16 / 16 / 53 / 256x256** |

**核验公式（防手滑）**：`PNG 宽 = X × Dim 数`，`PNG 高 = Y × Dim 数`；`世界宽(m) = X × Size`。

## 三·八、官方导入流程与"RGBA 四通道"之谜（待实机定案）

- **官方文档（[Terrain Creation](https://moddocs.bannerlord.com/zh_cn/editor/scene-editor/terrain_creation/)）**：Import Materialmap = 每图层一张 **8bit** 图 + Add Layer/选中/CTRL+A；Import Heightmap 同流程（8/16bit PNG 或 raw）
- **我们管线现状** = 一张 RGBA 4 通道整图 → 导入成功 + "换 R/G/B/A 次序重导"调色（用户实测 2026-09-04）→ 与官方文档说法存在 **A) 引擎隐藏整图导入路径** vs **B) 当时其实每一步都是对 default 层单层导入（碰巧）** 两种解释
- **待实机定案（2026-09-05 计划）**：ModKit 打开 **Taikou Main_map**（三·十三）→ Terrain Paint 面板看**图层列表有几个层**：
  - 只有 default 一层 + 地表四种材质 → A（整图导入真实存在，管线零改动）
  - 已有草/林/沙/雪 4+ 个层 → B（管线改型：拆 4 张 8bit 灰度，每层一张）
- 改型影响：生成器去掉 RGBA 打包，输出 L1..L4 灰度 PNG（算法零改，代码更少）

## 三·九、terrain.bin 容器（ZGR6RTRN，只读解析）

```
0x00: 魔数 "ZGR6RTRN"
0x08: u32 version = 2
0x0C: 段目录（每段 20B 头）: MIDX | HGHT | NRML | WGHT | PHYM
      （段名 4B + u32 1 + 12B 元信息）
段数据 = 内嵌 PNG 流（引擎魔改容器，部分 IHDR 非标准/分块 tile 化）：
  4 张大参考图（4096 宽：高度 8bit 灰度等）
  + 181 张真 257px 分块 tile（每节点 256+1 边界）
```
- HGHT/WGHT/NRML/PHYM = 高度/权重/法线/**物理层（physics 索引图）**
- 物理层索引 → terrain_materials.xml 的 physics 值 → **party 地形类型采样基础之一**
- 工具：`tools/ExportHeightMatMap/terrain_probe.py`（段名/PNG 流定位）；内部结构未完全解开（魔改 PNG 的 IHDR 不标准），不影响管线（引擎从我们导入的 PNG 自己生成 bin）

## 三·十、部队在坡地上能不能走（速度机制，2026-09-05 反编译结论）

**核心：大地图部队移动速度按"位置地形类型（TerrainType）"算，与高度坡度无关；高度图只管贴地/碰撞/相机。**

- 证据（TaleWorlds.CampaignSystem.dll 符号）：`currentPositionTerrainType` / `GetTerrainTypeAtPosition`（位置采样）、`GetTerrainTypeName`、`GetWeatherEffectOnTerrainForPosition`、`OnTraverseTerrain`
- 链条：**材质权重图（splat/层 mask）→ 地形物理层（terrain_materials.xml）→ TerrainType（草原/森林/沙漠/雪/水/岩）→ 速度倍率**（森林 ≈ -20%、沙漠 ≈ -30% 等，原版内置表）
- **水 = 陆军不可走**（TerrainType water）→ 原版桥梁实体（wooden_brige/map_bridge_b）做渡口；海上 = 海军机制（1.5.x 自带）
- 对你"山坡可走但影响速度"的实现 = **材质通道设计**（不是高度）：山坡给林通道（减速+植被匹配）、山顶裸岩（正常速）、河给 river 层（堵路走桥）、海全 0（海军）
- 坡度美术建议：峰 15~18m、山体底径 ≥60m → 坡 ≈25-28°（原版量级）；>40° 视觉贴墙出戏

## 三·十一、flora.bin 植被格式（2026-09-05 解析，生成器可直写）

```
0x00: 魔数 "FLR2"
0x04: u32 = 文件剩余字节（= 总长 − 8）
0x08: u32 = 实例数 N
0x0C: 记录流（变长步长 = 4 + 名字长 + 84）：
```

| payload 字段 | 语义 | 实测（原版首条棕榈） |
|---|---|---|
| f[0] | 恒 0 | 0 |
| f[1..10] | 朝向矩阵（内嵌旋转+缩放） | (-0.153, 0.592, 0, 0, -0.592, -0.153, 0, 0, 0, 0) |
| f[11] | 尺寸 | 0.611 |
| f[12] | 恒 0 | 0 |
| f[13..15] | **世界坐标 x/y/z（贴地）** | (457.26, 63.86, 4.34) |
| f[16..20] | 恒 1 | 1×5 |

- **树名注册表**：`Native/ModuleData/flora_kinds.xml`（每种植被 = flora_kind：夏/秋/冬季节变体 mesh + LOD 链 lod0 实体→lod5 billboard + 材质 + 碰撞体）。原版实盘 11 种：map_pine_a/b/c、map_tree_palm_a/b、worldmap_tree_acacia/beech/poplar/aspen/high_01、flora_grass_a_visualtest。
