## 一、核心概念：SaveableField 的数字是什么

### 简短回答

**`[SaveableField(10)]` 中的 `10` 是当前类（Type）内部的字段唯一标识符（field ID），不是优先级、不是版本号、不是全局 ID。**

### 为什么用数字而非字段名？

骑砍2 的 SaveSystem 通过 **field ID** 而非字段名字符串来序列化/反序列化：

```
保存时：引擎遍历所有 [SaveableField(n)] → 把 (n, 字段值) 写入存档
读档时：引擎读取存档中的 (n, 值) → 找标记了 [SaveableField(n)] 的字段 → 恢复值
```

**设计意图**：允许 mod 作者随意重构（改字段名），只要 ID 不变，旧存档就能兼容。代价是：**改了 ID = 旧存档该字段读不到值 → 字段回到默认值（0 / null / false）**。

### ID 作用域：类级别，非全局

```
┌──────────────────────────────────────────────────────┐
│  ID 只在当前 class 内部唯一                          │
│  · 不同 class 的同 ID 完全独立                       │
│  · 基类与子类的同 ID 完全独立                        │
│  · 不同 mod 的同 ID 完全独立                         │
│  · 不同 Issue/Quest 的同 ID 完全独立                 │
│                                                      │
│  引擎按 全限定类名 + field ID 来定位每个字段           │
└──────────────────────────────────────────────────────┘
```

所以你不必担心"别的 mod 也用了 SaveableField(10) 会冲突"——**不会**。类名本身已经是天然命名空间。

```csharp
// 这三个 10 互相完全独立：
public class MerchantNeedsHelpIssue : IssueBase {
    [SaveableField(10)] private Settlement _targetVillage;  // MerchantNeedsHelpIssue 的 10
}
public class FamilyFeudIssue : IssueBase {
    [SaveableField(10)] private Hero _targetHero;           // FamilyFeudIssue 的 10
}
public class MyCustomQuest : QuestBase {
    [SaveableField(10)] private int _myCounter;             // MyCustomQuest 的 10
}
```

### 为什么用 10, 20, 30 而不是 1, 2, 3？

**预留插空位置**。如果在后续版本中需要在两个已有字段之间插入新字段：

```csharp
// ❌ 密集编号——无法插入新字段
[SaveableField(1)] private int _a;
[SaveableField(2)] private int _b;  // 想在 a 和 b 之间加字段？只能全部改 ID（破坏兼容）

// ✅ 步进编号——轻松插入
[SaveableField(10)] private int _a;
[SaveableField(15)] private int _newField;  // ← 插入，旧存档兼容
[SaveableField(20)] private int _b;
[SaveableField(30)] private int _c;
```

这就是为什么原版 Quest 源码中会看到 `71` 这种奇怪的数字——那是后来插入的字段。

### ID 改了会怎样？

```csharp
// v1.0 发布
[SaveableField(10)] private int _targetCount;  // 存档里存为 ID=10

// v1.1 重构——把 ID 从 10 改成 11
[SaveableField(11)] private int _targetCount;  // 读 v1.0 存档时，引擎找 ID=11 找不到 → _targetCount = 0
```

**结果**：不是崩溃，但该字段静默归零。对于 Quest 这意味着任务进度丢失、NPC 引用变 null 等——可能在其他地方引发 NRE。

### 如果有字段不再需要了？

**不要重用它的 ID。** 标记为废弃即可：

```csharp
// [SaveableField(15)] private int _deprecatedField;  // v1.2 移除，ID 15 永久退役
```

重用 ID 意味着旧存档中该 ID 的值会被错误地反序列化到新字段上，类型不匹配可能导致存档损坏。

## 二、三层存档机制全景

```
┌──────────────────────────────────────────────────────────────┐
│  第 1 层：字段标记 — SaveableField / SaveableProperty        │
│  · [SaveableField(id)] 标记私有字段                          │
│  · [SaveableProperty(id)] 标记属性                           │
│  · 仅限 IssueBase / QuestBase 子类（引擎自动扫描）            │
│  · 仅限 CampaignBehaviorBase 子类（需手动 SyncData）          │
├──────────────────────────────────────────────────────────────┤
│  第 2 层：行为容器同步 — CampaignBehaviorBase.SyncData()      │
│  · dataStore.SyncData("key", ref field) 持久化任意数据        │
│  · 引擎在保存时自动调用 SyncData（写入），读档时自动调用（读取）│
│  · 适合存 JSON 序列化的复杂结构、字典、静态单例数据            │
├──────────────────────────────────────────────────────────────┤
│  第 3 层：自定义类型注册 — SaveableTypeDefiner                │
│  · 告诉引擎怎么序列化非原生类型（Dictionary<K,V>、自定义类等） │
│  · DefineClassTypes()：注册自定义 class                      │
│  · DefineContainerDefinitions()：注册泛型容器                 │
│  · 需要唯一的 base ID（构造函数参数）                         │
└──────────────────────────────────────────────────────────────┘
```

### 三层分别在什么时候用？

| 场景 | 用哪层 | 示例 |
|------|--------|------|
| Issue/Quest 的任务状态字段 | 第 1 层 | `[SaveableField(10)] private int _progress` |
| CampaignBehavior 持有的字典/列表 | 第 2 层 + 第 3 层 | `SyncData("key", ref _dict)` + `ConstructContainerDefinition(typeof(Dictionary<,>))` |
| 跨存档保留的复杂游戏状态（非 Quest） | 第 2 层 | `SyncData("lwn_trust", ref _json)` |
| JSON 序列化的静态单例 | 第 2 层 | 本项目 `TrustSystem.Serialize()` → `SyncData` |

## 三、SaveableField vs SaveableProperty

```csharp
// SaveableField — 标记字段（field）
[SaveableField(10)]
private int _targetCount;

// SaveableProperty — 标记属性（property）
[SaveableProperty(25)]
public CampaignTime ReturnTime { get; private set; }
```

| 特性 | SaveableField | SaveableProperty |
|------|---------------|-------------------|
| 标记目标 | 字段（field） | 属性（property） |
| 访问级别 | 通常 private | 通常 public（getter 公开） |
| 读写方式 | 引擎直接读写字段 | 引擎通过 getter/setter 读写 |
| 典型用途 | 内部状态 | 需要公开读取的内部状态 |
| ID 规则 | 同样类内唯一，10 步进 | 同样类内唯一，与 Field 共享 ID 命名空间 |

**重要**：SaveableField 和 SaveableProperty 的 ID **共享同一个命名空间**——同一个类里不能同时有 `[SaveableField(10)]` 和 `[SaveableProperty(10)]`。

### 原版惯例

- Issue 层通常只用 SaveableField（1-99）
- Quest 层通常只用 SaveableField（1-99）
- `CampaignTime` 类型总是用 SaveableProperty（引擎对它有特殊处理）
- `JournalLog` 用 SaveableField

## 四、SyncData：CampaignBehavior 级持久化

### 基础用法

`CampaignBehaviorBase` 的 `SyncData(IDataStore dataStore)` 在**保存和读档时都会被引擎调用**。`dataStore.SyncData("key", ref field)` 是双向的：

```csharp
public override void SyncData(IDataStore dataStore)
{
    // 保存时：引擎把 _myValue 写入存档，key="my_key"
    // 读档时：引擎从存档读取 key="my_key"，写回 _myValue
    dataStore.SyncData("my_key", ref _myValue);
}
```

**`dataStore.IsLoading` 属性**可区分当前是读档还是保存：

```csharp
public override void SyncData(IDataStore dataStore)
{
    // 简单值：直接 SyncData
    dataStore.SyncData("my_key", ref _simpleValue);

    // JSON 字符串模式：保存前序列化，加载后反序列化
    string json = MyData.Serialize();
    dataStore.SyncData("lwn_my_data", ref json);
    if (dataStore.IsLoading)
        MyData.Deserialize(json);
}
```

### 本项目惯用法：JSON 字符串模式

由于我们的很多子系统使用静态单例 + 字典/复杂对象，走的是 JSON 序列化 → SyncData 字符串 的模式：

```csharp
// MyBehavior.cs — 本项目实际代码模式
public override void SyncData(IDataStore dataStore)
{
    // 委托信任系统
    string trustJson = TrustSystem.Serialize();
    dataStore.SyncData("lwn_commission_trust", ref trustJson);
    if (dataStore.IsLoading)
        TrustSystem.Deserialize(trustJson);

    // 世界事件数据库
    string worldEventsJson = WorldEventDatabase.Serialize();
    dataStore.SyncData("lwn_world_events", ref worldEventsJson);
    if (dataStore.IsLoading)
        WorldEventDatabase.Deserialize(worldEventsJson);
}
```

**SyncData key 命名约定**：本项目统一用 `lwn_` 前缀，避免与引擎/其他 mod 的 key 冲突。

### 为什么是 `SyncData("key", ref field)` 而不是分开的 Save/Load？

因为引擎在保存和读档时**两次调用同一个方法**，通过 `dataStore.IsLoading` 区分。这是 TaleWorlds 的统一模式——和 Unity 的 `ISerializationCallbackReceiver` 类似思路。

## 五、SaveableTypeDefiner：自定义类型注册

当你的 SyncData / SaveableField 涉及**非原生类型**（自定义 class、Dictionary、嵌套泛型容器等），必须通过 `SaveableTypeDefiner` 告诉引擎怎么序列化它们。

### 基础结构

```csharp
public class SaveDefiner : SaveableTypeDefiner
{
    // base(id) — 唯一标识符，确保不和引擎/其他 mod 冲突
    // 引擎使用范围 ~1-100,000，mod 应该用大数字
    public SaveDefiner() : base(123456789) { }

    // 注册自定义 class
    protected override void DefineClassTypes()
    {
        // AddClassDefinition(typeof(MyClass), classId);
        // classId 在此 Definer 内唯一
        AddClassDefinition(typeof(GeneratedStoryResult), 10);
    }

    // 注册泛型容器
    protected override void DefineContainerDefinitions()
    {
        // ConstructContainerDefinition(typeof(泛型类型));
        ConstructContainerDefinition(typeof(Dictionary<string, string>));
        ConstructContainerDefinition(typeof(Dictionary<string, Dictionary<string, string>>));
    }
}
```

### 什么时候必须注册？

| 类型 | 需要注册？ |
|------|-----------|
| `int`, `bool`, `float`, `string` | ❌ 引擎内置 |
| `Hero`, `Settlement`, `ItemObject` 等 MBObjectBase 子类 | ❌ 引擎内置（存 StringId 引用） |
| `CampaignTime` | ❌ 引擎内置 |
| `List<T>`（T 是内置类型或 MBObjectBase） | ❌ 引擎内置（需确保 T 可序列化） |
| `Dictionary<K, V>` | ✅ **必须注册** |
| 自定义 class（非 MBObjectBase 子类） | ✅ **必须注册** |
| 嵌套泛型（`Dictionary<string, Dictionary<,>>` 等） | ✅ **每层都必须注册** |

### SaveableTypeDefiner 的 base ID 是什么？

```csharp
public SaveDefiner() : base(123456789) { }
```

这个数字是 **SaveableTypeDefiner 自身的唯一标识**。引擎用它来确保不同 Definer 注册的 class ID 不会冲突——引擎内部会将 `(DefinerBaseId, ClassId)` 组合成全局唯一 ID。

- 引擎内置 Definer 使用 `1-100,000` 范围
- 每个 mod 的 Definer 应该用一个**不重复的大数字**（官方推荐 ~100,000+）
- **不需要全局注册表**——只要不在同一个 mod 里用两个相同的 Definer base ID 就行
- 不同 mod 用了相同的 Definer base ID 理论上可能出问题，但实践中极少见，因为 class ID 只在同一个 Definer 内唯一

## 六、InitializeQuestOnGameLoad：读档重建

### 为什么需要这个？

**存档系统只保存数据，不保存运行时注册（事件订阅、对话注册等）。** 读档后需要手动重建这些。

```csharp
protected override void InitializeQuestOnGameLoad()
{
    // 1. 重新注册对话流（ConversationManager 中的注册不会自动恢复）
    SetDialogs();

    // 2. 验证存档中引用的对象是否还存在
    if (!string.IsNullOrEmpty(_escortPartyId))
    {
        bool partyExists = Campaign.Current.MobileParties.Any(
            mp => mp.StringId == _escortPartyId);
        if (!partyExists)
        {
            // 部队被消灭了——任务失败
            CompleteQuestWithFail();
        }
    }
}
```

### 什么需要重建，什么不需要？

| 需要手动重建 | 不需要（引擎自动恢复） |
|-------------|---------------------|
| 对话注册（SetDialogs） | 字段值（SaveableField 标记的） |
| 验证引用对象是否存在 | CampaignEvents 的事件订阅 |
| 重新绑定 UI/JournalLog | SyncData 的数据 |
| 重新计算派生状态 | 引擎对象引用（Hero/Settlement 等通过 StringId 恢复） |

### 注意：事件订阅

通过 `CampaignEvents.xxx.AddNonSerializedListener(this, handler)` 注册的事件在存档恢复时会**自动重新注册**——引擎在 `CampaignBehaviorBase` 层面处理了这个。但如果你的事件订阅逻辑在构造函数或静态初始化里，读档后不会重新执行，需要注意。

## 七、支持的与不支持的类型

### SaveableField / SaveableProperty 可标记的类型

| 类型 | 支持？ | 备注 |
|------|--------|------|
| `int`, `bool`, `float`, `double`, `string` | ✅ | 基本类型 |
| `CampaignTime` | ✅ | 用 SaveableProperty |
| `Hero`, `Settlement`, `ItemObject`, `CharacterObject` 等 | ✅ | 存 StringId，读档时通过 MBObjectManager 查找恢复 |
| `Clan`, `Kingdom`, `CultureObject` | ✅ | 同上，StringId 引用 |
| `JournalLog` | ✅ | 用 SaveableField |
| `List<T>`（T 是上面某种） | ✅ | T 必须可序列化 |
| `Vec2`, `Vec3` | ✅ | 引擎内置 |
| `TextObject` | ⚠️ | 有限支持，可能丢翻译 |
| `Dictionary<K,V>` | ❌ | **SaveableField 不支持**，必须走 SyncData + SaveableTypeDefiner |
| 自定义 class | ❌ | 必须在 SaveableTypeDefiner 注册后用于 SyncData |
| `Action`, `Func`, 委托 | ❌ | 不可序列化 |
| `System.Object` / 多态 | ❌ | 引擎需要确切类型 |

### SyncData 可处理的类型

SyncData 支持的泛型参数比 SaveableField **更广**，因为它直接用引擎的序列化管道：

```csharp
// SyncData 支持的类型签名：
dataStore.SyncData<T>(string key, ref T data);
// T 可以是：int, bool, float, string, CampaignTime, Vec2,
//           MBObjectBase 子类, 任何在 SaveableTypeDefiner 注册的类型
```

**实际项目中**，复杂数据（Dictionary、自定义类型）最好的做法是：
1. 序列化成 JSON 字符串
2. SyncData 存这个字符串
3. 读档后反序列化

这也是本项目在 `MyBehavior.SyncData` 中使用的模式——简单、不容易出错、不需要注册大量类型。

## 八、坑点与常见错误

### 1. 循环引用导致存档损坏

```csharp
// ❌ 危险：Hero 之间有循环引用
[SaveableField(10)] private Hero _heroA;
[SaveableField(20)] private Hero _heroB;
// 如果 _heroA 和 _heroB 通过 Hero.Relation 等间接形成循环，
// 保存时可能栈溢出或存档膨胀
```

**解决**：只存 StringId（`string`），使用时再 `FindHeroById`。

### 2. 存了 MBObjectBase 子类但没 null-guard

```csharp
// ❌ 如果 TargetSettlement 引用的 Settlement 被其他 mod 移除了
//    读档时 MBObjectManager.GetObject<T>(stringId) 返回 null
[SaveableField(10)] private Settlement _targetSettlement;

// ✅ 使用时必须 null check
if (_targetSettlement == null)
{
    // 存档中引用的定居点已不存在——任务无法继续
    CompleteQuestWithCancel();
    return;
}
```

### 3. SaveableField 改了 ID 没做迁移

```csharp
// v1.0
[SaveableField(20)] private int _progress;

// v1.1 重构——ID 从 20 改成 21
[SaveableField(21)] private int _progress;
// → v1.0 存档中 ID=20 的值被忽略，_progress 归零
```

**如果必须改 ID**，在 `InitializeQuestOnGameLoad` 中检测并迁移：
```csharp
protected override void InitializeQuestOnGameLoad()
{
    // 迁移 v1.0 → v1.1
    if (_progress == 0 && /* 检查是否从旧档加载 */)
    {
        // 手动处理迁移
    }
}
```

但实际上**引擎不提供检测"从哪版存档加载"的 API**，所以最好就是**不要改 ID**。

### 4. 在 SyncData 里忘了 IsLoading 判断

```csharp
// ❌ 反序列化逻辑在保存时也执行了，浪费且可能出错
string json = MyData.Serialize();
dataStore.SyncData("lwn_my_data", ref json);
MyData.Deserialize(json);  // 保存时也调了 Deserialize！

// ✅ 只在读档时反序列化
string json = MyData.Serialize();
dataStore.SyncData("lwn_my_data", ref json);
if (dataStore.IsLoading)
    MyData.Deserialize(json);
```

### 5. SaveableTypeDefiner 没注册容器

```csharp
// ❌ 存档会失败或跳过该字段
private Dictionary<string, int> _myDict = new Dictionary<string, int>();
dataStore.SyncData("my_dict", ref _myDict);  // 没注册 Dictionary<string,int>！

// ✅ 先在 SaveDefiner 里注册
protected override void DefineContainerDefinitions()
{
    ConstructContainerDefinition(typeof(Dictionary<string, int>));
}
```

### 6. JournalLog 没加 SaveableField

```csharp
// ❌ JournalLog 不会自动持久化
private JournalLog _progressLog;  // 读档后丢失，任务日志消失

// ✅ 必须标记
[SaveableField(30)] private JournalLog _progressLog;
```

### 7. 只读属性用 SaveableField

```csharp
// ❌ SaveableField 不能用于属性，编译可能通过但运行时无效
[SaveableField(10)]
public int MyProperty { get; private set; }

// ✅ 属性用 SaveableProperty
[SaveableProperty(10)]
public int MyProperty { get; private set; }
```

## 十、🔴 存档二进制格式（.sav）——2026-08 实战逆向（排查"载入存档时发生了一个错误"）

> 本章全部内容经反编译 + Python 解析实测验证（1.3.15 客户端）。写 Python 脚本解析/修复存档时照此格式。

### 10.1 文件布局

```
[0:4)      int32  JSON 长度（小端）
[4:4+L)    MetaData JSON 明文（JsonConvert 序列化，无校验和——可安全修改）
[4+L:)     Deflate 压缩（raw deflate，zlib.decompress(data, -15)）的 GameData
```

- **MetaData 可改**：无校验和。改版本号（模块版本/游戏版本）即可骗过"模组不匹配"检查。
  实际格式：`{"List":{"Modules":"...","Module_Native":"v1.3.15.109797",...,"ApplicationVersion":"v1.3.15.109797",...}}`
- **⚠️ 版本号字符串长度影响 JSON 长度**：改完必须同步更新 [0:4) 的长度前缀。

### 10.2 GameData 布局（GameData.Write 顺序——与 GetData/CreateFrom 不同！）

```
int HeaderLen + Header bytes
int ObjectCount + (int len + bytes) × N
int ContainerCount + (int len + bytes) × M
int StringsLen + Strings bytes
```

⚠️ `GameData.Write`（保存路径）是 Header→Objects→Containers→Strings；
`GameData.GetData/CreateFrom`（另一条路径）是 Header→Strings→Objects→Containers。解析时按 Write。

### 10.3 ArchiveDeserializer 块格式（Header/Strings/每个 Object/Container 数据）

```
int folderCount
  folderCount × { 3B parentGlobalId, 3B globalId, 3B localId, 1B extension }   // 3B int 小端，符号扩展
int entryCount
  entryCount × { 3B folderId, 3B id, 1B extension, 2B short length, length bytes }
```

- extension 枚举：SaveFolderExtension{ Root=0, Object=1, Struct=2, Container=3, Strings=4 }；
  SaveEntryExtension{ Class=0, Struct=1, Field=2, Property=3, Key=4, Value=5, String=6, Config=7, Basics=8, Object=9, Txt=10 }
- **String entry 的 payload 内部 = 4B int32 str_len + str_len 字节 UTF-8**；
  **长度字段 = 4 + str_len**（实测：length=18 ↔ str_len=14 "player_faction"）。
  ⚠️ 这意味着"超长字符串"的实际内容比溢出长度少 4 字节（37,853B 溢出 → 内容 37,849B）——
  修复/预算按内容口径算，entry 长度字段按 4 + str_len 写回。
- **🔴 SyncData 的 key 与值在 Strings 表中成对相邻排列**（实测：`#9831 lwn_crime_events` →
  `#9832 {"events":[...]}`；`#9833 lwn_theft_ledger` → `#9834 <37KB 值>`）——
  SaveSystem 把 SyncData 的 key 字符串和值字符串都放进 Strings 表，key 在前、值在后。
  由此可：① `--dump=<key>` 直接定位 key 的下一条 entry 读值（save_inspect.py 的实现依据）；
  ② 用"值 entry 大小"体检各系统的膨胀程度（`lwn_crime_events` 实测 21,910B ≈ 上限 2/3，高危实证）。
- ObjectLoadData 的 Basics entry：SaveId + propertyCount(short) + childStructCount(short)
- entry 数据内部（VariableLoadData）：byte memberType + byte typeLevel + short localSaveId + 数据
  - memberType 枚举：Object=0, Container=1, String=2, Tuple=3, CustomStruct=4, Enum=5, BasicType=6
  - Object/Container/String 引用 = int32 id；CustomStruct = int32 child struct index；BasicType = SaveId + 值
- SaveId：byte 0=TypeSaveId(int32), 1=GenericSaveId, 2=ContainerSaveId(key TypeSaveId + value TypeSaveId)
- 字符串值（String 块 entry / ReadString）：int32 长度 + UTF-8 字节

### 10.4 🔴 Strings 表 16 位长度上限——超长字符串损坏存档（2026-08 事故核心）

- Strings 表每条 entry 的**长度字段是 2 字节 signed short，上限 32767 字节**。
- **任何单条字符串 > 32767 字节** → 写入时 `(short)` 静默溢出成负数（**不抛异常，玩家无感知**）→ 该 entry 之后全部错位（读出的长度/内容全错）→ **读档必崩**。
- 表现：读档时 `ArchiveDeserializer.LoadFrom` 读到负长度 → `ReadBytes(负数)` → `OverflowException: 数组维度超过了支持的范围`。
- **数据本身完整无损**（37853 字节 JSON 全写进文件了），只是长度字段溢出。
- **负长度还原**：`负值 + 65536 = 真实长度`（无损还原，一条不丢）。
- **诊断**：Strings 块扫描——entry 长度字段为负即损坏点；前一 entry 是正常 key（如 `lwn_theft_ledger`）。
- **修复（读档侧 = 主方案）**：patch `BinaryReader.ReadBytes`：`if (length < 0 && length >= -32768) length += 65536;`（仅 short 溢出范围，不掩盖 int32 真损坏）——任何超长存档无损读活，一劳永逸。
- **修复（存档侧 = 离线工具）**：`Scripts/save_inspect.py --fix`（截断超长字符串 + 修正长度字段 + 重排 + 重压缩写回，自动备份）。用于不装 mod 的环境 / 存档侧体检。
- **防御（写入侧 = 根因）**：
  - 所有进存档的 JSON 字符串必须按 **UTF-8 字节数**（非字符数！中文 1 字 = 3 字节）守卫 < 30000（`SaveStringGuard.GuardJson`，结构感知截断——数组型 JSON 逐元素保留，JSON 始终合法只丢最老）。
  - 膨胀型存储逐个加"队列 + 老数据淘汰"（**活引用永不淘汰**：Quest 进行中引用的 WorldEventId / 扣押中 `PlayerDetentionBehavior.CurrentEventId`；结案数据留 N 天缓冲；`[Trim]` 日志可追溯）。范本：`TheftLedger`（未清 60 + 已清 50）、`WorldEventStore`（活跃 Dormant 只淘汰未发现案件 + 结案 10）。
  - 保存成功但发生裁剪 → 弹窗提醒玩家（静默写坏是最阴险处，玩家必须知情；LWN key `LWN_save_trim_*`）。
  - 完整防线见 [plans/rules/wheels.d/save.md](../plans/rules/wheels.d/save.md)「存档字符串超长防护」。

### 10.5 类型命名空间陷阱

- `LoadContext` 完整名 = **`TaleWorlds.SaveSystem.Load.LoadContext`**（`.Load` 子命名空间！），**internal**。
- `LoadResult` 同 = `TaleWorlds.SaveSystem.Load.LoadResult`。
- `ObjectSaveData` = `TaleWorlds.SaveSystem.Save.ObjectSaveData`（`.Save` 子命名空间）。
- **internal 类型无法被 `AccessTools.TypeByName` 解析**（实测失败）——必须
  `typeof(SaveManager).Assembly.GetType("完整名")`（SaveManager 是 public，先强制加载程序集）。

## 十一、读档失败诊断方法论（"载入存档时发生了一个错误"排查）
### 11.1 失败链路（1.3.15 实测）

```
SaveLoadVM → SandBoxSaveHelper.TryLoadSave → LoadGameAction
  → MBSaveLoad.LoadSaveGameData(saveName)          (TaleWorlds.Core.dll)
  → SaveManager.Load(saveName, driver, true)        (TaleWorlds.SaveSystem.dll)
  → LoadContext.Load(loadData, loadAsLateInit)      (TaleWorlds.SaveSystem.Load 命名空间)
      → 反序列化异常被内部 catch 吞掉
      → 只调 Debug.Print(ex.Message)   ← 1.3.15 的 DebugManager.Print 是空实现，不落盘！
  → 返回 null → 弹"载入存档时发生了一个错误"（{=onLDP7mP}）
```

- 弹窗字符串在 `SandBox.dll` → `SandBoxSaveHelper._saveLoadingProblemText`。
- **Debug.Print 在 1.3.15 不落盘**（MBDebugManager.Print 空实现）——不要指望 rgl_log.txt。

### 11.2 取证五件套（已实现于 Debug/SaveStringGuard.cs，🔴 常驻）

> 原 `Debug/SaveLoadDiagnostics.cs`（排查期临时诊断）已删除并入本文件——SaveStringGuard 为常驻防线，
> Harmony `PatchAll()` 自动注册，无调用点。

1. **ReadBytesFix**（patch `TaleWorlds.Library.BinaryReader.ReadBytes`）——
   **short 溢出还原**（-32768..-1 → +65536，无损救档）+ 真损坏（< -32768）打 `Environment.StackTrace` 定位
   （异常自身的 StackTrace 会被 newarr 截断只剩一层）。
2. **AddOrGetStringId watchdog**（patch `SaveContext.AddOrGetStringId`）——
   存档侧字符串注册入口，超长时打日志 + 序列化对象栈——**定位哪个 key 超长的唯一可靠手段**
   （key 信息只存在于写入侧；读档侧表已错位无法反推）。
3. **SaveLoadFirstChance**（patch `SaveManager.Save/Load`，挂 `AppDomain.FirstChanceException`）——
   捕获**所有被 catch 吞掉的异常**（含 LoadContext.Load 内部），带完整堆栈。挂载窗口 = Save/Load 期间。
4. **GuardJson**（`SaveStringGuard.GuardJson(key, json)`）——业务层统一守卫，MyBehavior 14 个 SyncData key
   全部接入；超长裁剪 + `[SyncDataGuard]` 日志**精确到 key**；先结构感知截断（数组逐元素保留，JSON 合法），
   非数组回退硬截断（切坏仅该 key 读档后清空，Deserialize 有容错，不崩档）。
5. **降级提醒弹窗**（`SaveStringGuard.ShowTrimNoticeIfAny`，Save Postfix 触发）——
   保存**成功**但发生过超长裁剪 → Inquiry 弹窗告知玩家 + `[SaveStringGuard]` 日志详情（LWN key：`LWN_save_trim_*`）。

### 11.3 Harmony 陷阱（实测踩坑）

- **`Harmony.GetOriginalMethod` 重放原方法 → StackOverflow**（Harmony 2.4 行为：返回的方法仍带自己的 prefix）——
  不要用"prefix 手动调用原方法"模式；用 FirstChance 旁路取证。
- **`AccessTools.Method("Type:Name")` 对 internal 类型返回 null**（不抛异常）——
  PatchAll 的 `TargetMethod()` 返回 null 会触发 `HarmonyException: returned an unexpected result: null`。
- **子命名空间陷阱**：类型全名必须带子命名空间（`.Load` / `.Save`）。

## 十二、存档体检/修复工具 — `Scripts/save_inspect.py`（2026-08 新增，实测验证）

Python 3 CLI 工具：解析 .sav（MetaData + raw-deflate GameData）→ 体检 Strings 表 → 定点手术修复。

**用法**：
```bash
python Scripts/save_inspect.py <save.sav>                      # 体检（不改文件）
python Scripts/save_inspect.py <save.sav> --keys               # 列全部 lwn_* key 及大小（SyncData 体检）
python Scripts/save_inspect.py <save.sav> --strings [N]        # 列 Strings 全表（前 N 字符）
python Scripts/save_inspect.py <save.sav> --dump=<key>         # 查看某个 SyncData key 的具体 JSON 值
python Scripts/save_inspect.py <save.sav> --output=report.txt  # 任何模式输出落盘（UTF-8，控制台静默）
python Scripts/save_inspect.py <save.sav> --fix [--max 30000]  # 修复预览（自动备份 .bak.N）
python Scripts/save_inspect.py <save.sav> --fix --apply        # 修复并写回
```
- `--dump=<key>`：按"key 与值成对相邻"规律定位值 entry，**损坏 entry 的值也能无损读出**（数据完整只是长度字段溢出）。
  终端输出截断 4000 字符防刷屏；加 `--output=xxx.txt` 落盘输出**完整 JSON**。
- `--output=xxx.txt`：体检/keys/strings/dump 的输出落盘（UTF-8），控制台静默——玩家反馈场景直接发报告文件。

**核心原理**：
- **定点手术而非解析重建**：负长度 entry 之后的表在读取视角已错位，但原始字节完好——
  修复只对坏 entry 截断 + 重写长度字段，后续 entry 字节原样前移（解析-重建路径会输出错位垃圾，损坏存档）。
- **结构感知截断**：字符串是 JSON 数组/对象时逐元素保留完整记录直到预算（JSON 始终合法，只丢最老）；
  非 JSON 回退 UTF-8 字节硬截断（回退到合法字符边界）。
- **写回必须 raw deflate**：`zlib.compressobj(9, zlib.DEFLATED, -15)`——`zlib.compress()` 默认 zlib 包装格式，游戏读档解压失败（实测踩坑）。
- **修复后自检**：无负长度 + 每个 entry 校验 `str_len + 4 == length`，不通过拒绝写回。
- 实测（测试.sav）：37,853B 溢出 entry → 29,848B（115 条完整记录无损），复检全绿，JSON 可解析。

**典型用途**：玩家发来"读档必崩"的存档 → 体检定位超长 key → 修复 → 交还验证。
配合游戏内 `SaveStringGuard`（读档侧还原）双保险：游戏内自动救，工具做离线体检/修复。
