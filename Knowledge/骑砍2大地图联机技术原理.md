# 骑砍2 大地图联机（Campaign Multiplayer）技术原理

> 整理日期: 2026-06-25
> 来源: Web 搜索、BannerlordCoop 开源项目、希绝大陆 Online 开发组公开讨论
>
> 当前状态：**无项目在开发联机功能，此文档为知识储备。**

---

## 一、官方联机 vs 社区联机

### 官方联机：Mission 层 only

骑砍2 的官方多人模式只存在于 **Mission 层（战斗场景）**，不包含 Campaign 大地图：

| GameType | 层 | 联机能力 |
|----------|-----|---------|
| `Campaign` / `CampaignStoryMode` | Campaign + Mission | 纯单人 |
| `CustomGame` | Mission only | 单人自定义战斗 |
| `Multiplayer` | Mission only | 官方联机（队长模式/遭遇战/攻城/决斗） |

官方网络栈：
- **LobbyServer**（TaleWorlds 官方集群）— 服务器发现和匹配
- **DedicatedCustomServer**（玩家自建，端口 7210）— 实际游戏托管
- **LobbyClient API** — `GetCustomGameServerList()`, `RequestJoinCustomGame()`
- **GameNetwork** — `WriteMessage()` / `HandleNetworkPacketAsClient()`，仅在 Mission 生命周期内有效

### 社区联机：自建 Campaign 同步

两个主要项目：
- **BannerlordCoop**（开源）— 目标：原版 Campaign 加 co-op，小团队
- **希绝大陆 Online**（闭源，国产）— 目标：MMO 化，自定义大地图

## 二、核心架构：服务器权威（Server-Authoritative）

```
┌─────────────────────────────────────────┐
│         Server（主机/专用服务器）          │
│  运行完整 Campaign 模拟：                 │
│  AI、外交、经济、时间推进                  │
│  = 唯一真相源（Single Source of Truth）    │
└──────────┬──────────────────────────────┘
           │ 广播状态变更
    ┌──────┼──────┐
    ▼      ▼      ▼
  客户端  客户端  客户端
  (只渲染) (不模拟世界) (发送操作请求)
```

### 三层架构（BannerlordCoop）

| 层 | 组件 | 职责 |
|----|------|------|
| **Mod 层** | `CoopMod`, `MBModule` | 生命周期管理、Harmony 补丁注入 |
| **Sync 层** | `Sync`, `Persistence` | 字段级变更检测、ProtoBuf 序列化 |
| **Network 层** | `CoopClient`, `CoopServer` (Railgun) | UDP 连接管理、消息传递 |

### 序列化

- **ProtoBuf** 二进制序列化
- **Railgun** (`RailNetPeer`) — 自定义 UDP 网络库，带重试逻辑
- 包特性：压缩、批处理（batch 64）、最多重试 3 次

## 三、同步策略：分字段分级

不是全量序列化整个 Campaign 对象，而是**精确到字段级别**：

| 同步模式 | 适用场景 | 示例 |
|---------|---------|------|
| **仅服务器执行** | 客户端不需要知道的计算 | `NumberOfEnemiesSpottedAround` |
| **服务器执行 + 广播结果** | 服务器计算后通知所有人 | `Militia`, `SettlementHitPoints`, `CurrentSiegeState` |
| **客户端请求 → 服务器验证 → 广播** | 玩家主动操作 | `EnterSettlement`, `ClaimValue` |

### 数据流示例：部队进入城镇

```
1. 玩家客户端点击"进入城镇"
2. Harmony Transpiler Patch 拦截 EnterSettlement 调用（IL 级别）
3. 客户端不执行实际逻辑 → 发送 EnterSettlementRequest → 服务器
4. 服务器验证合法性 → 执行 EnterSettlement（修改权威状态）
5. 服务器广播 "PartyEnteredSettlement" → 所有客户端
6. 每个客户端更新本地显示
```

**关键**：使用的是 **Transpiler Patch**（IL 级别注入），不是简单的 Prefix/Postfix。因为需要在方法体内部改变执行流，而不只是在前后加逻辑。

### 连接初始化

```
1. 客户端发送 JoinRequest
2. 服务器检测新玩家 → 要求创建角色
3. 客户端创建角色 → 上传数据
4. 服务器分配 NetworkID → 返回【初始世界全量快照】（完整存档）
5. 客户端加载场景 → 注册网络对象
6. 后续只发增量更新
```

## 四、时间流逝（时间同步）— 最核心的难题

### 单机的原始逻辑

骑砍2 原版 Campaign 的时间假设：
- 进入战斗/城镇/对话 → **时间暂停**
- 大地图移动 → 时间流逝（可暂停/1x/2x/4x）
- `Campaign.TickMapTime()` 方法控制，通过 `IsMainPartyWaiting` 标识判断是否该推进时间

### 联机下的处理

#### BannerlordCoop 方案：服务器权威 + 客户端请求

```
两个网络事件：
  NetworkRequestTimeSpeedChange (Client → Server)  玩家请求变速
  NetworkTimeSpeedChanged      (Server → All)      服务器批准广播

流程：
  玩家按空格 → 客户端拦截 → 发 Request → 服务器批准 → 广播 Changed → 所有客户端同步设置 TimeControlMode
```

**当前规则**（MVP 阶段）：服务器无条件批准任何变速请求。不做投票。

**关键实现**：
- 所有自动时间触发（点击大地图自动快进、进城镇自动暂停、到达目的地自动暂停）全部被 Harmony 拦截
- 只有手动按钮（底部 UI）和键盘快捷键（1/2/3）能触发变速
- `IsMainPartyWaiting` 被强制设为 `false`（防止进入城镇后卡死所有玩家）

#### 网络队列过载保护

```
服务器检测到 NetworkQueueOverloaded →
  强制 TimeControlMode = Pause →
  广播给所有客户端 →
  队列排空后恢复之前的速度

过载期间收到的加速请求 → 直接拒绝
```

**原则**：宁可暂停等同步，也不让客户端在缺失数据的情况下推进时间。

#### 希绝 Online 方案：时间不可控

MMO 化设计，时间**恒常流逝**，玩家不能暂停/加速。这个选择从根本上避免了协商问题。

## 五、三大未解设计矛盾

### 矛盾 1：谁来控制时间速度？

| 方案 | 逻辑 | 采用者 |
|------|------|--------|
| 无条件批准 | 任何玩家随时变速，服务器直接批准 | BannerlordCoop（MVP） |
| 仅主机控制 | 只有 Host 能变速 | 最简单但体验差 |
| 多数投票 | N 个玩家 >50% 同意才变速 | 理论方案 |
| 恒常流逝 | 不允许手动变速 | 希绝 Online |

### 矛盾 2：玩家进入不同场景时，时间怎么办？

这是 Campaign 联机**最根本的矛盾**。原版假设 Campaign 和 Mission 是**串行**的（切换时时间暂停），联机下必须变成**并行**（一个玩家在战斗不影响其他人）。

| 方案 | 做法 | 采用者 | 优缺点 |
|------|------|--------|--------|
| **强制同队** | 所有玩家必须在同一 Party，进场景一起进 | BannerlordCoop（当前） | 简单但自由度极低 |
| **世界不暂停** | Mission 进行时 Campaign 时间继续流逝 | 希绝 Online | 沉浸、公平，但实现复杂 |
| **世界冻结** | 任何人进战斗 → 所有人暂停等待 | 原版逻辑扩展 | 和原版一致，但体验极差 |

**技术根源**：`Campaign.TickMapTime()` 中的 `IsMainPartyWaiting` 标识。单机下这个 flag = true 时不推进时间。联机下必须显式管理这个变量，否则进城镇/战斗就卡死世界。

### 矛盾 3：坐镇指挥 vs 亲自战斗的收益失衡

```
亲自战斗（Mission 层）：
  - 现实时间：10 分钟实际操作
  - Campaign 时间：取决于方案 B 或 C
  - 收益：战术表现 + 战利品

坐镇指挥（Campaign 层）：
  - 现实时间：0 秒瞬间结算
  - Campaign 时间：原版模拟计算
  - 收益：实力对比模拟结果
```

**在"世界冻结"方案下失衡最严重**：亲自战斗绑架所有玩家的时间 10 分钟，而坐镇 0 秒，造成反向激励。

可能的缓解方向：
- 坐镇加冷却时间
- 亲自战斗额外奖励（战利品/经验/声望加成）
- 坐镇改为后台计时（不是瞬间结算，而是强制等待模拟时间）
- 联机下禁用坐镇（过于极端）

## 六、与 LivingWorldNpcs 的潜在关联

如果未来考虑 LLM-NPC 在联机下的行为：

1. **LLM 调用天然适合服务器权威模型** — 服务器跑 LLM 推理，把 NPC 决策作为状态变更广播，客户端只管渲染
2. **时间敏感操作**（NPC 限时任务、剧情计时器）必须以服务器时间戳为准
3. **轻量 co-op 可复用 BannerlordCoop 开源框架**（时间控制层已实现）
4. **Mission 层联机**可直接用 `GameNetwork` 收发自定义 NetworkMessage 同步 LLM-NPC 行为数据
