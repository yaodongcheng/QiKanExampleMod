### 二、🔴 未解决：浮空病（详见 `plans/rules/wheels.d/assets.md` §15.3c）

> 🔴 **责任定性（别误读）**：**源动画是好的** —— 实测源侧脚底 `0.000`（贴地）。
> 这个浮空是**我们重定向/导出这一环造出来的 bug**（导出器把 bind pose 写歪），**不是素材问题**。

- **现象**：一部分动画（越不站姿越明显）在查看器/实机里**整体浮空** —— 实测脚底 `0.124`（普通施法）/ `0.275`（蹲着瞄的 `SpellChannel1_Up/Mid/Mid1/Down`）。

- **试过一个修法并失败**：清 pose 之后再摘掉 action → **姿态通道整个没了（动画冻结成 T 字）+ 丢了对象级位移**，已彻底回退（代码 + 72 条产物 + 交付目录全还原）。
- **下一步方向（未动）**：**改 `fbx_to_trf.py` 的旋转参照** —— 引擎是按**官方骨架的 rest** 读 TRF 旋转的，而脚本现在用的是**输入 FBX 自己的 rest**（恰是被写歪的那个）。换成官方骨架，且**完全不碰导出的动画/位移通道**。先验一条 clip 再铺开。

**项目自有素材里本来就有一条"从 idle 起、经过单臂高举、回 idle"的真 mocap —— `BarrierSpell`
（FCS 屏障族出手 · 蒙太奇 `M_MagicAttack_RH_Up`）。全程只搬真实动作、一处都没做逐骨插值，

### 方法（**没有任何"逐骨线性插值"**）

```
参考图 ──"哪个姿态最像?"──▶ 纯 Python FK 扫全部 233 条 TRF，按【右手过顶高度】排序
        └─ 命中 ue_BarrierSpell：峰值帧 40 右手过顶 +0.399 m、左手在身侧 −0.446 m（单臂举）= 参考图姿态

start = ue_BarrierSpell 帧 2..40        ← 真 mocap 切段（首帧逐骨 == MagicIdle，0.0°）
loop  = 峰值姿态 ∘ ( MagicIdle 的相对运动 M(t)∘M(0)⁻¹ )    ← 真呼吸当"姿态层"，sin² 窗两端压 0
end   = ue_BarrierSpell 帧 40..71       ← 真 mocap 切段（末帧 == MagicIdle，max 6.8°）＝ **取消**分支
cast  = 保持3帧 → slerp过渡5帧 → ue_ProjectileSpell 帧16..60 **原样播**  ← **丢出去**分支（真投掷）
```

- **起手/收招**为什么能直接切？实测 `ue_BarrierSpell` 首帧与 `MagicIdle` **逐骨完全一致（0.0°）**，
  末帧也几乎一致（max 6.8°）—— 这条资产本来就是按"从施法待机起、回施法待机"编排的。
- **loop** 为什么不是"定格"？定格会僵。这里把 `MagicIdle` 的**真实呼吸**当作**加性姿态层**叠上去：
  `result(t) = peak ∘ slerp(I, rel(t), w(t))`，`w = sin²` 窗 ⇒ **首末帧逐骨严格等于峰值姿态**
  ⇒ 与 start 末帧 / end 首帧零跳变、自身完美闭环。膝盖以下不打层 ⇒ **脚不滑**。
- 姿态层用的是**相对运动**（真人肩胛/脊柱/腕的配合都在里面），不是对关节角度做插值。

### 🔴 本轮最有价值的一条教训：**"相对运动移植"救不了姿态差太远的两段**

做 `Cast` 时先走的"标准加性层"路子：`cast(t) = 手势姿态 ∘ [投掷动作(t) ∘ 投掷动作(t0)⁻¹]`。
**结论：不行，且失败方式很反直觉。**

| 版本 | 现象 |
|---|---|
| 原样乘（含 pelvis） | **人直接翻跟头**（实测头位移动 0.94 m、帧 20~80 全身空中翻滚）—— pelvis 那道相对旋转（投掷类能到 90°+）一乘进目标姿态，**整身被转掉**。同 `trf_compose.py` 的 `--root-scale` 教训 |
| 加 `root_scale=0` + 屏蔽膝盖以下 | 人不再翻，**但手的位置轨迹被搞乱**：变成"下→上→后→前"的乱摆，读不出"丢出去"。原因：合成是**逐骨四元数乘法**，手的位置是整条链的乘积，不是线性叠加 —— **源里那条漂亮的前挥抛物线，搬过去形状就没了** |

⇒ **姿态差太远时，正确做法不是"移植相对运动"，而是"短过渡 + 把源动作原样播完"**：
`保持3帧 → slerp过渡5帧 → 源帧16..60 原样`。实测手部轨迹 = 高举 → 引臂后摆(y −0.53)
→ 前挥释放(y +0.87) → 收势回 idle，一步不差。过渡段只有 5 帧(0.17s)，而且"从高举落回引臂"
本来就是投掷的蓄力动作，看不出拼接。
（`rel_layer` 保留在 `trf_edit.py` 里做对照，`--cast-mode rel` 可复现上面那张失败表。）

### 下一步（可选）

- 想要**双臂上举**或**更贴参考图**的姿态：改 `build_spiral_hand.py` 的 `BASE`/峰值搜索窗口即可换基座，
  脚本已把"选姿态"这步做成自动（`--peak` / `--peak-lo` / `--peak-hi`）。
- `ue_SkyfallSpell`（双手过顶 +0.439 m）是最接近的"双臂版"候选，必要时可当第二个基座。
- 想要更"活着"的循环：`--loop-scale` 调大（默认 0.9；实测该值下 loop 内右手摆动 39.6°，
  若嫌太活可降到 0.4~0.5）。

## 0.8 🔴 **外部素材 → 骨骼动画**（第 4 种源 · 完整工作流）

> 🧭 **本节是 [§0.9 路线 2 与路线 3](#09--动作从哪来三条路线与选路指南) 的执行细节**
> （路线 2 = 关键帧→视频→提取；路线 3 = 实拍真人→提取；**两者从"提关键点"起共用同一条链路**）。
>
> 需求：把**完全独立的外部素材**（真人视频 / 单张照片 / AI 生成的动作）变成能进骑砍2 的骨骼动画。
> 一句话原理：**MediaPipe BlazePose 取 33 个 3D 关节点 → 纯几何 look-at 解算 → 直接生成骑砍2 28 骨动画。**
> 零模型下载、CPU 可跑、离线。选型依据与完整公式见 [docs/图视频转骨骼动画_机制与落地.md](docs/图视频转骨骼动画_机制与落地.md)。

---

### 两条取料路线（= §0.9 的路线 3 与路线 2）

| 路线 | 怎么拿素材 | 什么时候用 |
|---|---|---|
| **A. 实拍 / 现成视频** | 直接录或找 | 动作要真实、要提骨架（**BlazePose 在真人上最可靠**） |
| **B. AI 生成**（现实里没这个动作时） | `gpt-image-2` 出 5 张**正面关键帧** → Seedance **首尾帧驱动**串成一条视频 | 想要特定招式（如"蓄力→出手"） |

> 🔴 **路线 B 的铁律：形象必须无版权。**
> 实测：**版权角色**（火影忍者）的关键帧**过不了 Seedance 的内容审核** —— 连挡 3 次，
> 换提示词 / 去掉 IP 名称都没用，**触发点是参考图本身**；
> 换成 **UE5 Mannequin（小白人）后一次通过**。
> 而且小白人还有额外好处：它是**标准 3D 人形**，落在 BlazePose 的训练分布里，
> **关键点逐关节贴合**（对比：动漫立绘置信度 0.9+ 但手臂位置是错的）。

### 工作流：**4 步 + 2 道闸门**

```bash
# ① 素材 -> 关键点（含朝向/正反面判定 + 叠加自检图）
python pipeline/tools/vid2pose.py --in 某人.mp4 --out input/source/pose_mediapipe/dance01.json \
    --fps 30 --overlay output/verify/pose_mediapipe/dance01_overlay.png
#   ▶ 闸门 A：先看叠加图确认关键点检出对不对，再看朝向摘要

# ② 关键点 -> FBX + TRF（走统一入口，和其他 rig 完全一样）
python pipeline/run_retarget.py --rig pose_mediapipe --clip dance01 --name pose_dance01 --pelvis ground

# ③ 标准对照图（源/解算上下并排 · 同时间点 · 同正面机位）+ 自动打印诊断清单
python pipeline/tools/make_compare_sheet.py --src 某人.mp4 --clip dance01 --name pose_dance01 \
    --out output/verify/pose_mediapipe/dance01_源vs动画对照.png

# ④ 诊断 —— 两条一起过
python pipeline/tools/check_lr_consistency.py --clip dance01 --trf pose_dance01    # 确定性数值判据
#   + 把 ③ 的对照图交给【视觉模型】，逐条回答 ③ 打印出来的 6 条清单
```

**路线 B 的前置（AI 造动作）**：
`gpt-image-2` 出 5 张关键帧（**正面 / 全身 / 同机位 / 同打光 / 同形象**）→ 相邻两帧当首尾帧喂
`generate_video`（Seedance 2.0，每段 5s）→ 下载后拼接成一条连续视频 → 再进上面 ①~④。

> 🔴 **拼接别自己写 OpenCV**：Windows 上 OpenCV **写不出 H.264**（`libopenh264` 缺失），只能退 `mp4v`，
> 而**浏览器只认 H.264 / VP8 / VP9 / AV1** —— 实测把 mp4v 的 mp4 塞进网页，Chrome 报
> `DEMUXER_ERROR_NO_SUPPORTED_STREAMS`、**画面全黑**。
> 用 `pipeline/tools/concat_video.py`：**一次产两份**，`.mp4`(mp4v) 给下游读、`.webm`(VP9) 给网页播。

### 🔴 5 个已踩的坑（换骨架/换素材时逐条对号）

| # | 坑 | 现象 / 修法 |
|---|---|---|
| 1 | **别读骨骼局部轴当方向，用「子骨 head 偏移」** | 实测骑砍2 `l_thigh` 自身轴朝**前**、到 `l_calf` 的骨段却朝**下**；`l_hand` 自身轴朝内下、`l_finger0` 更外侧。和硬约束 14 同理，只是出现在**目标侧** |
| 2 | **多骨段要分摊** | "髋→肩"对应 spine/spine1/spine2 三根，都瞄同一终点会让第一根独自转完（自洽但难看）→ 用 `frac`(0.34/0.67/1.00) 对目标方向 slerp |
| 3 | **根骨要给完整基** | `pelvis` 自身轴朝前（实测 X=上 / Y=前 / Z=角色左），拿它当瞄准轴没意义 → 用 `up=髋中点→肩中点`、`left=左髋→右髋` 拼新基。**不做这步角色永远不转身** |
| 4 | **正反面要独立判；验证机位不能拍反** | MediaPipe 的 left/right 是**推断**的，判反就整段镜像且看不出来 ⇒ `vid2pose` 现在输出 `facing.yaw_deg`（0°=正面朝镜头）+ `front_conf`（**面部关键点可见度**，与骨骼无关的独立证据）+ 逐帧跳变 >60° 告警。另外**能拍到正面的相机必须在角色正前方**（目标骨架朝 +Y ⇒ 相机在 +Y 侧；`az=0` 是**背后**） |
| 5 | **落地补偿要在 TRF 上做，不能在 Blender 里写 location** | 实测在脚本里写 `pose_bone.location` 后导出，**TRF 位置轨恒为 0**（UE/SW2 线不走这条路径所以没暴露）⇒ 改为在 TRF 上后处理（先量再补、**幂等**）。`pose_rasen_mq` 脚底 0.1228 → **0.0021** |

**另有两条口径**：
- **视觉诊断 + 数值判据必须两条一起过**：视觉模型抓崩坏/穿模/正反面突变/幅度差，但**判"左右镜像"在近对称姿态下不可靠**
  （实测把"双手举高"判成疑似镜像，数值一致率 0.981 证明是误报）；数值判据则**看不出**穿模/关节反折。互补，缺一条假绿。
- **动漫立绘不能直接喂 BlazePose**：置信度 0.9+ 但关节位置可能是错的（实测手臂被放到身侧）。
  **必须先看 `--overlay` 叠加图**再往下走。

## 0.9 🔴 **动作从哪来：三条路线与选路指南**

> 这一节回答的是**"要一个新动作，该走哪条路"**。§0.7 / §0.8 是两条路各自的执行细节，本节把它们并起来对比。
> **先看结论**：库里能找到近似 → 走路线 1；库里有但要真实拍摄 → 走路线 3；现实里根本演不出来 → 走路线 2。

---

### 三条路线一句话

| 路线 | 本质 | 动作来源 | 本仓对应交付物 |
|---|---|---|---|
| **1. 动作库检索 + 剪辑 + 合成** | **拼**：找最像的 → 切段 → 叠层 | 已有真 mocap（UE 小白人 / CMU 2548 段 / GhostSamurai / SW2 / FCS 法术…） | `ue_SpiralHand_{Start,Loop,Cast,End}.trf`（§0.7） |
| **2. 关键帧 → 视频 → 提取** | **造**：生成新素材再提骨架 | 视频生成模型（Seedance） | `pose_rasen_mq.trf`（§0.8 会话 D） |
| **3. 实拍真人视频 → 提取** | **拍**：真实素材走提取链路 | 真人/实拍视频（提取链路与路线 2 **完全相同**） | `pose_dance01.trf`（§0.8 会话 C） |

> 🔴 **路线 2 与路线 3 的区别只在"素材怎么来"，从 ④ 起完全共用同一条链路**；
> **路线 1 是另一套完全不同的工具链**（TRF 剪辑/合成，不经关键点）。

---

### 三条路线各自的工作流

**路线 1 · 库检索 + 剪辑 + 合成**（4 步）

```bash
# ① 客观检索：扫库找最像的那条（纯 Python FK，不需 Blender）
python pipeline/tools/scan_pose_metrics.py --skel-json output/verify/bannerlord_skel.json \
    --trfdir output/trf --out scan.json          # 按"右手过顶高度"等几何指标排序
# ② 切段 / 定格 / 重采样 / 拼接
#    trf_edit.py 的 cut / hold_at / resample / renumber / concat
# ③ 合成 / 叠加（AimOffset、窗口化姿态层、加法层）
#    trf_compose.py（结果 = 基础 ∘ (参照⁻¹ ∘ 增量)）、trf_edit.rel_layer / slerp_tail / layer
# ④ 收尾（若需重定向走 run_retarget；然后闸门 + 查看器）
```
本仓实例：`pipeline/tools/build_spiral_hand.py`（从 `BarrierSpell` + `MagicIdle` 拼出 start/loop/cast/end，
接缝逐骨 **0.00°**）。**完整过程见 [§0.7](#07--交接2026-09-27-会话-b-从一张图片-pose-反推-startloopend-三阶段)。**

**路线 2 · 关键帧 → 视频 → 提取**（6 步）

```bash
# ① 出关键帧（正面 / 全身 / 同机位 / 同打光 / 同形象）——gpt-image-2
#    🔴 形象必须无版权：版权角色过不了 Seedance 内容审核（实测连挡 3 次）
# ② 相邻两帧当首尾帧喂视频模型（Seedance 2.0，每段 5s）
# ③ 下载 + 拼接成一条连续视频（OpenCV 重编码）
# ④ 提关键点
python pipeline/tools/vid2pose.py --in 拼好的.mp4 --out input/source/pose_mediapipe/x.json --overlay ov.png
# ⑤ 解算成 28 骨
python pipeline/run_retarget.py --rig pose_mediapipe --clip x --name pose_x --pelvis ground
# ⑥ 闸门
python pipeline/tools/check_lr_consistency.py --clip x --trf pose_x   # + 视觉模型诊断（两条一起过）
```

**路线 3 · 实拍 → 提取**：只有 ④⑤⑥ 三步（素材直接是真拍视频）。

---

### 优劣势对比（**这是选路的依据**）

| 维度 | **路线 1** 库检索+合成 | **路线 2** 关键帧→视频 | **路线 3** 实拍→提取 |
|---|---|---|---|
| **能不能做库里没有的** | ❌ **不能**（只能拼不能造） | ✅ **能**（想要啥描述啥） | ⚠️ 要现实里能演出来 |
| **人体自然度** | ✅✅ **最高**（全程真 mocap） | ⚠️ 看模型，可能有滑步/重心漂移/物理不合理 | ✅✅ 高（真人） |
| **外部依赖** | ✅ **无**（纯本地、离线） | ❌ 生成服务 + **内容审核** + 网络 | ⚠️ 要有素材 |
| **可复现性** | ✅ **完全确定**（同输入同输出） | ❌ 生成有随机性 | ⚠️ 取决于素材 |
| **链长 / 失败点** | 3~4 步，失败点集中（③ 合成） | **6 步**，每步都有失败模式 | 3 步，失败点集中（④ 提取质量） |
| **主要失败模式** | 库里没有 / **姿态差太远时"相对运动移植"会散架**（§0.7 实测：直接乘会翻跟头；摘掉根骨后手的位置轨迹仍被搞乱） | ① 审核拦 ② 形象风格化 ⇒ **BlazePose 高置信度报错**（实测动漫立绘手臂被放到身侧）③ 物理不合理 | 关键点被遮挡/置信度低 ⇒ 必须先看 `--overlay` |
| **姿态忠实度** | 接缝可 **0.00°**；但只能是"近似动作 + 调整" | 与生成视频一致（实测上臂/前臂方向角 **0.0°**），但生成视频本身可能不对 | 与真人一致 |
| **门槛在** | **检索 + 合成手艺**（"该叠谁、叠多少"） | **提示词 + 关键帧质量** | 素材质量 |
| **成本** | 本地算力（几乎为零） | 生成调用次数 | 素材采集 |
| **时长可控性** | ✅ 切多少就是多少 | ⚠️ 每段 5s，拼接后常偏长（实测 16s，需再裁） | ✅ |

### 三条路的**共同下游**（别重复造轮子）

不管走哪条，**从拿到"骑砍2 骨架动画"那一刻起，全都汇进同一条产线**：

```
… → ① CHECK_TRF_POS（位置轨语义）  ② verify_modkit_fbx（骨架规格）
   ③ check_lr_consistency（左右/上下） + 视觉诊断（两条一起过）
   ④ 查看器 dataset → 目视验收 → ModKit 导入
```

### 混用与互补（实际项目里常常是组合拳）

- **路线 1 + 路线 2**：用路线 2 造一段"库里有对应类型的动作"，再用路线 1 的合成工具把它和别人叠起来（§0.6 飞行动画的加法层就是这么用的）。
- **路线 2 造 Pose、路线 1 供 Motion**：关键帧只当"目标姿态"，过渡用库里真实动作的**相对运动**去补 —— 但**只在两者姿态接近时成立**（§0.7 踩过）。
- **路线 1 造壳、路线 3 填肉**：先确定要用哪条 clip 的结构，再拍一段真人去补缺失的那段。

## 1. 标准流程（唯一产线）

```
input/source/<来源>/                    源动画（只读）
        │
        ├── ue_mannequin/   UE5 小白人 FBX
        ├── sw2_gunner/     战国无双2 glTF
        └── pose_mediapipe/ ★ 第 4 种源：图片/视频抽出来的 33 点关键点
                            （怎么来的见 §0.8「外部素材 → 骨骼动画」）
        │
        ▼ ① 重定向 + ModKit 规格导出 + TRF      ← 一条命令，三者同时产出
   python pipeline/run_retarget.py --rig <骨架对> --clip <动作名> --name <输出名>
        │
        ├──▶ output/fbx/<name>.fbx     中间产物（28 骨 / 只骨架 / Z-up / cm / 根名 human_skeleton_notused）
        └──▶ output/trf/<name>.trf  ★ 最终交付物
                                     （语义：旋转 = 绝对局部变换；平移 = 相对静止姿势的增量。
                                       两条不一样，写反的后果见 §6 硬约束 5。）
        │
        ▼ ② 自检（脚本自动打印，必须看）
   CHECK_OK   绝对公式 vs Blender pose 矩阵 < 0.5°      ← 例：0.0396°
   CHECK_POS  位置轨首帧 ≈ 0（纯增量）                 ← 若量级是米（~0.86）说明误用绝对语义，产物作废
        │
        ▼ ③ ModKit 导入
   填 Source 1 / Source 2 = 该 TRF 的帧范围（如导出 1–41 就填 1 / 41），Duration > 0
   报错 "pos ipo[2,42] does not fit sources 0.00 and 0.00" 就是这个没填，不是 TRF 写错
        │
        ▼ ④ 预览（可选）
   output/glb/  ──复制──▶  viewer/datasets/<数据集>/assets/  ──▶  viewer/serve.py
```

### 一条命令示例

```bash
# SW2 线（源 glTF）
python pipeline/run_retarget.py --rig sw2_gunner --clip p006 --name sw2_gunner_p006_alig

# UE 线（源 FBX）
python pipeline/run_retarget.py --rig ue_mannequin --clip 010_01 --name ue_010_01

# 🆕 图片/视频线（先抽关键点，再走同一条产线；细节见 §0.8）
python pipeline/tools/vid2pose.py --in 某人.mp4 --out input/source/pose_mediapipe/dance01.json --fps 30
python pipeline/run_retarget.py --rig pose_mediapipe --clip dance01 --name pose_dance01 --pelvis ground

# 🆕 带位移的一次性动作（处决/冲锋/翻滚）：位移烘进骨盆位置轨（Root 变体 + --pelvis src）
python pipeline/run_retarget.py --rig ue_mannequin --clip GhostSamurai_Execution02 \
  --name gs_execution02_root --pelvis src \
  --animdir "input/source/ue_mannequin/clips_exec/GhostSamurai_katana/Mannequin/Animation/Apose/Execution/Root"

# 只看命令不执行
python pipeline/run_retarget.py --rig sw2_gunner --clip p006 --dry-run
```

> **`--pelvis` 三档（UE 线）**：`ground`=逐帧贴地、**丢弃源水平位移**（默认，原地动作）｜
> `src`=**保留源根位移的水平分量** + 逐帧贴地（带位移动作）｜`none`=不写位移轨（飞行/离地）。
> 🔴 源侧有水平位移却用 `ground` 时脚本会**主动告警**（以前是静默丢弃 → 实机"演完瞬移回原点"）。
> 位移进 TRF 只是上游；**引擎侧怎么让角色真被带走**见
> [Knowledge/动画带位移_RootMotion与代码推位移.md](../../Knowledge/动画带位移_RootMotion与代码推位移.md)。

**算法结论（已定稿）**：`--pose align`（世界增量 + 逐骨静止对齐 `A⁻¹`）是**唯一交付模式**，也是默认值。
`delta` / `absolute` 仅作对照，产物已归档 `_legacy/algorithm_archive/`，**不要交付或接入**。

## 3. 脚本分层约定

**新增一个源骨架 = 只加一个 `pipeline/rigs/<名>/` 目录，通用层不动。**

| 层 | 位置 | 放什么 | 判断标准 |
|---|---|---|---|
| 通用层 | `pipeline/common/` | TRF 导出、GLB 烘焙、骨架体检、质量校验、UE 导出、无头截图 | **与"哪套骨架"无关**，换骨架照样用 |
| 骨架专有层 | `pipeline/rigs/<rig>/` | `map.json`（骨映射/帧变换/单位）+ `retarget.py`（重定向算法） | **差异只此一份**，不含流程逻辑 |
| 目标规格 | `pipeline/rigs/bannerlord_target.json` | 骑砍 28 骨序、根名、轴向、单位、ModKit 导出参数 | 目标骨架的唯一事实来源 |
| 调度层 | `pipeline/run_retarget.py` | 选 rig → 组命令 → 跑 blender → 校验产物归位 | 不含算法、不含映射 |

**路径约定**：所有脚本用自动定位的项目根，**禁止硬编码绝对路径**：

```python
PROJECT_ROOT = _project_root(os.path.dirname(os.path.abspath(__file__)))  # 向上找含 pipeline/ 与 input/ 的目录
```

已新增一个源骨架时，只需在 `run_retarget.py` 的 `RIGS` 注册表加一条：

```python
"<新骨架名>": {
    "script": "pipeline/rigs/<新骨架名>/retarget.py",
    "map":    "pipeline/rigs/<新骨架名>/map.json",
    "source_kind": "fbx",          # 或 gltf
    "clip_arg": "--clip",          # 该脚本的动作名参数
    "desc": "…→骑砍2",
},
```

## 4. 通用查看器（只有一个）

```bash
cd viewer && python serve.py      # 自动找端口并打开浏览器
```

- 数据集通过 `viewer/datasets/index.json` 注册，页面**左上角下拉切换**，也可用 URL：`viewer.html?ds=ue_slim`
- 一个数据集 = 一个目录：`dataset.json`（描述）+ `assets/`（GLB/glTF）+ 可选的 `manifest.json`（clips 元数据）
- **`viewer.html` 里没有任何写死的文件名**，全部来自 `dataset.json`
- **逐帧定位（2026-09-22）**：底部「进度 / 帧」拉杆 —— **暂停后拖动即定位到某一帧**（1 格 = 1 帧 @30fps，
  拖动会自动暂停；拉杆聚焦后 `←/→` 微调 1 帧）；播放中拉杆自动跟随播放轴，暂停时不会被回写。
  URL 也可直达：`viewer.html?ds=ue_slim&clip=002_01&frame=17`（`?frame=N` 会同时暂停）

### dataset.json 关键字段

| 字段 | 作用 |
|---|---|
| `sides.src` / `sides.dst` | 左（源）/ 右（目标）两侧配置：`label` `color` `rotY` `slot` `footBones` `files[]` |
| `files[].url` | **相对 dataset.json 所在目录**（viewer 会自动加前缀） |
| `files[].mode` | `ground`（逐帧贴地）/ `src`（跟随源骨盆位移），用于双模式数据集自动切换 |
| `clipsFile` | 指向 clips 元数据文件（含 `clips`/`groups`/`P0`/`P1`），用于三级筛选 |
| `sides.*.stripPositionTracks` | 裁掉全部 `.position` 轨道（预览时不体现位移，仅看姿态） |
| 旋转侧根位移反向补偿 | **自动生效**：一侧 `rotY≈π` 时，其根位移会被翻转，viewer 自动对未旋转侧做水平反向，保证两人并排（见硬约束 13） |
| `sides.*.rootFixY` + `rootBone` | **根骨静止位移补偿**：某些源 glTF（如 SW2）导出的根位移是"髋空间增量"、丢掉了静止位移，直接播会整体下沉；按此字段在 group 层补回 |
| `sides.*.rootFixY` + `rootBone` | **根骨静止位移补偿**：某些源 glTF（如 SW2）导出的根位移是"髋空间增量"、丢掉了静止位移，直接播会整体下沉；按此字段在 group 层补回 |
| `sides.*.facingBones` | `[左踝, 左趾, 右踝, 右趾]`，供几何求【正面】用（**默认口径是头/眼线**，见硬约束 18；此字段是回退/校验） |
| `sides.*.freezeRootH` | 把根骨 `position` 轨的**水平分量归零**（竖直保留）。用于「就地比姿态」 |
| `sides.*.freezeRootRe` | `freezeRootH` 的**自定义匹配正则**。⚠️ 根位移有时挂在**骨架对象节点**上（如 `GhostSamurai_Execution02.position`）而不是 `pelvis`，此时默认正则匹配不到，要写 `"GhostSamurai_"` 之类 |
| `sides.*.pairAnchor` | **★ 成对动画「只对齐首帧」**：`{anchor, pelvisBone, gap, mode}`。切 clip 时**只算一次**平移量（先摆→量本侧骨盆落点→按差值补正的**闭环**），把本侧首帧骨盆放到锚点首帧骨盆的**正后方/正前方** `gap` 米；`mode` 缺省时按 clip 名自动判定：**`Ambush*` → `behind`（背后偷袭，两人同向）；`Execution*` → `front`（面对面，rotY 差 180°）**。算完立即停手，之后位移全交给动画自己的 root motion |
| `pairs` | **每个成对动作独立的 8 个参数**：`{ "<clip名>": { src:[x,y,z,t], dst:[x,y,z,t] } }`。x/y/z = group 世界坐标（米），`null` = 用 `pairAnchor` 自动值；t = 起点偏移（秒，正=跳过开头，负=首帧等待）。面板可见即改，**自动存 localStorage**；点「保存到 dataset.json」经 `serve.py` 的 `POST /api/save-pairs` 落盘并留备份 |
| `sides.*.clipStart` | （历史）成对动画的 head start。**现已全部归 0** —— 实测用户手调后认为"两侧延迟都设 0 最好，只有各 pair 的 Z 初始差不同" |

> **成对动画（处决/伏击）的正确摆法**：只在 `src` 上加 `pairAnchor{anchor:"dst", gap:1.5}`，`mode` 交给 clip 名自动判定。
> **不要再手调 `offsetX/offsetZ`**，也不要逐帧跟随（受击方中途倒地转身会把攻击方"锚"到别处）。
> 位移若出现"倒退/两人走散"，那是成对 clip 各自的 root motion 问题，与站位对齐无关（见硬约束 16）。

> **成对动画 = 一个「动画组」**：`sides.dst.fixedClipReplace` 存在时，查看器列表**只列攻击方那条**
> （`Executed*`/`Ambushed*` 不单列），选中即两侧各播自己的配对 clip。列表显示中文组名（伏击 01 / 处决 03）+ 站位标注。

> **额外展示侧**：`src`/`dst` 之外的第三侧（如 `ref` = 重定向前的 UE 源）会**自动跟随攻击方播同一条 clip**，
> 用来并排对比"重定向前 vs 后"。

> 无 clips 元数据的数据集会自动隐藏三级筛选器、改用 GLB 中的 clip 名列表 —— 新旧数据集都能用同一个查看器。

### 4.1 🔴 分层：`viewer/` 只放逻辑，数据一律放 `output/`

**`viewer/` 是进 git 的代码/页面层**（`viewer.html` `serve.py` `lib/` `启动查看器.bat` `datasets/`），
**报告 / 截图 / 展示页 / 视频都是数据，一律落 `output/`**（如 `output/交付总览/`、`output/verify/`）。

但 `serve.py` 原来只服务 `viewer/` 目录，`output/` 就访问不到 —— 所以它现在**把 `output/` 作为只读静态挂载接到 `/output/*`**
（同一个服务、同一个端口，代码在 `Handler.translate_path`）。于是：

```
http://127.0.0.1:<端口>/viewer.html                        查看器本体
http://127.0.0.1:<端口>/output/交付总览/index.html        成品展示页（放在 output/ 的数据）
```

展示页里指向查看器的链接写成 **`../../viewer.html?...`**（从 `/output/交付总览/` 回上两级到根）即可。

> 也可以**直接双击** `output/交付总览/index.html` 用 `file://` 打开 —— 图片和视频能正常看；
> 只有跳查看器的那些按钮需要 http 服务（浏览器的本地文件策略会拦住 GLB 加载）。

### 5.1 UE 源导出（把素材包变成 `input/`）

```bash
BM_OUT_DIR=<输出目录> BM_ANIM_FILTER=<子串过滤,;分隔>   <UE编辑器> <工程.uproject> -run=pythonscript   -script="<项目>/pipeline/common/export_ue_fbx.py" -unattended -nosplash -nullrhi -stdout
```

| 情况 | 做法 |
|---|---|
| 工程自带 `.uproject` | 直接用（3583=**UE5.0** / SuperheroFlight=**UE4.26**） |
| **素材包没有 `.uproject`** | 把它的内容目录挂到已有工程的 `Content/` 下，**路径必须匹配 uasset 内部的 `/Game/...` 路径** |
| 编辑器别搞混 | UE4 → `UE4Editor.exe`，UE5 → `UnrealEditor.exe` |
| 结果别只看 stdout | 读 `<BM_OUT_DIR>/export_trace.log`（stdout 会被引擎噪音淹没） |
| 过滤是**子串**匹配 | 会多带同前缀（`Anim_JU_in_PL` 带出 `_land`/`_fall_loop`）；多带可接受、少带不可接受 |
| **变体子目录必须区分** | 同一资产名在 `Inplace/` `Root/` `Sample/` 下各有一份，**扁平输出会互相覆盖**（实测 69 条导出只剩 23 个文件）→ 脚本已按父目录加 `__Inplace` 后缀 |
| **Git Bash 会改写 `/Game/...`** | MSYS 路径转换把过滤器变成 `C:/.../git-bash-binary/Game/...` → 过滤器失效。**必须加 `MSYS_NO_PATHCONV=1`** |

**实例（GhostSamurai，无 uproject）**：uasset 内部路径为 `/Game/GhostSamurai_katana/Mannequin/...`
→ 复制到 `SuperheroFlightAnimations/Content/GhostSamurai_katana/Mannequin/` 即被识别（4.21 资产由 4.26 自动升级）。
工程需启用 `PythonScriptPlugin`（SuperheroFlight 已启用，原文件备份为 `.bak_before_python_plugin`）。

### 5.2 UE 导出的 4 个坑（本会话实测）

| 坑 | 现象 | 修法 |
|---|---|---|
| **Git Bash 改写 `/Game/...`** | 过滤器被 MSYS 转成 `C:/.../git-bash-binary/Game/...` → 失效 | 命令前加 **`MSYS_NO_PATHCONV=1`** |
| **UE5 AssetRegistry 未扫描** | `get_all_assets()` 返回 0（mySekiro/UE5.3 实测） | 先 `scan_paths_synchronous(["/Game"], True, True)` + `wait_for_completion()` |
| **UE5 类名是 `TopLevelAssetPath`** | `"AnimSequence" in str(asset_class)` 匹配失败 | 取 `asset_class.asset_name`（兜底再 `rsplit(".",1)[-1]`） |
| **大批量导出静默丢文件** | trace 报"成功 2874"，实际只落 780 个 | **分批**（`BM_MAX_N`），每批 ≤150 验证；或分批 filter |
| **`ue retarget.py` 原本硬编码贴地** | 飞行动画被强行拉到地面（骨架压到 0.329） | 已加 `--pelvis ground\|none`，**飞行/离地必须用 `none`** |

## 6. 硬约束（踩过的坑，逐条对号）

| # | 约束 | 违反后果 |
|---|---|---|
| 1 | **骨数必须 = 28** | Blender `add_leaf_bones` 默认 True，会补 5 根 `_end` → 33 骨，ModKit 直接拒 |
| 2 | 根节点名 = `human_skeleton_notused` | 与引擎内置 `human_skeleton` 冲突 |

| 9 | ModKit `Source 1 / Source 2` = TRF 帧范围 | 报错 pos ipo does not fit sources 0.00 and 0.00 |

| **16** | **成对动画的根位移【方向不可信】**：逐帧实测，角色位移方向与自身朝向差 **~143°**（近似反向）；且**末帧骨盆共同收敛到原点**，说明两个 clip 共用同一参考点、位移是"从 UE 关卡原始站位走到共享点" | 直接拿它当站位 → 伏击方站到受击方**正面**。横向站位必须由几何关系算，不能用根位移 |

## 8. 调试方法论（本会话沉淀 · 比具体坑更值钱）

> 提炼自"一个现象查了三层原因"+"方向算了十几次"的实战。

### 8.1 判断产物对不对，先量**官方同类文件**做基准
| 基准 | 值 |
|---|---|
| 官方 `human_lod_4.fbx` 骨架高 | **1.575**（米制） |
| 我们的产物 | 1.492 → 同量级 ✅ |
| 曾出现 | **0.015** → 一眼看出小 100 倍（硬约束 4b） |

### 8.2 跨单位比较，一律换**无量纲比值**
两侧 GLB 一个 cm 一个 m，直接比 `dy` 会得出**错误**结论。用 `位移/身高`（与 viewer 归一化口径一致）：
```
源侧 471.854 / 165.516 = 2.8508
目标侧 4.517 /   1.575 = 2.8669   ← 吻合 0.6% ✅
```

### 8.3 一个现象常常是**多层原因叠加**
"位置对不上"实测拆出三层，每层单独修只能把症状**换一个**：只修空间换算→竖直位移丢失；再修单位/护栏→走向相反；全修完→才对齐。
> **别满足于"症状变了"，要确认"症状消失了"。**

### 8.4 ⭐ **求方向用几何推算，不要读骨骼的局部轴**
本次最大的坑：我用**骨盆局部 +Y 轴**（+54.5°）当"正面朝向"，而**真实正面是 −127°**——**差 180°**（骨盆 +Y 其实指向**背后**）。
**正确做法**：
```
正面 = normalize( 脚踝→脚尖 )        # 最直接（人站立时脚尖朝前）
      或 由 clavicle_l→r / thigh_l→r 的连线取垂直方向
```
> 骨骼的**局部轴约定是制作时随手定的**，不可信；**左右对称骨骼的空间位置关系才是客观的**。

| 坑 | 实测 |
|---|---|
| **源侧 / 目标侧的朝向数字不能混用** | 同一句"正面朝向"，骑砍2 模型 = **−Z（θ=+90°）**，UE 源 = **θ≈−127°**。差 180° = `Rot(Z,180°)` 帧变换。README 里那个 `−127°` **是源侧数字**，照搬到 viewer 里必然差 180° |
| **同一根骨的局部 +Y 在两套资产里含义相反** | 骑砍2 `bl_*.glb`：骨盆局部 +Y → (0,0,−1) = **正面**；UE `ue_*.glb`：骨盆局部 +Y → (0,0.004,−1)，而真实正面是 (−0.62,+0.78) → **背后**。所以「骨盆 +Y = 背后」这个结论**只对 UE 源成立**，别当通用规律 |
| **面向求法要选稳的** | `脚踝→脚尖` 在**倒地/被拖**时会乱转（实测伏击末帧 54°→86°）。求"谁在谁背后"这类**稳定朝向**时，用 `up × (clavicle_r − clavicle_l)`；`脚踝→脚尖` 留作校验 |
| **⭐ 正前方的权威口径 = 头（两眼之间的垂线），不是骨盆/肩线** | Ambush04 首帧三口径实测：**眼线 88.8° / 88.2°（两人只差 0.6°）**、肩线垂线 38.1° / 42.9°（差 4.8°）、脚尖 51.6° / 54.1°（差 2.5°）。攻击方**躯干会拧到 109° 而头部始终保持 ~89°**（盯着正前方出刀）→ 拿肩线/骨盆当正面必然算歪。<br>实现：绑定姿态下用几何正面（脚踝→脚尖）标定出 `head` 骨骼**局部空间的前向向量**，运行时取 `head.matrixWorld × 该向量`（`facingOf(L,'head')`，现为默认口径） |

### 8.5 别用「试数值」代替「算」
本会话后半程我放弃推理、开始撞数（±1.5/±2/0.8/0.95/1.7…），而且：
- `offset` 会被 viewer 的**身高归一化部分吸收** → **"试一个看一个"的反馈本身就是失真的**
- 手上有 `?probe=1` 能读世界坐标，却靠**看截图目测** → 等于自己蒙眼
> **正确姿势**：算出目标坐标 → 设值 → **用 probe 闭环验证**，而不是看图画画。

## 11. TRF 出厂验收 & ModKit 填值（2026-09-24 立 —— 一批坏件的教训沉淀）

> **背景**：2026-09-24 查出 09-20 那批 TRF（施法/处决/伏击共 140 条）的位移轨是**绝对语义**，
> 导进游戏会把角色**整体抬高约 1m**；而**那批坏件在查看器里看着完全正常**（查看器走 FBX 世界姿态路径，
> 天生把这个病抹掉）。**教训 = TRF 出厂必须过闸门，且判据不能靠肉眼看看器。**

### 11.1 出厂闸门：`check_trf_pos.py`

```bash
python pipeline/common/check_trf_pos.py <TRF目录或.trf文件...>
```
- **判据**：位置轨**首帧 |分量| > 0.30** 报警。正常动作自身的骨盆位移可到 ~0.15（引导起手 0.14）；病征量级是 **0.79~0.91**。
- 退出码 1 = 有坏件 → **可直接当流水线闸门**。`_` 前缀的归档目录自动跳过。
- 实测：`output/trf` 212 条里抓出 140 条（全在 09-20 那个窗口；09-21 之后的批次干净）。

### 11.2 第二种病：`check_fbx_bindpose.py`

```bash
blender -b --factory-startup --python pipeline/common/check_fbx_bindpose.py -- <a.fbx> ...
```
- **症状**：重出 TRF 后首帧不是 0，而是 **+0.71~+0.83 且每条数值不同**（**不是** 11.1 那个"整批同一个常数"）。
- **病根**：**FBX 的绑定姿势被烘成了躺姿**（骨盆静止高度实测 `0.024`，正常站姿是 `0.849`）⇒ 量出的增量天生带常数偏移。
- **判据**：**首帧 − 绑定姿势 ≠ 0**（好件是 `0.0000`）。
- 🔴 **改 TRF 治不好** —— 得**按官方骨架重做 FBX 的静止姿势**再重出（施法/处决那批 2026-09-24 就是这么修完的）。

### 11.3 判预览真假：`check_glb_feet.py`

```bash
blender -b --factory-startup --python pipeline/common/check_glb_feet.py -- <a.glb> [--clip 名字]
```
- 离线复算「查看器眼里的脚底高度」（复刻 viewer 的归一化规则），**不需要浏览器**。
- 🔴 **查看器会掩盖 11.2 那种病**（FBX 世界姿态路径与静姿无关）⇒ **别拿"查看器里看着对"当验收依据**。
- 要判"游戏里长什么样"，只能走 **TRF 直读烘焙**那条路或本脚本；范本数据集 **`viewer/datasets/ue_exec_trf/`**
  （同一条 clip 两条烘焙路径并排：左 FBX / 右 TRF，自带对照 —— 同 GLB 里修过的那条是 0.068、没修的是 0.8）。

### 11.4 ModKit 填值：`trf_root_travel.py` + `make_import_sheet.py`

TRF 导进 ModKit 后，clip 的 **`Source 1` / `Source 2` / `Duration` 默认是 0**，**必须手填**（否则动画不播，
报错 `pos ipo[2,42] does not fit sources 0.00 and 0.00`）；**带位移的还要填 `displacement` 向量 + `endProgress`**
（引擎不认 TRF 自带的位移轨 —— 详见 §7.2 T17）。

```bash
# 一条量：算出该填的 (X,Y,0) 与 endProgress
python pipeline/common/trf_root_travel.py --trf "<xxx.trf>"
# 整批出表（duration / Source1 / Source2 / displacement X·Y / endProgress 一列不少）
python pipeline/common/make_import_sheet.py        # → output/modkit_import_sheet.csv
```

- **口径**：`source1/source2` = 该 TRF 的帧号范围（不是 0..N）｜`duration` = 帧数 ÷ 30｜
  `displacement` = 角色本地水平面、单位**米**（**+X 右手侧 / +Y 正前方 / Z 恒 0**）、`endProgress` 0.4~1.0。
- **可信度**：拿装机验证过的 `Execution02`/`Executed02` 对过账，量出的值与文档记录**逐位吻合**。
- ⚠️ 工具会同时报**轨迹直线度**：引擎只认直线位移，中途拐弯的条填单向量是**近似**（实机 22 条里 17 条如此，
  原版自己也有这情况）。

## 12. TRF 文件结构（**只针对 FBX 动画型** = `skeleton_anim`）

> 适用范围：**从 FBX 动画**导出的那种 TRF（`pipeline/common/fbx_to_trf.py` 的产物，
> 头两行 `rfver 4` / `skeleton_anim 1`）。**网格 / 骨架类 TRF 不在此列**。
> 细节与坑见 `docs/TRF规范.md`；节 11 是出厂闸门。

### 12.1 逐行结构

```
rfver 4                      ← 版本行（判别用）
skeleton_anim 1              ← 类型行（判别用；动画型就是它）
<动画名> 1                    ← 第 3 行 = 【动画名】，见 §12.4
 <骨数>                       ← 行首有 1 个空格
   ┌ 以下「块」重复 <骨数> 次（每根骨一块，**顺序就是骨序**）
   │ <该骨的帧数>
   │ <t> <x> <y> <z> <w>     ← 四元数按 x y z w 写，6 位小数
   │ …（共 <该骨的帧数> 行）
   └
 <位置轨帧数>                  ← 旋转块写完之后的位移块（可能为 0）
 <t> <x> <y> <z>
 …（共 <位置轨帧数> 行）
end                          ← 收尾
```

要点（写给要写解析器的人）：
- **纯文本、UTF-8**；除 `rfver`/`skeleton_anim`/`end` 外**每行行首有一个空格**（`trf_compose.py` 读的时候 `strip()`，容错）。
- 用 `rfver 4` + `skeleton_anim 1` 认类型；别的类型第二行不是 `skeleton_anim`。
- **没有骨名** —— 骨序（第 1 块 = 第 1 根骨）是唯一契约。骑砍 28 骨、顺序见 `pipeline/rigs/bannerlord_target.json`。
- 位移块**只对 0 号骨（pelvis）有意义**；多数条就写一块。
- 时间列 = **Blender 帧号**（不是从 0 开始的序号）—— 例：`fly_A_Flight_HoverMove_A.trf` 是 `2~62`。

### 12.2 两条轨道语义不一样（🔴 最容易写错的地方）

| 轨道 | 语义 | 写反的后果 |
|---|---|---|
| **旋转** | **绝对局部变换**（每根骨相对父骨的局部旋转，直接可赋给 pose bone） | 写成增量 ⇒ 姿态炸开 |
| **平移** | **相对该骨架静止姿势的纯增量**（所以**首帧 ≈ 0**） | 写成绝对值 ⇒ 角色整体抬高约 6 cm~1 m（引擎按"增量"读） |

判据：位置轨**首帧应 ≈ 0**；量级是米（≈0.86）就是误用了绝对语义 ⇒ 产物作废（闸门 `check_trf_pos.py`，§11.1）。

### 12.3 跟 FBX / ModKit 的对应关系

| TRF 里的东西 | 从哪来 | 进 ModKit 时 |
|---|---|---|
| 骨数 / 骨序 | 目标骨架（骑砍 `human_skeleton`，28 骨） | 必须 28 骨，否则报骨骼数不一致 |
| 时间列 | Blender 帧号（FBX 动作按**时间**重采到 30fps 后的帧） | 填 `Source 1` / `Source 2` = 该 TRF 的帧范围（§11.4） |
| 第 3 行动画名 | `--name`（缺省 = 输出文件名） | **ModKit 靠它生成 clip 名**（`fly_A_Flight_HoverMove_A_AddL` → clip `flight_hovermove_a_addl`） |
| 位置轨 | 根骨位移（相对静止的增量） | 带位移的还要填 `displacement` / `endProgress`（§11.4） |

### 12.4 🔴 第 3 行（动画名）的三条规矩

1. **必须是"这条动画的名字"，且各条唯一** —— ModKit 拿它生成 clip 名，重名 = 资产撞名。
2. **绝不能用骨架名**（骨架在 **FBX 侧**必须叫 `human_skeleton_notused`，那是引擎硬要求；TRF 的动画名跟它是两回事）。
3. **改文件名就等于改 clip 名** ⇒ 改名要**连带改接线**（`action_sets.xml` 的 `animation=`、
   `statemachines/*.xml` 的状态/动作名）—— 名字写错**不报错**，静默解析成 `act_none`，只是播不出来。

### 12.5 FBX 动画型 TRF 的生成与自检

```
blender --background --factory-startup --python pipeline/common/fbx_to_trf.py -- \
    --fbx <in.fbx> --out <out.trf> [--name 动画名] [--start N] [--end N] [--root 骨名]
```
脚本自己会打印：
- `CHECK_OK`：旋转的"绝对公式" vs Blender `pose_bone.matrix` 交叉核对（< 0.5° 才算过）
- `CHECK_POS`：位置轨首帧（应 ≈ 0）
- 骨数 / 帧范围 / 每骨帧数 / 骨序逐行

🔴 **FBX 导入会改 `scene.render.fps`** —— 采样后必须把帧率还原 / 按时间重采到 30fps，否则时长会差 3.4%~25%。
