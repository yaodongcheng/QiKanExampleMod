# UE5 → 骑砍2 重定向「失败」原因复查

> 📁 **路径说明**：本文写于旧目录结构；现已重组为 `input/ pipeline/ output/ viewer/`（见顶层 `README.md`）。
> 文档里的 `out/xxx` 对应现在的 `output/fbx|trf/`，脚本对应 `pipeline/`。**内容结论不变**。

> 日期：2026-09-18 · 复查对象：`D:/BrainMaker/骑砍2动画重定向`（`README_复盘.md` 所记的 UE5 重定向项目）
> 方法：借「战国无双2 铁炮兵 → 骑砍2」这次踩坑的经验回查。**结论与那份 README 的自我判断不同 —— 不是物理极限，是两个可修的 bug。**

---

## 0. 结论先行

那份 README 的最终判断是：

> 「手写脚本无法跨过 **rest 站姿 + 骨长/比例** 差异……要让四肢严格对齐，需要 **Auto-Rig Pro / MotionBuilder**，**纯手写脚本做不到**。」

**这个结论不成立。** 用同一份 UE 源、同一个骑砍骨架，手写脚本可以做到：

| 片段 | 源 fps | 他们 output_world | **本次 align 法** |
|---|---|---|---|
| 010_01 | 25 | 时长 ×1.036 · 姿态差 **37.53°** | 时长 ×1.001 · **3.10°** |
| 002_07 | 25 | 时长 ×1.040 · 姿态差 **49.68°** | 时长 ×1.000 · **3.10°** |
| 013_17 | **30** | 时长 **×1.250** · 姿态差 **53.31°** | 时长 ×1.000 · **3.40°** |
| 010_02 | 25 | 时长 ×1.034 · 姿态差 **42.36°** | 时长 ×1.001 · **3.11°** |

（姿态差 = 逐骨「父关节→本关节」肢段方向夹角，**已穷举 rotZ 0/±90/180 × 是否 X 镜像 共 8 种变换取最优**，对双方都公平。0° = 肢体朝向完全一致。）

→ 姿态误差降低 **12~15 倍**，时序误差清零。所以失败是**工程 bug**，不是能力边界。

## 1. 真凶一：导出帧率被目标 FBX 改掉（时序错，最大 25%）

两边的脚本都**完全没有处理 fps**。实测 Blender 行为：

```
factory reset            fps = 24
手动设为 30              fps = 30
导入 UE5 源 FBX 之后      fps = 25（或 30，取决于源 FBX 自带帧率）
导入骑砍 human_lod_4.fbx  fps = 24   ← 目标 FBX 自带 24fps，把场景改掉了
```

之后 glTF/FBX 导出按「帧 ÷ **当前** fps」换算时间，于是输出时长 = 源帧数 ÷ 24：

| 片段 | 源帧数 | 源 fps | 源时长 | 输出 fps | 输出时长 | 偏差 |
|---|---|---|---|---|---|---|
| 010_01 | 167 | 25 | 6.675 s | 24 | 6.917 s | +3.6% |
| 002_07 | 469 | 25 | 18.758 s | 24 | 19.500 s | +4.0% |
| 013_17 | 1210 | **30** | 40.333 s | 24 | 50.417 s | **+25.0%** |
| 010_02 | 123 | 25 | 4.917 s | 24 | 5.083 s | +3.4% |

**症状**：播放起来"慢慢拖、跟不上原动作"；源是 30fps 的片段会明显**慢 1/4**，19 秒的片段累积漂移近 0.75 秒。
**修法**：在导入目标 FBX **之后**把 `scene.render.fps` 设回源帧率（本次 `ue_align.py` 已这么做，时长比立刻变成 1.000~1.001）。

## 2. 真凶二：姿态传递公式少了「逐骨静止对齐」这一项（姿态差 37~53°）

他们的脚本提供了两种模式，恰好各差一半：

| 模式 | 公式 | 结果 |
|---|---|---|
| `pose=delta` | `T = (F·D_src·F⁻¹) · T_rest` | 运动忠实，但**把源与目标的静止站姿差原样保留** → 手臂恒偏 25~33°、大腿段偏 57°（本次 SW2 项目实测：纯 delta 的误差**恰好等于各骨的静止差常数**） |
| `pose=absolute` | `T = F·S_pose·F⁻¹` | 直接把源的绝对世界朝向写给目标。**两套骨架连"骨骼自身轴向约定"都不同**（源骨 Y 轴水平 / 骑砍骨另一套），结果骨盆被多转 90°、人倒挂 |

**缺的是这一项**（本次用到、也已在 UE 上验证有效）：

```
D_src(i) = S_pose(i) · S_rest(i)⁻¹            源骨世界旋转增量
R(i)     = F · D_src(i) · F⁻¹                 换到目标帧
A(i)     = 「源静止肢段方向(F 旋转后) → 目标静止肢段方向」的最小旋转
T_pose(i)= R(i) · A(i)⁻¹ · T_rest(i)          ← 就是少的 A⁻¹
```

性质：src 处于 rest 时目标落回自身 rest；任意帧下**目标的肢段方向与源逐帧精确相等**。
多分支骨（`pelvis` / `spine2`）只认「子树包含 `head` 的那条躯干延续子骨」，否则不做对齐
—— 否则会把一条腿的对齐强行加给另一条腿（本次踩过，右腿一度偏到 159°）。

README 里记的「躯干/手臂偏、弯腰驼背」，正是缺 `A⁻¹` 的表现；**它不是骨长问题，是朝向问题**。
（骨长/比例差异确实会导致「关节绝对落点」对不齐，但那是个小得多的残余项，而不是 37~53° 这种量级。）

## 2.5 真凶三（追加）：漏掉了「扭骨」，导致小臂/手朝向偏 30~44°

查 UE 的动画到底动了哪些骨，发现 **67 根骨全都被 K 了**，而映射表只覆盖 22 根标准骨，漏掉的包括：

- **扭骨**：`upperarm_twist_01_l/r`、`lowerarm_twist_01_l/r`、`thigh_twist_01_l/r`、`calf_twist_01_l/r`
- 30 根手指骨（`thumb/index/middle/ring/pinky_01~03`）
- IK 骨（`ik_foot_*`、`ik_hand_*`）

扭骨卡在映射骨**中间**（`lowerarm_l → lowerarm_twist_01_l → hand_l`），不传下去就会让手/前臂朝向直接偏掉。
实测单骨误差：`hand_l` 42.9°、`lowerarm_l` 31.7°、`lowerarm_r` 39.5° —— 和"手部不还原"的现象完全对上。

**修复**：把 UE 扭骨接到骑砍的多级扭骨上

```
upperarm_twist_01_l → l_upperarm_twist1      upperarm_twist_01_r → r_upperarm_twist1
lowerarm_twist_01_l → l_foretwist1           lowerarm_twist_01_r → r_foretwist1
```

（原映射表把骑砍的 `*_twist1 / *_foretwist1` 放在 `target_keep_rest` 里刻意不动，等于主动丢掉了扭骨信息。）
手指骨与 `thigh/calf_twist` 骑砍侧无对应骨，仍无法映射 —— 这是真实的骨架能力差异。

> 顺带一个教训：如果要做"源 vs 目标"并排查看器，**源那一侧也必须按全部 67 根骨自映射**，
> 否则源自己就先丢了扭骨（实测源 GLB 与源 FBX 差 15.98°），看起来会像"重定向错了"，其实是"源显示错了"。

### ⚠️ 2026-09-19 更正：扭骨只在**源侧**必须映射，**目标侧不要映射**

上面「扭骨必须映射」只对**源侧显示**成立；对**目标侧（UE → 骑砍）**实测是**反的**：

| 场景 | 做法 | 实测误差（同一片段 010_01） |
|---|---|---|
| **源侧**（UE → UE 自映射） | **必须**映射 22 标准骨 + 8 扭骨 | 不映射 **15.98°** → 映射后 **0.29°** |
| **目标侧**（UE → 骑砍） | **不要**把扭骨接到骑砍的 `*_twist1` | 映射 **6.93°** → 不映射 **3.30°** |

**原因（拓扑不同）**：
- UE 的 `lowerarm_twist_01_l` 是**旁支叶骨**（没有子骨，**不在 `hand` 链路上**）
- 骑砍的 `l_foretwist1` 是**内联骨**（`hand` 是它的子级）

把旁支骨的旋转搬到内联骨上 = 给手部链路**多注入一次旋转**，所以更差。
代码侧已把该开关默认关掉（`pipeline/common/fbx_to_glb.py` 的 `--twist`，默认 false），
两个骑砍 GLB 也已按"不映射"重建（6.93° → 3.30°）。

## 3. 为什么当时会误判成"物理极限"

1. **两个模式各修好一半，给人"怎么调都差一口气"的错觉**：`delta` 保运动但不保朝向；`absolute` 保朝向但被骨轴约定毁掉。缺的第三项（静止对齐）没有出现在他们的迭代列表里。
2. **验收指标选得不对**：当时用「逐骨世界旋转增量 RMS ≈ 0.1–0.2°」当达标标准 —— 这个指标**恰恰对 `delta` 模式恒等于 0**（因为 delta 的定义就是"搬增量"），也就是说：**它无法证伪 delta 的问题**，只会一路报"达标"。本次改用「肢段方向夹角」，偏差立刻显形（37~53°）。
3. **坑 7 被当成显示问题放过了**：README 记了「静态 FBX 骨骼 rest 朝向横躺（沿 +Y）」并判为"仅影响可视化"。实际上这正说明**两套骨架的骨骼轴向约定不同**，是 `absolute` 模式失败的根因，也提示需要按"方向"而不是"绝对朝向"来做对齐。
4. **时长 bug 一直没被发现**：4%（或 25%）的时长偏差在静态逐帧对比里看不出来，只有连续播放才暴露；而当时的验收是"逐帧数值 + 静态对比图"。

---

## 4. 怎么修（三步）

1. **导入目标 FBX 之后把 `scene.render.fps` 还原成源帧率**；导出前再设一次兜底。
2. **把 `pose=delta` 升级成 `align`**：按上面的公式加逐骨静止对齐项 `A⁻¹`（`A` 由"源/目标各自的静止肢段方向"算，与骨骼轴向约定无关）。多分支骨按"躯干延续"选子骨。
3. **验收换成「肢段方向夹角」**（与骨骼轴向约定无关），并且**必须穷举朝向/镜像变换取最优**再下结论，否则会把约定问题误判成姿态问题。

本次已产出可直接用的实现：`ue_align.py`（UE5 FBX → 骑砍2，align 模式 + fps 修复 + 自动贴地）。
