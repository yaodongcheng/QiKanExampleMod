# 从「一张图 / 一段视频」迁移出骨骼动画 —— 机制、选型与本仓落地

> 适用：想拿**完全独立的外部素材**（真人视频、单张照片、影视截图）变成能进骑砍2 的骨骼动画。
> 本文记录**选型依据 + 解算原理 + 实测结果 + 限制**，避免下次重新趟一遍。
> 最后更新：2026-09-27 ｜ 真身：`pipeline/tools/vid2pose.py` + `pipeline/rigs/pose_mediapipe/`

---

## 0. 一句话

**用 MediaPipe BlazePose 取 33 个 3D 关节点，再用"每根骨瞄准对应人体骨段方向"的
纯几何 look-at 解算直接生成骑砍2 的 28 骨动画 —— 不需要下载任何模型权重，CPU 就能跑。**

### 标准交付流程（**4 步 + 2 道闸门**）


```bash
# 视频/图片 -> 关键点
python pipeline/tools/vid2pose.py --in 某人.mp4 --out input/source/pose_mediapipe/dance01.json \
    --start 300 --end 540 --fps 30 --overlay output/verify/pose_mediapipe/dance01_overlay.png
# 关键点 -> FBX + TRF（走统一入口，和其他 rig 完全一样）
python pipeline/run_retarget.py --rig pose_mediapipe --clip dance01 --name pose_dance01 --pelvis ground
```

**③ 标准对照图**（源/解算上下并排、同时间点、**同正面机位**；自动打印视觉模型的诊断清单）

```bash
python pipeline/tools/make_compare_sheet.py --src 某人.mp4 --clip dance01 --name pose_dance01     --out output/verify/pose_mediapipe/dance01_源vs动画对照.png
```

**④ 诊断 —— 🔴 两条一起过，缺一条会假绿**

```bash
python pipeline/tools/check_lr_consistency.py --clip dance01 --trf pose_dance01   # 确定性数值判据
#  + 把 ③ 的对照图交给【视觉模型】，逐条回答 ③ 打印出来的那 6 条清单
```

**闸门 A（在 ① 之后）**：**先看 `--overlay` 叠加图**确认关键点检出对不对（绿=有效/红=无效），再看朝向摘要。

**闸门 B（在 ③ 之后）**：**视觉诊断 + 数值判据，两条一起过**。
视觉模型能抓"一眼看得出的崩坏"（上下翻转 / 正反面突变 / 穿模 / 关节反折），
但**判"左右镜像"在近对称姿态下不可靠** —— 两只手都举着、高低差几厘米时"谁更高"根本看不出来。
**实测踩过**：视觉模型把 t=80%（双手举高的球门柱式）判成"疑似镜像"，
而 `check_lr_consistency.py` 给出左右一致率 **0.981**、上下 **0.997**，放大 3 倍复核确认是**误报**。
反之数值判据**看不出**穿模/关节反折/正反面突变。⇒ 两者互补，**视觉诊断的"左右镜像"必须以数值判据为准**。
完整案例：`output/verify/pose_mediapipe/dance01_诊断记录.md`

## 2. 解算原理（这是本文最值钱的部分）

### 2.1 输入长什么样

`pose.json` 里每帧两组坐标，**语义完全不同，别混**：

| 字段 | 含义 | 能不能出全局位移 |
|---|---|---|
| `world` | 33×3，**米制**，原点=**双髋中点**，y 向下为正，z 越负越近相机 | ❌ 本身就是"髋中心"局部坐标 |
| `norm` | 33×4，图像归一化 (x, y, z, visibility) | ✅ 只能从这里估 |

⇒ 默认 **原地（`--pelvis none`）**：绝大多数游戏 clip 本来就要原地。要全局走位得从 `norm` 反推，
受相机标定影响大，本仓暂不做（见 §6 限制）。

### 2.2 核心公式

设 `W_rest(b)` = 该骨静止时的世界旋转，`E(b)` = 世界空间的**相对静止的旋转增量**，
`d_rest(b)` = 静止时"从 b 的骨头指向其子骨骨头"的方向，`d_now(b)` = 关键点算出的同一段方向。

```
每根骨要求：      E(b) @ d_rest(b) = d_now(b)
层级关系：        E(b) = E(parent) @ G(b)
把父的转掉：      G(b) = RotationBetween( d_rest(b),  E(parent)⁻¹ @ d_now(b) )
写进 Blender：    basis(b) = W_rest(b)⁻¹ @ G(b) @ W_rest(b)
```

⭐ **为什么这样对**：`G` 是"两点向量的最小旋转"（**swing-only，不含 twist**），
twist 天然由父链继承 ⇒ 不会像逐轴欧拉那样把关节转飞。

> **这条不是我们首创**：GitHub 上 `tejaswigowda/mediapipe-pose2bvh`（25★）就是这么做的
> —— `computeR(A,B)` 造两点旋转、`SetRbyCalculatingJoints()` 逐骨把"世界方向"转进"父链局部方向"、
> `R_chain` 逐骨累乘。我们把它**从 three.js 移植成本仓的 Blender/py 实现，并补了三件它没做的事**：
> ① **多骨段分摊**（它的骨架每段正好一根骨；骑砍2 的"髋→肩"有 spine/spine1/spine2 三根）；
> ② **根骨完整基**（见 2.3）；③ **落地补偿**。

### 2.3 三个必须自己补的坑（照抄公式会踩）

**(a) 根骨不能只给一个朝向。** 骑砍2 的 `pelvis` 自身轴是**朝前**的（实测 X=上 / Y=朝前 / Z=角色左），
拿它当"瞄准轴"毫无意义。根骨要给**完整基**：
`up = 髋中点→肩中点`、`left = 左髋→右髋`，正交化后 `fwd = left × up`，再拼成新基去替换静止基。
**这一步不做，角色永远不会转身（yaw 恒为 0）。**

**(b) 多骨段必须分摊。** "髋→肩"这一整段在骑砍2 上是 spine→spine1→spine2 三根。
若三根都瞄同一个终点，数学上**第一根独自转完、后两根几乎不动**（自洽但难看）。
解法：给每根一个 `frac`，把目标方向沿"静止方向→目标方向"做 slerp 分摊（0.34 / 0.67 / 1.00）。

**(c) 别读骨骼的局部轴当方向 —— 用"子骨 head 偏移"。**
实测骑砍2 的 `l_thigh` 自身轴是 `(-0.01, 1.00, -0.07)`（**朝前**），而它到 `l_calf` 的实际骨段是**朝下**的。
`l_hand` 自身轴朝内下、`l_finger0` 在更外侧 —— 骨骼轴和"骨段方向"根本不是一回事。
⇒ 一律用 `child.head_local - bone.head_local` 当静止朝向；只有**真叶骨**（head / toe0 / finger0）
才退回自身轴，或者干脆保持静止继承父骨。
（这条和 README 硬约束 14「求方向用几何推算，不要读骨骼的局部轴」是同一个道理，只是这次出现在**目标侧**。）

## 3.5 交付前诊断（视觉模型 + 数值判据）

| 工具 | 作用 | 判据 |
|---|---|---|
| `pipeline/tools/make_compare_sheet.py` | 出**标准对照图**（源/解算上下并排、同时间点、**同正面机位**），并打印诊断清单 | 机位固定为正面，调用方不许自己写机位 |
| `pipeline/tools/render_glb_frames.py` | GLB → 按时间比例渲帧；**机位语义的唯一定义处**（名字 f/b/s/q → 方位角） | `az=0` = 角色**背后**；正面是 `az=180` |
| `pipeline/tools/check_lr_consistency.py` | **确定性**左右/上下一致性 | 左右一致率 **≥0.90**、上下 **≥0.90**、平均图像平面偏差 <0.6 肩宽；退出码可直接当闸门 |
| 视觉模型（如 `@cowork-vision`） | 抓崩坏/穿模/正反面突变/幅度差，逐格 1~5 打分 | 与数值判据**都过**才签收 |

## 4. 实测结果（2026-09-27，真机跑通）

**素材**：一条真人舞蹈竖屏视频（720×1280 @60fps），取 300~540 帧（4 秒）。

| 环节 | 结果 |
|---|---|
| `vid2pose` | 120 帧 @30fps，**120/120 帧有效**，最低可见度 0.55 / 平均 0.70 |
| 解算 | 驱动 19 骨、静止 8 骨，`CHECK_OK 0.056°`（绝对公式 vs Blender pose 矩阵） |
| TRF 闸门 | `CHECK_TRF_POS_OK`（位置轨首帧 ≈ 0，纯增量语义正确） |
| FBX 体检 | **PASS**（28 骨 / 根名 `human_skeleton_notused` / 无叶骨 / 无 mesh / 米制） |
| 关节在动 | 最大转角 **134.0°**（`l_foretwist` 134° / `r_foretwist` 117° / `r_calf` 99°）—— 在 100~180° 合理区间，不是冻结 |
| **脚底** | **首/中/末 = 0.0006 / 0.0119 / −0.0437 m（基本贴地 ✅）** |

> 🔴 **脚底这一项值得单独说**：本仓此前那批 TRF 直读烘焙的预览件脚底浮空到 **0.893**（§0.5 的"浮空病"）。
> 本链路**天然没有这个问题** —— 因为它是**直接在目标骨架上生成姿势**，不经过"FBX 导出把当前姿势写成 bind pose"那一环。
> 也就是说：**这条路顺带绕开了项目一直没解决的浮空 bug。**

**视觉验收**：`output/verify/pose_mediapipe/`
- `dance01_overlay.png` —— 关键点检出叠加图（8 格，绿=有效）
- `dance01_源vs动画对照.png` —— **上=源视频真人，下=解算出的骨骼动画**，6 个时间点逐格对照：举手 / 展臂 / 抬腿 / 交叉抱胸全部对上
- `photo_fullbody_源vs动画对照.png` —— 单张全身照 → 静止姿态（`--pelvis ground` 后双脚落地）

**单张图片模式**也跑通了：1 帧 → 30 帧定格（便于当姿态格 / 起手帧用）。

**左右手性（无镜像）已数值核验** —— 渲染截图上很难肉眼分清正反，所以直接量"哪只手臂伸得更远"：

| 帧 | 源（MP: `R腕距肩` vs `L腕距肩`） | 我们（骑砍2: `R手距骨盆` vs `L手距骨盆`） | 一致？ |

| 0 / 24 / 48 / 96 / 119 | 右手更远 | 右手更远 | ✅ |

## 5. 能做什么 / 不能做什么（**上线前先读这节**）

### ✅ 能
- 从**任意真人视频**取到关节角度可用的动画（舞蹈 / 挥拳 / 施法手势 / 走路……）
- 从**单张全身照**取到一个静止姿态
- 全程离线、无外部权重、CPU 可跑
- 直接产出 ModKit 规格 FBX + TRF，走的是**和其他 rig 完全一样**的下游

### ❌ 不能 / 要注意
| 限制 | 具体 |
|---|---|
| **没有 twist** | swing-only 解算 ⇒ 前臂/小腿的**旋转**（掌心朝向、脚掌内外翻）**不还原**，由父链继承。要做扭转得额外估 |
| **手型驱动不了** | 骑砍2 每只手只有 1 根**静态**手指骨（`map.json` 里 `target_keep_rest`）。MediaPipe 给的手部 21 点目标侧根本接不上 |
| **全局位移不可靠** | `world` 是髋中心局部系；从 `norm` 反推需要相机标定，本仓**默认原地**（对游戏 clip 反而正好） |
| **朝向假设** | 解算假定"受试者面朝镜头"。背对镜头时整体会反过来 —— 用 `--yaw 180` 补 |
| **单张图质量全看素材** | 半身立绘 / 四肢被裁 / 遮挡重 ⇒ 关键点置信度掉到 0.3 以下，解出来就是错的。实测一张半身立绘就是废的（`min-vis` 0.27）。**必须先看 `--overlay` 叠加图再往下走** |
| **抖动** | BlazePose 逐帧抖，已用 Savitzky-Golay（`--smooth 9`）压过；抖得厉害就加大窗口 |
| **不解决遮挡/穿模** | 手插兜、腿交叉、被物体挡 ⇒ 关键点会"猜"，动画会抽 |

### 🔴🔴 最坑的一条：**"正反面"必须独立判，而且验证用的机位不能拍反**

这条是**被用户当场抓出来的**（2026-09-27）：对照图看上去"一会儿左右一致、一会儿像镜像"。
查完发现是**两个独立的问题叠在一起**，而且都很隐蔽：

**(1) 数据侧没问题，但必须自带正反面证据。**
MediaPipe 的 `left/right` 是**推断**出来的：人背对镜头时它可能判反，一旦判反，髋线方向就翻 180°，
算出来的"角色前方"**整段镜像** —— 而且**看不出来**（每个关节点的位置都还"正确"，只是左右互换）。
所以 `vid2pose.py` 现在会独立算两件事并写进 JSON：

| 字段 | 怎么算 | 怎么读 |
|---|---|---|
| `facing.yaw_deg` | 髋线 + 髋→肩 构成 `fwd`，取它相对骨架 +Y 的方位角 | **0° = 正面朝镜头 = 骑砍2 标准前方** |
| `front_conf` | **面部关键点（眼/鼻/嘴/耳）的平均可见度** | 高=人朝镜头、低=背对 —— **与骨骼无关的独立证据** |
| `facing.n_jumps_gt60` | 逐帧 yaw 的最大跳变 | **>60° 突跳 = 大概率左右判反**，必须回看叠加图 |

`retarget.py` 会打印这份摘要；疑似背对时提醒用 `--auto-yaw`（自动把中位 yaw 转回 0°）。
**实测本 case：中位 yaw −17.2°、逐帧最大跳变 3.5°、0 次突跳、面部可见度 1.00 ⇒ 全程正面，无翻转。**

**(2) 更隐蔽的是：验证时自己的渲染机位拍反了。**
目标骨架**面朝 +Y** ⇒ 能拍到正面的相机必须在 **+Y 侧**。
我原来的渲染脚本 `place(az)` 是 `cam = center + (R·sin az, −R·cos az, …)`，**az=0 落在 −Y = 角色背后**，
却被标成了"正面" ⇒ 拿"源的正面"去比"我们的背面"，非对称动作自然看着像镜像、对称动作又"看着一致"。
**注意：查看器 `viewer.html` 的「正面」按钮是同一个毛病**（`setView('front')` 把相机放在 +Z，
而角色在查看器里朝 −Z）—— 这是**既有问题，影响所有数据集**。

**(3) 验证方法：别用"手相对肩的角度"。**
手垂在身侧时，"手相对肩的方向角"是**病态**的 —— 5 cm 的横向差就能造成 65° 的角度差，会假报"镜像"。
**改用「相对骨盆、按肩宽归一化的图像平面位置向量」**，并且**先只看符号**（左右一致？上下一致？）再看幅度：

| 检查 | 本 case 实测 |
|---|---|
| 上下方向一致 | **20/20 ✓** |
| 左右方向一致 | **16/20 ✓**（4 帧不一致，但那几帧手都贴着中线，横向只差几厘米 —— 病态位形，不是翻转） |

**(4) 还有一个必须知道的固有比例差**：MediaPipe 的 `pose_world_landmarks` 的**骨段长度是压缩的**
（实测 `肩→腕` 只有 0.33 m，真人约 0.55 m，约 0.6×）。
我们**只用方向**，所以姿态本身没问题；但目标骨架的胳膊是**解剖学长度** ⇒
**手伸出去时，我们的手比源"伸得更远"**。这是旋转型重定向的固有性质，不是 bug；
要连比例一起搬就得改"缩放型重定向"（会破坏目标体型）。

### 判读铁律（沿用本仓既有纪律）
**先看叠加图确认"检出对不对"，再去看骨骼动画。** 关键点错了，后面全白搭。
再用 `check_glb_anim.py`（有没有在动，100~180°）+ `check_glb_feet.py`（脚底 ≈0）两条一起过，
**只看一条会假绿**（见 README §0.5 三）。

## 8. 下一步（想做更高质量时的升级路径）

1. **补 twist**：用 `norm` 的深度 + 手/脚关键点朝向，估前臂/小腿的自转，作为 `G` 之后的第二次旋转叠上去。
2. **补全局位移**：从 `norm` 的髋中心轨迹 + 已知身高做单目尺度标定（SMPL 系里的标准做法）。
3. **上 SMPL 系**（有条件时）：`GVHMR` / `WHAM` 出 SMPL 参数 → SMPL 的 24 关节比 33 点更贴解剖，
   且带体型参数与 twist。代价是要权重 + GPU + 一条新的"参数→骨骼"映射。
4. **多视角**：两条以上同步视频可解掉深度歧义（`easyMocap` 路线），本仓无此素材，暂不做。
5. **接进 AI 生视频**：`图片 → 视频（图生视频）→ 本链路` 就能把一张任意立绘变成一段动作，
   **图生视频那一步的输出质量直接决定最终动画质量**（这是本链路的上限）。
